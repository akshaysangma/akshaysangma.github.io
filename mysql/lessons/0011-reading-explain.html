Reading EXPLAIN

Stop guessing whether an index is used. EXPLAIN shows the optimizer's plan — and four columns tell you almost everything.

~12 min Chapter 2 · Internals & modeling Practical superpower Retrieval practice inside
The win You'll run EXPLAIN on any query and read the type, key, rows, and Extra columns to say — out loud — whether it's efficient and what to fix.

The plan, not the result

Prefix any query with EXPLAIN and MySQL returns how it intends to run it (no rows executed). The four columns that matter most:

What to read first in an EXPLAIN row.
ColumnRead it as
typeThe access method — the headline. Best→worst: const → eq_ref → ref → range → index → ALL. ALL = full table scan.
keyWhich index was actually chosen (NULL = none).
rowsEstimated rows examined for this step. Big numbers on big tables = trouble.
ExtraNotes: Using index (good — covering), Using filesort / Using temporary (sorting/grouping work — often improvable).
The 30-second read Glance at type and key: a ref/range with a named key and small rows is healthy. type = ALL with key = NULL on a large table is the classic "add an index" signal. Then check Extra for surprise sorts.
Trap — "Using index" vs "Using index condition" Using index means a covering index answered the query with no row lookup — great. Don't confuse it with Using index condition (index-condition pushdown) or Using where (a post-filter). And rows is an estimate from statistics — re-run ANALYZE TABLE if it looks wildly off.

Check yourself

EXPLAIN shows type = ALL on a million-row table. What does that mean?
A. type = ALL is a full table scan — every row examined. On a large table that's the prime "add or fix an index" signal. const (B), range (C), and the covering case (D) all use an index and read far fewer rows.
The Extra column says Using index. What does that signal?
A. Using index = a covering index supplied every needed column, so no hop to the row was required — efficient. Using filesort (B) and Using temporary (C) are the extra-work flags to watch for.
