How a SQL query actually runs

You write SELECT first — but the database runs it almost last. Learn the real order and half of SQL's "gotchas" stop being mysterious.

~10 min Chapter 1 · Foundations Interview favourite Retrieval practice inside
The win By the end you'll recite the logical processing order of a query and use it to explain — out loud, in an interview — why an alias breaks in WHERE but works in ORDER BY, and why aggregate filters live in HAVING, not WHERE.

The order you write ≠ the order it runs

A query is written SELECT … FROM … WHERE … GROUP BY … HAVING … ORDER BY …. That reads nicely for humans, but the engine evaluates the clauses in a different logical order. Each step takes the rows from the step before it, transforms them, and hands the result to the next step. Think of it as a pipeline of clauses.

Logical processing order — what each step receives and produces.
#ClauseWhat it does
1FROM / JOINPick the source tables and combine them into one big working set of rows.
2WHEREThrow away individual rows that fail the condition. Rows only — no groups yet.
3GROUP BYCollapse the surviving rows into groups (one row per distinct group key).
4HAVINGThrow away whole groups that fail the condition. Can see aggregates.
5SELECTCompute the output columns and expressions. Aliases are born here.
6DISTINCTRemove duplicate output rows.
7ORDER BYSort the result. Runs after SELECT, so it can use aliases.
8LIMIT / OFFSETKeep only the first N rows of the sorted result.

A memory hook: From Where Group Having Select Distinct Order Limit — "Foxes Won't Get Hurt; Squirrels Don't Object, Llamas." Silly sticks; that's the point.

Logical vs physical This is the logical order — the meaning the SQL standard guarantees. The optimizer is free to physically execute differently (e.g. use an index to skip rows early) as long as the result matches the logical order. Interviews test the logical model; performance tuning later is about the physical plan (that's Lesson 11, EXPLAIN).

Watch it run on one query

SELECT   customer_id, COUNT(*) AS order_count
FROM     orders
WHERE    status = 'paid'
GROUP BY customer_id
HAVING   COUNT(*) > 5
ORDER BY order_count DESC
LIMIT    10;

Trace it in logical order, not top-to-bottom:

  1. FROM orders — start with every order.
  2. WHERE status = 'paid' — drop unpaid rows. (No counts exist yet — there are no groups.)
  3. GROUP BY customer_id — collapse to one row per customer.
  4. HAVING COUNT(*) > 5 — drop groups (customers) with 5 or fewer paid orders.
  5. SELECT customer_id, COUNT(*) AS order_count — now compute outputs; order_count exists from here on.
  6. ORDER BY order_count DESC — sort by that alias (legal: ORDER BY runs after SELECT).
  7. LIMIT 10 — keep the top 10.

Two gotchas this explains (both common interview traps)

Trap 1 — aggregate in WHERE WHERE COUNT(*) > 5 is an error. WHERE (step 2) runs before GROUP BY (step 3), so no counts exist yet. Filtering on an aggregate must wait for HAVING (step 4). Rule of thumb: WHERE filters rows, HAVING filters groups.
Trap 2 — alias in WHERE SELECT price*qty AS total FROM line WHERE total > 100 fails with "unknown column total." The alias is created in SELECT (step 5), but WHERE (step 2) already ran. ORDER BY total would work, because it runs after SELECT.
MySQL-specific note Standard SQL forbids aliases in GROUP BY and HAVING. MySQL is lenient and permits them as a vendor extension. Lean on the strict mental model in interviews — it's portable and it's what most graders expect — and just know MySQL bends this rule. (MySQL manual: GROUP BY handling.)

Check yourself

Commit to an answer before revealing — the effort of choosing is what builds memory.

You want only customers with more than 5 paid orders. Where does the COUNT(*) > 5 test belong?
B. COUNT(*) is an aggregate, and groups don't exist until GROUP BY (step 3). WHERE (step 2) runs too early to see it; filtering on aggregates is exactly what HAVING (step 4) is for. SELECT displays a value, it doesn't filter; ORDER BY sorts, it doesn't filter.
This fails: SELECT price*qty AS total FROM line WHERE total > 100. Why?
A. The alias total is created in SELECT (step 5), but WHERE (step 2) has already run — so the name doesn't exist yet. Fix it by repeating the expression: WHERE price*qty > 100. Note ORDER BY total would work, since ordering happens after SELECT.
