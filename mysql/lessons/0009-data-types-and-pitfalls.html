MySQL data types & their pitfalls

Picking the right type is a correctness decision, not a detail. Three classic traps — money, dates, and "utf8" — cause real production bugs.

~11 min Chapter 2 · Internals & modeling Production bug source Retrieval practice inside
The win You'll choose numeric, string, and temporal types deliberately, and never again store money in FLOAT, miss a timezone with DATETIME, or hit the utf8-isn't-real-UTF-8 trap.

The families

The types you'll reach for, and the right default in each family.
FamilyCommon typesSensible default
IntegerTINYINT … INT … BIGINTINT for ids until you'll exceed ~2.1B, then BIGINT
Exact decimalDECIMAL(p,s)Money, always. Stored exactly, no rounding drift
ApproximateFLOAT, DOUBLEScientific/measurement values where tiny error is fine
StringVARCHAR(n), CHAR(n), TEXTVARCHAR for variable text; CHAR only for fixed-length codes
TemporalDATE, DATETIME, TIMESTAMPSee the timezone trap below

Three traps interviewers (and prod) love

Trap 1 — money in FLOAT FLOAT/DOUBLE are binary approximations: 0.1 + 0.2 ≠ 0.3. Summing prices in FLOAT drifts by cents over millions of rows. Use DECIMAL(10,2) for currency — it's exact.
Trap 2 — DATETIME vs TIMESTAMP TIMESTAMP stores UTC and converts to the session timezone, but has a range that ends in 2038. DATETIME has a huge range but stores no timezone — it's a wall-clock value. Pick by intent: an instant in time (TIMESTAMP, or DATETIME with UTC by convention) vs a local calendar value.
Trap 3 — "utf8" is not UTF-8 MySQL's legacy utf8 charset is a 3-byte subset that can't store emoji or some CJK. The real, full Unicode encoding is utf8mb4 — use it for every text column. The old name is a historical wart.

Check yourself

You're storing product prices and order totals. Which type is correct?
A. Money must be exact, so use DECIMAL(p,s). FLOAT/DOUBLE are binary approximations that accumulate rounding error across sums. (Storing integer cents in a BIGINT is a valid alternative, but plain INT dollars loses the cents — D is wrong.)
Your app stores user names with emoji, but they're being truncated or rejected. Likely cause?
C. MySQL's legacy utf8 is only 3 bytes per character and can't hold 4-byte code points like emoji. Switch the column (and connection) to utf8mb4. CHAR vs VARCHAR and length don't determine which Unicode characters are representable.
Primary source: MySQL 8.0 Manual — Data Types, especially the utf8mb4 section.
