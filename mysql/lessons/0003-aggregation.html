Aggregation: GROUP BY and HAVING

Collapsing many rows into one summary number per group — and the two rules interviewers love to probe.

~11 min Chapter 1 · Foundations Interview favourite Retrieval practice inside
The win You'll write correct GROUP BY queries, choose between WHERE and HAVING without hesitating, and avoid the "SUM ignores NULL but COUNT(*) doesn't" surprises.

Aggregate functions collapse rows

An aggregate function takes many rows and returns one value per group.

The five you'll use constantly. All ignore NULLs — except COUNT(*).
FunctionReturnsNULL handling
COUNT(*)Number of rows in the groupCounts every row, NULLs included
COUNT(col)Number of non-NULL values in colSkips NULLs
SUM(col) / AVG(col)Total / mean of non-NULL valuesSkips NULLs (affects AVG's denominator!)
MIN(col) / MAX(col)Smallest / largest non-NULL valueSkips NULLs
Trap — AVG and NULL AVG(score) over [10, 20, NULL] is 15, not 10 — it sums to 30 and divides by 2 (the non-NULL count), not 3. If you want NULLs treated as zero, say so: AVG(COALESCE(score, 0)).

Every selected column must be grouped or aggregated

Once you GROUP BY customer_id, the output has one row per customer. So every column in SELECT must either be the group key or wrapped in an aggregate — otherwise "which row's value should appear?" is undefined. 

SELECT   customer_id, MAX(created_at) AS last_order, COUNT(*) AS n
FROM     orders
GROUP BY customer_id;        -- ✅ customer_id is the key; the rest are aggregates
MySQL-specific note Standard SQL rejects a bare non-grouped column. Old MySQL silently returned an arbitrary row's value — a notorious foot-gun. MySQL 8.0 enables ONLY_FULL_GROUP_BY by default, so it now errors like the standard. Good: write standard-compliant GROUP BY and it's portable.

WHERE vs HAVING — the clause-order payoff

Straight from Lesson 1: WHERE (step 2) filters rows before grouping; HAVING (step 4) filters groups after. Use WHERE whenever you can — it discards rows early, before the expensive grouping.

SELECT   region, COUNT(*) AS paid_orders
FROM     orders
WHERE    status = 'paid'        -- row filter: cheap, runs first
GROUP BY region
HAVING   COUNT(*) > 100;         -- group filter: needs the aggregate

Check yourself

You want regions whose paid orders exceed 100. Which split is correct?
B. status='paid' is a per-row test, so it belongs in WHERE (cheap, early). COUNT(*) > 100 is an aggregate, so it can only live in HAVING. You can't put the count in WHERE (no groups yet) nor the row test efficiently in HAVING.
COUNT(*) over a group is 5, but COUNT(phone) is 3. What does that tell you?
C. COUNT(*) counts all rows (5); COUNT(phone) counts only non-NULL phones (3). The gap of 2 is exactly the number of rows where phone IS NULL. This is a handy way to count missing values in one shot.
