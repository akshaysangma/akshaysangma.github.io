Keys, constraints & relationships

How the database enforces that your data stays valid — and the three relationship shapes every schema is built from.

~11 min Chapter 2 · Internals & modeling Schema basics Retrieval practice inside
The win You'll distinguish primary / foreign / unique keys, name what a foreign key actually guarantees (referential integrity), and model 1:1, 1:N, and M:N — including why M:N always needs a junction table.

Keys identify; constraints enforce

The constraints you'll declare on almost every table.
ConstraintGuarantees
PRIMARY KEYOne column-set uniquely identifies a row; implies NOT NULL + unique. One per table.
FOREIGN KEYEvery value must match an existing row in the parent table — referential integrity.
UNIQUENo two rows share the value (but NULLs are allowed and don't collide).
NOT NULLThe column must always have a value.
CHECKA row-level boolean must hold (e.g. price >= 0). Enforced in MySQL 8.0.16+.
Natural vs surrogate key A natural key is real-world data (an ISBN, an email). A surrogate key is a meaningless generated id (AUTO_INCREMENT / UUID). Surrogates are usually preferred as the PK: they never change and they keep foreign keys small and stable. (Index implications come in Lesson 10.)

The three relationship shapes

  • One-to-one (1:1) — put a UNIQUE foreign key on one side (e.g. user ↔ user_profile). Often just merge into one table unless splitting is deliberate.
  • One-to-many (1:N) — the most common. The "many" side carries the foreign key (an order has many order_items; each item points back to its order).
  • Many-to-many (M:N) — can't be expressed with a single FK. Introduce a junction table holding two foreign keys (student_id, course_id), one row per pairing.
Trap — ON DELETE behaviour Deleting a parent with children fails by default (RESTRICT) — that's referential integrity protecting you. Choose intent explicitly: ON DELETE CASCADE (delete children too) or ON DELETE SET NULL. Silent CASCADE on the wrong relationship deletes more than you expect.

Check yourself

Students enrol in many courses; courses hold many students. How do you model it?
C. A single FK on either side can only express one-to-many. Many-to-many needs a junction (bridge) table with (student_id, course_id) — one row per enrolment. D violates 1NF (Lesson 7); A and B can't capture both directions.
What does declaring a FOREIGN KEY actually guarantee?
B. A foreign key enforces referential integrity: you can't reference a parent that doesn't exist, and you can't orphan children by deleting the parent (without CASCADE). It doesn't forbid NULL (an unset FK is allowed) nor dictate physical storage.
