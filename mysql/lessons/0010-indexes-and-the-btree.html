Indexes & the B-tree

The single biggest lever on query speed. Understand the B-tree, the InnoDB clustered key, and the left-prefix rule, and you can reason about almost any slow query.

~14 min Chapter 2 · Internals & modeling Highest-value internals Retrieval practice inside
The win You'll explain why a B-tree index turns a full scan into a log-time lookup, what a clustered index is in InnoDB, and the left-prefix rule that decides whether a composite index gets used.

An index is a sorted lookup structure

Without an index, finding WHERE email = 'x' means scanning every row — O(n). A B-tree index keeps the column values sorted in a shallow, balanced tree, so a lookup is O(log n). Because it's sorted, one index serves equality, range (>, BETWEEN), prefix LIKE 'abc%', and ORDER BY on the same column.

A trailing wildcard (LIKE 'abc%') can use the index; a leading one (LIKE '%abc') cannot — there's no sorted prefix to seek to. That asymmetry is a common interview probe.

InnoDB: the table is the primary-key B-tree

In InnoDB the primary key is a clustered index: the rows are physically stored in PK order, inside the PK's B-tree leaves. Consequences worth saying out loud:

  • Every table has exactly one clustered index (the PK). Choose a small, monotonic PK (e.g. AUTO_INCREMENT) so inserts append rather than fragment.
  • A secondary index stores its column(s) plus the PK value as the row pointer. So a secondary-index lookup that needs other columns does a second hop back to the clustered index.

Composite indexes: the left-prefix rule

The rule that trips everyone An index on (a, b, c) can be used for predicates on a, on a,b, or on a,b,c — always starting from the left. It cannot be used for a query that filters only on b or only on c: there's no leading value to seek. Order composite columns by how you query them, most-selective leading equality first.

A covering index includes every column the query needs, so MySQL answers from the index alone — no hop to the row. That shows up as Using index in EXPLAIN (Lesson 11).

Trap — indexes aren't free Every index speeds reads but slows writes (each insert/update maintains every index) and costs disk. Low-selectivity columns (a boolean, a status with 3 values) rarely benefit. Index for your real query patterns; don't blanket-index every column.

Check yourself

An index exists on (last_name, first_name). Which query can use it?
A. Left-prefix rule: the index is sorted by last_name first, so a query filtering on last_name (or last_name + first_name) can seek into it. Filtering on first_name alone has no leading value to seek and falls back to a scan.
In InnoDB, what is the clustered index?
A. InnoDB stores the rows themselves inside the primary key's B-tree, in PK order — that's the clustered index. Secondary indexes point back to it via the PK value, which is why a small, stable PK matters.
