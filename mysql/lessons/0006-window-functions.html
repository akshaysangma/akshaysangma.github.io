Window functions

Compute across a set of rows without collapsing them — rankings, running totals, "compared to the row before." The senior-SQL differentiator.

~13 min Chapter 1 · Foundations Senior-interview edge Retrieval practice inside
The win You'll read and write OVER (PARTITION BY … ORDER BY …), choose between ROW_NUMBER, RANK, and DENSE_RANK correctly, and solve the classic "top N per group" question that GROUP BY alone can't.

Aggregate collapses; window keeps every row

GROUP BY turns 100 rows into one per group. A window function returns a value for every row, computed over a "window" of related rows. The window is defined by OVER (…): 

SELECT salesperson, region, amount,
       ROW_NUMBER() OVER (PARTITION BY region ORDER BY amount DESC) AS rn
FROM   sales;
  • PARTITION BY region — split rows into groups (like GROUP BY, but rows survive).
  • ORDER BY amount DESC — order within each partition (defines "first", "running").
  • The function runs per row, seeing its partition.
The three ranking functions differ only in how they treat ties.
FunctionOn a tie (amounts 50, 50, 40)Use for
ROW_NUMBER()1, 2, 3 — unique, arbitrary tiebreak"Pick exactly one per group"
RANK()1, 1, 3 — ties share, then a gapCompetition ranking
DENSE_RANK()1, 1, 2 — ties share, no gap"Distinct tiers"

The killer pattern: top N per group

"The highest-paid employee in each department" — impossible with plain GROUP BY (it can't keep the employee's name alongside the max). With a window + an outer filter, it's clean:

WITH ranked AS (
  SELECT name, dept, salary,
         ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn
  FROM   employees
)
SELECT name, dept, salary FROM ranked WHERE rn = 1;
Trap — you can't filter a window in WHERE WHERE ROW_NUMBER() OVER(...) = 1 errors. Window functions are computed at the SELECT step (after WHERE), so wrap the query in a CTE/subquery and filter the alias outside — exactly the clause-order logic from Lesson 1.

Beyond ranking

Running totals (SUM(x) OVER (ORDER BY d)), and row-to-row comparisons with LAG() / LEAD() ("this month vs last month") are the other heavy hitters. Same OVER machinery.

Check yourself

You need exactly one row — the single latest order — per customer. Which function?
C. You want exactly one row even if two orders tie on timestamp — only ROW_NUMBER guarantees a unique 1 per partition. RANK/DENSE_RANK would return both tied rows as rank 1; COUNT doesn't rank at all.
Why must "keep only rank 1" go in an outer query, not the WHERE of the same SELECT?
B. Logical order again: WHERE (step 2) runs before SELECT (step 5), where window functions are evaluated — so the rank doesn't exist yet in WHERE. Compute it in a CTE/subquery, then filter the alias in the outer query.
