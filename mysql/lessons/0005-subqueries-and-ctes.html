Subqueries & CTEs

Building a query out of smaller queries — and using WITH to keep the result readable instead of a nest of parentheses.

~12 min Chapter 1 · Foundations Readability matters Retrieval practice inside
The win You'll tell apart the three subquery shapes (scalar, IN-list, correlated), refactor an ugly nested query into a clean CTE, and explain the NOT IN-with-NULL trap one more time — because it bites here too.

Three shapes of subquery

Where a subquery sits determines what it must return.
ShapeReturnsExample use
ScalarExactly one row, one columnWHERE price > (SELECT AVG(price) FROM products)
List (IN)One column, many rowsWHERE id IN (SELECT customer_id FROM orders)
CorrelatedRe-runs per outer rowWHERE EXISTS (SELECT 1 FROM o WHERE o.cid = c.id)
EXISTS vs IN EXISTS stops at the first match and is NULL-safe; NOT IN breaks if the subquery can return a NULL (Lesson 2's trap, again). For "has at least one related row", prefer EXISTS / NOT EXISTS.

CTEs: name a subquery with WITH

A Common Table Expression is a subquery you name up front and reference below. Same result as an inline subquery, but readable top-to-bottom and reusable within the query.

WITH paid AS (
  SELECT customer_id, COUNT(*) AS n
  FROM   orders
  WHERE  status = 'paid'
  GROUP  BY customer_id
)
SELECT c.name, paid.n
FROM   customers c
JOIN   paid ON paid.customer_id = c.id
WHERE  paid.n > 5;

Read it as a pipeline: build paid, then join to it. Nesting that same logic as an inline subquery would push the "what" to the inside-out. CTEs (MySQL 8.0+) also enable recursion for hierarchies (org charts, category trees) via WITH RECURSIVE.

Trap — a CTE is not always a temp table Don't assume a CTE is materialised once. MySQL may inline it into the outer query (and may evaluate it more than once). It's for readability and recursion, not a guaranteed performance win — measure with EXPLAIN (Lesson 11) if it's hot.

Check yourself

"Customers who have never placed an order." Which is the safest, clearest form?
B. NOT EXISTS is NULL-safe and stops at the first match. NOT IN (A) silently returns nothing if any customer_id is NULL. C is nonsense (you can't test = NULL); D needs a join/group and is clumsier than NOT EXISTS.
What is the main reason to rewrite a deeply nested subquery as a CTE?
A. CTEs primarily buy clarity (and recursion). They are not guaranteed to materialise once (B is false — MySQL may inline or re-evaluate), they don't change NULL semantics (C), and they don't persist anything (D).
