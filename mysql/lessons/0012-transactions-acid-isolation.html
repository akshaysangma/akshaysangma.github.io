Transactions, ACID & isolation

What guarantees a database makes when many users hit the same data at once — and the trade-off dial called the isolation level.

~14 min Chapter 2 · Internals & modeling Interview favourite Retrieval practice inside
The win You'll define ACID crisply, name the three read anomalies, and place the four isolation levels on the concurrency-vs-correctness dial — including MySQL InnoDB's default and why it's REPEATABLE READ.

A transaction is all-or-nothing

A transaction groups statements so they commit together or roll back together (START TRANSACTION … COMMIT / ROLLBACK). The guarantees are ACID:

ACID — the four guarantees.
LetterGuarantee
AtomicityAll statements succeed, or none do — no partial transaction survives.
ConsistencyA transaction moves the DB from one valid state to another (constraints hold).
IsolationConcurrent transactions don't see each other's half-done work (degree set by the isolation level).
DurabilityOnce committed, it survives a crash (written to durable storage / the redo log).

The three read anomalies isolation prevents

  • Dirty read — you read another transaction's uncommitted change (it might roll back).
  • Non-repeatable read — you re-read a row and its value changed because another transaction committed in between.
  • Phantom read — you re-run a range query and new rows appear that match.
Higher isolation = fewer anomalies, less concurrency. Each level blocks everything below it.
LevelAllows
READ UNCOMMITTEDDirty, non-repeatable, phantom — fastest, least safe
READ COMMITTEDNon-repeatable + phantom (no dirty reads)
REPEATABLE READ (InnoDB default)Phantoms in theory — but InnoDB's gap/next-key locks largely block them too
SERIALIZABLENothing — transactions behave as if run one at a time
InnoDB specifics worth saying InnoDB defaults to REPEATABLE READ, and uses MVCC (each transaction reads a consistent snapshot) so plain reads don't block writers. For range writes it adds gap / next-key locks to stop phantoms. When two transactions lock rows in opposite order you get a deadlock — InnoDB detects it and rolls one back; your app should retry.

Check yourself

What is InnoDB's default transaction isolation level?
A. InnoDB defaults to REPEATABLE READ (many other engines/databases default to READ COMMITTED — a common interview "gotcha"). InnoDB's gap/next-key locks mean it also resists phantoms in practice, not just non-repeatable reads.
You read a row, another transaction commits an update, you re-read and the value changed. Which anomaly?
A. Re-reading the same row and getting a different committed value is a non-repeatable read. A dirty read would see uncommitted data; a phantom is about new rows appearing in a range, not an existing row changing.
Primary source: MySQL 8.0 Manual — InnoDB Transaction Isolation Levels. For the deeper theory, Kleppmann's DDIA, chapter 7.
