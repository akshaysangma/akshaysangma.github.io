CDC, the binlog & replication

How data leaves MySQL for the pipeline without hammering it — by reading the same write-ahead log MySQL already keeps for replication.

~12 min Chapter 3 · Data pipelines Real-time pipelines Retrieval practice inside
The win You'll explain what the binary log is, why log-based CDC beats polling, and how tools like Debezium turn MySQL row changes into a stream — the real-time bridge from OLTP to everything downstream.

The binlog: MySQL's ordered record of every change

InnoDB already writes a binary log (binlog) — an ordered record of every committed data change — primarily to feed replication (a replica replays the primary's binlog to stay in sync). Change Data Capture (CDC) piggybacks on this: instead of querying tables, a CDC tool reads the binlog and emits each insert/update/delete as an event.

Three ways to get changes out — log-based is the modern default.
ApproachHowCost
Full reloadRe-copy the whole table each runSimple, but heavy and not fresh
Query pollingSELECT … WHERE updated_at > last_runAdds load; misses deletes; needs a reliable timestamp
Log-based CDCRead the binlogLow source impact, captures every change incl. deletes
How Debezium-style CDC works Set binlog_format = ROW so the log records the exact before/after values of each changed row. The connector takes an initial consistent snapshot, then streams the binlog from that point onward into Kafka (or similar). GTIDs (global transaction ids) let it fail over to a replica without losing its place.
Trap — ROW vs STATEMENT format STATEMENT format logs the SQL text, which is ambiguous for CDC (e.g. NOW(), non-deterministic updates) and can't give you clean before/after row images. CDC needs binlog_format = ROW. Also: binlogs are purged on a retention schedule, so a connector that's offline too long must re-snapshot.

Check yourself

How does log-based CDC capture changes from MySQL?
A. Log-based CDC reads the binary log MySQL already keeps for replication, so it captures every change (including deletes) with minimal load on the source. Polling (B) adds query load and misses deletes; snapshots (C) are heavy and stale; triggers (D) are intrusive and slow writes.
Why must binlog_format be ROW for reliable CDC?
A. ROW format logs the actual changed row images (before/after), which is what a CDC consumer needs. STATEMENT format (D) logs SQL text — ambiguous and non-deterministic for capture.
