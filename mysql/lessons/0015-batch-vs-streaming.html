Batch vs streaming

Process data in scheduled chunks, or continuously as it arrives. The choice is about data freshness — and the complexity you're willing to pay for it.

~11 min Chapter 3 · Data pipelines Architecture choice Retrieval practice inside
The win You'll define the bounded-vs-unbounded distinction, pick batch or streaming from latency requirements, and explain why streaming needs windowing and careful delivery semantics.

Bounded vs unbounded data

The two processing models.
BatchStreaming
InputBounded — a finite dataset (last night's orders)Unbounded — an endless flow of events
LatencyMinutes to hours (scheduled runs)Seconds or less (continuous)
ComplexitySimpler: read all, compute, writeHarder: ordering, late data, state
Use whenDaily reports, backfills, billingFraud alerts, live dashboards, real-time sync
Decide from latency, not hype Most analytics needs are fine on batch (cheaper, simpler, easier to reason about). Reach for streaming only when freshness genuinely matters — a minute-old fraud signal is useless. "Micro-batch" (small frequent batches) is a common middle ground.
Streaming's two hard parts Windowing: you can't "sum an infinite stream", so you slice it into finite windows (e.g. tumbling 5-minute buckets) and emit per window. Delivery semantics: networks retry, so aim for exactly-once (or at-least-once + idempotent writes — Lesson 18) to avoid double-counting.

Check yourself

What fundamentally separates batch from streaming?
A. The core distinction is bounded (finite, batch) vs unbounded (endless, streaming) input. Batch isn't "slower by design" — it's higher-latency by schedule; streaming can absolutely aggregate and join (via windows and state).
Why does a streaming pipeline use windowing?
A. You can't aggregate an infinite stream as a whole, so windows carve it into finite intervals (tumbling, sliding, session) you can compute and emit. Windowing isn't about storage (B), converting to batch (C), or dedup (D).
