Normalization (1NF → 3NF)

Designing tables so a fact is stored once. Get the three normal forms as a story about killing redundancy — and know when to break them on purpose.

~12 min Chapter 2 · Internals & modeling Interview favourite Retrieval practice inside
The win You'll explain 1NF, 2NF, and 3NF in one breath each, spot the update anomaly that redundancy causes, and justify denormalizing for read-heavy analytics — which is exactly the bridge to the pipelines chapter.

The three forms as one story: store each fact once

Each form removes one kind of duplication. The mantra: "the key, the whole key, and nothing but the key."
FormRuleFixes
1NFEvery column holds one atomic value; no repeating groups or listsA tags column like 'red,green'
2NF1NF + every non-key column depends on the whole composite keyA column that depends on only part of a composite key
3NF2NF + no non-key column depends on another non-key column (no transitive dependency)customer_name living in the orders table
Why redundancy hurts — the three anomalies Storing customer_address on every order row means: update anomaly (change it in one row, others go stale), insertion anomaly (can't add a customer without an order), and deletion anomaly (delete the last order, lose the customer). Normalization removes all three by putting each fact in exactly one place.

When to denormalize (on purpose)

Normalization optimizes for writes and integrity — perfect for OLTP. But analytics reads join a lot of tables, and joins cost. So warehouses deliberately denormalize into wide tables / star schemas (Lesson 16) to make reads fast, accepting controlled redundancy. The skill is knowing which world you're in: normalize for transactions, denormalize for analytics.

Check yourself

A column holds 'red,green,blue' as one comma-joined string. Which rule does that break?
A. A list packed into one column violates 1NF — values must be atomic. Fix it with a separate child table (one tag per row). 2NF/3NF are about dependencies, not atomicity; foreign keys are unrelated here.
Each order row repeats the customer's name and address. What's the core problem?
A. The customer's name depends on the customer, not the order — a transitive dependency that violates 3NF. Repeating it invites update anomalies (change the address once, stale everywhere else). Split customers into their own table and reference by customer_id.
