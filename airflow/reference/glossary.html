Apache Airflow Glossary

The canonical language for this course — the words to reach for when explaining Airflow out loud.

How this grows A term is added only once you've met and used it correctly in a lesson — this is a record of compressed understanding, not a dictionary to read ahead. Every lesson uses these exact words.

Foundations (Lesson 1)

Workflow orchestration
Coordinating a set of steps so they run in the right order, on a schedule, with retries and a single view of every run. The job Airflow exists to do.
Avoid: scheduling, automation (too vague — cron "schedules" but doesn't orchestrate)
DAG (Directed Acyclic Graph)
The model of a workflow: boxes (tasks) joined by one-way arrows (dependencies), with no loops. The arrows fix the order; "acyclic" guarantees the order is resolvable.
Avoid: pipeline, flowchart, script (a DAG is the dependency structure specifically)
Task
One box in the DAG — a single discrete unit of work (e.g. "clean the events"). Tasks are arranged by dependencies and run on workers.
Avoid: step, job, node (informal; say "task")
Operator
A reusable template for a kind of work (run a Bash command, a Python function, a SQL query). Placing an operator in a DAG creates a task — operator is the cutter, task is the cookie.
Avoid: using "operator" and "task" interchangeably
DAG run
A single execution of a DAG for one scheduled period (e.g. "tonight's run for June 29th's data"). The same DAG produces many DAG runs over time.
Avoid: calling a run "the DAG" — the DAG is the plan, the run is one execution
Dependency
An arrow between two tasks meaning "the upstream task must finish before the downstream one starts." Written in code with >> (read as "then").
Avoid: "link", "connection" (a Connection is a different Airflow concept)

Architecture (Lesson 2)

Scheduler
The component that decides what runs and when — it finds due DAG runs and tasks whose dependencies are met, and hands them to the executor.
Avoid: "the engine", "the server" (name the specific component)
Executor
The configuration, running inside the scheduler, that decides how/where a ready task runs and dispatches it to a worker. Not a separate process you start.
Avoid: conflating it with the scheduler or with workers
Worker
The process that actually executes a task's code — a thread on the scheduler's machine, or a separate machine/pod, depending on the executor.
Avoid: "node", "runner"
Metadata database
The single source of truth for state: every DAG, run, task state, Variable, and Connection. Typically Postgres or MySQL.
Avoid: "the backend", "the store" (say metadata database)
Dag processor
The component that parses your .py DAG files and serializes their structure into the metadata database. Runs frequently — which is why top-level code must stay cheap.
Avoid: "the parser" used loosely
API server (web server)
Serves the UI and the REST API; in Airflow 3 workers report task progress through it. Called the "webserver" in Airflow 2.
Avoid: assuming workers write straight to the database (Airflow 3 routes via the API server)
Triggerer
An optional component that runs deferred (async) tasks in an event loop, so workers aren't tied up while a task merely waits.
Avoid: confusing it with a "trigger rule" (unrelated)

Scheduling (Lesson 3)

Data interval
The window of time a single DAG run is responsible for (e.g. one calendar day). The run fires after the interval ends, so the period's data is complete.
Avoid: "the run time", "the schedule"
Logical date
The label for a run: the start of its data interval — not the wall-clock time it executes. Called execution_date before Airflow 2.2.
Avoid: "the run date", "execution time", "now"
Catchup
DAG setting controlling whether the scheduler creates runs for every interval missed since start_date (True) or only the latest (False, the usual default).
Avoid: confusing it with backfill (catchup is automatic on deploy)
Backfill
Manually running a DAG for a past date range (via CLI/UI) — e.g. to reprocess history after a fix.
Avoid: using "backfill" for the automatic catchup behaviour

Task lifecycle & control flow (Lessons 4–5)

Task instance
One task as it exists within a specific DAG run — it carries a state that changes as it progresses.
Avoid: using "task" when you mean a specific run's instance
Task state
The status of a task instance — e.g. scheduled, queued, running, success, failed, up_for_retry, skipped, upstream_failed.
Avoid: "status" used vaguely; name the specific state
Trigger rule
The condition that decides when a task runs given its parents' outcomes. Default all_success; all_done for cleanup; none_failed_min_one_success to join after a branch.
Avoid: confusing with the triggerer component
Branching
Choosing a path at runtime: a branch task returns the task_id(s) to follow; the unchosen paths are skipped.
Avoid: "if/else task" (say branching)

Building blocks (Lessons 6–8)

Sensor
A special operator that waits for a condition before proceeding. poke mode holds a worker slot; reschedule mode frees it between checks.
Avoid: "watcher", "poller"
Provider
A package that adds operators and hooks for an external system (S3, Postgres, Slack…), installed alongside Airflow's small core.
Avoid: "plugin", "integration package" used loosely
TaskFlow API
The modern style: plain Python functions decorated with @task; dependencies are inferred from calls and return values flow automatically via XComs.
Avoid: "decorator DAGs"
XCom
Cross-communication: the built-in channel for passing small values between tasks in a run, keyed by name plus origin task_id/dag_id. Stored in the metadata DB.
Avoid: using it for large data — pass a reference instead
Connection
A named bundle of credentials/endpoint parameters for an external system, identified by a conn_id. Keeps secrets out of DAG code.
Avoid: confusing with a dependency ("connection" between tasks)
Hook
A high-level interface to an external system that uses a Connection for credentials. Operators are often thin wrappers around hooks.
Avoid: "client", "driver"
Variable
A global key/value config value read at runtime, shared across DAGs — distinct from an XCom (per-run data) and a Connection (credentials).
Avoid: using it to pass per-run data (that's an XCom)

Running it (Lessons 9–10)

LocalExecutor
Runs tasks as subprocesses on the scheduler's own machine. Simplest; suits dev or a small single-machine deployment.
Avoid: assuming it can scale across machines
CeleryExecutor
Distributes tasks to a persistent pool of worker machines via a queue/broker. Scale by adding workers.
Avoid: "Celery" alone when you mean the executor
KubernetesExecutor
Runs each task in its own pod, created on demand and torn down after — elastic and isolated, with per-task startup overhead.
Avoid: "K8s mode" used loosely
Idempotency
The property that running a task more than once yields the same result as running it once — essential because tasks are retried and backfilled. Usually achieved by overwriting, not appending.
Avoid: "rerun-safe" without the precise meaning
