Passing data with XComs (and when not to)

How one task hands a value to the next when they might run on different machines — and the size trap that catches everyone.

~7 min Lesson 7 · Building blocks A little code
Your win You can define an XCom, explain push/pull and the auto-pushed return_value, and state the golden rule: small data only. "How do tasks share data?" comes up constantly.

The problem: tasks are isolated

Tasks may run on entirely different workers, even different machines. They don't share variables in memory. So how does clean get the events that pull produced? Through an XCom — short for cross-communication, Airflow's built-in channel for passing a small value from one task to another.

Each XCom is identified by a key (its name) plus the task_id and dag_id it came from. The two operations:

xcom_push(key="rows", value=42)                # task A publishes a value
xcom_pull(key="rows", task_ids="task_a")       # task B reads it back

The shortcut: return values become XComs

You rarely call those by hand. Most operators and every @task function automatically push their return value to a key named return_value (because do_xcom_push=True by default). And xcom_pull defaults to that same key. That's the machinery behind the tidy TaskFlow line from Lesson 6:

clean(pull())   # pull's return is pushed as an XCom; clean pulls it in
So when a @task function returns something and another task takes it as an argument, Airflow is quietly pushing to return_value and pulling it back. The "automatic data flow" is just XComs with sensible defaults.

The golden rule: small data only

Here's the trap. XComs are stored in the metadata database (serialized). They're built for small values — a row count, a filename, a flag. The docs are blunt: do not use them to pass around large values like dataframes.

The right pattern Don't push a 2 GB dataframe through an XCom — you'll bloat the database and slow everything down. Instead, write the big data to storage (e.g. an S3 path or a table) and pass the reference — the path or id — through the XCom. The next task reads the data from there. "Pass a pointer, not the payload."

Check yourself

Which is the right use of an XCom?
B. A small reference like a path is the textbook XCom. A is the classic misuse — big payloads belong in storage, with only the pointer in the XCom. C and D describe other components, not what an XCom is for.
A @task function returns a value and you call xcom_pull with no key. Which key is used?
B. Return values are auto-pushed to return_value, and xcom_pull defaults to that key — which is why TaskFlow's automatic hand-off works. The other names aren't what Airflow uses.
