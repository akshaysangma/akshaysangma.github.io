The best-practice themes interviewers reward

1. Make every task idempotent

Because Airflow retries tasks (Lesson 4) and you can backfill history (Lesson 3), any task may run more than once for the same period. So a task must be idempotent — running it twice leaves the same result as running it once. The fix is almost always: overwrite the target for that period rather than append to it.

2. Parameterise by the logical date, not "now"

A task that reads today() isn't reproducible — re-run it next week and it processes the wrong data. Key your work to the run's logical date / data interval (Lesson 3) so a backfill of "last Tuesday" actually reprocesses last Tuesday.

3. Keep DAG files lean — no heavy top-level code

The dag processor (Lesson 2) re-parses every DAG file frequently. Expensive work written at the top level of the file (an API call, a big query, a slow import) runs on every parse and drags the whole scheduler down. Put real work inside tasks; keep the file's top level to cheap definitions.

4. Pass pointers, not payloads

Don't shove large data through XComs (Lesson 7). Write it to storage and pass the reference. Don't hardcode secrets either — use a Connection (Lesson 8).

The one-line answers to rehearse "Tasks must be idempotent because they can be retried and backfilled." "Keep DAG files light because the scheduler re-parses them constantly." "Pass a reference through XCom, not the data itself." Three sentences that make you sound experienced.

Rapid-fire review (interleaved)

These jump across the course on purpose — mixing topics is what makes the knowledge stick, and it mirrors a real interview's flow.

Why must an Airflow task be idempotent (safe to run more than once)?
A. Retries (Lesson 4) and backfills (Lesson 3) mean the same task may run repeatedly for one period, so its effect must not compound. The other options aren't reasons for idempotency.
Why avoid heavy code at the top level of a DAG file?
A. The dag processor re-parses files frequently, so top-level work executes on every parse and burdens the scheduler. It doesn't block scheduling (B), bind workers (C), or duplicate storage (D).
A run labelled Monday reprocesses Monday's data. To stay idempotent, the task should…
B. Overwriting the partition for the run's logical date makes a re-run produce the same result — idempotent and reproducible. A drifts with wall-clock time (not reproducible), C confuses idempotency with failure handling, and D is the XCom size trap.
