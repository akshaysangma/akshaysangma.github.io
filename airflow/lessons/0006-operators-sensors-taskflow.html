Operators, Sensors & the TaskFlow API

What actually fills the boxes in your DAG — the ready-made templates, the "wait until…" tasks, and the modern Python style.

Operators: the templates

From Lesson 1: an operator is a template for a kind of work; placing one in a DAG makes a task. The three you'll always cite:

Core operators worth naming
OperatorWhat it does
BashOperatorRuns a shell command.

Providers: how Airflow talks to everything else

Airflow's core is deliberately small. Operators for the outside world — S3, Postgres, Slack, HTTP, Docker, BigQuery — live in provider packages you install alongside core. Need to talk to a new system? You add its provider, which brings the operators (and hooks, Lesson 8) for it.

This is why "Airflow integrates with X" is almost always true: there's a community-maintained provider for X. It keeps core lean while the ecosystem covers hundreds of systems.

Sensors: tasks that wait

A sensor is a special operator whose job is to wait for a condition before letting the pipeline proceed — "wait until the file lands in the bucket", "wait until yesterday's partition exists". How it waits matters:

  • poke mode — the sensor holds a worker slot and re-checks on an interval. Simple, but a slow wait ties up a worker.
  • reschedule mode — between checks it releases the slot and sits in the up_for_reschedule state (the one from Lesson 4), freeing capacity for long waits.

The modern, most efficient form is a deferrable sensor, which hands the wait to the triggerer (Lesson 2) so no worker is tied up at all.

The TaskFlow API: the modern Python style

Wiring up PythonOperators and passing data by hand is clunky. The TaskFlow API lets you write ordinary Python functions decorated with @task; Airflow turns each into a task, infers dependencies from how you call them, and passes return values automatically:

@task
def pull():  return fetch_events()      # returns data…

@task
def clean(events):  return tidy(events) # …received as an argument

clean(pull())   # calling them wires pull → clean automatically
Read it as a recipe: @task marks each function as a task. Writing clean(pull()) both passes pull's result into clean and declares the dependency — no >> needed. (Under the hood, that hand-off uses XComs — Lesson 7.) You won't author this yet; just recognise the @task style as "modern Airflow".

What is a Sensor in Airflow?
A. A sensor is an operator that blocks until a condition is met (a file arrives, a partition exists). B is the metadata database, C is scheduling, D is a worker — different components entirely.
Your team needs an operator for Amazon S3. Where does it come from?
A. Integrations ship in provider packages, not core (B) — core stays small. Operators are Python classes you import, not rows in the database (C) or things the scheduler invents (D).
