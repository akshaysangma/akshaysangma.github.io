Under the hood: Airflow's architecture

The whiteboard question — "what are the moving parts, and what happens when a DAG runs?" Five components, one story.

~8 min Lesson 2 · Foundations No Python required
Your win You can name the core components and, crucially, draw the flow: what happens between "a DAG is due" and "a task finishes". This is the most common Airflow whiteboard prompt.

The cast of components

From Lesson 1, Airflow is the conductor. But "Airflow" isn't one program — it's a handful of cooperating parts. Here's each one in a phrase, with the job it owns:

The core components and the single thing each is responsible for
ComponentIts one job
Scheduler (the brain)Decides what should run and when — checks which DAG runs are due and which tasks have their dependencies met.
Executor (the dispatcher)Decides how/where a ready task runs. It's config that lives inside the scheduler and hands tasks off to workers.
Workers (the muscle)Actually execute the task's code. May be threads in the scheduler, or separate machines / pods.
Dag processor (the reader)Parses your .py DAG files and writes their structure into the metadata database.
Metadata database (the memory)The single source of truth: stores the state of every DAG, task, and run (Postgres or MySQL).
API server / web server (the face)Serves the UI you click and the REST API. Workers also report task progress through it.
Triggerer (the waiter)Optional. Runs deferred (async) tasks that are just waiting on something, so workers aren't tied up idling.
Version note: in Airflow 3 the old "webserver" is now the API server, and workers talk to it via a Task Execution API instead of hitting the database directly — a security/isolation improvement. The roles above are unchanged.

The story: what happens when a DAG runs

Memorise this five-beat flow — it answers the whiteboard question directly:

1. Dag processor   reads your DAG .py file  ─▶ writes structure to ─┐
                                                                    ▼
2. Scheduler       sees a run is due, deps met ◀──── reads/writes ─ Metadata DB
                   marks the task "queued"                          ▲
                        │ (via the executor)                        │
                        ▼                                           │
3. Worker          picks up the task, runs the code                │
                        │                                           │
4.                 reports state (success/failed) ─── via API ─────┘
                        │
5. You             watch every run, live, in the UI

In words: your DAG file is parsed into the database; the scheduler notices a run is due and a task's dependencies are satisfied, so it hands the task to the executor, which queues it for a worker; the worker runs the code and reports the result back to the database; you see it all in the UI.

The distinction interviewers probe The scheduler decides what runs and when. The executor decides how/where it runs. People blur these. The executor is not a separate server you start — it's a setting inside the scheduler (you'll meet the options in Lesson 9).

Check yourself

A task's dependencies are met and it's ready. Which component decides where/how it actually runs?
B. The executor decides how/where a ready task runs and hands it to a worker. The scheduler decided that it should run (the "what/when"), but doesn't run the code itself. The metadata DB only records state; the triggerer handles deferred/async waiting.
What is the metadata database's role?
B. The metadata DB is the single source of truth for state — which runs exist and what state every task is in. Executing code is the worker's job (A); parsing files is the dag processor's (C); rendering the UI is the API/web server's (D).
