Scheduling & the data interval

Why a run "for Monday" actually executes on Tuesday — the single most common Airflow interview trap, demystified.

~8 min Lesson 3 · How DAGs run A little code
Your win You can explain the data interval and logical date, and answer "when does a scheduled run actually fire?" — plus what catchup does. Getting this right instantly signals real exposure.

The mental shift: a run is for a period, not at a moment

Beginners picture scheduling like an alarm clock: "run at 8am." Airflow thinks differently. Every scheduled DAG run is responsible for a window of time — its data interval. A daily DAG has one run per day, and each run "owns" that day's data.

You set the cadence with the schedule parameter — a cron string, a timedelta, or a preset like @daily:

schedule="@daily"   # one run per day; data interval = midnight to midnight
Version note: in modern Airflow the parameter is schedule. Older code used schedule_interval — same idea, old name. If you see schedule_interval in a tutorial, you're reading something written for Airflow 2.x.

The trap: the run fires after its interval ends

Here's the part that catches people. A daily run's logical date is the start of its data interval — but the run doesn't fire then. It fires after the interval has ended, so that all the data for that period actually exists when the task runs.

Run "for" Monday
   logical_date  = Mon 00:00   ← the label / start of the interval
   data interval = Mon 00:00  →  Tue 00:00
   actually runs ≈ Tue 00:00   ← after Monday's data is complete

So the run labelled Monday executes at the start of Tuesday. That's not a bug — it's the whole point. If you're aggregating "Monday's events", you must wait until Monday is over to have them all.

Say it correctly The logical date (called execution_date before Airflow 2.2) is not "now" and not wall-clock run time — it's the start of the data interval the run represents. Calling it "the time the DAG runs" is the classic tell that someone has only read about Airflow, not used it.

Catchup & backfill: filling in history

What if you deploy a DAG with a start_date a month ago? That's where catchup comes in:

  • catchup=False (the common, sane default) — Airflow only runs the most recent interval, ignoring the gap. Usually what you want.
  • catchup=True — the scheduler creates a run for every missed interval since start_date, working through history. Powerful, but can unleash a flood of runs.

Backfill is the manual cousin: you explicitly ask Airflow (via CLI or UI) to run a DAG for a past date range — e.g. to reprocess last week after fixing a bug.
