Connections, Hooks & Variables

How Airflow stores credentials and config — and talks to the outside world without you hardcoding a password in a DAG.

~7 min Lesson 8 · Building blocks A little code
Your win You can define Connection, Hook, and Variable, say how they relate, and explain why credentials never go in DAG code. Interviewers probe this to check you think about secrets and config.

The need: don't hardcode secrets

Pipelines constantly talk to external systems — databases, APIs, cloud storage. Each needs a host, a login, a password. Putting those in your DAG file is a security and maintenance disaster (they end up in version control, and change per environment). Airflow gives you three named concepts so they don't.

Connection — the credentials bundle

A Connection is a named set of parameters — host, login, password, port, and the type of system — identified by a conn_id. You define it once (in the UI, CLI, an environment variable, or a secrets backend); your DAG just refers to it by id:

# DAG references the id, not the password
PostgresOperator(task_id="load", postgres_conn_id="warehouse_db", sql="...")

Hook — the friendly interface

A Hook is a high-level interface to an external system that lets you talk to it without writing low-level API code. A hook uses a Connection to get its credentials — e.g. PostgresHook looks up the connection postgres_default unless you point it elsewhere. Hooks are the building blocks that operators are made of: an operator is often just a thin wrapper around a hook.

Operator  ──uses──▶  Hook  ──uses──▶  Connection (the conn_id's credentials)

Variable — global config

A Variable is a simple global key/value setting, read at runtime — a tunable shared across DAGs, like a batch size or a target bucket name:

size = Variable.get("batch_size")   # a global config value, not run-specific
Three look-alikes, kept straight XCom = small data passed between tasks within one run (Lesson 7). Variable = global config shared across DAGs and runs. Connection = credentials/endpoint for an external system. Mixing these up — especially XCom vs Variable — is a common stumble.

Check yourself

Your DAG must connect to a Postgres database. Where should the credentials live?
B. Credentials belong in a Connection, referenced by conn_id — so they stay out of code and version control. A is the anti-pattern; XComs (C) are for per-run data, not secrets; D isn't how Airflow manages connections.
What's the difference between an XCom and a Variable?
B. XComs move small data between tasks in a run; Variables are global config shared across DAGs. A reverses them, C is wrong (distinct concepts), and credentials are a Connection's job, not either of these (D).
