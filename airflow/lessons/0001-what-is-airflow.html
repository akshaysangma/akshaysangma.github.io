What Airflow is & the DAG mental model

The one question every Airflow conversation starts with — and the single idea the whole tool is built on.

~7 min Lesson 1 of the Foundations chapter No Python required
Your win By the end you can answer two classic openers out loud: "What is Airflow and what problem does it solve?" and "What is a DAG?" — using the right words, the way someone who's used the tool would.

The problem: someone has to be the conductor

Imagine a nightly job at a company like ours: pull yesterday's events → clean them → load them into a warehouse → refresh a dashboard. Four steps, and they have a strict order. Step 3 must not start until step 2 actually succeeded. If step 1 fails at 2 a.m., someone should retry it a couple of times, and if it still fails, raise an alarm — not silently skip ahead and corrupt the dashboard.

You could wire this up with cron (the classic "run this script at this time" scheduler). But cron only knows how to start things at a time. It can't express any of the things that actually matter here:

What the job needs vs. what plain cron gives you
The job needs…Cron offers…
"Run step 3 only after step 2 succeeds"Nothing — each entry runs blind to the others
"Retry a failed step 3 times, then alert"Nothing — it fails and stays silent
"Show me which runs passed or failed, and why"Nothing — you go read scattered log files
"Re-run last Tuesday's data"Nothing — no concept of which day a run is for

That missing layer — ordering, dependencies, retries, scheduling, and a single place to watch it all — is called workflow orchestration. Airflow is a tool that provides it. The official one-liner is deliberately plain:

From the docs "Airflow is a platform that lets you build and run workflows." A workflow is represented as a DAG, and contains individual pieces of work called Tasks, arranged with dependencies.
— Airflow core-concepts: overview

So Airflow is the conductor: it doesn't usually do the heavy work itself, it decides what runs, in what order, when, and what to do when something breaks — and it shows you the whole performance on one screen.

The one idea: a workflow is a DAG

Everything in Airflow rests on one shape. Your workflow is modelled as a DAG — a Directed Acyclic Graph. Three small words, each doing real work:

  • Graph — a set of boxes connected by arrows. The boxes are your steps; the arrows are "this must happen before that".
  • Directed — the arrows point one way. "Clean" comes after "Pull", never the reverse. Direction is the dependency.
  • Acyclic — no loops. Following the arrows can never bring you back to where you started. This is the rule that makes the workflow runnable at all: if step A waited on step B and B waited on A, neither could ever begin.

Picture our nightly job as a DAG:

pull_events ──▶ clean_events ──▶ load_warehouse ──▶ refresh_dashboard

Each box is a Task — one discrete unit of work. The arrows are the dependencies. Airflow reads this shape and guarantees the order: it won't start clean_events until pull_events has succeeded, and so on.

Easy to fumble A DAG is the plan (the boxes-and-arrows definition). A single execution of that plan — say, "tonight's run for June 29th's data" — is a separate thing called a DAG run. The same DAG is run over and over, once per scheduled period. Mixing up "the DAG" and "a DAG run" is a classic giveaway in interviews.

Task vs. Operator — the distinction interviewers love

You now know a Task is one box in the graph. But how do you say what that box actually does? With an Operator. An operator is a ready-made template for a kind of work — "run a Bash command", "run a Python function", "run a SQL query". When you drop an operator into a DAG, that placed instance becomes a Task.

Operator = the cookie cutter (the type of work). Task = the cookie (one use of it, sitting in your DAG).

Here's the smallest possible peek at the code — you do not need to write Python yet; just read it like a recipe:

pull = BashOperator(task_id="pull_events", bash_command="...")
clean = BashOperator(task_id="clean_events", bash_command="...")

pull >> clean   # the arrow: pull must finish before clean starts
Line by line: BashOperator(...) picks the "run a shell command" template and names this step. We make two of them, pull and clean. The last line, pull >> clean, is Airflow's way of drawing the arrow — read >> as "then". That one line is the dependency you couldn't express in cron.

Commit to an answer before revealing the explanation — the effort of recalling is what makes it stick.

An interviewer asks: "Why use Airflow instead of just scheduling scripts with cron?" Strongest answer?
B. Cron only starts things at a time; Airflow adds ordering/dependencies, automatic retries, scheduling, and one place to see every run. A is wrong — Airflow doesn't make your code faster, it orchestrates it. C is wrong — you still write code (often Python). D is wrong — Airflow needs a metadata database to track state (more in Lesson 2).
In "DAG", what does the Acyclic part guarantee about your workflow?
B. "Acyclic" means no loops — following the arrows never returns you to a task you've already passed, so nothing can depend (directly or via a chain) on itself. That's what makes the order resolvable. A, C, and D describe things acyclicity says nothing about — parallelism, retries, and graph size are all independent of it.
