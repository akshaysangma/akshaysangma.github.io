Task states, retries & failure handling

Follow one task through its life — and learn what Airflow does, on your behalf, when it breaks at 3 a.m.

~8 min Lesson 4 · How DAGs run A little code
Your win You can describe a task's lifecycle, explain retries and the up_for_retry state, and say what happens to downstream tasks when one fails. "How does Airflow handle failures?" is an interview staple.

A task instance moves through states

Remember: a DAG is the plan, a DAG run is one execution. Inside a run, each task becomes a task instance — and that instance carries a state that changes as it progresses. Don't memorise all of them; group them by what they mean:

Task instance states, grouped
GroupStatesMeaning
Waitingnone, scheduled, queuedDependencies being checked, or waiting for a free worker.
Activerunning, deferredExecuting on a worker, or parked waiting on an async event (the triggerer).

Finishedsuccess, failed, skipped, upstream_failedTerminal — done well, done badly, deliberately not run, or blocked by a failed parent.

The happy path is just: scheduled → queued → running → success. Everything else is Airflow reacting to trouble.

Retries: the 3 a.m. babysitter

Transient failures happen — a network blip, a service briefly down. Instead of paging a human, you tell Airflow to try again, per task:

retries=3                       # try up to 3 more times after the first failure
retry_delay=timedelta(minutes=5)  # wait 5 minutes between attempts
Line by line: retries=3 says "if this task errors, attempt it three more times before giving up." retry_delay is the pause between attempts — here, five minutes, giving a flaky service time to recover.

When a task errors with retries remaining, it enters up_for_retry and gets rescheduled. Only when the attempts are exhausted does it become failed.

Failure cascades downstream

So a task finally fails. What about the tasks that depended on it? By default they don't run — they're marked upstream_failed. This is the safety property from Lesson 1: Airflow won't load a warehouse from data that was never cleaned.

pull ──▶ clean (FAILED) ──▶ load (upstream_failed) ──▶ dashboard (upstream_failed)

When you genuinely want something to run anyway — say, a cleanup or an alert that should fire whether or not the pipeline succeeded — you override this with a trigger rule (Lesson 5). And to actively notify a human, you attach an on_failure_callback that fires when the task fails.

Seed for Lesson 10 Because Airflow retries tasks, every task must be idempotent — safe to run more than once without doubling its effect. A task that "appends today's rows" will duplicate them on retry. Hold that thought; it's a top interview theme.

Check yourself

A task errors out but still has retry attempts left. What state does it enter?
B. With retries remaining, the task goes to up_for_retry and is rescheduled. It only becomes failed once attempts are exhausted — so A is premature. It hasn't succeeded (C) and isn't stuck queued (D).
An upstream task failed and your task needed it. What state does your task get?
B. Under the default trigger rule, a failed required parent blocks the child, which is marked upstream_failed and never runs. It isn't retried (A — its own code never ran), doesn't run anyway (C), and a failure isn't a pass (D).
