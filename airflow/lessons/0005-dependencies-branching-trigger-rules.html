Dependencies, branching & trigger rules

Shaping the graph: how to wire tasks together, take different paths, and override the "only run if everything succeeded" default.

~8 min Lesson 5 · How DAGs run A little code
Your win You can declare dependencies (>>), fan out and fan in, describe branching, and name the trigger rule you'd use for a "run no matter what" cleanup task — including the classic branch-plus-join gotcha.

Declaring the arrows

You met >> ("then") in Lesson 1. It and its mirror << are the standard way to draw dependencies. Lists let you fan out (one task to many) and fan in (many to one):

pull >> [clean_a, clean_b] >> load   # pull → both cleans → load
# same as the verbose form: pull.set_downstream(clean_a)
pull >> [clean_a, clean_b] makes both cleans wait for pull; [clean_a, clean_b] >> load makes load wait for both. For bigger graphs there are helpers — chain() (string tasks in a line) and cross_downstream() (connect every task in one list to every task in another).

Branching: choosing a path at runtime

Sometimes the graph should fork — "if the file is large, take the heavy path; otherwise the light one." That's branching. A branch task (the @task.branch decorator, or BranchPythonOperator) runs a small decision function that returns the task_id to follow. Airflow runs that task and skips the paths not chosen.

@task.branch
def choose(size):
    return "heavy_path" if size > 1_000 else "light_path"
The function returns the name of a downstream task. Whichever id it returns is the path taken; every other branch is marked skipped. (You don't need to write this — just recognise the shape and the word "branch".)

Trigger rules: when does a task run, given its parents?

By default a task uses the trigger rule all_success: it runs only if all its parents succeeded. That's the safe default — but you can change it per task. The ones worth knowing:

Trigger rules you'll actually be asked about
RuleTask runs when…
all_success (default)every parent succeeded
all_doneevery parent finished — success or fail. Use for cleanup/alerts.
one_successat least one parent succeeded (don't wait for the rest)
one_failedat least one parent failed — useful for failure handlers
none_failed_min_one_successno parent failed and ≥1 succeeded — the join after a branch rule
The branch + join gotcha Skips cascade: under all_success, a parent that was skipped makes the child skip too. So a task that joins paths back together after a branch will wrongly skip — because one branch was skipped by design. The fix is to give the join task none_failed_min_one_success. This exact trap is a favourite interview question.

Check yourself

A cleanup task must run regardless of whether its upstream tasks passed or failed. Which trigger rule?
B. all_done fires once every parent has finished, regardless of outcome — exactly right for cleanup. all_success (A) would skip the cleanup whenever the pipeline failed, which is when you most need it.
A @task.branch function returns the id of one downstream task. What happens to the others?
B. Branching follows the returned id and marks the unchosen paths skipped — not failed (C) or retried (D), and certainly not all run (A, which would defeat the point of branching).
