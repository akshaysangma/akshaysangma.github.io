Executors: how Airflow scales

The "how would you run this in production?" question — the executor options, and how to pick one in a sentence.

~7 min Lesson 9 · Running it No Python required
Your win You can name the main executors, explain the local-vs-remote split, and justify a choice for a given scale. This is the standard "how do you deploy / scale Airflow?" round.

Recap: what the executor is

From Lesson 2: the executor decides how and where a ready task runs, and it lives inside the scheduler process — it's a configuration choice, not a separate server you launch. Swapping executors is how you go from "runs on my laptop" to "runs across a cluster" without rewriting a single DAG.

Local vs remote: the core split

There are two families. Local executors run tasks on the scheduler's own machine. Remote executors send tasks out to separate workers or containers, so you can scale horizontally.

The executors worth naming
ExecutorHow it runs tasksUse it when…
LocalExecutor (local)As subprocesses on the scheduler's machine.Dev, or a small single-machine deployment.
CeleryExecutor (remote)A fleet of worker machines pull tasks off a shared queue (via a broker like Redis/RabbitMQ).A steady, busy workload; scale by adding workers.
KubernetesExecutor (remote)Each task runs in its own pod, created on demand and torn down after.Elastic, bursty load; strong per-task isolation.
EdgeExecutor (remote)Workers run at remote/edge locations, talking over HTTP.Distributed/edge setups (newer option).
Version note: Airflow 3.0 removed the "statically coded" hybrid executors (LocalKubernetesExecutor, CeleryKubernetesExecutor). If asked, you can note that hybrid setups are now configured differently. The four above are the ones to know.

How to choose — the one-liner

The trade-off is simplicity vs. scale & isolation:

  • One machine, simple → LocalExecutor.
  • A persistent fleet of workers under steady load → CeleryExecutor (add workers to scale).
  • Elastic, isolated, container-native → KubernetesExecutor (a pod per task; pay a little startup overhead for clean isolation and on-demand scaling).

Check yourself

You want each task to run in its own isolated, on-demand container. Which executor?
B. The KubernetesExecutor gives each task its own pod — on-demand, isolated, torn down after. Local (A) runs on one machine, Celery (C) uses a persistent worker pool, and Edge (D) targets remote sites rather than per-task containers.
How does the CeleryExecutor scale to handle more work?
A. Celery workers pull from a shared queue, so you scale by adding workers. Running tasks in the scheduler (B) is the Local model; a pod per task (C) is Kubernetes; database rows (D) have nothing to do with execution capacity.
