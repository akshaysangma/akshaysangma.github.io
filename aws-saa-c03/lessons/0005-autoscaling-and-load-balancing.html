Elasticity: Auto Scaling & Load Balancers

How to design an elastic, highly-available tier — and how to pick the right load balancer for the traffic in front of it. The core engine of two whole exam domains.

Lesson 5 ~10 min Resilient 26% + Performant 24% Core

The win

By the end of this lesson you'll be able to design an elastic, highly-available compute tier — instances spread across Availability Zones in an Auto Scaling group, fronted by the correct load balancer — and pick the right load balancer from the four ELB types based on the traffic and the priority word. Together these patterns sit at the heart of Resilient Architectures (26%) and High-Performing Architectures (24%) — half the exam.

Why this is the engine of two domains

Reliability asks: does it survive failure and recover? Performance Efficiency asks: does it scale with demand using the right resource? A single mechanism answers both — EC2 Auto Scaling across multiple AZs behind a load balancer. It keeps capacity matched to demand (performance) and keeps serving when an instance or an entire AZ dies (reliability). If you can draw this picture and choose its parts, you've covered the highest-frequency scenario shape on the exam.

The mental picture Load balancer spans AZs → spreads requests to an Auto Scaling group whose instances also span AZs → ASG launches/terminates instances from a launch template to hold target capacity and replace anything unhealthy. Memorise this diagram; many questions are just one piece of it.

EC2 Auto Scaling — what it actually does

An Auto Scaling group (ASG) maintains a desired number of EC2 instances between a min and max. Four behaviours matter for the exam:

  • Spans Availability Zones for HA. Place the ASG across multiple AZs and it balances instances across them. Lose an AZ and the survivors keep serving while the ASG launches replacements elsewhere. This — not a bigger instance — is how you survive an AZ failure.
  • Launch templates define the instances. AMI, instance type, security groups, user data. (Launch templates supersede the older launch configurations and support versioning + mixed instances.)
  • Replaces unhealthy instances automatically. Using EC2 status checks or, better, the load balancer's health checks — a failed instance is terminated and replaced with no human in the loop.
  • Scales out fast, scales in slow. It adds capacity aggressively when demand rises and removes it conservatively, deliberately favouring availability over squeezing out the last cent.

Scaling policy types

Pick by the trigger described in the scenario. Target Tracking is the default unless the question implies otherwise.
PolicyTriggerCooldownChoose when
Target TrackingHold a metric at a target (e.g. 50% CPU)No cooldownDefault; "keep utilisation around X"
Step ScalingAlarm breach with stepped adjustments by magnitudeNoPrecise multi-step control
Simple ScalingSingle alarm thresholdYes — 300 s defaultBasic / legacy
ScheduledTime / cron—Predictable patterns (business hours, end-of-month)
PredictiveML forecast (needs ≥ 24 h of data)—Anticipate recurring spikes before they arrive

Exam tells: "keep CPU at ~50% automatically" → Target Tracking. "Scale up every weekday at 9am" → Scheduled. "Forecast tomorrow's recurring peak" → Predictive (and remember it needs 24h of history before it can act).

Load balancers — the four ELB types

Layer 7 = application/HTTP; Layer 4 = transport/TCP-UDP. The layer mostly decides the type.
TypeLayerProtocolsKey powerExam tell
ALB7HTTP, HTTPS, gRPCPath & host routing; targets EC2, IP, and LambdaMicroservices, route by URL / hostname
NLB4TCP, UDP, TLSStatic IP, ultra-low latency, millions of RPS, PrivateLinkNon-HTTP, static IP, extreme throughput
GWLB3/4IPInsert 3rd-party virtual appliances (firewalls/IDS/IPS)Security/inspection appliance fleets
Classic (CLB)4/7TCP, HTTP(S)Legacy — avoid for new designsOnly when "existing/legacy" is stated

The decision is usually binary on the exam: need Layer-7 features (path-based or host-based routing, HTTP/HTTPS, routing to Lambda)? → ALB. Need Layer-4 traits (a static/Elastic IP, TCP/UDP or non-HTTP protocols, PrivateLink, or simply enormous throughput at the lowest latency)? → NLB. Reach for GWLB only when you're chaining third-party network appliances, and Classic only when a question explicitly says "legacy".

Sticky sessions Need a client pinned to the same target? ALB does it with cookies (duration-based or application-controlled). NLB does it by source IP (flow hash) — no cookies at Layer 4.

See it in action

Run the procedure from Lesson 1 on each: find the priority word, eliminate what doesn't work, then let the pillar choose. Commit before you reveal.

Q1. Which option does the procedure select?
A web tier runs on EC2 in a single AZ. The business needs it to stay available even if an entire Availability Zone fails, while keeping cost reasonable. What should the architect do?
Priority phrase: "even if an entire AZ fails" → Reliability (high availability). HA against AZ loss means spreading across AZs — only (C) does that. A bigger instance (A) is the classic trap: it still dies with its AZ. Snapshots (B) speed recovery but don't keep you serving. Termination protection (D) doesn't help if the AZ itself goes down. Answer: C.
Q2. Which option does the procedure select?
A single application needs requests to /api/* sent to one fleet of containers and requests to /images/* sent to a different fleet, all over HTTPS. Which load balancer setup meets this?
Priority: route by URL path → Layer-7 content routing → ALB. Path-based (and host-based) routing is an ALB feature. (B) NLB is Layer 4 — it can't read the URL path. (C) GWLB is for inserting appliances, not app routing. (D) Classic is legacy and lacks path rules. Answer: A.
Q3. Which option does the procedure select?
A gaming backend serves millions of requests per second over a custom TCP protocol (not HTTP) and must expose a single static IP that partners can whitelist. Which load balancer fits?
Priority: non-HTTP TCP + static IP + extreme throughput → Layer 4 → NLB. NLB gives a static/Elastic IP per AZ, handles non-HTTP protocols, and scales to millions of RPS at very low latency. (A) ALB is HTTP-only and has no static IP. (B) Classic is legacy. (C) GWLB is for chaining appliances, not as your client-facing balancer. Answer: D.
Q4. Which option does the procedure select?
An Auto Scaling group should automatically keep average CPU utilisation around 50% with the least configuration effort, adding or removing instances as load changes. Which scaling policy?
Priority: "keep a metric at a target automatically, least effort" → Target Tracking. You name the metric and the target value; AWS manages the rest with no cooldown to tune. (A) Scheduled is for known time patterns, not a utilisation target. (C) Simple works but is basic and adds cooldown delay. (D) Predictive needs ≥24h of history and suits anticipating recurring spikes, not simply holding a steady target. Answer: B.

The one sentence to remember

Takeaway Elasticity = an Auto Scaling group across multiple AZs (HA + capacity) fronted by the right ELB — ALB for Layer-7 routing, NLB for static IP and Layer-4 throughput — with Target Tracking as your default scaling policy.
