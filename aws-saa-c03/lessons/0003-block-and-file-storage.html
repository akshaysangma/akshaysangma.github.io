Block & File Storage

EBS, Instance Store, EFS, and FSx. How to pick the right storage service for a workload — and, when it's EBS, the right volume type.

Lesson 3 ~10 min Domain 3 · Performance Storage

The win

By the end of this lesson you can read a workload description and confidently answer two questions the exam loves to ask: which storage service (EBS, Instance Store, EFS, or FSx) fits, and — when the answer is EBS — which volume type. The decisive tells are durability needs, whether storage must be shared, whether it must survive the instance, and whether the workload is IOPS-bound or throughput-bound.

Two axes that decide everything

Almost every storage question turns on two distinctions. Get these and the options sort themselves:

  • Block vs file. Block storage (EBS, Instance Store) is a raw disk attached to one instance — you put a filesystem on it. File storage (EFS, FSx) is a shared filesystem many instances mount over the network.
  • SSD vs HDD. SSD is IOPS-oriented — small, random I/O (databases, boot volumes). HDD is throughput-oriented — large, sequential I/O (big-data scans, log processing). When a scenario stresses "transactions per second" or "random reads", think SSD; when it stresses "MB/s" or "streaming large files", think HDD.

EBS volume types

EBS (Elastic Block Store) is a network-attached block volume that lives in a single AZ and attaches to one instance (with a Multi-Attach exception below). It persists independently of the instance — if "delete on termination" is off, the data survives. Five volume types you must know:

The gp3 headline gp3 is the default for a reason: it ships a flat baseline of 3,000 IOPS and 125 MiB/s on every volume, and you can dial IOPS (up to 80,000) and throughput (up to 2,000 MiB/s) up independently of capacity. With gp2 you had to over-provision size just to buy more IOPS (3 IOPS/GiB). "Predictable baseline, pay only for the IOPS you need, decoupled from size" = gp3.

Note: these are the current AWS-documented ceilings (80,000 IOPS / 2,000 MiB/s / 64 TiB). Some older third-party question banks still list lower figures — trust the current AWS docs. The baseline (3,000 IOPS / 125 MiB/s) and the "decoupled from size" concept are what actually get tested.
Volume-type tells the exam reuses io2 when the words are "mission-critical" / "highest durability" (99.999%). io2 Block Express for extreme scale — up to 256,000 IOPS and 64 TiB. st1 for throughput-heavy big-data/log workloads; sc1 for cold, infrequently accessed data at lowest cost.
Two HDD traps HDD volumes (st1, sc1) are throughput-only and cannot be boot volumes — if an option puts an OS root on st1/sc1, eliminate it. And Multi-Attach (one volume attached to multiple instances in the same AZ) is supported on io1 and io2 only — never on gp3, gp2, or HDD.

Picking the service: EBS vs Instance Store vs EFS vs FSx

Before volume type, you must pick the right service. This table is the heart of the lesson — the "survives terminate?" and "sharing" columns settle most questions:

The Instance Store trap Instance Store is physically attached local disk — extremely fast, but ephemeral: data is lost when the instance stops, terminates, or the host fails. It is perfect for scratch space, caches, buffers, and replaceable temp data — and wrong for anything that must persist. When a scenario says "fine to lose" or "temporary", the answer is Instance Store, and EBS is the distractor (EBS persists, which you don't need and may pay extra for).
EFS vs FSx in one line EFS = NFS, Linux, regional/multi-AZ, scales to thousands of concurrent instances — the default "shared Linux filesystem across AZs". FSx = the rest: Windows (SMB), HPC/ML (Lustre), and multi-protocol/legacy needs.

See it in action

Run the Lesson-1 procedure: find the priority/keyword, eliminate what can't work, then pick. Commit to an answer before revealing the explanation.

Q1. Which storage service fits?
A content team runs dozens of Linux EC2 instances spread across multiple Availability Zones. They all need to read and write the same set of files concurrently, and the filesystem must survive any single instance. Which service?
Keywords: many Linux instances, across AZs, shared concurrent access. That is exactly EFS — an NFS, regional (multi-AZ) filesystem that thousands of instances can mount at once. (A) is impossible: EBS is single-AZ and (outside io1/io2 same-AZ Multi-Attach) one instance only. (B) Instance Store is ephemeral and not shared. (D) FSx for Windows is SMB for Windows hosts, not Linux. Answer: C.
Q2. Which storage service fits?
A video-encoding instance needs a large, very fast scratch area for intermediate frames while a job runs. The data is regenerated every run and is fine to lose when the instance stops. They want the highest local I/O at no extra persistence cost. Which service?
Keywords: scratch, regenerated each run, fine to lose on stop. Ephemeral local disk is Instance Store — fastest local I/O, no persistence you don't need. The trap is EBS (A, C): it persists, which the scenario explicitly doesn't require, and io2 Block Express is expensive overkill. (B) EFS is network file storage, not local scratch. Answer: D.
Q3. Which EBS volume type fits?
A team wants the most cost-effective SSD boot/data volume with a predictable performance baseline, and wants to raise IOPS without growing the volume's size. Which EBS type?
Keywords: cost-effective SSD, predictable baseline, IOPS decoupled from size. That's gp3 — baseline 3,000 IOPS / 125 MiB/s, with IOPS and throughput provisioned independently of capacity. gp2 (B) ties IOPS to size (3/GiB). io2 Block Express (C) is high-end provisioned IOPS, far pricier than needed. st1 (D) is HDD and can't be a boot volume. Answer: A.
Q4. Which storage service fits?
A Windows-based line-of-business application needs a fully managed SMB file share with Active Directory integration and NTFS permissions. Which service?
Keywords: Windows, SMB, Active Directory, NTFS. That is the exact profile of FSx for Windows File Server. EFS (A) is NFS for Linux, not SMB. Lustre (C) is HPC/ML, not a general Windows share. io2 Multi-Attach (D) is block storage (same-AZ, no managed SMB share). Answer: B.

The one paragraph to remember

Takeaway Decide the service first: need it shared across many instances/AZs? File storage — EFS (Linux/NFS) or FSx (Windows/SMB, Lustre HPC, ONTAP multi-protocol, OpenZFS). Single instance? Block storage — EBS if it must persist, Instance Store if it's ephemeral scratch. Then pick the EBS volume type: gp3 by default, io2 / io2 Block Express for mission-critical or extreme IOPS, st1 / sc1 for throughput-heavy or cold (never as boot volumes).
