RDS & Aurora

Managed relational databases on AWS — and the single distinction the exam tests more than any other: Multi-AZ for availability vs Read Replicas for scaling reads.

Lesson 7 ~10 min D2 Reliability · D3 Performance Heavily tested

The win

By the end of this lesson you'll never confuse the two relational HA/scaling features again. When a scenario says "survive an AZ failure" you'll reach for Multi-AZ; when it says "offload read traffic" you'll reach for Read Replicas. That one reflex earns you points across both the Reliability and Performance domains — and it's the trap AWS sets most often.

RDS: managed relational, six engines

Amazon RDS runs the relational engines you already know — MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, and Db2 — and hands AWS the chores: patching, backups, failover, monitoring. You still pick the instance class and storage; AWS runs the operating system and database software underneath.

On the exam, RDS is the default answer for "relational OLTP with familiar SQL, least operational overhead". If a question wants a self-managed database on EC2, it's almost always a distractor — managed beats self-managed (Lesson 1's step 4).

Multi-AZ vs Read Replicas — the core distinction

These two features look similar (both make a second copy of your data) but solve completely different problems. Memorise this table.

The two are not interchangeable. Multi-AZ is for staying up; Read Replicas are for scaling reads.
 Multi-AZRead Replicas
PurposeHigh availability / disaster recoveryScale read throughput
ReplicationSynchronous standbyAsynchronous
Serves traffic?No — standby is idle until failoverYes — handles read queries
FailoverAutomatic on AZ/instance failureNot automatic; can be promoted to standalone
RegionAnother AZ, same regionSame or cross-region
How manyOne standbyUp to 15 (engine-dependent)
The #1 database exam rule Multi-AZ = high availability (synchronous standby, automatic failover, the standby serves no traffic — so it does not scale reads). Read Replicas = read scaling (asynchronous, can be cross-region, can be promoted). If the question says "offload reads / reporting" → Read Replica. If it says "survive an AZ failure / automatic failover / minimal downtime" → Multi-AZ.

A common trap: a scenario complains about read load on the primary and offers Multi-AZ as a choice. It's wrong — the Multi-AZ standby is passive and answers no queries. You can also combine both: Multi-AZ for resilience and Read Replicas for scale.

One nuance for completeness: the rule above describes the classic Multi-AZ instance deployment (the exam default, and the right pick on most questions). AWS also offers a newer Multi-AZ DB cluster deployment with two readable standby instances — so if an answer explicitly says "Multi-AZ DB cluster," its standbys can serve reads. Don't let it shake the default rule unless the question names the cluster option.

Backups: automated vs manual snapshots

AspectAutomated backupsManual snapshots
Retention0–35 days (default 7; 0 disables)Kept until you delete them
RecoveryPoint-in-time restoreRestore to the snapshot moment
Cross-regionCopyableCopyable / shareable

Need to keep a backup beyond 35 days (e.g. for compliance)? That's a manual snapshot — automated backups can't be retained longer.

RDS Proxy: connection pooling

RDS Proxy sits between your application and the database, pooling and reusing connections so a flood of short-lived clients doesn't exhaust the database's connection limit. It also speeds up failover. The classic exam tell: "Lambda functions are opening too many connections / exhausting the database" → RDS Proxy. Serverless functions scale out fast and each can open its own connection, so pooling is exactly what they need.

Encryption: decide at creation

RDS encryption at rest uses KMS and covers the database, its logs, snapshots, and read replicas. The catch tested on the exam: you enable it when you create the instance. You can't simply toggle encryption on an existing unencrypted database — you encrypt by restoring/copying a snapshot into a new encrypted instance.

Aurora: AWS's cloud-native relational engine

Aurora is MySQL- and PostgreSQL-compatible but re-architected for the cloud. Key facts the exam loves:

FeatureDetail
Storage durability6 copies across 3 AZs, self-healing, auto-growing
Read scalingUp to 15 Aurora Replicas, all sharing the same storage
FailoverPromote a replica typically in under 60 s
Global Database1 primary region + up to 10 secondary regions, replication lag typically <1 s
Serverless v2Fine-grained auto-scaling of compute for variable/unpredictable load

Aurora Global Database is the answer when you see MySQL/PostgreSQL-compatible plus sub-second cross-region reads or cross-region disaster recovery. Don't confuse it with DynamoDB Global Tables — that's for NoSQL key-value, active-active. Aurora Global Database is relational, one writable primary.

See it in action

Commit to an answer before revealing each explanation — retrieval is what makes it stick.

Q1. Which option does the procedure select?
An RDS MySQL database serves a busy application. A new analytics team wants to run heavy reporting queries without slowing down the production workload. What should you add?
Priority: "offload heavy reads" → Read Replica. A Read Replica (B) takes read/reporting traffic off the primary. (A) is the classic trap — the Multi-AZ standby is passive and serves no queries, so it can't offload reads. (C) snapshots aren't queryable databases. (D) scales up but still loads the one primary. Answer: B.
Q2. Which option does the procedure select?
A finance app on RDS PostgreSQL must fail over automatically with minimal downtime if its Availability Zone goes down. Which configuration meets this?
Priority: "automatic failover if the AZ fails" → Multi-AZ. Multi-AZ (C) keeps a synchronous standby in another AZ and promotes it automatically — exactly the requirement. Read Replicas (A) aren't automatic failover and same-AZ defeats the purpose. Snapshots (B) mean manual recovery and data loss. RDS Proxy (D) pools connections; it doesn't provide AZ failover. Answer: C.
Q3. Which option does the procedure select?
A MySQL-compatible application must serve users in three regions with sub-second read latency locally and provide cross-region disaster recovery. Which database design fits best?
Priority: "MySQL-compatible + sub-second cross-region reads + DR" → Aurora Global Database. Aurora Global Database (A) replicates to secondary regions with typically <1 s lag for local reads and fast regional failover. (B) is single-region — no cross-region reads. (C) is NoSQL, not MySQL-compatible. (D) backups give DR but not low-latency live reads. Answer: A.
Q4. Which option does the procedure select?
A spiky workload of AWS Lambda functions is exhausting the RDS database's connection limit during bursts, causing failures. What's the most appropriate fix?
Priority: "Lambda exhausting connections" → RDS Proxy. RDS Proxy (D) pools and reuses connections, absorbing the surge of short-lived Lambda invocations — the textbook serverless pairing. Read Replicas (A) add read capacity, not connection management. Multi-AZ (B) is availability, not capacity. (C) is brute-force and still hits limits. Answer: D.

The one sentence to remember

Takeaway Multi-AZ keeps you up (synchronous standby, automatic failover, serves no reads); Read Replicas scale reads (asynchronous, cross-region, promotable). For relational + global + fast failover, reach for Aurora.
