DynamoDB, Caching & Purpose-Built Stores

When NoSQL or a cache beats a relational database — and how to pick the right add-on once you've chosen it. The "which data store?" judgment is everywhere on the exam.

Lesson 8 ~10 min D3 · Performance & D4 · Cost Databases

The win

By the end of this lesson you'll recognise when a scenario is steering you away from relational — toward DynamoDB, a cache, or a purpose-built store — and you'll pick the right one fast. Lesson 7 covered RDS and Aurora (the relational world). This is the other half: the moment the question stops sounding like "rows and joins" and starts sounding like "key-value at massive scale", "microseconds", or "analytics over petabytes".

The signal: when relational is the wrong tool

Relational databases (RDS, Aurora) are the default for structured data with joins and transactions. But SAA-C03 loves scenarios where that default is a trap. Listen for these tells:

  • "Key-value", "massive scale", "single-digit millisecond", "unpredictable/spiky traffic" → DynamoDB.
  • "Microsecond reads", "extreme read throughput", "in-memory" → a cache (DAX for DynamoDB, ElastiCache for the rest).
  • "Complex analytical queries", "BI", "data warehouse", "OLAP", "petabytes of historical data" → Redshift, not RDS.
  • "Highly connected data", "relationships", "ledger", "time-series" → a purpose-built store.

DynamoDB — serverless NoSQL key-value

DynamoDB is a fully managed, serverless key-value and document database delivering single-digit millisecond latency at any scale. No servers, no patching, no capacity planning of instances — you provision throughput (or let it scale), not hardware. This is the go-to answer whenever the workload is key-value and the scale is large or unpredictable.

Capacity modes

Pick the mode from the traffic pattern the question describes.
ModeUse whenCost shape
On-demandUnpredictable or spiky traffic; new apps with unknown load; "don't want to manage capacity"Pay per request; no planning
Provisioned (+ auto scaling)Predictable, steady traffic you want to optimise for costCheaper per request; set RCU/WCU, auto scaling adjusts within bounds

RCU/WCU: 1 RCU = one strongly-consistent read of 4 KB/s (or two eventually-consistent); 1 WCU = one write of 1 KB/s.

The add-ons that show up as answers

FeatureWhat it gives you
DAXDynamoDB Accelerator — an in-memory cache that turns single-digit-millisecond reads into microsecond reads for read-heavy / repeated-read workloads. Purpose-built for DynamoDB; no app rewrite.
GSI (Global Secondary Index)Query on a different partition key; can be added any time (up to 20). Use when you need to query by an attribute that isn't the table's key.
LSI (Local Secondary Index)Same partition key, different sort key; must be defined at table creation only.
StreamsItem-level change log (24 h retention) that can trigger Lambda — the classic event-driven pattern (e.g. "when an item changes, do X").
Global TablesMulti-region, active-active replication (last-writer-wins). The answer for "low-latency reads/writes in multiple regions" or "multi-region key-value store".
TTLAuto-expire items by a timestamp attribute, no WCU cost. Great for session data, temporary records.
Classic trap When a question wants microsecond DynamoDB reads, the trap answer is "put ElastiCache in front of it". The purpose-built, correct answer is DAX — it's integrated with DynamoDB and needs no cache-management logic in your app. Reach for ElastiCache when the backing store is not DynamoDB (e.g. RDS) or you need rich cache data structures.

ElastiCache — Redis vs Memcached

ElastiCache is managed in-memory caching. It offloads repeated reads from a database (cutting latency and DB load) and stores ephemeral data like sessions. The exam almost always frames the choice as Redis vs Memcached:

FeatureRedisMemcached
PersistenceYes (snapshots / AOF)No (volatile)
Replication / Multi-AZ failoverYes — high availabilityNo
Data structuresRich: sorted sets, lists, pub/sub, streamsSimple key-value only
ThreadingSingle-threadedMulti-threaded
Exam tellDurability, failover, leaderboards, sessions, pub/subSimple, cheap, multi-threaded distributed cache, volatile is fine

Mnemonic: Redis = "rich + resilient" (need persistence, failover, sorted sets, leaderboards, pub/sub). Memcached = "minimal + multi-threaded" (just a fast volatile cache you can scale horizontally).

Caching strategies

  • Lazy loading (cache-aside): read the cache; on a miss, fetch from the DB and populate the cache. Only requested data is cached, but data can go stale and the first read is slow (a miss).
  • Write-through: write to the cache and the DB together on every write. The cache is never stale, but every write pays extra latency and you may cache data that's never read.

Often combined: lazy loading to populate, plus a TTL to bound staleness. "Data is stale" in a question points at lazy loading; "extra write latency / always fresh" points at write-through.

Purpose-built & analytics stores (one-liners)

These are usually one right answer in a list of relational distractors. Learn the trigger phrase for each:

ServicePick it when the scenario says…
RedshiftData warehouse / OLAP; complex analytical SQL, joins, and BI reporting over huge historical datasets (columnar, petabyte scale)
AthenaServerless, ad-hoc SQL directly on data in S3 — no infrastructure, no loading, pay per query
NeptuneGraph database — highly connected data: social graphs, recommendations, fraud detection, knowledge graphs
DocumentDBMongoDB-compatible document database, AWS-managed
KeyspacesCassandra-compatible wide-column store, serverless
QLDBImmutable, cryptographically verifiable ledger — an append-only audit trail you can prove wasn't tampered with
TimestreamTime-series data — IoT sensors, application metrics; cheap at scale
Redshift vs Athena vs RDS All three "run SQL", so the exam tests which. RDS/Aurora = transactional (OLTP), live application reads/writes. Redshift = heavy analytical queries (OLAP) over a loaded warehouse for BI. Athena = ad-hoc queries straight on S3 files with zero infrastructure. "Complex BI over petabytes" → Redshift, not RDS. "Query the logs already sitting in S3" → Athena.

See it in action

Run the same procedure from Lesson 1: find the priority/signal word, eliminate what doesn't fit, then pick the purpose-built match. Commit before revealing.

Q1. Which data store fits?
A new mobile game needs to store player profiles as key-value items. Launch traffic is completely unpredictable — it could be 100 or 10 million users — and reads must return in single-digit milliseconds. The team doesn't want to manage capacity or servers.
Signals: "key-value", "single-digit milliseconds", "unpredictable traffic", "no capacity to manage" → DynamoDB on-demand. On-demand (C) absorbs any spike without you guessing capacity. Provisioned sized for peak (B) wastes money and still risks throttling if peak is wrong. RDS (A) and Aurora (D) are relational — wrong tool for a key-value workload at this scale. Answer: C.
Q2. Which add-on fits?
A read-heavy application on DynamoDB repeatedly reads the same hot items. Single-digit-millisecond latency is no longer fast enough — the team needs microsecond read latency with no application rewrite.
Signal: "microsecond reads on DynamoDB" → DAX. DAX (A) is the purpose-built, in-memory cache for DynamoDB — microsecond reads, no app rewrite. ElastiCache (B) is the trap: it works but means cache-management code and isn't DynamoDB-native. A GSI (C) lets you query a different key — it doesn't make reads faster. Strong consistency (D) makes reads slower, not faster. Answer: A.
Q3. Which design fits?
A retailer runs a key-value catalog in DynamoDB. They're expanding to Europe and North America and need low-latency reads and writes in both regions, with data kept in sync active-active.
Signal: "multi-region active-active key-value" → Global Tables. Global Tables (D) replicate active-active across regions with last-writer-wins, giving local low-latency reads and writes everywhere. "Read replica" (A) isn't a DynamoDB concept (that's RDS/Aurora). DAX (B) is a read cache, not cross-region replication. Nightly restore (C) isn't active-active and loses a day of data. Answer: D.
Q4. Which analytics store fits?
A BI team needs to run complex analytical SQL with large joins over petabytes of historical sales data to power dashboards. Queries are heavy and run repeatedly throughout the day.
Signals: "complex analytical SQL", "petabytes", "BI dashboards", "heavy + repeated" → Redshift (OLAP). Redshift (B) is columnar and built for exactly this. RDS (A) is OLTP — read replicas don't make it an analytics engine, and petabyte joins will crush it (the trap). DynamoDB (C) can't do complex joins/analytics. Athena (D) suits ad-hoc queries on S3, but for heavy queries run repeatedly all day a provisioned warehouse is the better, more cost-predictable fit. Answer: B.

The one paragraph to remember

Takeaway Key-value at scale → DynamoDB (on-demand for spiky, provisioned+auto-scaling for steady). Need it faster → DAX for microsecond reads; multi-region active-active → Global Tables; event on change → Streams → Lambda. Generic caching → ElastiCache (Redis for persistence/failover/leaderboards/sessions, Memcached for simple multi-threaded volatile). Analytics → Redshift (warehouse/OLAP) or Athena (serverless SQL on S3). Then the purpose-built one-liners: graph→Neptune, ledger→QLDB, time-series→Timestream.
