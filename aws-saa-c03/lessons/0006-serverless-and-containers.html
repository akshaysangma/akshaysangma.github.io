Serverless & Containers

Lambda, Fargate, ECS, EKS, and App Runner — and how to pick the lowest-operational-overhead compute for event-driven and containerized workloads.

Lesson 6 ~10 min D3 Performance · D4 Cost Compute

The win

By the end of this lesson you'll reliably pick the lowest-ops compute for two recurring exam shapes: an event-driven task (something fires, do a short job) and a containerized workload (you have a container, run it). The trick is knowing where each service sits on the "how much do I have to manage?" ladder — and remembering Lambda's one hard ceiling that turns it into a trap.

The operational-overhead ladder

Recall the procedure from Lesson 1: the phrase "least operational overhead" almost always points to a managed or serverless option. Compute services line up on a ladder from "AWS runs everything" to "you run the host fleet":

Lower on the list = more you manage. The exam rewards climbing as high as the requirements allow.

Fargate is a launch type, not a separate orchestrator — both ECS and EKS can run their tasks/pods on Fargate (serverless) or on EC2 (you own the nodes). "Serverless containers" → Fargate launch type.

Lambda — the event-driven default

Lambda runs your code in response to an event, scales from zero to thousands of concurrent executions automatically, and bills only for the milliseconds it runs. No servers, no patching, no idle cost. It's the canonical "least operational overhead" answer for short, bursty, triggered work.

Common triggers worth recognizing: S3 (object created/deleted), API Gateway (HTTP request), SQS (messages on a queue), and EventBridge (scheduled or event-pattern). If a scenario says "when an object lands in S3…" or "on a schedule…" and wants minimal ops, Lambda is your first read.

Classic trap — the 15-minute wall Lambda caps any single invocation at 15 minutes (900 s). The moment a scenario implies a job that runs longer — a big batch transform, a video encode, a multi-hour ETL — Lambda is out, no matter how loudly the question says "serverless" or "least ops". The intended answer becomes Fargate (or ECS/EKS). Watch for the duration buried in the scenario; it's there to disqualify Lambda.

Containers — Fargate vs. ECS-on-EC2 vs. EKS

Once you have a container, the question is who runs the underlying machines:

  • Fargate — serverless. No EC2 instances to provision, patch, or scale. No execution time limit, so it's the go-to when a containerized job is long-running but you still want zero server management. This is the default "containers, least ops" answer.
  • ECS on EC2 — you own and manage the EC2 host fleet. Pick this only when the scenario demands control of the hosts: special instance types (GPU, specific licensing), daemon access, or squeezing cost on steady, predictable load.
  • EKS — managed Kubernetes. The tell is organizational: the team has standardized on Kubernetes, needs K8s tooling/APIs, or wants portability across clouds. If "Kubernetes" appears in the requirements, EKS is almost always the answer.
  • App Runner — the simplest path for a web app or API: hand it a container image or source repo and it builds, deploys, load-balances, and auto-scales for you. Reach for it when the workload is "just a web service" and the question stresses simplicity.
"Serverless containers" trap When a question wants containers with no servers to manage, the answer is Fargate — not "ECS on EC2". ECS-on-EC2 still leaves you patching and scaling the instance fleet. ECS is the orchestrator; Fargate is the launch type that removes the servers.

See it in action

Run the Lesson 1 procedure on each. Find the priority word, eliminate what can't work (watch durations!), then climb as high up the ladder as the requirements allow. Commit before revealing.

Q1. Which option does the procedure select?
When users upload photos to an S3 bucket, the app must generate thumbnails. Uploads are spiky and unpredictable, each resize takes a few seconds, and the team wants the least operational overhead.
Priority phrase: "least operational overhead" + short, event-triggered, spiky → Lambda. S3 can invoke Lambda directly on upload; it scales to zero and to spikes with no servers to manage, and a few-second resize is well under the 15-minute cap. (B) is always-on and self-managed. (C) and (D) carry full cluster/host management you don't need. Answer: A.
Q2. Which option does the procedure select?
A team has containerized a long-running data-processing service. They want to run it without managing any servers and without rewriting it. Which is best?
Priority phrase: "without managing any servers" + already a container → Fargate. Fargate runs containers with no EC2 fleet to patch or scale and has no execution time limit. (B) ECS-on-EC2 still makes you own the hosts — the classic trap. (D) is fully self-managed. (A) forces a rewrite and hits the 15-minute wall on a long-running service. Answer: C.
Q3. Which option does the procedure select?
A nightly job parses and transforms a large dataset. End-to-end it runs for about 40 minutes. The team wants a serverless, low-ops option. Which fits?
Eliminate the non-functional first: 40 minutes > Lambda's 15-minute (900 s) hard cap. So (A) fails, and (C) is impossible — you cannot set a 60-minute Lambda timeout; 900 s is the ceiling. (B) more memory speeds CPU but can't break the 15-minute wall. A scheduled Fargate task is serverless, has no time limit, and EventBridge can trigger it nightly. Answer: D.
Q4. Which option does the procedure select?
An enterprise has standardized on Kubernetes across teams and wants to keep using their existing K8s manifests, tooling, and skills on AWS with a managed control plane. Which service fits best?
Tell: "standardized on Kubernetes" → EKS. EKS gives a managed Kubernetes control plane so existing manifests and K8s tooling carry over (and support multi-cloud portability). (A) ECS is AWS's own orchestrator — not Kubernetes-compatible. (C) App Runner hides orchestration entirely, so K8s tooling doesn't apply. (D) isn't containers at all. Answer: B.

The one sentence to remember

Takeaway Climb as high up the ladder as the requirements allow — Lambda for short event-driven work, Fargate for serverless containers, EKS when they've named Kubernetes — but check the clock first: anything over 15 minutes knocks Lambda out.
Primary source to read next (10 min): the AWS Lambda quotas. Lock in the timeout (900 s), memory range (128 MB–10,240 MB), payload (6 MB sync), and default concurrency (1,000) — these are the exact numbers the exam turns into traps.
