Decoupling & Messaging

SQS, SNS, EventBridge, Kinesis, and Amazon MQ. The most-tested "loosely coupled" decision on the exam — and a small set of tells that picks the right service every time.

Lesson 12 ~10 min Resilient Architectures · 26% Integration

The win

By the end of this lesson you'll be able to read an integration scenario and pick the right messaging service on the first pass — distinguishing a queue (SQS) from pub/sub (SNS) from an event bus (EventBridge) from a stream (Kinesis) from a managed broker (Amazon MQ). These questions reward pattern recognition, not memorisation, and they map straight onto the Reliability pillar: decoupling is how AWS architectures survive failure.

Why "loosely coupled" matters on the exam

A tightly coupled system fails as a unit: if the worker tier is down or slow, the web tier blocks or drops requests. AWS designs the exam around the opposite instinct — put a buffer or a broker between components so each can fail, scale, and recover independently. When a scenario says "decouple", "absorb a burst", "process asynchronously", or "so one component's failure doesn't take down the other", it is steering you toward one of these five services.

Heuristic The whole family exists to break a synchronous call into an asynchronous one. First ask what shape the decoupling needs: one consumer pulling work (queue), many consumers each getting a copy (pub/sub), routing by event content (bus), or an ordered replayable firehose of records (stream).

SQS — the default decoupler

Amazon SQS is a pull-based queue: producers send messages, consumers poll and process them. It's the canonical answer for "put a buffer between a fast front end and a slow back end". A consumer that's down doesn't lose messages — they wait in the queue (retention up to 14 days).

ConceptWhat to remember
StandardAt-least-once delivery, best-effort ordering, near-unlimited throughput. Possible duplicates — design consumers to be idempotent.
FIFOExactly-once processing, strict ordering; up to ~3,000 msg/s with batching. Use when duplicates or out-of-order are unacceptable.
Visibility timeoutDefault 30 s (range 0–12 h). Hides a message while one consumer works it so others don't double-process.
Long pollingWait up to 20 s for a message before returning — cuts empty receives and cost vs short polling.
Dead-letter queue (DLQ)After N failed receives, route "poison" messages to a DLQ for inspection instead of looping forever.
Trap SQS is not pub/sub. One message is processed by one consumer and then deleted. If a scenario needs the same message delivered to several independent systems, a lone SQS queue is wrong — you want SNS (often fanning out to multiple SQS queues).

SNS — fan-out to many

Amazon SNS is push-based pub/sub. Publishers send to a topic; every subscriber gets its own copy. Subscribers can be SQS queues, Lambda functions, HTTP/S endpoints, email, or SMS. The classic pattern is SNS→SQS fan-out: one event lands in the topic and is delivered into several queues, each owned by a different downstream service that processes at its own pace. Filter policies let each subscriber receive only the messages it cares about, so you don't need a topic per message type.

EventBridge — routing by event pattern

EventBridge is an event bus: events arrive (from AWS services, your apps, or SaaS partners), and rules with pattern matching route each event to targets. Reach for it when the decision is "which events, by their content, go where" — especially with AWS service events or third-party SaaS sources. Pipes add point-to-point integration (source → optional filter/enrich → target) for plumbing one service into another.

SNS vs EventBridge Both fan out. Choose SNS for high-throughput, low-latency delivery to many subscribers. Choose EventBridge when you need rich content-based routing, a schema registry, SaaS/AWS event sources, or an event archive/replay.

Kinesis — ordered, replayable streams

Kinesis Data Streams handles high-volume real-time data: clickstreams, telemetry, logs. Data is split across shards (each ~1 MB/s in, 2 MB/s out), ordered per shard, and replayable within the retention window (24 h up to 365 days). Multiple consumers can independently read the same stream — and re-read it. That replayability and ordering is the tell.

Kinesis Data Firehose is the no-code sibling: fully managed delivery to S3, Redshift, or OpenSearch (near-real-time, with optional buffering/transformation). If the requirement is "just land the stream in S3/Redshift with no servers", that's Firehose, not Data Streams.

Trap: SQS vs Kinesis Both "queue up" data, but SQS deletes a message once consumed and isn't built for replay or multiple independent readers of the same data. If you see ordered, replayable, multiple consumers, real-time analytics, or shards → Kinesis, not SQS.

Amazon MQ & Step Functions — the edge cases

Amazon MQ is managed ActiveMQ/RabbitMQ. Its single exam purpose: migrate an existing application that already uses an industry-standard broker protocol (JMS, AMQP, MQTT, STOMP) to AWS without rewriting it. Greenfield AWS-native apps should use SQS/SNS; MQ is the "lift-and-shift the legacy message broker" answer.

Step Functions isn't messaging — it's orchestration. When a scenario describes a multi-step workflow with state, branching, retries, and human/wait steps ("coordinate these steps in order, with error handling"), that's Step Functions, not a queue.

See it in action

Run the same procedure each time: name the shape of the decoupling, eliminate services that can't do it, then match the remaining tell. Commit to an answer before revealing the explanation.

Q1. Which service fits best?
A web tier accepts order submissions far faster than a downstream worker tier can process them, and traffic arrives in unpredictable bursts. The team wants the web tier to stay responsive and never drop a request even when the workers fall behind — with the least operational overhead.
Shape: buffer one producer → one consumer group, absorb bursts. That's the textbook SQS use case (C): the queue holds the backlog, the web tier stays responsive, and workers pull at their own rate. (A) stays synchronous — the web tier still blocks when workers are slow. (B) SNS pushes and has no buffer; a slow/down worker means lost or retried deliveries, not a durable backlog. (D) Kinesis works but adds shard management and replay machinery you don't need for simple decoupling. Answer: C.
Q2. Which service fits best?
When an order is placed, three independent systems must each react to the same event simultaneously: the fulfilment service, the analytics pipeline, and the email-notification service. Each should process at its own pace and a failure in one must not affect the others.
Shape: one event → many independent subscribers. That's SNS fan-out (D). Giving each system its own SQS queue subscribed to the topic means every system gets its own durable copy and processes independently — a failure in one queue's consumer doesn't touch the others. (A) is wrong: one SQS queue delivers each message to only one consumer, so the three would compete, not all receive it. (B) is tightly coupled and fails as a unit. (C) sequences steps — it doesn't fan one event to parallel independent consumers. Answer: D.
Q3. Which service fits best?
A payments service must process transactions in the exact order received, and the same transaction must never be processed twice. Throughput is modest (a few hundred per second).
Tell: strict order + no duplicates. That's exactly what SQS FIFO guarantees — exactly-once processing and strict ordering, well within its ~3,000 msg/s capacity for "a few hundred per second" (B). (A) Standard is at-least-once with best-effort ordering, so it allows duplicates and reordering — disqualified by the requirement. (C) SNS is pub/sub, not an ordered work queue. (D) Firehose just lands data in S3; it isn't an ordered exactly-once processing queue. Answer: B.
Q4. Which service fits best?
A retailer wants to ingest a high-volume clickstream for real-time analytics. The data must preserve order, and several teams need to consume the same stream independently — including the ability to replay the last few days to backfill a new model.
Tells: high-volume, ordered, replayable, multiple independent consumers. That's Kinesis Data Streams (C): per-shard ordering, retention from 24 h up to 365 days for replay, and multiple consumers reading the same stream. (A) SQS deletes on consume — no replay, no multiple independent readers of the same data. (B) SNS has no retention/replay and isn't ordered. (D) EventBridge routes discrete events by pattern; it isn't a high-throughput, replayable stream for analytics.

Bonus tell: if instead the scenario were "migrate an existing app that already communicates over JMS/AMQP without rewriting it", the answer would be Amazon MQ — the managed-broker migration path. Answer: C.

The one sentence to remember

Takeaway Queue & buffer → SQS (FIFO when order/no-dupes matter). One event to many → SNS (often SNS→SQS fan-out). Route by event pattern / SaaS sources → EventBridge. Ordered, replayable real-time stream → Kinesis. Legacy broker protocol → Amazon MQ. Multi-step workflow → Step Functions.
