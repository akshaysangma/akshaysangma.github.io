IAM & Encryption

Identity and data protection — the heart of Domain 1. Least privilege, roles over keys, and choosing the right encryption and secrets service.

Lesson 13 ~10 min Security 30% — biggest domain Domain 1

The win

Security is 30% of SAA-C03 — the single biggest point pool, larger than any other domain. By the end of this lesson you'll reliably do three things the exam rewards: apply least privilege, choose IAM roles over embedded access keys, and pick the right encryption or secrets service for a scenario. These three reflexes turn most Domain 1 questions into quick eliminations.

Identities: users vs groups vs roles

IAM gives you three kinds of identity to attach permissions to. Knowing which one a scenario wants is half the battle.

The three IAM identities. Roles are the exam's favourite answer for workloads and cross-account access.
IdentityWhat it isCredentials
UserOne person or one long-lived workload that can't use a roleLong-term: password and/or access keys
GroupA collection of users; a way to attach one policy to many usersNone — a group is just a permissions container, it can't be a principal
RoleAn identity assumable by anyone/anything that needs itNone standing — you get temporary credentials on assume

AWS's own words on roles: "a role does not have standard long-term credentials such as a password or access keys associated with it. Instead, when you assume a role, it provides you with temporary security credentials for your role session."Source: IAM roles. Those temporary credentials are issued by AWS STS (Security Token Service) and expire automatically.

Mental model A group is for organising people. A role is for granting access to workloads and other accounts without handing out permanent keys. If the scenario involves an EC2 instance, a Lambda function, or another AWS account needing access — think role.

Roles = temporary credentials via STS (the preferred way)

When an EC2 instance, Lambda function, or external account assumes a role, STS hands back credentials that expire on their own. Nothing long-lived sits on the instance to be stolen or to need rotating. That's why AWS treats roles as the default for:

  • EC2 / Lambda accessing AWS services — attach a role (for EC2 this is delivered through an instance profile). The SDK picks up the rotating credentials automatically.
  • Cross-account access — "Roles are the primary way to grant cross-account access." The resource account creates a role with a trust policy naming the trusted account; the partner assumes it via STS.
  • Identity federation — external users (SAML 2.0 / OIDC corporate directory) are mapped to a role and receive temporary credentials. IAM Identity Center is AWS's recommended front door for workforce access across many accounts.
Exam trap Never embed IAM access keys on an EC2 instance (in code, a config file, or an env var) to let an app call AWS. Any answer that says "store the access key/secret key on the instance" is wrong on a best-practice question. The right answer is almost always "attach an IAM role / instance profile." Hard-coded keys are long-lived, leak easily, and have to be rotated by hand.

Policy types & the evaluation rule

Permissions come from JSON policies. Two types matter most for the exam:

  • Identity-based policies — attached to a user, group, or role. They say "this identity can do these actions on these resources."
  • Resource-based policies — attached directly to a resource and name a principal. The classic examples are S3 bucket policies and IAM role trust policies. These enable cross-account access without the caller needing a role as a proxy.

When a request is evaluated, the decisive rule is short and absolute:

The rule Default is implicit deny. An Allow in any applicable policy opens access — unless something says Deny. AWS: "An explicit deny in any of these policies overrides the allow." Explicit deny always wins.

And the discipline that frames every policy you write — least privilege: "granting only the permissions required to perform a task… Start with a minimum set of permissions and grant additional permissions as necessary." On a "most secure" question, the answer that grants the narrowest scope beats the one that grants broad or wildcard access.

Protect the front door: MFA & the root user

  • Enable MFA on privileged identities — and especially on the account root user. A policy condition like aws:MultiFactorAuthPresent can even require MFA for sensitive actions.
  • Lock away the root user. Don't use it for daily work, don't create access keys for it, and protect it with strong MFA. Create least-privilege IAM identities (or Identity Center users) for everyday administration instead.

Encryption: KMS vs CloudHSM

For data protection, the default managed answer is AWS KMS. AWS: "AWS Key Management Service (AWS KMS) is an AWS managed service that makes it easy for you to create and control the keys used to encrypt and sign your data."

Choosing between KMS and CloudHSM. KMS is the default; CloudHSM is for dedicated-hardware requirements.
AWS KMSAWS CloudHSM
ModelManaged, multi-tenant key serviceDedicated, single-tenant HSM you fully control
KeysKMS keys (formerly "CMKs"); keys never leave KMS unencryptedYou manage keys directly inside your HSM cluster
IntegrationNative with S3, EBS, RDS, and most AWS servicesUsed via APIs/PKCS#11; less turnkey AWS integration
AuditKey usage logged in CloudTrailYou operate and audit the appliance
Pick when…You want easy, audited, AWS-integrated encryption (default)You need single-tenant hardware or strict custody/compliance control

KMS uses envelope encryption: a root key in KMS protects data keys, which protect your data. KMS keys are protected by FIPS 140-3 Security Level 3 validated HSMs and never leave the service unencrypted.Source: What is AWS KMS. On the exam, "encrypt S3 / EBS / RDS with audited, managed keys" → KMS. "We must own dedicated hardware" → CloudHSM.

Secrets: Secrets Manager vs Parameter Store

Both store sensitive values encrypted with KMS. The deciding factor on the exam is usually automatic rotation.

  • Secrets Manager — purpose-built for credentials, API keys, and tokens, and the key feature is built-in rotation. AWS: "With Secrets Manager, you can configure an automatic rotation schedule for your secrets." It has native integration to rotate RDS/database credentials. Choose it when the requirement says "rotate the database password automatically."
  • SSM Parameter Store — designed for configuration data; its SecureString type encrypts values with KMS. The standard tier is free and great for app config, but it does not provide built-in automatic rotation of secrets the way Secrets Manager does.
Exam trap When a scenario demands automatic rotation of a database password, the answer is Secrets Manager, even though Parameter Store SecureString could store the password. Parameter Store is the cheaper config store; rotation is Secrets Manager's job.

See it in action

Apply least privilege and "roles over keys" to each question. Commit to an answer before revealing the explanation.

Q1. Which option does best practice select?
An application running on an EC2 instance needs to read objects from an S3 bucket. What is the most secure way to grant this access?
Roles over keys. An IAM role attached via an instance profile (B) gives the app temporary, auto-rotating credentials from STS — nothing long-lived to leak or rotate by hand. (A) and (C) embed long-term keys on the instance, the classic anti-pattern. (D) breaks least privilege and exposes data publicly. Answer: B.
Q2. Which option does best practice select?
A partner company (a separate AWS account) needs temporary, scoped access to read from one of your S3 buckets for an audit. You want no long-term credentials shared.
Roles are the primary way to grant cross-account access. A role with a trust policy naming the partner account (C) lets them assume it and receive temporary, scoped credentials — no shared keys, access expires. (A) shares long-term keys. (B) over-exposes data. (D) grants far more than needed, violating least privilege. Answer: C.
Q3. Which option does best practice select?
An application stores a database password. Security requires the password be rotated automatically on a schedule, with the app retrieving the current value at runtime.
Automatic rotation → Secrets Manager. Secrets Manager (A) is purpose-built for credentials and offers a built-in automatic rotation schedule, with native support for database credentials. Parameter Store SecureString (B) encrypts the value but has no built-in rotation — a deliberate trap, since it can store the password but not rotate it. (C) and (D) are manual and insecure. Answer: A.
Q4. Which option does the evaluation logic produce?
A user is in a group whose identity-based policy allows s3:DeleteObject on a bucket. A separate policy attached to that same user contains an explicit Deny for s3:DeleteObject on the same bucket. The user attempts to delete an object.
Explicit deny always wins. AWS evaluates all applicable policies together; "an explicit deny in any of these policies overrides the allow." There is no ordering or priority number (A, C are invented), and explicit deny applies across identity-based policies too (B is wrong). The delete is denied. Answer: D.

The one sentence to remember

Takeaway Grant the least privilege that works, prefer roles (temporary STS credentials) over embedded access keys, remember explicit deny always wins, and pick the managed service the scenario asks for — KMS for encryption, Secrets Manager when rotation is required.
