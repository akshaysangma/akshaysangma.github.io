DNS, Content Delivery & Global Acceleration

Route 53 routing policies, CloudFront, and Global Accelerator. The exam wants two decisions from you: which routing policy and which edge service. This lesson makes both reflexive.

Lesson 10 ~10 min D3 · Performance & D2 · Reliability Networking

The win

By the end of this lesson you'll reliably do two things on edge/DNS scenarios: match the requirement to the right Route 53 routing policy (canary? failover? by country?), and pick the right edge service among CloudFront, S3 Transfer Acceleration, and Global Accelerator. These three are constantly swapped as distractors for one another — the trick is knowing the one property that separates them.

Route 53: it's just DNS, plus routing logic

Route 53 is AWS's managed DNS. The exam-relevant part is the routing policy you attach to a record — it decides which answer Route 53 returns to a query. Memorise the trigger phrase for each.

The seven Route 53 routing policies. The phrase in column two is what the question will say.
PolicyUse when the scenario says…
SimpleOne resource, no logic. Single record, no health checks.
Weighted"Send 10% of traffic to the new version" — canary / A/B testing by percentage split.
Latency"Serve users from the lowest-latency Region."
Failover"Active-passive disaster recovery" — primary + standby, with health checks.
GeolocationRoute by the user's country/continent (compliance, localization, licensing).
GeoproximityRoute by resource location, with a bias to shift more/less traffic to a Region.
MultivalueReturn up to 8 healthy records at random — simple, DNS-level HA (not a substitute for a load balancer).
Don't confuse the two "geo" policies Geolocation = decide by where the user is (their country). Geoproximity = decide by where the resource is, and you can dial a bias to deliberately overweight one Region. If the question mentions a bias/lever to shift traffic, it's Geoproximity.

Alias vs CNAME — the apex rule

A CNAME cannot be created at the zone apex (the bare domain, e.g. example.com) — DNS forbids it because the apex must also carry SOA/NS records. An Alias record is an AWS extension that can sit at the apex, points at AWS resources (CloudFront, ALB, S3 website, etc.), and is free (no charge for Alias queries to AWS targets).

Exam tell "Point example.com (the apex) at a CloudFront distribution / ALB" → Alias, every time. CNAME would only work for a subdomain like www.example.com. If an option says "create a CNAME at the apex", it's wrong — that's not allowed.

The three edge services

Now the second decision. CloudFront, S3 Transfer Acceleration, and Global Accelerator all "make things faster from far away", which is exactly why they're swapped as distractors. Separate them by what they actually do.

Pick by the workload, not by "is it fast".
ServiceWhat it isPick it when…
CloudFrontCDN — caches static and dynamic web content at edge locations. HTTP/HTTPS only.You're delivering a website / API / media globally and want lower latency via caching.
S3 Transfer AccelerationRoutes uploads to S3 over the AWS edge backbone.Users far from the bucket need faster uploads to S3.
Global AcceleratorAnycast static IPs at the edge; routes over AWS backbone to the nearest healthy Region. TCP/UDP, any protocol.You need non-HTTP (gaming/VoIP/IoT), static IPs, and fast multi-Region failover.

CloudFront details worth knowing

  • OAC (Origin Access Control) locks an S3 origin so objects are reachable only through CloudFront, not via the public bucket URL. (OAC is the modern replacement for OAI.)
  • Signed URLs / signed cookies serve private content to authorised users — signed URL for one file, signed cookies for many files / whole sections.
  • It caches dynamic content too — don't fall for "CloudFront is only for static files".
The classic trap CloudFront is HTTP/HTTPS only. The moment a scenario says UDP, TCP for a non-web protocol, static IP addresses, or fast regional failover for a game/voice/IoT app — it's Global Accelerator, and CloudFront is the bait. Also: Global Accelerator does not cache; CloudFront does.

The procedure for edge questions

  1. Web or not? If it's HTTP/HTTPS content delivery → think CloudFront first. If it's a non-HTTP protocol → Global Accelerator.
  2. Upload or download? "Faster uploads to S3" is its own answer: S3 Transfer Acceleration.
  3. Static IPs / failover? A need for fixed IP addresses or fast multi-Region failover screams Global Accelerator.
  4. For DNS: name the requirement — percentage split (Weighted), DR pair (Failover), by-country (Geolocation), lowest latency (Latency) — and the policy names itself.

See it in action

Commit to an answer before opening the explanation.

Q1. Which option does the procedure select?
You need example.com (the zone apex) to resolve to a CloudFront distribution. The record must work at the apex and you'd prefer not to pay for the DNS lookups.
The apex rule. A CNAME cannot exist at the zone apex (A is invalid by DNS rules). An Alias record can sit at the apex, points natively at AWS resources like CloudFront, and is free for AWS targets (B). CloudFront has no fixed customer IP to hardcode (C). Routing policy is irrelevant here (D). Answer: B.
Q2. Which option does the procedure select?
You're releasing v2 of an API and want to send 10% of live traffic to it as a canary while 90% stays on v1, adjusting the split over time.
Percentage split = Weighted. Weighted routing lets you assign a relative weight per record to control the proportion of traffic — exactly the canary/A-B pattern (C). Latency routes by Region distance, not by share (A). Failover is active-passive DR, not a controlled split (B). Multivalue returns random healthy records for simple HA, with no proportional control (D). Answer: C.
Q3. Which option does the procedure select?
A global web application serves a mix of static assets and dynamic pages. Users worldwide complain about latency. You want to cut latency by caching at the edge.
Edge caching of web content = CloudFront. CloudFront caches static and dynamic HTTP/HTTPS content at edge locations, directly addressing the latency complaint (A). Transfer Acceleration only speeds uploads to S3 (B). Global Accelerator improves routing but does not cache (C). Latency routing helps multi-Region deployments but doesn't cache content (D). A bigger instance doesn't help distant users (E). Answer: A.
Q4. Which option does the procedure select?
A multiplayer game uses a UDP protocol. The studio needs fixed static IP addresses for client config and fast failover between Regions if one goes down.
Non-HTTP + static IPs + fast failover = Global Accelerator. It provides two anycast static IPs, supports TCP and UDP, and fails over across Regions in seconds over the AWS backbone (D). CloudFront is the trap here — it's HTTP/HTTPS only and can't carry UDP (A). Transfer Acceleration is for S3 uploads (B). Geolocation is DNS routing by country, with no static IPs and slower DNS-TTL-bound failover (C). Answer: D.

The one sentence to remember

Takeaway Name the DNS requirement (percentage → Weighted, DR → Failover, country → Geolocation, apex → Alias), and for the edge ask "HTTP web content?" → CloudFront, "uploads to S3?" → Transfer Acceleration, "non-HTTP + static IPs + failover?" → Global Accelerator.
