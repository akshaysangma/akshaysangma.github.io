Reliable queues — the processing-list trick

The naive Redis queue is one line: producers RPUSH jobs …, workers BLPOP jobs. It's FIFO, it blocks cheaply, and it has one fatal flaw — the instant BLPOP returns, the job is gone from Redis. If the worker crashes mid-job, that work has evaporated. There is no copy anywhere.

The fix is to move the job rather than pop it: atomically transfer it onto a per-worker processing list in the same step that claims it. The work is now in flight and still durably parked. Finish the job, then remove it from the processing list — that removal is your acknowledgement. Crash before the removal, and the job sits in the processing list for a reaper to reclaim.

Use BLMOVE, not BRPOPLPUSH The old idiom was BRPOPLPUSH src dst timeout. As of Redis 6.2 that command is deprecated in favour of BLMOVE src dst <from> <to> timeout (and non-blocking LMOVE), which lets you pick both ends explicitly. Same mechanism, clearer direction. Write new code with LMOVE/BLMOVE. Both are O(1).

One honest limit: this is reliable, not magic. The acknowledgement is a value-based LREM, so jobs should carry a unique id (you remove that job, not "a job that looks like it"). And a crashed worker's processing list needs a recovery process — nothing re-queues it for you. When you want server-managed acknowledgement, per-message ids, redelivery and replay built in, that's exactly what Streams consumer groups (lesson 08) give you: XADD to append, XREADGROUP to claim into the group's pending entries list, XACK to confirm, XAUTOCLAIM to reap stragglers. At-least-once delivery, no processing-list bookkeeping of your own.Rule of thumb: list-queue when the work is fire-once and you control recovery; Streams when you need acks, consumer groups, or to replay history. The decision table at the end makes this concrete.

Run this — claim a job without losing it 
> RPUSH jobs "job:42" "job:43"     # producer enqueues; read oldest from the left
(integer) 2
> LMOVE jobs processing LEFT RIGHT  # claim oldest + park it, atomically (O(1))
"job:42"
> LRANGE processing 0 -1            # the in-flight job lives here now
1) "job:42"
> LRANGE jobs 0 -1                  # still queued, untouched
1) "job:43"
> LREM processing 1 "job:42"        # work done → ack by removing it
(integer) 1
A real worker would block: BLMOVE jobs processing LEFT RIGHT 5 waits up to 5 s for a job. Crash between the LMOVE and the LREM and job:42 is still sitting in processing — recoverable, not lost.

Rate limiting — three designs, increasing fidelity

All three answer "has this caller exceeded N actions per window?" — they differ in accuracy and cost.

1 · Fixed window — INCR + EXPIRE

One counter per caller per window. Increment on each request; the first increment also sets the TTL so the counter self-destructs when the window ends. Over the limit? Reject. Both commands are O(1) and the whole thing is two keystrokes.

The trap is the boundary: a window is a hard edge, not a rolling view. A caller can fire N requests in the last second of one window and N more in the first second of the next — 2N requests in two seconds, each window individually "compliant." For coarse abuse protection that's fine; for fairness it isn't.

Run this — a fixed-window limiter 
> INCR rate:user:42         # first hit this minute
(integer) 1
> EXPIRE rate:user:42 60 NX  # set TTL only if unset — NX flag added in 7.0
(integer) 1
> INCR rate:user:42         # later hits just increment
(integer) 2
> TTL rate:user:42          # window still draining
(integer) 60
Calling EXPIRE … NX after every INCR is safe and avoids the classic "if reply == 1 then EXPIRE" round-trip race: it only sets a TTL when the key has none.

2 · Sliding-window log — a sorted set of timestamps

Want a true rolling window? Keep one sorted set per caller where each request is a member scored by its timestamp. On each request: drop everything older than now − window with ZREMRANGEBYSCORE, count survivors with ZCARD, and admit only if under the limit. ZADD and ZREMRANGEBYSCORE are O(log N)-class; ZCARD is O(1). Exact, at the cost of storing one entry per request in the window — so cap it or pair it with a TTL.Members must be unique (a set!). Use a request id, or timestamp:counter — two requests in the same millisecond would otherwise collide and undercount.

Run this — a sliding-window log 
> ZADD slide:user:42 1700000000000 "req-1"   # score = ms timestamp
(integer) 1
> ZADD slide:user:42 1700000000500 "req-2"
(integer) 1
> ZREMRANGEBYSCORE slide:user:42 0 1699999940000  # evict > 60s old
(integer) 0
> ZCARD slide:user:42                         # live count in the window
(integer) 2

3 · Token bucket — atomic refill in Lua

Sliding-window log is exact but memory grows with traffic. The token bucket stores just two numbers — current tokens and last-refill time — refills lazily based on elapsed time, and spends a token per request. It allows controlled bursts (up to the bucket capacity) while bounding the long-run rate. The catch: read-tokens → refill → maybe-spend → write-back is a read-modify-write, and two requests interleaving would corrupt it. So you do it server-side in one atomic Lua script (lesson 12 — the whole script runs on the single thread with nothing interleaving):

-- KEYS[1] = bucket   ARGV: rate(tokens/sec), capacity, now(sec), requested
local b   = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tok = tonumber(b[1]); local ts = tonumber(b[2])
local rate=tonumber(ARGV[1]); local cap=tonumber(ARGV[2])
local now =tonumber(ARGV[3]); local need=tonumber(ARGV[4])
if tok == nil then tok = cap; ts = now end           -- cold start: full bucket
tok = math.min(cap, tok + (now - ts) * rate)         -- refill by elapsed time
local ok = tok >= need
if ok then tok = tok - need end                      -- spend
redis.call('HSET', KEYS[1], 'tokens', tok, 'ts', now)
redis.call('EXPIRE', KEYS[1], math.ceil(cap / rate) * 2)
return { ok and 1 or 0, tok }                         -- {allowed?, remaining}

Pass now from the caller (keeps the script deterministic and Cluster-safe). You can instead read redis.call('TIME') inside the script — under effects replication (default since Redis 5.0) that's permitted — but injecting time keeps the script pure. Invoke with EVAL/EVALSHA or load it as a Redis Function (7.0).

Leaderboard recap (lesson 07): the fourth classic recipe is just a sorted set — ZADD board <score> player to post, ZREVRANGE board 0 9 WITHSCORES for the top ten, ZREVRANK board player for "what's my position?" All O(log N). Nothing to assemble; the data structure is the pattern. That's why lesson 07 called zsets the crown jewel.

Pub/Sub — fire-and-forget fan-out

Everything above persists. Pub/Sub does the opposite, and that's the whole point. PUBLISH channel msg delivers the message to every client currently SUBSCRIBEd to that channel and then forgets it forever. At-most-once, no persistence, no history, no acknowledgement. Subscribed and connected when the message went out? You get it. Offline, slow, or you subscribe one millisecond later? It's gone — there is no buffer to catch up from. PUBLISH returns the number of clients that received it (which can be 0), and that's the only receipt you'll ever get.

SUBSCRIBE takes exact channels; PSUBSCRIBE news.* matches by glob pattern. PUBLISH is O(N+M) — N subscribers on the channel plus M pattern-subscriptions to test.A subscribed connection enters a restricted mode: in RESP2 it may only run (P)SUBSCRIBE/(P)UNSUBSCRIBE/PING/QUIT. RESP3 (lesson 15) lifts this — push messages arrive out-of-band, so the same connection can keep issuing normal commands.

Sharded Pub/Sub on Cluster — SPUBLISH (7.0) Classic PUBLISH on a Redis Cluster broadcasts the message to every node so any subscriber anywhere receives it — correct, but it floods the cluster bus and scales badly. Redis 7.0 added sharded Pub/Sub: SPUBLISH / SSUBSCRIBE / SUNSUBSCRIBE confine a channel to the single shard that owns its slot, so traffic stays local. Same fire-and-forget semantics; far better cluster scaling.
Run this — needs two terminals 
# Terminal A — the subscriber, parked and listening:
A> SUBSCRIBE news
1) "subscribe"  2) "news"  3) (integer) 1

# Terminal B — publish while A is listening:
B> PUBLISH news "deploy finished"
(integer) 1            # 1 client received it

# Terminal A now prints, unprompted:
1) "message"  2) "news"  3) "deploy finished"
Now publish before anyone subscribes: PUBLISH news "hi" returns (integer) 0 and the message is gone. No subscriber, no delivery, no trace — there's your at-most-once proof.

Keyspace notifications are Pub/Sub in disguise: enable them with CONFIG SET notify-keyspace-events KEA and Redis publishes on __keyevent@0__:expired, __keyspace@0__:<key>, and friends whenever keys change or expire. Genuinely useful for reacting to events — but because it rides Pub/Sub, it inherits the same caveat: a disconnected listener silently misses notifications. For change capture you can't afford to drop, write events to a Stream instead.

Picking the primitive

The three messaging shapes look interchangeable until a worker crashes or a subscriber blinks. This is the table to internalise:

Pub/Sub vs list-queue vs Streams — choosing the messaging primitive
PropertyPub/SubList queue (LMOVE)Streams + groups
Persists / has historyNoUntil poppedYes (append-only log)
Delivery guaranteeAt-most-onceOnce (with ack list)At-least-once
Fan-out (all see msg)Yes — to all subsNo — one consumerYes — per group
Built-in ack / redeliverNoDIY (processing list)Yes (PEL + XACK)
Replay past messagesNoNoYes (XRANGE / id)
Offline consumer catches upNo — misses allYes — work waitsYes — reads backlog
Hot-path costO(N+M) publishO(1) moveO(1) add / ack
Reach for it when…live notify, lossy OKsimple work queuedurable jobs / events
The one decision Ask one question: is it acceptable to lose a message? If yes and you need instant fan-out → Pub/Sub. If no and one worker should handle each job → list-queue (Streams if you want acks/replay free). If no and multiple independent consumers each need the full feed → Streams consumer groups. Persistence and delivery semantics decide it — not syntax.

Check yourself

Commit to an answer before reading the explanation — retrieval is what makes these stick.

Q1. A worker grabs a job and crashes before it finishes the work. Which queue design lets another worker recover that lost job?
The job must not silently vanish just because one worker died mid-processing.
B. BLMOVE atomically moves the job to a per-worker processing list in the same step that claims it; a crash leaves it there for a reaper to reclaim. A and D both remove the job with no safety copy — a crash loses it. C only reads: two workers would grab the same job, and nothing claims it. (This is the deprecated BRPOPLPUSH pattern, modernised — see the Redis 6.2 note above.)
Q2. Your fixed-window limiter allows 100 requests per minute, yet one client slips 200 requests through in roughly two seconds. What happened?
C. A fixed window is a hard edge: 100 requests in the last second of one minute plus 100 in the first second of the next is 200 in ~2 s, each window individually compliant. The cure is a sliding-window log (sorted set of timestamps) or a token bucket. A — Redis ints are 64-bit; no overflow here. B and D are real failure modes but would under-count or block, not allow a clean 2× burst.
Q3. A subscriber disconnects for ten seconds, reconnects, and finds the messages published meanwhile are simply gone. Why — and what should it have used?
Nothing was down; Redis stayed healthy and other subscribers received those messages live.
A. Pub/Sub is at-most-once with no persistence, no buffer, no replay — a disconnected subscriber misses everything sent in the gap. For a feed that must survive disconnects, use Streams (lesson 08): XADD persists each entry and a consumer group's pending list lets the subscriber read its backlog on reconnect. B, C, and D each invent a guarantee — buffering, replay, durability — that Pub/Sub simply does not provide.
