maxmemory, Eviction Policy & Capacity Planning

L18 told you how Redis decides what to delete under pressure. This is the applied other half: how you set the limit, pick the policy, and size the box so that pressure lands where you intend it to.

Phase 5 · Operations ~10 min Hands-on Builds on: eviction internals (L18) · memory (L17)
Recall first Before reading on: in L22 you sharded a dataset across a Redis Cluster by CRC16(key) mod 16384. Hold that thought — the last decision in this lesson is exactly when a single instance has run out of road and you reach for that.

The limit is a policy boundary, not a wall

By default a 64-bit Redis has maxmemory 0 — no limit. It will keep allocating until the OS kills it (the OOM killer) or the box starts swapping, and a swapping Redis is a dead Redis: the single thread (L01) blocks on page faults and every client stalls. So the first act of capacity planning is to give Redis a number it will respect.

Setting maxmemory doesn't reserve RAM and it doesn't make Redis frugal. It draws the line at which the eviction policy takes over. What happens at that line is entirely decided by maxmemory-policy — the eight policies you met in L18. The limit and the policy are one mechanism: a budget plus a rule for what to do when you hit it. Set one without thinking about the other and you've planned nothing.

The two dials, together maxmemory = how much Redis may use before it acts. maxmemory-policy = what it does when it gets there — evict something, or refuse the write. Neither is meaningful alone.

Leave headroom — maxmemory is not box RAM

The cardinal sizing mistake is maxmemory = total_RAM. The dataset is not the only thing competing for that RAM, and three other consumers spike at exactly the worst moments:

  • The persistence fork. BGSAVE and BGREWRITEAOF fork() a child that shares the parent's pages copy-on-write (L19). Every page the parent writes while the child runs must be duplicated. On a write-heavy load that COW spike is unbounded by the dataset size — in the pathological case the parent dirties most of its pages and the process transiently needs close to double the dataset in RAM.This is why a fork that's invisible on a read-mostly cache can OOM the same box under a write burst. The spike is proportional to write churn during the fork, not to dataset size.
  • Allocator fragmentation. jemalloc rounds every allocation up to a size class (L17), so resident memory (used_memory_rss) runs above the logical total (used_memory). The ratio between them — mem_fragmentation_ratio — is commonly 1.1–1.5. That overhead is real RSS the kernel must back.
  • Everything else. Client output buffers, the replication backlog (L20), query buffers, Lua/Function state, and the OS itself.

So maxmemory governs the dataset; the box must hold the dataset plus fork COW plus fragmentation plus overhead. A common, defensible starting point on an instance that does its own RDB/AOF: set maxmemory to roughly half of box RAM, then measure your real fork spike and fragmentation under load and tighten from there. If persistence runs on a replica instead of the primary, the primary's fork pressure drops and you can run the limit higher.

The 100%-of-RAM trap Pinning maxmemory to total RAM means the very first BGSAVE under write load asks the kernel for memory that isn't there. Best case the OS swaps and Redis grinds to a halt; worst case the OOM killer reaps the process mid-snapshot. The headroom is the durability config — without it, persistence is the thing that takes you down.

Pick the policy from the workload

L18 gave you the eight policies and the mechanics (approximated LRU/LFU, sampling). The applied question is narrower: is every key in this instance disposable? That single distinction picks your family.

Choosing maxmemory-policy by what the data is.
WorkloadPolicyWhy
Pure cache, recency winsallkeys-lruAny key may be dropped; evict least-recently-used.
Pure cache, popularity winsallkeys-lfuKeeps hot keys a one-off scan would evict under LRU.
Cache + must-keep keys mixedvolatile-lru/-lfuOnly keys with a TTL are evictable; persistent keys are safe.
No key is safe to dropnoevictionRefuse writes at the limit rather than lose data.

For a CDN-style or session cache where losing any entry just means a recompute, allkeys-lru (or allkeys-lfu when a few keys are far hotter than the rest) is the honest default. The moment the same instance also holds data you can't regenerate — a job queue, a leaderboard, a lock — allkeys-* will happily delete it. Then you either separate concerns onto different instances or move to volatile-* and put a TTL only on the disposable keys, so eviction can only touch those.

The volatile-* footgun (recall L18) A volatile-* policy evicts only among keys that have a TTL. If you're at the limit and no key has a TTL, there's nothing eligible — so Redis behaves exactly like noeviction and starts returning OOM errors on writes. A policy that quietly degrades to "refuse everything" is a 3 a.m. page. Confirm keys actually carry TTLs before trusting a volatile-* policy to make room.

Estimate the dataset before you trust a number

You can't size headroom around a dataset you haven't estimated. The back-of-envelope from L17:

Sizing formula dataset ≈ key_count × (avg_value_size + per-key overhead), then × mem_fragmentation_ratio for RSS, then + fork/COW headroom for the box.

The term people forget is per-key overhead. From L17: every top-level key carries a redisObject (~16 bytes), the SDS key string, and dict-entry plus hash-bucket pointers — call it tens of bytes before the value. A million keys holding a 20-byte value each are dominated by overhead, not data. This is the applied case for L16's small-encoding aggregates: packing fields into one listpack-encoded hash or zset pays the per-key tax once instead of a million times. DBSIZE (O(1)) gives you the key count; MEMORY USAGE key (L17) samples real per-key cost so you can multiply with a measured number rather than a guessed one.

Scale up, then scale out

When the estimate exceeds the box, there are two moves and an order to them:

  • Scale up first. A bigger instance is operationally trivial and keeps every multi-key op, transaction (L11), and Lua script (L12) on one node. Vertical scaling is the right answer far longer than people expect.
  • Scale out when up stops paying. The ceiling on a single instance isn't only RAM — it's the single thread (L01) and the fork(): a very large dataset means a long fork pause and a large COW spike on every snapshot. Past that point you shard with Redis Cluster (L22), trading the cross-slot multi-key freedom for horizontal capacity and parallel forks across smaller masters.
The deciding question Reach for Cluster (L22) when one instance can no longer hold the dataset with its fork/fragmentation headroom, or when fork-induced latency blips on a huge keyspace breach your SLO — not merely because the dataset is "big." Sharding is capacity and parallel forks bought with the loss of cheap cross-key atomicity.

Set it, then watch it

Configure the dials at runtime with CONFIG SET (effective immediately, O(1)) and read the truth back from INFO. The metrics that tell you whether your plan is holding live in INFO memory and INFO stats.

Run this — bound an instance and read its vitals In redis-cli: 
> CONFIG GET maxmemory
1) "maxmemory"
2) "0"                          # 0 = no limit (the default — fix it)
> CONFIG SET maxmemory 2gb
OK
> CONFIG SET maxmemory-policy allkeys-lru
OK
> INFO memory                    # excerpt of the fields that matter
used_memory:893410512
used_memory_human:852.02M
used_memory_rss:1003290624      # resident set — what the OS actually backs
mem_fragmentation_ratio:1.12     # rss/used; >1 fragmentation, <1 swapping (bad)
maxmemory:2147483648
maxmemory_policy:allkeys-lru
> INFO stats                     # is the policy actually evicting?
evicted_keys:10342              # keys dropped to stay under maxmemory
keyspace_hits:998123
keyspace_misses:23410           # hit ratio = hits/(hits+misses)
> DBSIZE
(integer) 740118
Watch three numbers over time: evicted_keys climbing fast means you're undersized for the working set (or the policy is wrong); mem_fragmentation_ratio drifting well above ~1.5 means real RSS is outrunning your headroom; the same ratio dropping below 1 means the box is swapping — the worst state of all.
CONFIG SET is ephemeral A runtime CONFIG SET maxmemory … applies instantly but is not written to redis.conf — a restart reverts it to the file's value (often 0). Persist it with CONFIG REWRITE, or set it in redis.conf in the first place. Capacity limits that vanish on restart are how a "sized" instance OOMs after a routine reboot.

Check yourself

Commit to an answer before opening the explanation — the retrieval is the point.

Q1. A box has 8 GB of RAM and a write-heavy dataset. An operator sets maxmemory 8gb to "use all of it." What goes wrong first?
Reads are fine for days. Then a nightly BGSAVE fires during a write burst and the instance freezes, then the process is killed.
C. BGSAVE forks a child sharing pages copy-on-write (L19); writes during the snapshot duplicate pages, and with maxmemory at 100% there's no headroom for that spike — the kernel swaps, then the OOM killer reaps Redis. The headroom you left out is what persistence needed. (A misreads eviction; B is a different failure; D is not a real mechanism.)
Q2. One instance holds session cache and a job queue. Memory fills and writes to the queue start failing with OOM errors. The policy is volatile-lru. Why no eviction?
The cache entries were written with SET … EX; the queue keys were written plain, with no expiry set on them.
B. volatile-* policies only consider keys that carry a TTL (L18). If the cache TTLs have mostly lapsed and the queue keys never had one, the eligible pool is nearly empty, so Redis degrades to noeviction and returns OOM. Fix: separate the queue onto its own instance, or give disposable keys a TTL. (A describes allkeys-lru; C and D invent constraints.)
Q3. You're sizing a cache of 5 million keys, each value ~30 bytes. The naive estimate (5M × 30B = 150 MB) badly undershoots the real footprint. The dominant missing term is —
A. From L17, each top-level key carries tens of bytes of fixed overhead (redisObject ~16B + SDS key + dict-entry/bucket pointers) before its value — with 30-byte values, overhead dominates the total. This is precisely why L16's packed small-encoding aggregates win: pay the per-key tax once, not 5 million times. (B, C, D are real consumers but tiny next to 5M × per-key overhead.)
