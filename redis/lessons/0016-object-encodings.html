Object Encodings — How One Type Has Many Shapes

A hash is one type, but it has two bodies — a compact one and a fast one. Knowing which body it's wearing, and when it changes clothes, is the difference between Redis sipping RAM and Redis stalling.

Phase 4 · Internals ~10 min Hands-on Builds on: the datatypes + typed values (L01)
Recall first Before reading on: in lesson 15 you traced a value across the wire as RESP bytes. But how does that same value sit in RAM while it waits? One hash with 3 fields and one with 30,000 fields are the same type — are they the same thing in memory? Hold your guess; this lesson is the answer.

One type, two (or three) bodies

Every value in Redis is wrapped in a small C struct called a redisObject. It carries the type you already know (string, list, hash, set, zset) and a second field you've never looked at: the encoding — the concrete in-memory representation actually holding the bytes.In the source this is object.c / server.h: robj has a type and an encoding field, plus a refcount and an LRU/LFU slot you'll meet in lesson 18.

The split is the whole game. Type is the contract — what commands are legal, what TYPE reports. Encoding is the implementation — Redis is free to swap it underneath you for the same logical value. A small hash is physically a flat, cache-friendly blob; a large one is a real hash table with pointers. Same HGET semantics; wildly different memory and CPU.

You inspect it with one command:

> OBJECT ENCODING somekey
"listpack"

OBJECT ENCODING is O(1) — it just reads the struct field, it doesn't scan the value.OBJECT also has REFCOUNT and IDLETIME/FREQ sub-commands — refcount ties to shared integers (lesson 17), idletime/freq to eviction (lesson 18).

The encodings, type by type

Each type starts in a compact encoding while it's small and promotes to a big encoding once it crosses a threshold. Here is the full map for Redis 7.x:

Compact → big encodings per type (Redis 7.x). "listpack" replaced "ziplist" in 7.0.
TypeCompactBigPromotes when…
stringint / embstrrawnot an integer & > 44 bytes, or mutated in place
listlistpackquicklisttoo many entries / a too-big entry
hashlistpackhashtabletoo many fields / a too-long field or value
setintset or listpackhashtablea non-integer added, or size limit crossed
zsetlistpackskiplisttoo many members / a too-long member

Three things deserve a sentence each:

  • String is special. An integer that fits a C long is stored as a real int (and shares the object — lesson 17). A short non-integer (≤ 44 bytes) is embstr: the redisObject header and the string sit in one allocation, so it's cheap and cache-local. Anything longer is raw (two allocations). The 44-byte cutoff is exact in modern Redis.
  • Set has two compact forms. An all-integer set uses intset (a sorted packed array of ints — tiny, with O(log N) membership). The moment you add a non-integer, it can't be an intset; it becomes a listpack if still small — and that listpack option for small non-integer sets is new in 7.2. Before 7.2 it would jump straight to hashtable.
  • quicklist isn't a flat structure — it's a linked list whose nodes are listpacks. So a big list is "listpacks all the way down," chained. The skiplist zset keeps a probabilistic skip list plus a hash table (member → score) so ZSCORE stays O(1) while ranges stay O(log N) — that's the structure behind lesson 7's leaderboards.
Why "listpack" and not "ziplist"? Pre-7.0 the compact encoding was the ziplist. It had a nasty failure mode — a "cascading update" where one edit could force every following element to be re-sized in a chain. Redis 7.0 replaced it with the listpack, which removed that hazard. You'll still see ziplist in old configs, old blog posts, and the legacy config aliases (hash-max-ziplist-entries still works) — read it as "listpack."

The thresholds — and the one-way door

You control exactly where each promotion happens. The knobs (Redis 7.x; legacy -ziplist- aliases still resolve):

Promotion thresholds. Stock redis.conf values shown — your build may differ, so always CONFIG GET.
ConfigDefaultCrossing it converts…
hash-max-listpack-entries128listpack → hashtable (field count)
hash-max-listpack-value64listpack → hashtable (any field/value bytes)
list-max-listpack-size128listpack → quicklist (see note on sign)
set-max-intset-entries512intset → listpack/hashtable (int count)
set-max-listpack-entries128listpack → hashtable (member count, 7.2)
set-max-listpack-value64listpack → hashtable (any member bytes, 7.2)
zset-max-listpack-entries128listpack → skiplist (member count)
zset-max-listpack-value64listpack → skiplist (any member bytes)

list-max-listpack-size overloads its sign: a positive value caps a node by entry count; a negative value caps it by size (-1=4 KB, -2=8 KB … -5=64 KB). Many builds ship -2. It governs both the single-listpack→quicklist promotion and the size of each quicklist node.

Conversion is a one-way door Promotion happens automatically when you cross a threshold — but Redis never converts back. Grow a hash past 128 fields and it's a hashtable forever, even if you HDEL back down to 3 fields. Push a 100-byte value into a small hash and it's hashtable permanently, even after you delete that value. The reasoning: shrink-checking on every delete would cost CPU on the hot path, and a collection that got big once tends to get big again. If you need the compact form back, you rebuild the key from scratch.
The trade-off in one line Compact encodings (listpack/intset) store data inline with no per-element pointers, so they're dramatically smaller in RAM and cache-friendly — but their operations are O(N) linear scans. The big encodings spend pointers and overhead to buy O(1)/O(log N) access. Small-and-linear beats big-and-indexed precisely because N is small — and a 200-element linear scan on Redis's single thread is still nothing. This is the whole reason "a thousand tiny hashes" can be cheaper than "a thousand-field hash" or "a million top-level keys" (lesson 17).

Hands-on — watch a hash change its body

Run this — promote a hash, then prove it won't demote A small hash is a flat listpack. Cross hash-max-listpack-value with one long field and watch it become a hashtable — then delete that field and watch it stay a hashtable. The one-way door, live: 
> HSET profile name akshay age 31 city istanbul
(integer) 3
> OBJECT ENCODING profile         # small → compact
"listpack"
> CONFIG GET hash-max-listpack-value
1) "hash-max-listpack-value"
2) "64"
> HSET profile bio "a bio string that is comfortably longer than sixty-four bytes, tipping it over"
(integer) 1
> OBJECT ENCODING profile         # one long value → promoted
"hashtable"
> HDEL profile bio                # shrink it back down…
(integer) 1
> OBJECT ENCODING profile         # …still big. one-way door.
"hashtable"
Now feel the other transitions in a few lines — string and set: 
> SET n 12345
OK
> OBJECT ENCODING n               # integer-that-fits-a-long
"int"
> SET n 1000000000000
OK
> APPEND n "x"                    # in-place mutation forces raw
(integer) 14
> OBJECT ENCODING n
"raw"
> SADD tags 1 2 3                 # all integers → packed array
(integer) 3
> OBJECT ENCODING tags
"intset"
> SADD tags hello                 # a non-int → listpack (7.2+)
(integer) 1
> OBJECT ENCODING tags
"listpack"
Every output above is from a real Redis 7.x/8.x session. Try the string boundary yourself: a 44-byte value is embstr, 45 bytes is raw.

Check yourself

Commit to an answer before you read the explanation — that's the retrieval that makes it stick.

Q1. You build a hash of small fields (listpack), then HSET one field to a 200-character string, and a second later HDEL that field. What does OBJECT ENCODING report now?
The hash now holds only three short fields again — exactly the shape it had when it was a listpack at the start.
C. The 200-char value crossed hash-max-listpack-value (64) and promoted the hash to hashtable. Conversion is one-way: deleting the field doesn't shrink the encoding back (A is the classic wrong intuition; B ignores the crossing). D is nonsense — intset is a set encoding, hashes never use it.
Q2. You raised hash-max-listpack-entries to 10000 to "save memory," and now a 6000-field listpack hash gets HGETALL'd on a hot path — and every other client briefly stalls. Why is the compact encoding implicated?
The same 6000-field hash, if left as a hashtable, would not have stalled the other clients this way.
B. Interleaving lesson 1: a listpack is a flat blob with no index, so field access is a linear O(N) scan — and on Redis's one thread, a 6000-element scan monopolises the server while everyone waits. Raising the threshold defeated the point: compact encodings only win while N is small. (A/C/D invent mechanisms listpacks don't have — no tree, no shadow copy, no per-field locks.)
Q3. You run SET userid 1000000000000, then APPEND userid "x", checking OBJECT ENCODING after each. What pair of encodings do you see?
A. The number fits a C long, so the fresh value is int. APPEND mutates the string in place, which Redis can only do on a modifiable raw SDS — so it converts to raw (and the value is now "1000000000000x" anyway). C is wrong — integers never start as embstr; D is wrong — that magnitude fits a long fine.
