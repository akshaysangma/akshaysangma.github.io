Streams — An Append-Only Log With Consumer Groups

A list can be a queue, but it forgets what it hands out and only one worker can take each item. A Stream is the log-shaped datatype that fixes both — history you can replay, and a group of workers that share the load with acknowledgement.

Recall first Before reading on: in Lesson 05 you built a queue with RPUSH + BLPOP. When a worker pops an item and then crashes mid-job, where does that item go — and which other worker can still see it? Hold your answer; the Stream exists precisely because the honest answer is "gone, and nobody."

The reframe: a log, not a list

A Redis Stream is an append-only log of entries. Each entry is a small set of field–value pairs stamped with a monotonically increasing ID, and — this is the whole point — appending an entry does not consume the ones before it. The log persists its history until you deliberately trim it. A list-as-queue is destructive: LPOP reads and removes in one move, so the item is gone the instant it leaves. A Stream separates those two ideas. Reading never deletes; deletion is its own explicit act.

That single change unlocks two things a list cannot do: replay (re-read the same entries later, from any point) and fan-out with bookkeeping (many workers split the load, and the server tracks who got what and whether they finished).Streams arrived in Redis 5.0 — the newest core datatype, and the one most shaped by a real design problem: a durable, replayable message log inside Redis itself. See antirez's introduction in the primary source below.

Entry IDs and writing the log

Every entry's ID has the form <ms>-<seq>: milliseconds since the Unix epoch, then a per-millisecond sequence counter. IDs are strictly increasing, so the log is totally ordered in time. You almost always let the server mint the ID by passing * to XADD:

> XADD orders * sku A12 qty 3      # * = server-assigned ms-seq ID
"1718900000000-0"
> XADD orders * sku B7 qty 1
"1718900000005-0"

XADD is O(1) for the append itself. The structure underneath is a radix tree of macro-nodes, so writes stay cheap as the log grows. Three flags earn their keep:

  • MAXLEN ~ 10000 — cap the log at roughly N entries, trimming oldest first. The ~ (approximate) form lets Redis trim whole macro-nodes at a time, which is far cheaper than exact trimming; prefer it. MINID (Redis 6.2) trims by ID/age instead of count.
  • NOMKSTREAM (Redis 6.2) — don't create the stream if the key is absent. Without it, XADD on a missing key creates the stream; with it, the append is a no-op returning nil.
  • An explicit ID instead of * — rarely needed, but you can pass <ms>-<seq> yourself (must be greater than the last ID).
Trimming is the only thing keeping a Stream bounded Unlike a list-queue, reading never shrinks a Stream — so a Stream with no MAXLEN/MINID trim policy grows forever and will eventually eat your RAM. XADD ... MAXLEN ~ N is not optional in production; it is how the log stays a log and not a memory leak. XLEN (O(1)) tells you the current count; XTRIM trims after the fact at O(N) in entries evicted.

Reading a closed range is XRANGE key start end (and XREVRANGE for descending). Use - and + as the minimum and maximum possible IDs. It is O(N) in entries returned — so always bound it with COUNT, which makes it effectively O(1):

> XLEN orders
(integer) 2
> XRANGE orders - + COUNT 10        # oldest→newest, bounded
1) 1) "1718900000000-0"
   2) 1) "sku" 2) "A12" 3) "qty" 4) "3"
2) 1) "1718900000005-0"
   2) 1) "sku" 2) "B7" 3) "qty" 4) "1"

Reading new entries: XREAD and BLOCK

XREAD reads entries with an ID greater than the one you pass — it's a "what's new since X" cursor that you, the client, advance. The magic ID $ means "only entries that arrive after this call," and BLOCK ms parks the connection until something does (or the timeout elapses), instead of busy-polling:

> XREAD COUNT 100 BLOCK 5000 STREAMS orders $
# blocks up to 5s; returns the next entries appended after now,
# or (nil) on timeout. Re-issue with the last ID you saw to continue.

This is a fine fan-out primitive — every XREADer sees every entry, like a tailable log. But it has no notion of "this entry is mine, the others keep off" and no record of what you finished. For a worker pool that splits work and survives crashes, you need the group.

Consumer groups: split the load, track the work

A consumer group is a named cursor shared by several consumers, plus a per-message ledger. The group has one logical read position; each XREADGROUP hands the next un-delivered entries to one consumer and records the delivery in the group's PEL — the Pending Entries List. An entry leaves the PEL only when a consumer calls XACK. That ledger is what gives Streams at-least-once delivery: nothing is considered done until it's acknowledged.

> XGROUP CREATE orders fulfil 0          # group "fulfil", start at 0 (replay all)
OK
> XREADGROUP GROUP fulfil worker-1 COUNT 1 STREAMS orders >
# the special ID  >  means "messages never delivered to any consumer"
1) 1) "orders"
   2) 1) 1) "1718900000000-0"
         2) 1) "sku" 2) "A12" 3) "qty" 4) "3"
> XACK orders fulfil 1718900000000-0      # done → drop from the PEL
(integer) 1

Two special IDs do all the steering here: > means "give me entries no one has been handed yet" (and advances the group cursor); any other ID means "re-read my own pending entries from the PEL" — that's how a restarted worker recovers its in-flight messages. XACK is O(1) per message.

When a consumer dies and never acks, its entries sit in the PEL forever. XPENDING inspects that ledger (summary form O(1); the extended form is O(N) in entries returned). To reassign a dead worker's messages to a live one, you claim them:

  • XCLAIM — transfer specific message IDs to a new consumer, typically gated by a minimum idle time so you only steal genuinely-stuck work. O(log N) in the size of the PEL.
  • XAUTOCLAIM (Redis 6.2) — scan the PEL and claim the next batch of idle messages in one call, returning a cursor to continue. O(1) if COUNT is small. This is the modern recovery loop; it replaces the old "XPENDING then XCLAIM each ID" dance.
  • XINFO STREAM / XINFO GROUPS — introspect the stream, its groups, and their lag (O(1)).
The delivery contract, stated plainly Streams give you at-least-once, never at-most-once. An entry can be delivered again (after a crash, via claim) but is never silently dropped while unacked. Your handlers must therefore be idempotent — processing the same order ID twice must be safe. The PEL is the durable record that makes "at least once" true; XACK is the only thing that ends an entry's pending life.

When a Stream — and when not

Three log-shaped tools look similar from a distance. They are not interchangeable:

Choosing among the message-passing primitives (full Pub/Sub treatment in L14).
 List queue (L05)Pub/Sub (L14)Stream
History / replayNo — pop deletesNo — fire-and-forgetYes — until trimmed
Fan-out to manyNo — one takerYes — all subscribersYes — read or groups
AcknowledgementNoNoYes — PEL + XACK
DeliveryAt-least-once*At-most-onceAt-least-once
Offline subscriberBuffered in listMisses everythingReads when back

*A list queue is only at-least-once if you use a reliable-queue pattern (LMOVE to a processing list); a plain BLPOP loses the item on a worker crash. We assemble that pattern, and contrast it with Streams, in Lesson 14.

Reach for a Stream when you want a durable, ordered event log that multiple workers consume cooperatively with retry-on-failure — order processing, event sourcing, an activity feed, sensor ingestion. Reach for a list when you want the simplest possible single-consumer hand-off and don't care about history. Reach for Pub/Sub when you want low-latency broadcast and explicitly don't want history or backpressure.

Hands-on: feel replay, fan-out, and the PEL

Run this — one stream, one group, a crash, a recovery Type these into redis-cli (Redis 7.x) and watch the ledger do its job: 
> XADD events MAXLEN ~ 1000 * type login user 42
"1718900100000-0"
> XADD events MAXLEN ~ 1000 * type click user 42
"1718900100010-0"
> XGROUP CREATE events analytics 0      # start at 0 → consume the backlog
OK
> XREADGROUP GROUP analytics c1 COUNT 10 STREAMS events >
... both entries handed to consumer c1 ...
> XPENDING events analytics            # the ledger: 2 unacked, owned by c1
1) (integer) 2
2) "1718900100000-0"
3) "1718900100010-0"
4) 1) 1) "c1" 2) "2"
> XACK events analytics 1718900100000-0   # ack the first only
(integer) 1
> XAUTOCLAIM events analytics c2 0 0       # c2 claims c1's idle (min-idle 0) leftovers
... the still-unacked entry now belongs to c2 ...
You just saw the whole model: a bounded log, a group replaying the backlog from 0, the PEL recording un-acked work, an XACK retiring one entry, and XAUTOCLAIM rescuing the orphan for a fresh consumer. No item was ever lost — and none vanished merely by being read.

Check yourself

Commit to an answer before opening the explanation — the retrieval is the lesson.

Q1. You need a job queue where a pool of workers shares the load, and any job a crashed worker held can be redelivered later.
Throughput matters, but so does not silently losing a job when a worker dies mid-task.
C. Only the consumer group splits work across consumers and records each delivery in the PEL, so an un-acked job from a dead worker can be claimed and retried. (A plain BLPOP list loses the item on crash and gives no fan-out; Pub/Sub delivers every job to every worker and keeps no record; a sorted set has no delivery ledger at all.)
Q2. A consumer reads 5 entries with XREADGROUP using the > ID, then crashes before processing them. What happens to those 5 entries?
B. XREADGROUP records the delivery in the Pending Entries List the moment it hands the entries over; they remain owned-but-unacked until an XACK retires them — or another consumer takes them over with XCLAIM/XAUTOCLAIM. Reading does not delete from a Stream (A); the original entries never move or duplicate in the log (C); claiming is something you trigger, not an automatic broadcast (D).
Q3. You run XRANGE bigstream - + with no COUNT on a stream holding ten million entries. What is the real risk?
C. Straight back to Lesson 01: XRANGE is O(N) in entries returned, and one thread serves one command at a time — so an unbounded range over ten million entries monopolises the server and freezes every other client until it completes. Always pass COUNT (which makes it effectively O(1)) and paginate. Redis won't reject the call (B) or trim anything (D); the laziness in (A) is wishful thinking.
