Bitmaps, HyperLogLog & Geo

Three "specialized" features that aren't new types at all — they're command families layered on the String and the Sorted Set you already know. Learn to count millions in kilobytes, pack flags into bits, and query by distance.

Phase 2 · Data Structures ~10 min Hands-on Builds on: Strings (L03) & Sorted Sets (L07)
Recall first Before new material: a Redis string is a raw, bit-addressable byte array up to 512 MB (L03), and a sorted set keeps members ordered by a float score with O(log N) inserts (L07). Hold both — everything below is built on exactly those two.

The reframe — no new types here

Redis has a small, fixed set of value types. "Bitmaps," "HyperLogLog," and "Geo" are not among them. They are specialized command sets that operate over a value of an existing type:

  • Bitmaps — a String read as an array of bits. SETBIT/GETBIT address individual bit offsets.
  • HyperLogLog — a String holding a fixed-size probabilistic sketch. PFADD/PFCOUNT read and write it.
  • Geo — a Sorted Set whose score is a 52-bit geohash of a coordinate. GEOADD is a ZADD in disguise.

This is the single idea the lesson hangs off: you can run TYPE on any of these keys and see string or zset staring back. A geo key answers ZRANGE; a bitmap answers STRLEN. The specialized commands are a lens, not a new container.Why care? It tells you the cost model. A geo key has a sorted set's O(log N) writes and memory profile; a bitmap has a string's flat byte cost. You already know how these perform.

Bitmaps — one bit per fact

A bitmap is the cheapest possible per-entity flag: one bit, addressed by integer offset. The canonical use is a daily-active-user set where the offset is the user id. SETBIT key 42 1 marks user 42 active; BITCOUNT tells you how many bits are set — i.e. how many distinct users.

Run this — flags as bits, and the string underneath 
> SETBIT dau:2026-06-28 42 1   # user 42 was active today
(integer) 0
> SETBIT dau:2026-06-28 99 1
(integer) 0
> GETBIT dau:2026-06-28 42
(integer) 1
> BITCOUNT dau:2026-06-28      # how many distinct users active
(integer) 2
> TYPE dau:2026-06-28          # it is just a String
string
> STRLEN dau:2026-06-28        # bytes = ceil((99+1)/8) = 13
(integer) 13
Now combine days with BITOP — boolean algebra across whole bitmaps: 
> SETBIT dau:2026-06-29 42 1
(integer) 0
> BITOP OR wau dau:2026-06-28 dau:2026-06-29   # active either day
(integer) 13
> BITCOUNT wau                 # weekly-active = 2 distinct users
(integer) 2

The memory math is the whole point. A bitmap of N bits costs N/8 bytes flat — tracking one million sequential user ids takes ~125 KB, a rounding error. BITOP AND of seven daily bitmaps gives "active every day this week"; OR gives weekly reach; XOR gives churn. BITPOS finds the first 0 or 1 bit. BITFIELD goes further: it treats the string as packed integers of arbitrary width (e.g. sixteen 4-bit counters in 8 bytes) with atomic INCRBY/GET/SET and overflow control — packed counters without one key each.

The trap — offset is allocation SETBIT at offset O grows the backing string to ceil((O+1)/8) bytes immediately. SETBIT k 4000000000 1 for a sparse, high user id allocates ~500 MB for one bit. Bitmaps only pay off when ids are dense (0..N). Sparse or UUID ids? Map them to a dense integer space first, or you've built a 500 MB way to store one boolean.

HyperLogLog — cardinality in 12 KB

You want "how many distinct visitors this month" over tens of millions of ids. A Set (L06) gives an exact answer but stores every member — gigabytes. A bitmap needs a dense id space. HyperLogLog answers the same question in a fixed ~12 KB maximum, forever, no matter the cardinality — by storing a statistical sketch instead of the elements.

Run this — add, count, merge 
> PFADD visitors:2026-06-28 alice bob carol
(integer) 1
> PFADD visitors:2026-06-28 alice           # already counted
(integer) 0
> PFCOUNT visitors:2026-06-28               # estimated distinct
(integer) 3
> PFADD visitors:2026-06-29 carol dave
(integer) 1
> PFMERGE visitors:week visitors:2026-06-28 visitors:2026-06-29
OK
> PFCOUNT visitors:week                     # union, deduped: 4
(integer) 4
> TYPE visitors:week                        # a String, like everything PF
string

The number is an estimate, with a standard error of about 0.81% — for 10 million uniques, expect to be off by roughly ±81 thousand. For dashboards and analytics that is a non-issue; for billing it is disqualifying. The killer feature is mergeability: PFMERGE unions sketches, so per-day HLLs roll up into a per-week or per-month unique count with no double-counting and no re-scan of the raw events.Small HLLs use a compact sparse encoding and are far under 12 KB; they auto-promote to the 12 KB dense form as cardinality grows. That conversion is one-way — encodings never shrink back (the general rule you'll meet again in L16).

The trap — it counts, it cannot enumerate An HLL stores no members. You can ask "how many?" but never "which ones?", never "is x in here?", and never remove one. It is write-and-count only. If you need membership tests or the actual elements, that is a Set's job (L06) — the trade you make for the 12 KB ceiling is giving up the elements entirely.

Geo — a sorted set you query by distance

Geospatial commands store each location as a member of a Sorted Set, with the score set to a 52-bit geohash — longitude and latitude interleaved into a single sortable integer. Nearby points get nearby scores, which is what makes radius search a sorted-set range scan. GEOSEARCH (Redis 6.2) replaced the now-deprecated GEORADIUS/GEORADIUSBYMEMBER; GEOSEARCHSTORE writes the hits into a new key.

Run this — and watch it admit it's a zset 
> GEOADD cities 13.361389 38.115556 "Palermo"
(integer) 1
> GEOADD cities 15.087269 37.502669 "Catania"
(integer) 1
> GEODIST cities Palermo Catania km
"166.2742"
> GEOSEARCH cities FROMLONLAT 15 37 BYRADIUS 200 km ASC
1) "Catania"
2) "Palermo"
> ZRANGE cities 0 -1 WITHSCORES   # the geohash scores, exposed
1) "Palermo"
2) "3479099956230698"
3) "Catania"
4) "3479447370796909"
> TYPE cities                     # proof: it was a zset all along
zset

GEOADD takes lon lat member (longitude first — a classic ordering slip), GEOPOS returns coordinates, GEODIST measures between two members. GEOSEARCH filters BYRADIUS or BYBOX from either a member (FROMMEMBER) or a raw point (FROMLONLAT), with COUNT, ASC/DESC, and optional WITHCOORD/WITHDIST/WITHHASH. Because it's a zset, you remove a location with plain ZREM — there is no GEODEL.Valid latitudes are −85.05112878 to 85.05112878 (the geohash projection's limit); the poles are out of range. GEOADD on an out-of-range coordinate returns an error.

The cost model

One table, because on a single thread (L01) the Big-O is the latency story:

Time complexity — Redis 7.x (source: redis.io command pages)
Underlying typeCommandBig-O
String (Bitmap)SETBIT / GETBITO(1)
String (Bitmap)BITCOUNT / BITPOS / BITOPO(N)
String (Bitmap)BITFIELDO(1) per subcommand
String (HLL)PFADDO(1) per element
String (HLL)PFCOUNTO(1) one key / O(N) keys
String (HLL)PFMERGEO(N) HLLs merged
Sorted Set (Geo)GEOADDO(log N) per item
Sorted Set (Geo)GEOPOS / GEODISTO(1)
Sorted Set (Geo)GEOSEARCH / GEOSEARCHSTOREO(N + log M)

For GEOSEARCH, N is the elements in the grid-aligned bounding box around your shape and M the items inside it — so a tight radius on a dense set is cheap, a continent-wide radius is not.

Check yourself

Commit to an answer before reading the explanation — retrieval is what makes it stick.

Q1. You must report daily distinct visitors across ~50M users. Exact counts aren't required, ~0.8% error is fine, and memory must stay tiny.
Fifty million ids, one count per day, rolled up weekly — all on a memory-constrained instance.
B. HyperLogLog gives ~0.81% error at a fixed ~12 KB and merges across days via PFMERGE — exactly this job. A Set (A) stores all 50M members (gigabytes). A bitmap (C) only works if ids are dense 0..N, not given here, and would also need a huge backing string. A sorted set (D) stores every member too, with no dedup benefit over a Set.
Q2. To flag a user whose id is 4 billion, a teammate runs SETBIT active 4000000000 1. What happens to memory?
B. A bitmap is a String; offset O forces a backing length of ceil((O+1)/8) bytes — 4×10⁹ bits ≈ 500 MB, allocated for one set bit. The offset is legal (max is 2³²−1), so it isn't rejected (C), nor is it sparse (A) or hashed (D). Bitmaps demand dense ids; map sparse ids down first.
Q3. After GEOADD cities …, a teammate runs ZRANGE cities 0 -1 WITHSCORES and is surprised it returns the city names with large float scores.
They expected a "geo type" to reject a sorted-set command. Why does it answer?
B. There is no separate geo type (recall L01: a key holds one typed value). GEOADD is a ZADD whose score is the 52-bit geohash, so TYPE returns zset and every sorted-set command — ZRANGE, ZREM, ZCARD — works directly. It is neither a String (C) nor a Hash (D).
