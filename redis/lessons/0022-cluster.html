Redis Cluster — Sharding by Hash Slot

Sentinel gave you availability on one dataset. Cluster splits the dataset across many masters — and hands the routing problem partly to your client. This is how Redis scales past one machine's RAM.

Phase 5 · Operations ~10 min Hands-on Builds on: Sentinel & replication
Recall first Before today: Sentinel (L21) watches one master + its replicas and does automatic failover — but every key still lives on that one master. What problem does Sentinel not solve? Hold that answer; it's exactly the gap Cluster fills.

The reframe

Sentinel makes one dataset highly available. It does nothing for capacity: if your data won't fit in one machine's RAM, or one machine's single thread can't keep up with the write rate, no number of Sentinels helps — every key still routes to the same master. Cluster is the answer to that wall.

The one sentence Redis Cluster shards the keyspace across many masters by assigning every key to one of 16384 hash slots, and gives each master replicas so it is highly available too. Sharding and HA — that's the line that separates it from Sentinel.

The whole design hangs off one decision: Redis does not hash keys directly onto nodes. It hashes them onto a fixed number of slots, and then assigns slots to nodes. That indirection is what makes resharding possible without rehashing every key — so start there.

1 · Keys → slots → nodes

There are exactly 16384 hash slots, numbered 0–16383. Every key maps to one slot by a fixed formula:

The slot formula slot = CRC16(key) mod 16384

CRC16 is cheap and deterministic — the same key always lands in the same slot, on every node, forever. Each master owns a set of slots (contiguous or not; resharding can leave a master holding scattered ranges). To find which node serves a key you compute its slot, then look up which node owns that slot.16384 = 2¹⁴. antirez picked it deliberately: small enough that the slot-ownership bitmap each node gossips is tiny (2KB), large enough to spread evenly across the few-hundred-node ceiling Cluster targets.

Why slots instead of hashing straight to nodes? Because node count changes — you add a master, you lose one — and you don't want every key to move when it does. Slots are a stable middle layer: to rebalance, you reassign slots between nodes, and only the keys in those slots move. The key→slot mapping never changes; only slot→node does.

2 · MOVED and ASK — the client learns the map

Connect to a cluster node and request a key it doesn't own, and it won't proxy the request for you. It replies with a redirect telling you where to go. There are two kinds, and conflating them is the classic mistake:

The two redirects — same shape, opposite meaning
RedirectMeansClient should
MOVEDThis slot permanently lives on another node nowUpdate its cached slot map, then retry there
ASKThis one key is mid-migration right nowRetry once on the named node, do not update the map

MOVED is durable: the slot has been reassigned, so a good client caches the new ownership and stops asking the wrong node. ASK is a single-request hint during an in-progress slot migration — the slot is still officially owned by the source node, but this particular key has already been copied to the target, so just this one lookup gets redirected. Treat ASK as permanent and you'll corrupt your slot map; treat MOVED as one-off and you'll redirect on every single request.An ASK redirect requires the client to send ASKING to the target node immediately before retrying the command — that's how the target agrees to serve a key for a slot it doesn't yet officially own.

Smart clients cache the map A cluster-aware client fetches the slot→node map up front with CLUSTER SHARDS (7.0+) or the older CLUSTER SLOTS, caches it, and routes each command straight to the right node — zero redirects in steady state. A MOVED is its signal to refresh that cache. This is why you point a smart client at the cluster, not a single node.

3 · Multi-key ops and the CROSSSLOT wall

Here is the constraint that reshapes how you model data on a cluster. A command touching multiple keys only works if all those keys live in the same slot. MSET a b c, SINTER, a MULTI/EXEC spanning keys, a Lua script reading two keys — if the keys hash to different slots, you get a CROSSSLOT error, not a result.

The trap There is no cross-slot atomicity. A transaction or Lua script cannot span two slots, full stop — and two arbitrary keys almost never share a slot. Cluster cannot atomically touch keys that live on different masters, because that would mean a distributed transaction, which Redis deliberately does not do. Your single-node multi-key patterns do not automatically survive the move to Cluster.

The escape hatch is hash tags. If a key contains a substring in curly braces, only the part inside the braces is hashed. So {user:42}:cart and {user:42}:session both hash on user:42 — same slot, guaranteed — and multi-key ops across them work.

Hash tag rule When a key holds {…}, the slot is CRC16(substring-between-first-{-and-next-}) mod 16384. Co-locate related keys by giving them a shared {tag}; they'll land in one slot and one master.

This is a modelling decision you make up front: keys you'll ever touch together — in a transaction, a Lua script, or a multi-key command — must share a hash tag. The cost is balance: jam too much under one tag and that slot becomes a hotspot the cluster can't spread.Only the first {…} with a non-empty body counts. {}foo and foo{}{bar} have no valid tag, so the whole key is hashed normally. Don't rely on nesting.

4 · Gossip, failover, and resharding

Nodes don't need a separate Sentinel process — Cluster has HA built in. Every node opens a second port, the cluster bus, at its client port + 10000 (so a node on 6379 gossips on 16379). Over that bus, nodes continuously gossip: exchanging who's alive, who owns which slots, and who they suspect is down. When enough masters agree a master has failed, one of its replicas promotes itself automatically and takes over its slots — the same failover idea as Sentinel, but run by the data nodes themselves.

Resharding moves slots between masters while the cluster serves traffic. For each slot being moved, Redis migrates its keys one key at a time from source to target; during that window the source answers with ASK for keys already moved, then a final MOVED once the slot's ownership flips. Live, incremental, key-by-key — that's why the slot indirection exists.

The trap A cluster needs a majority of masters reachable to stay available, and replica promotion needs the failed master to have had a replica. Run at least 3 masters (the recommended floor) — with two, a single failure costs you majority and the cluster stops accepting writes. And a master with no replica that dies takes its slots offline until you fix it manually.

Sentinel vs Cluster — the one-line distinction

Same company, different job
ConcernSentinel (L21)Cluster (L22)
High availabilityYes — auto failoverYes — auto failover
Sharding / capacityNo — one datasetYes — 16384 slots
Who routesClient asks Sentinel for masterSmart client caches slot map
Multi-key opsAll keys, alwaysOnly within one slot

If you only need HA on a dataset that fits one box, Sentinel is simpler. Reach for Cluster when capacity or write throughput — not just availability — is the wall.

See it on a real cluster

Spin up a throwaway cluster with the bundled helper. From a Redis 7 source build or the Docker image, the create-cluster script gives you 6 nodes (3 masters + 3 replicas) on ports 30001–30006:

# from the Redis source tree:
cd utils/create-cluster
./create-cluster start
./create-cluster create     # answer "yes" to the slot layout

# or point redis-cli at any node with -c (cluster mode = follow redirects)
redis-cli -c -p 30001
Run this — slots, redirects, and hash tags In redis-cli -c -p 30001, watch the routing happen: 
> CLUSTER INFO
cluster_enabled:1
cluster_state:ok
cluster_known_nodes:6
cluster_size:3            # 3 masters serving slots
> CLUSTER KEYSLOT foo       # which slot does "foo" hash to?
(integer) 12182
> SET foo bar               # node 30001 owns 0–5460, not 12182 →
-> Redirected to slot [12182] located at 127.0.0.1:30003
OK                        # -c followed the MOVED for you
> CLUSTER KEYSLOT user:42:cart      # unrelated keys scatter:
(integer) 9081
> CLUSTER KEYSLOT user:42:session
(integer) 15584           # different slots → MSET would CROSSSLOT
> CLUSTER KEYSLOT {user:42}:cart    # hash-tag them:
(integer) 4585
> CLUSTER KEYSLOT {user:42}:session
(integer) 4585            # SAME slot — now multi-key ops are legal
> MSET {user:42}:cart 1 {user:42}:session 2
OK
CLUSTER KEYSLOT is O(N) in the key's byte length — it's literally running the CRC16 you just learned. Run CLUSTER SHARDS too: that's the map a smart client caches.

Q1. A client sends GET k to a node and receives a MOVED reply pointing elsewhere. What should a well-behaved smart client do?

C. MOVED means the slot permanently lives elsewhere now, so the client caches the new slot→node ownership and routes future keys in that slot correctly — no more redirects. (A is the ASK behaviour, which keeps the map; D and the ASKING dance belong to ASK mid-migration, not MOVED; B and E throw away the whole point of a cached map.)
Q2. You move to Cluster and a MULTI/EXEC over cart:42 and session:42 now fails with CROSSSLOT. What's the fix that keeps them atomic together?
B. Multi-key atomicity requires one slot. Rewriting to {user:42}:cart and {user:42}:session hashes both on user:42, landing them in the same slot and the same master — so MULTI (and Lua) work. (A fails identically — a Lua script also can't span slots; C makes scattering worse; D doesn't change where keys hash; E abandons the atomicity you needed.)
Q3. A colleague says "we run Sentinel, so we don't need Cluster — they both do failover." When is that reasoning actually wrong?
Interleave with L21: both give HA, but only one of them shards the keyspace.
A. Sentinel and Cluster both provide HA, so failover (B), dynamic master discovery (C), quorum sizing (D), read replicas (E), and async-replication data loss (F) are true of both — none distinguishes them. The single thing only Cluster does is shard the keyspace across masters, so the colleague is wrong precisely when capacity (or write throughput) exceeds one box. That's the Sentinel-vs-Cluster line.
