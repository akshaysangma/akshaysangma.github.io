Distributed Locks & the Redlock Debate

A correct single-instance lock is four words and one tiny Lua script. Everything past that — Redlock, fencing tokens, the famous antirez–Kleppmann argument — is about how much you can trust a lock that lives in RAM and expires on a clock.

Phase 3 · Patterns & Atomicity ~10 min Hands-on Builds on: SET NX (L03) & Lua (L12)
Recall first Lesson 12 ended on the one guarantee that makes server-side logic safe: a whole Lua script runs atomically on Redis's single thread — no other command interleaves between its redis.calls. Hold that thought. It is the entire reason a lock can be released safely, and we lean on it in the very first transcript below.

The naive lock is one command

A lock is just a key whose existence means "taken." Acquiring it is a conditional create; the trick is doing the check and the create as one atomic step. You met the pieces in Lesson 3 — here they combine:

The acquire SET resource <unique-token> NX PX <ttl-ms> — set the key only if it does not exist (NX), and give it a millisecond expiry (PX). One command, O(1), atomic. Reply is OK if you got the lock, (nil) if someone already holds it.

Two parts of that command are non-negotiable, and both have a story:

  • The TTL (PX) is mandatory. A lock with no expiry is a deadlock waiting to happen: the holder crashes, the key lives forever, every future client blocks. The TTL is the auto-release that survives a dead holder.
  • The value is a unique token, not a constant. A random per-acquisition value (a UUID, or a counter you trust to be unique). It is how a client proves, at release time, that the lock it is about to delete is still its own lock — see the next section for why that matters enormously.
Don't do this with SETNX + EXPIRE The pre-2.6.12 idiom was SETNX then a separate EXPIRE (recall L03). Two commands means a window: crash between them and you've created a lock with no TTL — a permanent deadlock. The single SET … NX PX closed that gap. Always use the one-command form.

Release MUST be compare-and-delete (in Lua)

Releasing looks trivial — just DEL resource, right? No. Consider the timeline that a plain DEL walks straight into:

  • Client A acquires the lock with TTL 10s and starts work.
  • A stalls — a GC pause, a slow syscall, a network hiccup — for longer than 10s. The lock expires.
  • Client B now acquires the same key freely and starts its own work.
  • A wakes up, finishes, and runs DEL resource — deleting B's lock. Now C can acquire it too, and B and C run concurrently. The lock has silently failed.

The fix: before deleting, check the token still matches yours. But "GET then DEL" as two commands re-opens the exact same race — the key can expire and be re-acquired by someone else in between your GET and your DEL. The check and the delete must be one atomic operation. That is precisely what Lua gives you (recall the warm-up):

-- release.lua — compare-and-delete, runs atomically
-- KEYS[1] = lock key, ARGV[1] = the token we set at acquire time
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end

This is the canonical release script from the official docs. It returns 1 if it deleted your lock, 0 if the key was gone or held by someone else. Because the whole script is one atomic unit on the single thread, no client can sneak between the GET and the DEL.In practice you'd SCRIPT LOAD this once and call it by SHA with EVALSHA (L12) — fewer bytes on the wire, same atomicity.

Run this — acquire, fail to steal, release safely Two logical clients, one terminal. Watch the token gate the release: 
> SET lock:order:42 tok-A1B2 NX PX 30000   # client A acquires, 30s TTL
OK
> SET lock:order:42 tok-C9D8 NX PX 30000   # client C tries — key exists →
(nil)
> PTTL lock:order:42                       # time left, in ms
(integer) 28714
> EVAL "if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('DEL',KEYS[1]) else return 0 end" 1 lock:order:42 tok-WRONG
(integer) 0                                  # wrong token → refused, lock intact
> EVAL "if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('DEL',KEYS[1]) else return 0 end" 1 lock:order:42 tok-A1B2
(integer) 1                                  # right token → released
> GET lock:order:42
(nil)                                       # gone — anyone may acquire now
The wrong-token EVAL returning 0 is the whole point: a stale holder cannot delete the live lock.

The hazard that no token fixes: expiry vs work time

The token protects the release. It does nothing about the deeper problem the timeline above exposed: the lock can expire while you still believe you hold it. If your protected work can ever run longer than the TTL — and a long GC pause, a paused VM, or a packet delay can make any work exceed any TTL — then two clients can be inside the critical section at once. Setting a bigger TTL only widens the deadlock window when a holder dies; it cannot eliminate the overrun. This is the real fault line, and it is where the famous debate begins.

Efficiency lock vs correctness lock — decide this first Martin Kleppmann's framing (2016): a lock is for efficiency (avoid doing the same work twice — a double-sent email, a recomputed cache entry; failure is a minor cost) or for correctness (two actors must never overlap or state corrupts — money, inventory, a file). For efficiency, a single-instance Redis lock is perfect and you should stop here. For correctness, no expiring lock is sufficient on its own — read on.

Fencing tokens — Kleppmann's correctness fix

If you genuinely need correctness, the lock alone can't deliver it, because of the overrun above. Kleppmann's answer moves the guarantee to the resource being protected. The lock service hands out a fencing token: a number that strictly increases every time the lock is granted. Every write to the protected resource carries its token, and the resource remembers the highest token it has seen and rejects any lower one.

# Client A acquires, gets token 33, then stalls past its TTL.
# Client B acquires the now-free lock, gets token 34, writes:
storage.write(data, fencing_token=34)   # accepted; resource now at 34

# A wakes up, still thinks it holds the lock, writes:
storage.write(data, fencing_token=33)   # REJECTED: 33 < 34

The stale writer is "fenced off" even though it wrongly believes it holds the lock. Notice what this requires: the resource itself must understand and enforce tokens. That is a real demand — many storage systems can't do it — and it is exactly the demand the debate turns on.A single Redis instance can mint monotonic tokens cheaply with INCR on a counter key (recall L03). The hard part is never Redis; it's getting the downstream resource to reject stale tokens.

Redlock, and the argument about it

A single-instance lock has one more weakness: that instance is a single point of failure. Put a replica behind it and replication is asynchronous (you'll meet this in L20) — a failover can lose the just-written lock key, and two clients hold the "same" lock. Redlock (antirez, 2014) addresses this by avoiding any single master.

The Redlock algorithm, in brief Run N independent Redis masters (typically 5 — no replication between them). To acquire: (1) note the current time; (2) try SET … NX PX on all N, sequentially, each with a small per-node timeout so a dead node can't stall you; (3) you hold the lock only if you got a majority (N/2+1) and the total elapsed time is less than the TTL. Your effective validity is the TTL minus elapsed time minus a clock-drift margin. Release by running the compare-and-delete on all N.

Then in February 2016 Kleppmann published "How to do distributed locking", and antirez replied the same week with "Is Redlock safe?". It is one of the best-argued disputes in our field. Here is each side, fairly — and no, this lesson will not crown a winner, because the disagreement is narrower and more interesting than the internet made it.

The Redlock debate — both sides, stated fairly
IssueKleppmann (critique)antirez (rebuttal)
Fencing tokens Redlock generates no monotonically-increasing number, so it can't fence stale writers. Without fencing, no lock is safe for correctness. If the resource can do a conditional/CAS write to reject stale work, you often don't need a strong lock at all; and Redlock's random token can drive such a check.
Clocks & timing Redlock assumes bounded clock drift, network delay, and pauses. A clock jump or long GC pause breaks safety — it's a synchronous-model assumption dressed as a practical one. Redlock needs only relative time counted at roughly equal rates (bounded drift), not synchronized absolute clocks; big jumps are operational faults, mitigated by monotonic-clock APIs and NTP discipline.
Process pauses A pause after acquisition lets the lease expire while the holder still thinks it's safe — Redlock can't prevent the overlap. True, but this afflicts every auto-expiring lock equally, not Redlock specifically; acquisition itself re-checks the time, so a pause there only shortens usable validity.

Where they actually agree is the part worth keeping: for an efficiency lock, a single Redis instance is fine and Redlock is overkill; for correctness, you need a guarantee no clock-based lease can give by itself (fencing, or a resource-level conditional write). They disagree on whether Redlock's timing model is a reasonable engineering assumption and whether fencing is strictly required — not on the underlying physics.

When NOT to reach for a Redis lock If a double-run would corrupt data — money moved twice, inventory oversold, a ledger entry duplicated — a TTL-based Redis lock is an efficiency tool doing a correctness job. Use a system built for it: a real consensus/coordination service (ZooKeeper, etcd, Consul) that provides linearizable locks and monotonic fencing tokens — or push the mutual exclusion into the resource itself (a unique constraint, a conditional/CAS write, a fencing check). Redis locks are an optimization, not a safety mechanism.

Check yourself

Don't peek — commit to an answer first. Retrieval is what makes this stick.

Q1. Why must lock release be a Lua compare-and-delete rather than a GET then a separate DEL?
Your release code reads the token, confirms it matches, then issues DEL as the next command.
A. Between your GET (token still yours) and your DEL, the key can expire and be re-acquired by another client — your DEL then deletes their lock. Only running the check and the delete as one atomic Lua unit closes the gap. (B is a real but irrelevant perk — speed isn't the point; C is false, DEL removes keys regardless of TTL; D is invented.)
Q2. A locked job occasionally outlives its TTL, so two workers run at once and corrupt shared data. Best response?
A. Corruption from overlap is a correctness problem, and no expiring lock can prevent the overrun — a pause can exceed any TTL. Move the guarantee to the resource with monotonic fencing tokens it enforces. (B can't bound an arbitrary GC/VM pause and only worsens the dead-holder deadlock; C removes the only safety you had; D doesn't address the overlap at all.)
Q3. You need mutual exclusion where a double-run corrupts billing records permanently. What is the soundest choice?
The window is correctness-critical: two actors must never both commit the same charge.
A. Correctness-critical mutual exclusion wants a linearizable lock service with monotonic fencing tokens — exactly what consensus systems provide. (B and C are TTL/clock-based efficiency tools; both Kleppmann and antirez agree they don't make a correctness lock. D's WATCH/CAS from L11 only guards the Redis keys it watches, not the external billing resource, so it can't fence a stale writer there.)
