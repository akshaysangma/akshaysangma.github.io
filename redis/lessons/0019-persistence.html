Persistence — RDB vs AOF

RAM serves; disk survives. This lesson is about the "survives" half — the two ways Redis writes itself to disk, the fork trick that makes snapshots cheap, and how to choose a durability profile on purpose.

Phase 5 · Operations ~10 min Hands-on Builds on: in-memory model (L01)
Recall first Before disk: from Lesson 18, what's the difference between a key expiring and a key being evicted? Hold that — both delete data on purpose, while persistence is about not losing data by accident. Different problem, different machinery.

The reframe: two questions, not one

Redis lives in RAM. Pull the power and RAM is gone. Persistence is how a restarted process gets its dataset back — but "persist to disk" hides two genuinely different mechanisms with opposite trade-offs. Don't blur them.

The split RDB writes a point-in-time snapshot of the whole dataset — a compact binary file, taken now and then. AOF writes an append-only log of every write command — replay the log and you rebuild the dataset. Snapshot vs journal. You can run either, both, or neither.

The axis that separates them is durability granularity: how much recent data you're willing to lose if the process dies right now. A snapshot from five minutes ago loses five minutes. A log fsynced every second loses about a second. That single number drives most of the config.

RDB — the point-in-time snapshot

An RDB file (dump.rdb) is the entire keyspace serialised as a compact binary blob. It's small, it loads fast on restart, and it's the natural thing to copy off the box. Two commands produce one:

  • SAVE — serialises in the main thread. It blocks every other client until the file is written. O(N) over the whole dataset (single thread — recall L01: one slow command freezes everyone). You almost never run this in production.
  • BGSAVE — forks a child process that writes the file while the parent keeps serving. This is the one that runs in practice, including the automatic saves.

Automatic snapshots are driven by save points in the config — "snapshot if at least C keys changed in S seconds." A common default looks like save 3600 1 300 100 60 10000: every hour if ≥1 change, every 5 min if ≥100, every minute if ≥10000. Set save "" to disable RDB entirely.The save directive is additive — each pair is one independent rule, and Redis snapshots when any rule fires. More rules = more frequent saves under load, fewer when idle.

The fork trick: copy-on-write

How does the child snapshot a consistent dataset while the parent keeps mutating it? fork(). The OS gives the child a virtual copy of the parent's memory, but the pages aren't actually duplicated — parent and child share the same physical pages, marked read-only. They only diverge copy-on-write: when the parent writes to a page, the kernel copies that page so the child keeps seeing the original. The child serialises a frozen, consistent view; the parent races ahead.

The COW memory spike Shared pages are free — until they're written. Under a write-heavy load during the save, the parent dirties many pages and each one gets duplicated, so resident memory climbs for the duration of the fork. In the worst case (you touch nearly every page) RSS can approach double. Treat it as a spike you must leave headroom for, not a guarantee you'll hit — a mostly-read workload barely moves. This is why you never set maxmemory to 100% of the box (capacity planning → L23).

RDB's costs: you lose everything since the last snapshot if the process dies between saves, and the periodic fork is a CPU/memory event. Its wins: tiny files, fast restarts, trivial to ship as a backup artifact.

AOF — the append-only log

Turn it on with appendonly yes. From then on, every write command is appended to a log. Rebuild = replay the log from the top. The knob that matters is when the log is fsynced to disk — appendfsync:

appendfsync — the durability vs throughput dial
Settingfsync cadenceWorst-case lossThroughput
alwaysevery write≈ one commandlowest
everyseconce per second≈ one secondhigh (default)

everysec is the default and the sane choice: a background thread fsyncs once a second, so a crash costs about a second of writes and throughput stays near in-memory speed. always fsyncs on every write — maximal durability, but you now pay a disk round-trip per command and throughput drops hard. no lets the OS flush on its own schedule (often ~30 s), fastest and least safe."fsync every second" still means a write is in the OS buffer the instant the command returns — the one-second window is about surviving a power loss, not a clean restart. A graceful shutdown flushes everything.

Rewrite: keeping the log from growing forever

A pure command log grows without bound — INCR k a million times is a million lines that rebuild to a single integer. AOF rewrite compacts it: Redis writes a new, minimal AOF that reproduces the current dataset in the fewest commands, then swaps it in. It's triggered automatically by auto-aof-rewrite-percentage (rewrite when the AOF has grown N% past its last-rewrite size) and auto-aof-rewrite-min-size, or on demand with BGREWRITEAOF. Like BGSAVE, the rewrite runs in a forked child — same COW story.

Since 7.0 — multi-part AOF (the "hybrid") Modern AOF isn't one file. A rewrite produces a base file plus one or more incremental files, tracked by a manifest, all living in the directory named by appenddirname (default appendonlydir). The base can be written in RDB format (aof-use-rdb-preamble yes, the default) — a fast, compact snapshot — with subsequent writes appended as plain AOF commands. That RDB-base + AOF-tail combination is the "hybrid persistence" you'll hear named: the compactness of a snapshot with the small loss-window of a log.

Restart, recovery, and the thing persistence is not

On startup, if appendonly yes, Redis loads the AOF and ignores the RDB — the AOF is the more complete, more recent record. RDB is loaded only when AOF is off. If the AOF has a truncated tail (a half-written command from a crash mid-fsync), aof-load-truncated (default yes) loads everything up to the corruption and carries on, rather than refusing to start.

Persistence is not backup RDB and AOF protect you from a process restart. They do not protect you from a fat-fingered FLUSHALL, a bad migration, ransomware, or a dead disk — that destructive write is faithfully snapshotted or logged like any other. A real backup is a copy of dump.rdb shipped off the host, versioned and tested for restore. Same file, completely different discipline.

Choosing a profile

Picking a durability profile
WorkloadConfigWhy
Pure cache (rebuildable)maybe none, or RDB onlyloss is cheap; favour speed and fast restart
Durability-sensitiveAOF everysec (+ RDB)~1 s loss window; RDB for fast restore + backups
Money / cannot lose a writeAOF alwaysper-write fsync; accept the throughput hit

The common production answer is both: AOF everysec for the tight loss window, RDB for fast restarts and a clean artifact to copy off-box. They're not mutually exclusive — and remember the master's RDB is also the vehicle replicas sync from (→ L20).

Check yourself

Don't peek — commit to an answer first. Retrieval is what makes this stick.

Q1. A write-heavy instance triggers BGSAVE and its resident memory climbs sharply for the duration of the save. What is happening?
The dataset itself didn't grow much, yet RSS rose toward nearly twice baseline while the child ran, then settled back down afterward.
C. fork() shares pages copy-on-write; while the child writes the snapshot, every page the parent mutates gets duplicated, so RSS rises with write volume and can approach double in the worst case — a spike, not a guarantee. (A misreads where the file is built; B invents a second load; D is eviction, a different mechanism from L18.) Leave headroom for this.
Q2. An instance runs both AOF (appendonly yes) and RDB. It crashes and restarts. Which file does Redis use to reconstruct the dataset?
B. When AOF is enabled it wins at load time — it captures writes since the last snapshot, so it's the fuller record; RDB is used only when AOF is off. (A invents timestamp arbitration; C is the restart-speed argument but not the load rule; D isn't how recovery works — though note the 7.0 multi-part AOF can itself contain an RDB-format base.)
Q3. A team copies dump.rdb to the same disk nightly and calls it their backup. A bad deploy runs FLUSHALL at noon. What protection do they actually have?
They reason: "We persist to disk, so our data is safe." The flush is then snapshotted by the next save like any other write.
A. Persistence survives a restart, not a mistake — the FLUSHALL is logged/snapshotted faithfully, so the next save overwrites the good file. They're saved only by the off-cycle nightly copy (and only if it's off-host and restore-tested). (B invents RDB history; C — AOF replays forward, it can't undo; D is false, but the destructive command being captured is exactly the problem.) Persistence ≠ backup.
