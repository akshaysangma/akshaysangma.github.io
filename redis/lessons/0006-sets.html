Sets — Membership and Algebra

A set answers one question in constant time — "is this in here?" — and then lets the server do the intersect/union/difference work you'd otherwise drag across the wire and write a loop for.

Phase 2 · Data Structures ~10 min Hands-on Builds on: Lists (L05)
Recall first Before we start: in a Redis list, why is reaching the middle element (LINDEX mylist 5000) an O(N) operation? Hold that answer — a set fixes exactly the access pattern a list is bad at.

The reframe

A list keeps order and allows duplicates; its cost is that "do you contain X?" means walking it. A set drops order and forbids duplicates — and in exchange gives you the thing a list can't: O(1) membership. The value is an unordered collection of unique, binary-safe strings, backed by a hash table, so "is this member present?" is a single lookup regardless of size.

The one idea A set is a hash table of members with no values — you store keys-only. That buys you two things a list can't: uniqueness (adding a member twice is a no-op) and O(1) membership tests. On top of that, Redis runs set algebra — intersection, union, difference — server-side, next to the data.

Two superpowers fall out of that. First, membership: "have I seen this user?", "is this id already tagged?", "is this IP blocked?" — each is a constant-time question. Second, algebra: "who follows both A and B?", "which products are in cart X but not cart Y?" — relational questions you answer with one command instead of pulling two collections to the client and looping.This is the same locality argument from L01: the server does the work next to the data. The difference here is that the "work" is now whole-collection set theory, not a single counter bump.

The membership primitives

The everyday core is small and mostly O(1). SADD adds members and returns how many were newly added (duplicates silently ignored — that return value is your dedup signal). SREM removes. SISMEMBER is the headline: one member in, 0 or 1 out, constant time. SMISMEMBER (Redis 6.2) checks several members in one round trip. SCARD is the count, and crucially it's O(1) — Redis tracks cardinality, it doesn't recount.

The SMEMBERS trap — and you've met it before SMEMBERS huge_set is O(N): it materialises every member into one reply. On a multi-million-member set that's the exact L01 failure — one slow command monopolises the single thread and every other client waits. Reach for SSCAN (cursor-based, O(1) per call) when you must walk a large set, and prefer SISMEMBER/SCARD when you only need an answer about the set, not its contents.

Set algebra — the real reason to use a set

This is where sets stop being "a list without duplicates" and become a query engine. Three operations, each with a non-storing form (returns the result) and a …STORE form (writes the result to a destination key, returning its cardinality):

  • SINTER / SINTERSTORE — intersection: members in all sets. "Users who follow A and B." Cost: O(N*M) worst case, N = size of the smallest set, M = number of sets. Redis starts from the smallest set, which is why intersecting one tiny set against a huge one stays cheap.
  • SUNION / SUNIONSTORE — union: members in any set. O(N) over the total members of all sets.
  • SDIFF / SDIFFSTORE — difference: members in the first set but none of the rest. "In cart X but not cart Y." O(N) over the total members.

And the one people miss: SINTERCARD (Redis 7.0) gives you the size of an intersection without building it, and takes a LIMIT so you can stop counting early — "do at least 100 users follow both?" returns as soon as it hits 100 rather than computing the full intersection.Before 7.0 the only way to get an intersection count was SINTERSTORE into a temp key then SCARD then clean up — three commands, a throwaway allocation, and no early exit. SINTERCARD … LIMIT collapses all of that.

Algebra is single-threaded too SINTER over two million-member sets is millions of hash lookups on the one thread. The …STORE variants are the safer production move for big results: they keep the payload server-side instead of serialising it back to the client, and the destination set is then yours to SSCAN at leisure. For a pure count, SINTERCARD … LIMIT beats them both.

Random members and moves

Two niche-but-useful tools. SRANDMEMBER reads a random member without removing it (great for sampling); SPOP removes and returns one — together they make a set a decent "draw without replacement" bag (think raffle, work-stealing, random assignment). Both are O(1) bare, O(N) with a count. SMOVE atomically relocates a member from one set to another — useful for state machines modelled as sets ("move this id from pending to done" in one indivisible step, courtesy of the single thread).

When a set is the wrong tool Sets are unordered — no ranking, no range queries, no "top N." The moment you need a score or an order, that's a sorted set (next lesson). And for counting unique things at massive scale, where storing every member would cost gigabytes, a set is the wrong economics — a HyperLogLog (L09) approximates the cardinality in ~12 KB. A real set is exact but pays per member.

That last line is a teaser: a small set of short strings is stored as a listpack, not a hash table — Redis swaps to a real hash table as it grows. A set of only-integers uses an even tighter intset. Encodings are Lesson 16; just notice the seam is there.

Check yourself

Commit to an answer before reading the explanation — the retrieval is the point.

Q1. You must check "is this user already a follower?" millions of times a second before deciding whether to add them.
The follower collection has hundreds of thousands of ids and changes constantly. You want the cheapest correct check.
A. Membership is exactly what a set is for: SISMEMBER is O(1) no matter how large the set gets, and SADD dedups for free. B and C are both linear scans of a list (the access pattern lists are worst at — recall L05). D works but explodes your keyspace into one key per follower with no atomic "add if absent" — the set does it in one command.
Q2. You want to know whether at least 100 users follow both creator A and creator B, where each set holds millions of ids.
You only need a yes/no-ish threshold answer, not the actual list of shared followers, and you want minimal work on the single thread.
C. SINTERCARD key1 key2 LIMIT 100 (Redis 7.0) counts the intersection and stops the moment it reaches 100 — it never builds the full result. A computes the whole intersection, allocates a temp set, and needs cleanup. B drags two million-member sets to the client. D builds and serialises the entire intersection just to count it. All three do far more work than the threshold question requires.
Q3. A teammate runs SMEMBERS active_sessions on a 4-million-member set and every other Redis call across the app freezes for a beat.
Fast GETs and SISMEMBERs from unrelated clients all hang until that one command returns.
A. This is the L01 lesson wearing a set costume: SMEMBERS is O(N), and one slow command monopolises the single execution thread, so everyone queues behind it. The fix is SSCAN (cursor-based, O(1) per call) — or, more often, realising you didn't need every member, just an SISMEMBER or SCARD. B, C, and D describe mechanisms that aren't what happened.

Where this goes next

You can now model uniqueness and relationships, and run intersect/union/difference where the data lives. Add one thing to a set — a score per member, keeping the collection ordered — and you get the most powerful structure Redis offers: the sorted set. Leaderboards, priority queues, sliding-window rate limiters, secondary indexes, range queries — five killer patterns, all on one type. It's the crown jewel; we give it weight.
