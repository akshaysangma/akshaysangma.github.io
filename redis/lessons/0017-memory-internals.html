Memory — Where the Bytes Go

Your values are not your memory bill. Each top-level key drags a fixed tax of headers and pointers — which is the deep reason the small encodings from last lesson are worth chasing.

Phase 4 · Internals ~10 min Hands-on Builds on: object encodings
Recall first Last lesson: a small hash, set, or zset rides in a listpack — one flat blob — until it crosses a configured threshold, then it converts (one-way) to a full hash table or skiplist. Hold that thought. Today you learn why that flat blob is so much cheaper than the alternative — and the alternative is a million separate keys.

The value is the cheap part

Picture a million keys like user:42:visits, each holding a tiny integer. Naïvely that's a few megabytes — a million integers. In reality it can cost ten times that. The integers are almost free; what you actually pay for is the machinery that lets Redis find each key in O(1).

Every top-level key in the keyspace carries four costs, only the last of which is "your data":

Anatomy of one top-level key (64-bit build, jemalloc — approximate, version- and arch-dependent)
Component~BytesWhat it is
dict entry~24Three pointers (key, value, next) in the keyspace hash table, plus a slot in the bucket array
key string (SDS)len + ~3–9The key name itself, with an SDS header and a trailing null; jemalloc then rounds up
redisObject~16The value header: type, encoding, an LRU/LFU field, a refcount, and a pointer to the payload
the valuevariesYour actual data. A small shared integer adds nothing (see below)

So a key holding the integer 100 costs not ~2 bytes but roughly 50–70 bytes once you add the dict entry, the key-name SDS, and the 16-byte redisObject header.The exact figure shifts with key-name length, the build's word size, the jemalloc version, and which size class the allocation rounds into. Treat every byte count here as a ballpark, not a constant — the shape of the cost is what matters. Multiply by a million and the headers, not the integers, are your memory bill.

The redisObject header Every value is wrapped in a redisObject — the same struct that carried type and encoding in lesson 16. It also holds a 24-bit lru field (idle-time tracking for eviction, lesson 18) and a 32-bit refcount. On a 64-bit build that struct is ~16 bytes, paid per value — so per top-level key.

Two ways Redis dodges the tax

Shared integers. Redis pre-allocates one immutable redisObject for every integer from 0 to 9999 at startup. A key whose value is a small integer doesn't get its own object — it points at the shared one. You can see this directly: a shared integer reports a refcount of 2147483647 (INT_MAX), the sentinel meaning "shared, owned by no one."Caveat: maxmemory policies that need per-object LRU/LFU bookkeeping (allkeys-lru, -lfu, etc.) disable integer sharing, because a shared object can't carry per-key idle stats. Lesson 18.

Pack many fields into one key. This is the punchline of lesson 16, now explained. A hash of 20 small fields in listpack encoding is one dict entry, one key SDS, one redisObject — the 20 field/value pairs live inside a single flat blob. Store those same 20 as separate top-level strings and you pay the full per-key tax twenty times over. Aggregates-in-one-key win on memory precisely because they amortise the header cost.

"A million tiny keys" is the classic blowup The most common memory surprise in production isn't big values — it's many small top-level keys. session:<id>, flag:<user>, counter:<thing> sprawled across the keyspace each pay ~50–70 bytes of overhead before their value. Group them — into a hash per user, a bitmap, a small zset — and the overhead collapses to one header per group.

The keyspace is two dicts

Each logical database is really two hash tables. The keyspace dict maps key → value for every key. A separate expires dict maps key → expiry timestamp, and holds an entry only for keys that have a TTL.This is why setting a TTL costs a little extra memory: a second dict entry in the expires table. It's also the structure lesson 18 builds the whole expiration cycle on. A key with no TTL appears in the first dict only. So "give every key an expiry" is not free — it populates the second dict too.

jemalloc, size classes, and fragmentation

Redis doesn't hand raw byte counts to the kernel; it asks an allocator. The default is jemalloc, bundled with Redis. jemalloc serves memory in fixed size classes (8, 16, 32, 48, 64, … bytes). Ask for 20 bytes and you get a 32-byte slot; the 12 wasted bytes are internal fragmentation — real RAM you paid for and can't use. This rounding is exactly why byte counts here are approximate: the allocator, not your data, picks the final size.

Two INFO numbers make this visible:

  • used_memory — the total Redis thinks it allocated (logical bytes, what the allocator reports back).
  • used_memory_rss — the resident set size the OS actually mapped to physical RAM, including allocator slack, page-level fragmentation, and stack/buffers.

Their ratio is mem_fragmentation_ratio = used_memory_rss / used_memory, and it reads two ways:

Reading mem_fragmentation_ratio
ValueMeaning
> 1 (e.g. 1.3)External fragmentation — the OS holds more RAM than Redis logically uses. A little is normal; a lot wastes memory.
≈ 1Healthy — resident memory tracks logical memory closely.
< 1 (e.g. 0.7)Bad. RSS is below logical memory — the kernel has swapped part of the dataset to disk. Latency death for an in-memory store.
A ratio under 1 is the alarm, not over 1 Beginners chase a high ratio. The genuinely dangerous case is the low one: < 1 means pages have been swapped out to disk, and an in-memory database serving from swap is catastrophically slow. On a near-empty instance the ratio also looks alarmingly high (RSS is dominated by fixed baseline allocations) — so judge it on a warm, loaded instance, not a fresh one.

For genuine external fragmentation that won't settle, Redis has active defragmentation (activedefrag yes, plus an active-defrag-* threshold family). It leans on jemalloc to relocate allocations and compact resident memory live, without a restart — spending a little CPU to claw back RAM.Active defrag only works with the bundled jemalloc; it's a no-op against libc malloc. Check mem_allocator in INFO memory to see which you're running.

Inspecting it: MEMORY and INFO

Four tools, in rough order of zoom:

  • MEMORY USAGE key — bytes for one key including its overhead (samples large aggregates, so O(N) in the sample count — pass SAMPLES to tune).
  • MEMORY DOCTOR — a plain-English health verdict on the whole instance.
  • MEMORY STATS — a detailed breakdown (overhead, dataset bytes, per-allocator stats, fragmentation).
  • INFO memory — the top-line section: used_memory, used_memory_rss, the fragmentation ratio, the allocator.
Run this — watch the overhead, and watch a shared integer 
> SET counter 100
OK
> OBJECT ENCODING counter      # stored as an int, not a string of digits
"int"
> MEMORY USAGE counter         # ~56 bytes for a ~2-byte value — that's the tax
(integer) 56
> OBJECT REFCOUNT counter      # INT_MAX → this value is a SHARED integer (0–9999)
(integer) 2147483647
> SET big 100000               # 100000 > 9999, so NOT shared
OK
> OBJECT REFCOUNT big           # refcount 1 → its own private redisObject
(integer) 1
Now compare twenty separate keys against one hash holding the same twenty fields: 
> MSET f0 v f1 v f2 v f3 v f4 v   # 5 top-level string keys
OK
> MEMORY USAGE f0
(integer) 56                     # ×5 keys ≈ 280 bytes, five full headers
> HSET profile f0 v f1 v f2 v f3 v f4 v   # same data, one key
(integer) 5
> OBJECT ENCODING profile
"listpack"
> MEMORY USAGE profile         # one header, fields packed flat — far less
(integer) 120
Your numbers will differ — encoding thresholds, key-name lengths, and jemalloc rounding all move them — but the direction is the lesson: one packed key beats many tiny ones.

Check yourself

Commit to an answer before you read the explanation — that's the retrieval that makes it stick.

Q1. You store 1,000,000 keys like user:42:visits, each a small integer, and used_memory dwarfs a million integers. Where did the extra memory go?
The values are tiny, yet the instance is using tens of megabytes for the keyspace.
C. Every top-level key pays a roughly fixed tax — a dict entry (~24 bytes), the key-name SDS, and a ~16-byte redisObject — that swamps a 2-byte integer. (A: keys without a TTL aren't in the expires dict at all, and integers aren't duplicated there. B: Redis doesn't pre-reserve per-value growth room. D: jemalloc rounds to the smallest fitting size class, not the largest.) This is exactly why packing into aggregates pays off.
Q2. INFO memory shows mem_fragmentation_ratio at 0.7 on a busy, loaded host. What's the most likely diagnosis?
B. A ratio below 1 means RSS is smaller than logical memory — the OS has paged part of the dataset to disk. For an in-memory store that's a latency emergency, not a tidiness win. (A causes the opposite: internal fragmentation pushes RSS above logical, ratio > 1. C and D would lower RSS toward logical, i.e. toward 1, never below it.) The dangerous direction is down, not up.
Q3. You can store each user's 20 small fields as 20 top-level string keys or as one hash. Which uses less memory, and why?
A. A small hash stays in listpack encoding — one dict entry, one key SDS, one redisObject, with all 20 pairs packed flat inside it — so it pays the per-key tax once instead of twenty times (interleaving lesson 16's encodings). (C names the right winner but the wrong reason: it's listpack packing, not hashtable sharing — a hashtable-encoded hash carries more overhead. B and D are real facts that don't make 20 keys cheaper.)
