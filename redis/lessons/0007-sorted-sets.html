Sorted Sets — The Crown Jewel

A set whose members carry a score, kept in score order at all times. It is two indexes in one structure — and it is the answer to more interview-grade problems than any other Redis type.

Phase 2 · Data Structures ~12 min Hands-on Builds on: Sets (L06)
Recall first Before we add ordering: a plain set gives you O(1) membership and server-side algebra (SINTER/SUNION), but it has no order — ask it for "the top 10" or "everyone between rank 50 and 60" and it can't answer. Hold that gap; the sorted set fills it exactly.

The reframe: a set with a second axis

A sorted set (zset) is a collection of unique members — same uniqueness guarantee as a set — where each member also carries a floating-point score. Redis keeps the members ordered by score at all times, and ties are broken lexicographically by member. That ordering is not recomputed on read; it is maintained on every write.

The mental model that unlocks everything: a zset is two indexes over the same members, kept in sync for free.

  • A hash from member → score, so ZSCORE is O(1).
  • A skiplist ordered by (score, member), so rank and range queries are O(log N).The skiplist is a probabilistic, layered linked list that gives balanced-tree behaviour without the rebalancing bookkeeping. It also tracks the span of each forward pointer, which is the trick that makes ZRANK O(log N) instead of O(N). Internals — encodings and when this becomes a compact listpack instead — are Lesson 16.

Because both indexes exist, you can ask two different kinds of question on the same data — "what is X's score / rank?" and "give me everyone in this score or rank window" — and both are cheap. That dual nature is the whole reason this type owns so many problems.

Writing: ZADD and its flags

ZADD is the workhorse. Base form ZADD key score member [score member ...] is O(log N) per member added. The flags are where the power is, and they compose:

ZADD update flags (all available in Redis 7.x; GT/LT arrived in 6.2)
FlagEffect
NXOnly add new members; never update an existing score.
XXOnly update existing members; never add new ones.
GTUpdate only if the new score is greater than the current one.
LTUpdate only if the new score is less than the current one.
CHReturn the count of changed members, not just newly added ones.
INCRBehave like ZINCRBY: increment the score and return the new value.

GT is the leaderboard flag: ZADD lb GT 120 bob records a high score only if it beats the existing one, with no read-then-write race — the single thread makes it atomic (recall Lesson 01). NX/XX are mutually exclusive, and so are GT/LT/NX. To bump a score, prefer ZINCRBY key delta member (O(log N)) — it reads cleaner than ZADD … INCR.

Scores are doubles, not integers A score is an IEEE-754 double. That buys you about 253 of exactly-representable integer precision — fine for timestamps in milliseconds, dangerous for 64-bit IDs used as scores. Beyond 253 consecutive integers stop being distinct. Special values +inf and -inf are valid scores and are genuinely useful as range sentinels.

Reading: scores, ranks, and ranges

Three families of read, by cost:

The reads you will reach for most, with Redis 7.x time complexity
CommandAnswersBig-O
ZSCORE / ZMSCOREscore of one / several membersO(1) / O(N) members
ZRANK / ZREVRANK0-based position, low→high / high→lowO(log N)
ZCARDmember countO(1)
ZCOUNThow many in a score rangeO(log N)
ZRANGE (by rank)a slice of the orderingO(log N + M) returned
ZRANGE … BYSCOREeveryone in a score windowO(log N + M) returned
ZRANGE … BYLEXeveryone in a lexical windowO(log N + M) returned

Notice the shape O(log N + M): a binary-search-like seek to the start of the window, then a linear walk over the M elements you actually return. The cost scales with the size of your answer, not the set — provided you bound M. Forget to bound it and a range over a huge zset becomes the same single-threaded stall as a giant SMEMBERS (Lesson 01). Use LIMIT offset count.

One ZRANGE to rule them all (6.2+)

Historically you used a different command per axis: ZRANGE, ZREVRANGE, ZRANGEBYSCORE, ZREVRANGEBYSCORE, ZRANGEBYLEX, ZREVRANGEBYLEX. Redis 6.2 unified them into one ZRANGE with modifiers — this is the modern idiom and what you should write on 7.x:

# ZRANGE key start stop [BYSCORE | BYLEX] [REV] [LIMIT offset count] [WITHSCORES]
ZRANGE lb 0 9 REV WITHSCORES              # top 10 by rank, high→low
ZRANGE lb 100 +inf BYSCORE               # everyone scoring >= 100
ZRANGE lb (50 100 BYSCORE LIMIT 0 20     # 50<score<=100, first 20; ( = exclusive
ZRANGE lb [a [n BYLEX                     # members from "a" to "n", equal scores only

The old six commands still work and aren't deprecated, but new code should prefer the unified form. Note BYSCORE and BYLEX use interval syntax: ( for exclusive, [ for inclusive lexical bounds, and -/+ as the lexical min/max sentinels. To store a range into a new key instead of returning it, use ZRANGESTORE (also 6.2, O(log N + M)).

BYLEX only means anything when all scores are equal Lexicographic ordering assumes every member shares one identical score (the zset then sorts purely by member). If scores differ, BYLEX results are unspecified — Redis won't error, it will just hand you nonsense. Use BYLEX deliberately, on a zset where you set every score to 0 precisely so the structure becomes a sorted index of strings (autocomplete, dictionaries).

The five problems sorted sets own

When you reach for a zset on instinct, it is almost always one of these. Learn the mapping; it is the most leveraged pattern recognition in Redis.

The zset's home turf — score = the thing you order by
ProblemScore is…Key reads
Leaderboardsthe points / ratingZADD GT, ZREVRANK, ZRANGE REV
Priority queuesthe priorityZADD, ZPOPMIN / BZPOPMIN
Rate limitingthe event timestampZREMRANGEBYSCORE, ZCARD
Time series / schedulinga timestamp / run-atZRANGE BYSCORE
Secondary indexesa numeric attributeZRANGE BYSCORE / BYLEX

Two are worth a sentence of mechanism. A priority queue is just ZPOPMIN (O(log N), atomically pops and returns the lowest-score member) — or the blocking BZPOPMIN when you want a worker to wait for work. A sliding-window rate limiter stores one zset per subject with score = timestamp: on each request, ZREMRANGEBYSCORE key -inf (now-window) evicts events that aged out, then ZCARD tells you how many remain in the window. Same idea powers a delayed-job scheduler: score = run-at-time, and a poller does ZRANGE … BYSCORE -inf now to find what's due. You'll assemble these end-to-end in Lesson 14.

Removing, popping, and combining

Removal mirrors the read axes: ZREM (O(M·log N) for M members), and the bulk ZREMRANGEBYRANK / ZREMRANGEBYSCORE / ZREMRANGEBYLEX (each O(log N + M)) for trimming a window — capping a leaderboard to its top 1000, or pruning an old time-series tail. ZPOPMIN / ZPOPMAX pop and return the extreme (O(log N · M) for M popped).

And the set algebra carries over, weighted by score — ZUNIONSTORE, ZINTERSTORE, ZDIFFSTORE (and the non-storing ZUNION/ZINTER/ZDIFF, added 6.2, plus ZINTERCARD, added 7.0). These combine sorted sets and aggregate the scores of shared members (AGGREGATE SUM|MIN|MAX, default SUM) with optional per-set WEIGHTS. Their cost is real — these are the O(N) commands of this type:

Aggregation cost (verbatim from redis.io, Redis 7.x)
CommandTime complexity
ZUNIONSTOREO(N) + O(M·log(M)), N = sum of input sizes, M = result size
ZINTERSTOREO(N·K) + O(M·log(M)) worst case, N = smallest input, K = number of inputs
ZDIFFSTOREO(L + (N−K)·log(N)), L = total elements, N = first set, K = result size

Iterate a large zset without blocking with ZSCAN (cursor-based, O(1) amortized per call) — the same SCAN discipline you learned for the keyspace.

Run this — build a leaderboard and query it three ways In redis-cli, type these and read each reply against what you just learned: 
> ZADD game:lb 100 alice 80 bob 95 carol

6) "95"
> ZRANGE game:lb 0 2 REV WITHSCORES # identical result, unified 6.2 form
1) "alice"
2) "125"
3) "bob"
4) "120"
5) "carol"
6) "95"
> ZREVRANK game:lb carol            # carol's 0-based rank from the top
(integer) 2

1) "bob"
2) "120"
3) "alice"
4) "125"
You just used both indexes: ZREVRANK walked the skiplist for a position in O(log N); ZRANGE … BYSCORE seeked to score 100 and walked the window. Same members, two questions, both cheap.

Check yourself

Commit to an answer before you read the explanation — retrieval is what makes it stick.

Q1. You must show one player's position on a 10-million-entry leaderboard, fast. The data could live in a plain set — but which command answers this, and why is it cheap?
A plain set knows membership but not order, so it cannot answer "what rank is this player?" at all.
B. ZREVRANK returns the 0-based position from the top in O(log N), because each skiplist forward pointer stores the span it skips — rank is a sum of spans along the search path, no scan needed. (A returns the score, not the position; C would be O(N) and would stall the single thread on 10M members — Lesson 01; D returns the total count, not a position. And a plain set, recall Lesson 06, can't do any of this — no order.)
Q2. You're building a 60-second sliding-window rate limiter: one sorted set per user, each request added with score = its timestamp. Before counting requests in the window, which step prunes the events that have aged out?
Goal: count only requests whose timestamp falls within the last 60 seconds, then compare against the limit.
A. Scores are timestamps, so "too old" is a score condition: ZREMRANGEBYSCORE key -inf (now-60s) evicts exactly the aged-out events in O(log N + M), then ZCARD counts what remains. (B prunes by rank, which doesn't map to a time boundary; C removes just one entry, so old events pile up; D is lexical — meaningless when scores differ, per the BYLEX trap.)
Q3. You stored autocomplete terms in a sorted set, each with a different score, then ZRANGE … BYLEX returns members in an order that looks scrambled. What went wrong?
A. Lexical ordering is only defined when all scores are equal — then the skiplist's tiebreak (member name) becomes the sole order, and BYLEX walks it correctly. With differing scores the primary order is by score, so a lexical range is unspecified. Fix: set every score to 0 and use the zset as a pure sorted string index. (B is the opposite of the requirement; C describes BYSCORE; D — encoding, Lesson 16 — has no effect on correctness.)
