Keys & the Keyspace

One flat namespace, millions of keys, and a single thread serving them. This lesson is about moving through that keyspace — and expiring keys — without ever freezing it.

Phase 1 · Foundations ~10 min Hands-on Builds on: single thread → KEYS * is dangerous
Recall first Before reading on: from Lesson 1, why does one careless O(N) command — say KEYS * over a huge keyspace — stall every other client? Say it out loud, then watch this lesson turn that one fact into a working habit.

One global, flat keyspace

Every key you have ever set lives in one namespace. There are no tables, no folders, no schema — just a single dictionary mapping a key to its typed value.Internally it's a hash table (the "main dict"). A second dict, the expires dict, tracks only the keys that have a TTL. We'll open both up in Phase 4. A SET from your cache code and a ZADD from a leaderboard land in the same flat space, side by side.

Keys are binary-safe strings. A key can be the text user:42, an empty string, or a JPEG's raw bytes — Redis only compares bytes, it never interprets them. That freedom is why convention matters: nothing stops you naming keys u42, User-42, and users/42 in the same instance, and then no human can guess what exists.

The colon convention The community standard is object-type:id:field, segments joined by colons: user:42:session, cart:99:items, leaderboard:2026-06. It is purely a naming discipline — Redis attaches no meaning to the colon — but it makes the flat space legible and gives SCAN patterns something predictable to match against.

Inspecting the keyspace, one command at a time

A handful of commands answer "what's in here?" — and all the safe ones are O(1), which is exactly why they're safe on the single thread.

Keyspace commands and their cost (Redis 7.x).
CommandDoesBig-O
EXISTS k [k …]How many of these keys exist (counts duplicates)O(N) in number of keys
TYPE kThe value's type at kO(1)
RENAME k newkRename, overwriting newk if presentO(1)
RANDOMKEYOne random key nameO(1)
DBSIZETotal key count in this DBO(1)
DEL k [k …]Delete keys, freeing memory nowO(N) keys (+O(M) elems)
UNLINK k [k …]Unlink keys, free memory in backgroundO(1) per key
KEYS patternEvery matching key, in one shotO(N) — danger
SCAN cursor …One page of keys per callO(1) per call

DEL and UNLINK both remove keys; the difference is who pays for freeing the memory. DEL frees it inline — so deleting one key holding ten million elements blocks the single thread while it walks and frees every element. UNLINK removes the key from the keyspace immediately (so it's instantly invisible) and hands the actual deallocation to a background thread. On a big aggregate, reach for UNLINK.UNLINK arrived in Redis 4.0 alongside the lazy-free background threads. The command thread is still single; only the freeing is offloaded.

The KEYS trap — recall Lesson 1 KEYS * is O(N) over the entire keyspace and returns all matches in a single reply. On a production instance with millions of keys it monopolises the one thread — every GET, INCR, and health check waits in line behind it. It reads like a harmless debugging command; it's an outage. Treat KEYS as a REPL-on-an-empty-dev-box tool only. In any code, the answer is SCAN.

SCAN: walk millions of keys without blocking

SCAN replaces the one giant O(N) sweep with many tiny O(1) steps. You call it in a loop, passing a cursor: it returns a batch of keys plus the next cursor. You keep going until the returned cursor is 0 again — that marks a completed full iteration.

# the loop shape, by hand:
> SCAN 0 MATCH user:* COUNT 100
1) "12288"            # next cursor — NOT a count, an opaque token
2) 1) "user:42"
   2) "user:7"
> SCAN 12288 MATCH user:* COUNT 100
1) "0"               # cursor back to 0 → iteration complete
2) 1) "user:99"

The cursor is opaque — it encodes a position in the hash table, not "the 12,288th key." You never compute it; you only echo back what the last call gave you. Three properties make SCAN trustworthy and set its caveats:

  • Full-iteration guarantee. Any key present for the whole scan will be returned at least once. Nothing that stayed put gets skipped.
  • Duplicates are possible. A key may come back more than once across calls — your code must tolerate that (e.g. dedupe, or treat the work as idempotent).
  • Churn is undefined. Keys added or removed during the iteration may or may not appear. SCAN is a live view, not a snapshot.

Three modifiers shape each call:

  • MATCH pattern — glob-filter the results. Crucial point: filtering happens after a bucket is fetched, so a call can legitimately return zero keys with a non-zero cursor. An empty batch is not the end — only cursor 0 is.
  • COUNT n — a hint for how much work to do per call (default 10), not a limit on results. Bigger COUNT = fewer round-trips but more work per step (longer single-thread stall per call). It's the dial you trade latency against throughput on.
  • TYPE t — return only keys of a given type, e.g. TYPE zset The TYPE option was added in Redis 6.0. Like MATCH, it filters after fetching, so it doesn't make a scan cheaper — it just saves you a client-side TYPE check.
Same pattern, three structures SCAN iterates the keyspace; its siblings HSCAN (hash fields), SSCAN (set members) and ZSCAN (sorted-set members) apply the identical cursor protocol inside one big key. Learn the loop once, reuse it everywhere you'd otherwise reach for an O(N) bulk read. (We'll use them in Phase 2.)

Expiration: setting, reading, and clearing TTLs

You already know TTL as "the key disappears later." Here's the full toolset. All of these are O(1) — setting an expiry is just a write into the expires dict.

Expiration commands (all O(1)).
CommandMeaning
EXPIRE k secs / PEXPIRE k msExpire after a relative duration
EXPIREAT k ts / PEXPIREAT k ms-tsExpire at an absolute Unix time
TTL k / PTTL kRemaining life, in secs / ms
PERSIST kRemove the TTL — make k persistent

TTL has three telling return values: a positive number (seconds left), -1 (the key exists but has no expiry), and -2 (the key doesn't exist at all). That -1 vs -2 distinction is the quickest way to tell "persistent" from "already gone."

As of Redis 7.0, the EXPIRE family takes conditional flags: NX (set only if no TTL yet), XX (only if one exists), GT (only if the new expiry is greater than the current), and LT (only if less). GT/LT let you extend-but-never-shorten a session TTL without a read-then-write race.

Plain SET wipes the TTL Overwriting a key with a bare SET key newval discards any existing TTL — the key becomes persistent. This silently breaks "refresh the value, keep the countdown" logic. The fixes, all on SET itself: add KEEPTTL to retain the current TTL (Redis 6.0+), or set a fresh one inline with EX/PX (relative) or EXAT/PXAT (absolute). The flags NX (only if absent) and XX (only if present) gate the write, and GET returns the old value in the same atomic step (Redis 6.2+). One round trip, no race — recall why that single-thread atomicity is free.
Run this — scan, expire, and watch a TTL die Seed a chunk of keys, scan them safely, then drive one key's TTL to zero: 
> MSET user:1 a user:2 b user:3 c order:1 x
OK
> SCAN 0 MATCH user:* COUNT 100   # safe enumeration, not KEYS
1) "0"
2) 1) "user:1"
   2) "user:2"
   3) "user:3"
> SET user:1 a EX 100             # value + a 100s TTL, atomically
OK
> TTL user:1
(integer) 100
> SET user:1 a2                   # plain SET — the trap →
OK
> TTL user:1                      # TTL gone, key now persistent
(integer) -1
> SET user:1 a3 EX 5 KEEPTTL      # note: cannot combine EX with KEEPTTL
(error) ERR syntax error
> SET user:1 a3 EX 5              # pick one: fresh 5s TTL
OK
> PTTL user:1                     # millisecond precision
(integer) 4994
> UNLINK user:1 user:2 user:3     # async delete; safe even if huge
(integer) 3
The ERR syntax error is the point: KEEPTTL means "leave the old TTL" and EX means "set a new one" — they contradict, so Redis rejects the pair. Use one or the other.

The 16 logical databases — and why prefixes won

One Redis process exposes 16 numbered databases by default (0–15, tunable via the databases config). SELECT 0..15 switches your connection's current DB; each is an independent keyspace, so user:42 in DB 0 and DB 3 are unrelated keys.

It looks like free namespacing — but it's largely discouraged for application use. They share the one process and one thread, so they buy you no isolation that matters; there's no per-DB access control or memory accounting; client libraries juggle the per-connection SELECT state awkwardly; and critically, Redis Cluster supports only DB 0. The idiomatic answer is a key prefix (tenant:42:user:7) in a single DB — it survives a move to Cluster, scans cleanly with MATCH, and keeps everything visible. Numbered DBs are handy for a quick test-vs-scratch split in redis-cli; reach past that and you'll regret it.SWAPDB and FLUSHDB act per-database; FLUSHALL wipes every DB. MOVE shifts a key between DBs. All niche next to "just use a prefix."

Commit to an answer before you read the explanation — the retrieval is the point.

Q1. A teammate needs every key matching session:* from a live instance holding ~20 million keys. What should they do?
The instance is serving production traffic right now; latency budgets are tight.
B. SCAN spreads the work across many O(1) calls, so the single thread is never monopolised. (A is the classic outage — KEYS is one O(N) sweep that freezes every other client, exactly Lesson 1's trap. C inspects a different, empty DB and counts nothing useful. D is unbounded, returns duplicates, and never terminates reliably.)
Q2. You must delete one key holding a 10-million-field hash on a busy instance, without stalling other clients. Which command fits?
B. UNLINK removes the key from the keyspace at O(1) and offloads freeing all 10M fields to a background thread, so the command thread stays free. (A frees inline — that O(M) walk blocks everyone, the very thing to avoid. C still frees the memory synchronously when the expiry fires, so it only delays the same stall. D renames in O(1) but you still have to delete tmp, solving nothing.)
Q3. A key has a 30-second TTL. You need to overwrite its value but keep the original countdown running. What works?
B. KEEPTTL (Redis 6.0+) is the one option that overwrites the value while leaving the existing expiry in place. (A is the trap — a bare SET discards the TTL and makes the key persistent. C, like a plain write, also clears the TTL. D actively removes the TTL with PERSIST first, the opposite of the goal.)
