Strings, and the Numbers Hiding in Them

The string is the type you already know — and the one you most underuse. It's a binary-safe byte array, an atomic counter, and a bit-addressable buffer, all behind SET.

Phase 1 · Foundations ~10 min Hands-on Builds on: keys & typed values
Recall first Lesson 2: a key with no TTL never expires on its own, and setting a value then its TTL in two steps leaves a window where the key has no expiry. Which single command writes a value and its TTL atomically? Hold that answer — strings are where it lives, and we lean on it again at the end.

A string is a byte array, not text

Forget "string = text." A Redis string is an opaque, binary-safe sequence of bytes — it can hold UTF-8, a JPEG, a serialized protobuf, a counter, or a packed bitfield. Redis neither inspects nor transforms it. The only hard limit is size: a single string value maxes out at 512 MB.Binary-safe means embedded NUL bytes and arbitrary binary are fine — the length is stored, not inferred from a terminator. The same property held for keys in lesson 2; values share it.

That one type quietly does three jobs: a blob you read and write whole, a buffer you slice and patch in place, and a number you mutate atomically. The rest of this lesson is those three faces.

Face one — the blob: fewer round trips

You know SET / GET (both O(1)). The upgrade is doing more per network hop. Each command is a round trip to the server; batching them is the single easiest latency win you have.

  • MSET k1 v1 k2 v2 … / MGET k1 k2 … — set or get many keys in one call, O(N) in the number of keys. One round trip instead of N.
  • APPEND key val — append to (or create) a string, returns the new length, O(1) amortized.
  • STRLEN key — byte length, O(1) (it's stored, not counted).
  • GETDEL key — get the value and delete the key in one atomic step, O(1) (since 6.2).
  • GETEX key … — get the value and adjust its TTL (EX/PX/EXAT/PERSIST) in one step, O(1) (since 6.2).

Want the old value back when you overwrite? The classic command is GETSET (O(1)), but it's deprecated as of 6.2 in favour of SET key val GET — the GET option returns the previous value while honouring the other flags (EX, KEEPTTL, etc.). Reach for SET … GET on Redis 7.

Face two — the buffer: slice and patch in place

Because a string is a byte array with a known length, Redis can read or overwrite a sub-range without shipping the whole value:

  • GETRANGE key start end — return the byte slice (negative indices count from the end), O(N) where N is the length of the returned substring, not the whole value.
  • SETRANGE key offset val — overwrite bytes starting at offset, zero-padding if the string is shorter. O(1) amortized for small writes; O(M) where M is the length of the value argument when the copy is large.

This is the same byte-addressing idea that bit operations (SETBIT, GETBIT, BITCOUNT, BITFIELD) take down to individual bits — those count millions of flags in kilobytes and get their own treatment in lesson 09. Today, just register that a string is addressable.

Face three — the number: atomic counters

Here's the face people miss. If a string looks like a base-10 integer, Redis will do arithmetic on it server-side, atomically:

  • INCR key / DECR key — ±1, returns the new value, O(1).
  • INCRBY key n / DECRBY key n — ±n (integer), O(1).
  • INCRBYFLOAT key x — add a float (no DECRBYFLOAT — pass a negative), O(1).

Why this matters: the obvious DIY counter is GET, add one in your app, SET back. Under concurrency that's a lost-update race — two clients read 41, both write 42, one increment vanishes. INCR has no such window. Recall lesson 1: the single thread runs one command to completion before the next starts, so INCR is atomic for free — read, add, store, all indivisible. No lock, no transaction, no race.

The trap INCR only works on a value that parses as a 64-bit base-10 integer. INCR on "hello", on "3.14", or past ±2^63 returns (error) ERR value is not an integer or out of range. And INCRBYFLOAT does not make a key float-typed — there is no float type. The value is still a string; it just currently holds digits.

That a counter is "still a string" is more than pedantry. Internally Redis stores an integer-looking string in a compact int encoding — the bytes "100" aren't kept as three characters but as a machine integer — which is why counters are cheap. You'll inspect this directly with OBJECT ENCODING in lesson 16; for now just note the teaser when it shows up in the transcript below.

Strings as lock primitives

Two narrow-purpose string commands exist mainly as building blocks: SETNX key val (set only if the key does not exist, O(1)) and SETEX key sec val (set with a TTL, O(1)). Both are deprecated as of 2.6.12 — the modern, composable form is SET with flags: SET key val NX, SET key val EX 30, or both at once.

Combine them and you have the skeleton of a lock: SET lock token NX EX 30 claims the key only if it's free and attaches a 30-second TTL in the same atomic command — answering the recall question that opened this lesson. That single-command atomicity is exactly why it's a viable lock; we build the full (and surprisingly subtle) distributed lock on top of it in lesson 13.

Check yourself

Commit to an answer before reading the explanation — the retrieval is the point.

Q1. Two workers bump the same page-view counter at once, each doing GET, add one in app code, then SET back. Counts drift low under load. Best fix?
Both workers read 41 in the same instant, both compute 42, both write 42 — one increment is silently lost.
B. INCR does read-add-store as one indivisible command; the single thread (lesson 1) can't interleave another client between the read and the write, so no update is lost — and it's O(1). A client mutex only coordinates one app's threads, not other clients or hosts; a random delay narrows the race window without closing it; a replica is read-only and adds staleness. The whole point of server-side atomic counters is to delete this race entirely.
Q2. On Redis 7 you must overwrite a key and get its previous value back in a single atomic step — a feature-flag swap that returns the old flag. Which approach?
B. SET key val GET (since 6.2) returns the prior value while writing the new one, atomically — the modern replacement for the deprecated GETSET. A is two round trips and not atomic (a writer can slip in between). C is two commands, loses atomicity, and drops any TTL. D appends rather than overwrites, so the value would become old-plus-new, not replaced.
Q3. You must claim a lock key only when it is currently absent, and have it auto-release after thirty seconds even if the holder crashes. Best command?
A. SET lock token NX EX 30 tests-and-sets and attaches the TTL in one atomic command. The two-step options (B, C, D) all share the same flaw from lesson 2: if the process dies between the set and the EXPIRE, you're left with a lock that has no TTL — so it never auto-expires, and the lock is stuck forever. (D also can't express "only if absent.") Folding both into one command closes that window — the foundation we build distributed locks on in lesson 13.
