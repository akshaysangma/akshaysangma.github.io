Transactions — MULTI, EXEC, WATCH

Redis transactions are not SQL transactions. They give you a no-interleave batch and an optimistic compare-and-set — and pointedly not rollback. Knowing the difference is the whole lesson.

Phase 3 · Patterns & Atomicity ~10 min Hands-on Builds on: single-thread atomicity (L01)
Recall first Last lesson, the fix for a cache stampede was a per-key mutex built from one atomic command — SET key val NX. That worked because a single command can't be interrupted. Hold that thought: today is about making several commands behave as one uninterrupted unit.

What a Redis transaction actually is

A single command is atomic for free — that's the single thread from Lesson 1. But real logic often needs several commands to land as a unit: debit one key, credit another, with no other client wedging in between. That's what MULTI/EXEC buys you.

The model is small and worth memorising exactly:

  • MULTI opens a transaction. From here, commands you send are not executed — they're queued, and each reply is just QUEUED.
  • EXEC runs the whole queue in order, with no other client interleaving, and returns an array of every command's reply.
  • DISCARD throws the queue away and ends the transaction without running anything.

The guarantee is serialised execution: once EXEC starts, the single thread runs your queued block start-to-finish before serving anyone else. No GET from another client slips between your two commands.This is the same single thread from Lesson 1 doing the work. A transaction doesn't add locking — it just hands the thread a batch instead of one command. That is the only isolation Redis offers; there are no isolation levels in the SQL sense, no read/write phases, no SELECT … FOR UPDATE.

The shape of every transaction MULTI → queue commands (each replies QUEUED) → EXEC (runs the batch) — or DISCARD to bail. Add WATCH before MULTI when the transaction's correctness depends on a value you read first.

The headline: there is no rollback

This is where SQL intuition betrays you. If a command fails while the transaction is running, Redis does not undo the commands that already ran. There is no rollback. The other queued commands execute regardless, and the error sits in the reply array at its position.

You have to split "failure" into two cases that behave completely differently:

Two kinds of error — and only one aborts the transaction
Failure happens at…ExampleWhat Redis does
Queue time (before EXEC)Unknown command, wrong arity — the command can't even be queuedTransaction is flagged; EXEC refuses with EXECABORT and nothing runs
Run time (during EXEC)Right syntax, wrong type — e.g. LPOP on a string keyThat command errors in the result array; all other commands still apply

So a command that queues successfully but turns out to be wrong at execution (the classic WRONGTYPE) leaves every command before and after it applied. A command that's malformed enough to be rejected at queue time poisons the whole transaction, and EXEC runs none of it.Why no rollback? antirez's argument: runtime errors are almost always programming bugs (wrong key, wrong type) that shouldn't reach production, and supporting rollback would cost the simplicity and speed that define Redis. The queue-time abort was added in 2.6.5 to catch the obvious mistakes cheaply.

The trap "Transaction" does not mean "all-or-nothing." A WRONGTYPE in the middle of your EXEC does not roll back the debit you already did. If you need real all-or-nothing logic with branching, that's a Lua script or a Redis Function (next lesson) — those run as one indivisible call where you control the flow. MULTI/EXEC is a no-interleave batch, nothing more.

WATCH — optimistic locking for check-then-set

The batch alone can't express "read a value, then decide what to write based on it" — because the queued commands don't execute until EXEC, so you can't read inside the transaction and branch on the result. The race is the classic check-then-set: you GET a balance, decide to debit, but another client changes it before you write.

WATCH solves this with optimistic concurrency — compare-and-set (CAS), not a lock. You WATCH the keys you read, build your MULTI/EXEC based on what you saw, and Redis makes a promise: if any watched key is touched by anyone between your WATCH and your EXEC, the EXEC aborts and returns a null reply instead of running. You detect the nil and retry.

  • WATCH must come before MULTI (watching inside a transaction is an error).
  • "Touched" means modified by any client — overwritten, deleted, or expired — even if set to the same value. It is key-level, not value-level.
  • EXEC, DISCARD, and UNWATCH all clear your watches. After EXEC (abort or not) you're watching nothing.
  • It's optimistic: no one is blocked, no lock is held. Under low contention it's nearly free; under high contention you retry more.
The CAS retry loop The canonical pattern: WATCH key → read it → MULTI → queue the update computed from what you read → EXEC. If EXEC returns nil, someone moved the key under you — loop and try again from the WATCH.

See it: WATCH catching a race

This needs two redis-cli windows so you can interleave them by hand. Client A starts a watched transaction; Client B sneaks in a write before A's EXEC.

Run this — two terminals, watch EXEC return nil Client A — set up, watch, and start queuing: 
A> SET balance 100
OK
A> WATCH balance         # CAS guard armed on this key
OK
A> MULTI
OK
A> DECRBY balance 30      # queued, not yet run
QUEUED
Now, before A runs EXEC, Client B touches the same key: 
B> INCRBY balance 50      # another client mutates balance
(integer) 150
Back in Client A, fire the transaction: 
A> EXEC
(nil)                     # aborted — balance was touched since WATCH
A> GET balance
"150"                   # A's DECRBY never ran; B's write stands
The (nil) is the signal. A's job now is to loop: WATCH again, re-read the fresh 150, and rebuild the transaction. Had B not touched balance, EXEC would have returned 1) (integer) 70 and committed.

See it: no rollback vs. queue-time abort

One terminal is enough for these two. First, a runtime error in the middle — note both neighbours still apply:

Run this — a WRONGTYPE mid-transaction does not roll back 
> SET foo bar            # foo holds a string
OK
> MULTI
OK
> INCR counter           # valid → queued
QUEUED
> LPOP foo               # valid syntax, wrong type → still queued!
QUEUED
> INCR counter           # valid → queued
QUEUED
> EXEC
1) (integer) 1           # ran
2) (error) WRONGTYPE Operation against a key holding the wrong kind of value
3) (integer) 2           # ran anyway — no rollback
> GET counter
"2"                     # both INCRs applied
The wrong-type command queued fine (Redis only checks types at run time), failed at position 2, and the command after it still executed. counter is 2, not 1.
Run this — a queue-time error aborts the whole batch 
> MULTI
OK
> INCR counter
QUEUED
> NOTACMD foo            # unknown command → rejected here, tx poisoned
(error) ERR unknown command 'NOTACMD', with args beginning with: 'foo'
> SET k v
QUEUED
> EXEC
(error) EXECABORT Transaction discarded because of previous errors.
> GET counter
"2"                     # unchanged — nothing in this tx ran
Because one command failed at queue time, EXEC refuses outright: zero commands run, counter stays 2. This is the one case that is all-or-nothing — and it's about catching malformed commands, not about undoing successful ones.

The five commands, and their cost

The transaction surface — all management ops are O(1)
CommandDoesBig-O
MULTIOpen a transaction; start queuingO(1)
EXECRun the queued block, no interleavingO(1) + the queued commands' cost
DISCARDDrop the queue; end without runningO(1)
WATCH key […]Arm CAS on these keysO(1) per key
UNWATCHForget all watched keysO(1)

The management commands are trivially cheap; the cost of an EXEC is just the sum of the commands you queued — and that sum runs uninterrupted on the one thread, so the Lesson 1 rule still bites: a giant O(N) command inside a transaction blocks every other client for its full duration, now with no chance for them to slip in.

Q1. Inside an EXEC, the second of three queued commands fails with WRONGTYPE. What is the final state?
The three commands were all accepted as QUEUED earlier; only the middle one turns out to mismatch its key's type at run time.
B. Redis has no rollback. A runtime error (the command queued fine, then mismatched at execution) errors only at its own position; the commands before and after it still apply. (A imports SQL intuition Redis doesn't have; C invents an early-halt that doesn't exist; D is the queue-time EXECABORT/WATCH-nil behaviour, not a runtime error.)
Q2. You WATCH a key, read it, MULTI, queue an update — and another client writes that key before your EXEC. What does EXEC do?
A. WATCH is optimistic CAS: a touched watched key makes EXEC abort and return nil, running nothing — your cue to retry from the WATCH. (B ignores the guard entirely; C describes a pessimistic lock, which WATCH is explicitly not; D invents a merge Redis never does.)
Q3. While EXEC runs your queued commands, can another client's GET slip in between two of them?
A busy server has dozens of clients issuing fast reads while your transaction's EXEC is mid-flight.
A. This is just Lesson 1: the one thread serves one thing at a time, and EXEC hands it the whole block — so it runs start-to-finish with no other command, read or write, interleaved. (B and C imagine concurrency Redis doesn't have; D misreads WATCH — it's optimistic CAS, it holds no lock and isn't even required for the no-interleave guarantee.)
