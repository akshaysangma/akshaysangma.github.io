Lists — Queues, Stacks, and Their Sharp Edges

A Redis list is an ordered sequence you push and pop from either end in O(1). That one fact makes it a great queue and a great stack — and a terrible array.

Phase 2 · Data Structures ~10 min Hands-on Builds on: hashes (L04)
Recall first Before lists: a HGETALL on a hash with a million fields is O(N) — and on Redis's one thread, that stalls every other client. Hold that single-thread reflex; lists have their own O(N) traps, in different places.

The shape: a list is a deque

A Redis list is an ordered collection of strings, kept in insertion order. You add to the head (left) or the tail (right), and you remove from either end. Both ends are O(1) — that's the whole point. Think of it as a double-ended queue (a deque), not a numbered array.Internally it's a quicklist: a linked list of listpack nodes. That structure is exactly why the ends are cheap and the middle is not — encodings get their own treatment in L16.

The four primitives:

  • LPUSH key v [v …] / RPUSH key v [v …] — prepend / append. O(1) per element (so O(N) for N values in one call). Creates the list if the key is absent.
  • LPOP key [count] / RPOP key [count] — remove and return from the head / tail. O(1) for a single element; O(N) for N when you pass count (added in 6.2).

From those two pairs you already have both classic structures. A queue (FIFO) is push one end, pop the other: RPUSH to enqueue, LPOP to dequeue. A stack (LIFO) is push and pop the same end: LPUSH then LPOP. Same data type, two disciplines.

Reading the names Every list command is prefixed L (for list), and the side is Left (head) or Right (tail). LPUSH = push left, RPOP = pop right. Once that clicks, the whole command family reads itself.

Inspecting and slicing

You'll reach for these constantly:

  • LLEN key — length. O(1); Redis tracks it.
  • LRANGE key start stop — return a slice; indices are 0-based and negatives count from the tail (-1 is last). O(S+N), where S is the distance of the start offset from the nearest end (head or tail) and N the number of elements returned — so tail-relative ranges like LRANGE key -100 -1 are cheap. LRANGE key 0 -1 dumps the whole list — handy, and O(N), so the same caution as HGETALL applies.
  • LTRIM key start stop — keep only that range, discard the rest. O(M) where M is the number of elements removed. This is how you build a capped list (next section).
  • LPOS key element — find the index of a matching element (with optional RANK/COUNT). O(N). Added in 6.0.6.

The sharp edge: the middle is O(N)

Here is the one thing experts internalise about Redis lists. Random access by index is not cheap. A list is a linked structure, not a contiguous array, so reaching element i means walking i nodes:

  • LINDEX key i — get the element at index i. O(N) (it's O(1) only for the head or tail).
  • LSET key i v — set the element at index i. O(N) (again O(1) at the ends).
  • LINSERT key BEFORE|AFTER pivot v — insert next to the first matching value. O(N) to find the pivot.
  • LREM key count element — remove matching elements. O(N+M) (scan the list, remove M matches).
Lists are not arrays If your access pattern is "give me item 500,000," a list is the wrong structure — every LINDEX/LSET walks the chain on the single thread. Lists are for the ends. When you need indexed or ordered-by-key access, reach for a sorted set (L07) or a hash (L04) instead. Use a list when you only ever touch the head and tail.

Moving and blocking: real queues

Polling a queue with LPOP in a tight loop wastes CPU and round-trips. Lists give you blocking pops that sleep until work arrives:

  • BLPOP key [key …] timeout / BRPOP … — pop from the first non-empty list, or block up to timeout seconds (0 = forever). O(N) in the number of keys you pass; the wait itself is free. This is the heart of a worker pulling jobs.
  • LMOVE src dst LEFT|RIGHT LEFT|RIGHT — atomically pop from one list and push to another, picking the side at each end. O(1). Added in 6.2, it supersedes the older RPOPLPUSH.
  • BLMOVE … — the blocking version of LMOVE (6.2). The building block of a reliable queue: move a job into an in-progress list so a crash doesn't lose it.
  • LMPOP numkeys key [key …] LEFT|RIGHT [COUNT n] and BLMPOP … — pop from the first non-empty of several lists, with an optional count. O(N+M) (N keys, M elements). Both added in 7.0.

Because pops are atomic and the server is single-threaded, two workers both running BLPOP jobs 0 can never receive the same element — Redis hands each waiting client a different one. That's a real work queue with no locking on your side.But plain BLPOP is at-most-once: if a worker crashes after popping and before finishing, the job is gone. The BLMOVE-into-processing-list pattern fixes that, and Streams (L08) make acknowledgement and replay first-class. We'll build both in L14.

Capped lists: a bounded log

A common job is "keep the last N of something" — recent events, a chat backlog, the latest activity. Push, then trim:

# keep only the 100 most recent entries after each push
RPUSH events "user:42 login"
LTRIM events -100 -1

The LTRIM key -100 -1 keeps the last 100 elements and drops the rest in O(M). Run it after each RPUSH and the list self-bounds — memory stays flat no matter how long the firehose runs. For a true append-only event log with IDs and ranges, Streams (L08) are the grown-up tool; a capped list is the quick, cheap version.

Run this — a queue, a stack, and a cap in one session In redis-cli, watch insertion order, both disciplines, and the O(N) edge: 
> RPUSH q job1 job2 job3   # enqueue at the tail →
(integer) 3
> LPOP q                   # dequeue at the head: FIFO →
"job1"
> LRANGE q 0 -1            # what's left, in order →
1) "job2"
2) "job3"
> LPUSH s a b c            # a stack: push left…
(integer) 3
> LPOP s                   # …pop left: LIFO, newest first →
"c"
> LINDEX q 1               # random access — works, but O(N) →
"job3"
> RPUSH log e1 e2 e3 e4 e5
(integer) 5
> LTRIM log -3 -1          # cap to the last 3 →
OK
> LRANGE log 0 -1
1) "e3"
2) "e4"
3) "e5"
Then open a second redis-cli and run BLPOP q 0; back in the first, RPUSH q job9 and watch the blocked client wake instantly with the job.

Check yourself

Don't peek — commit to an answer first. Retrieval is what makes this stick.

Q1. You need a FIFO job queue: producers add work, one worker takes the oldest job next. Which pairing gives you that?
Order must be preserved — the first job added is the first job processed.
C. FIFO means push one end and pop the other: append with RPUSH, take the oldest with LPOP. A pops then dequeues newest-first (that's a stack). B pops the most recent too (also LIFO). D doesn't remove anything and both calls are O(N) — wrong tool entirely.
Q2. A service stores a 2-million-element list and reads the middle with LINDEX list 1000000 on every request. Latency spikes across all clients. Why?
Unrelated GETs and INCRs slow down at exactly the same time.
B. A list is a linked structure, so LINDEX to a middle index is O(N) — Redis walks ~1M nodes, monopolising the single thread while every other client waits (recall L01). A: Redis serves from RAM, not disk. C: there's no read throttle at maxmemory. D: nothing dropped the connections. Indexed access wants a sorted set or hash.
Q3. You want a list that keeps only the 50 most recent log lines, no matter how many you push over a day. What runs after each push?
A. LTRIM key -50 -1 keeps the last 50 elements and discards everything else, bounding memory — the capped-list idiom. B only reads a slice; it changes nothing. C removes by matching value and count, not by position. D removes the 50 oldest from the head, the opposite of what you want.
