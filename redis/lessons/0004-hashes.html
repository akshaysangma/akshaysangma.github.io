Hashes — Objects Without a Key Explosion

A hash is a key whose value is itself a little map of field → value. It's how you put a whole object behind one key, and mutate one field of it atomically without touching the rest.

Phase 2 · Data Structures ~10 min Hands-on Builds on: Strings (L03)
Recall first Before new material: in Lesson 03 you used INCR / INCRBY on a string to get an atomic counter for free. Why was no lock needed? Hold that answer — hashes give you the same atomic mutation, but on one field inside an object.

The problem hashes solve

You want to store a user object — name, email, logins. With only strings (Lesson 03) you'd reach for one key per attribute:

# the key-explosion approach — three top-level keys per user
> SET user:1000:name "Ada"
> SET user:1000:email "ada@x.io"
> SET user:1000:logins 0

That works, but it scatters one logical object across three entries in the global keyspace. You can't fetch the whole object in one round trip, you can't delete it atomically, and each top-level key carries its own overhead (the cost story is Phase 4 — Lesson 17). A hash collapses all of that into a single key:

The one idea A hash is a value that is a map of field → value — both binary-safe strings. One key, many fields. It's the natural home for an object whose fields you read and update individually.

The core verbs

Every hash command is prefixed H and takes the key first, then operates on fields within it. Set fields, read them back one or many, and mutate in place:

> HSET user:1000 name "Ada" email "ada@x.io" logins 0
(integer) 3           # 3 new fields added
> HGET user:1000 email
"ada@x.io"
> HMGET user:1000 name logins missing
1) "Ada"
2) "0"
3) (nil)          # absent field → nil, not an error
> HEXISTS user:1000 email
(integer) 1
> HLEN user:1000
(integer) 3

HSET is variadic — set many fields in one call — and it replaced the now-deprecated HMSET.HMSET still exists for compatibility but has been deprecated since Redis 4.0; reach for HSET. HSETNX sets a single field only if it doesn't already exist — the per-field cousin of SETNX from Lesson 03. HDEL removes fields (and drops the key entirely when the last field goes); HKEYS, HVALS, and HGETALL return all fields, all values, or both.

Atomic field counters

Here's where a hash earns its place over a JSON blob. HINCRBY and HINCRBYFLOAT increment a single field in place — atomically, for the same single-threaded reason INCR was atomic in Lesson 03. No read-modify-write, no race:

> HINCRBY user:1000 logins 1
(integer) 1
> HINCRBY user:1000 logins 1
(integer) 2
> HINCRBYFLOAT user:1000 balance 9.99
"9.99"

Compare that to storing the user as a serialized JSON string: to bump logins you'd GET the whole blob, parse it, increment, re-serialize, and SET it back — five steps, a parse cost, and a lost-update race between two clients doing it at once. The hash does it in one atomic server-side op, and leaves the other fields untouched.

Run this — mutate one field, leave the rest alone 
> HSET game:42 player "ada" score 0 level 1
(integer) 3
> HINCRBY game:42 score 250        # atomic, single field
(integer) 250
> HINCRBY game:42 level 1
(integer) 2
> HGETALL game:42                  # player untouched →
1) "player"
2) "ada"
3) "score"
4) "250"
5) "level"
6) "2"
Note HGETALL's shape: a flat list, alternating field then value. RESP3-aware clients render this as a map instead.

The Big-O — and the one trap

Most hash operations are O(1): you address a field by name through an internal hash table, so cost doesn't grow with how many fields the hash holds. The commands that touch every field are the exceptions — and on a large hash they're exactly the Lesson 01 single-thread hazard.

Hash command complexity (Redis 7.x). N = number of fields involved.

HGETALL on a big hash freezes the server HGETALL is O(N) over the entire hash. On a hash with millions of fields it monopolises the single thread serializing every field — the same incident shape as SMEMBERS / KEYS * from Lesson 01. For large hashes, iterate with HSCAN (cursor-based, like SCAN for keys) or fetch named fields with HMGET. Keep hashes that you HGETALL bounded in size.

HSCAN takes a cursor and returns a slice per call, so it never blocks the server for long — and HSCAN ... NOVALUES (Redis 7.4) returns just the field names when you don't need the values:

> HSCAN user:1000 0 COUNT 100
1) "0"                # next cursor; 0 = iteration complete
2) 1) "name"
   2) "Ada"
   3) "email"
   4) "ada@x.io"
   5) "logins"
   6) "2"

When a hash wins — and when it doesn't

Reach for a hash to group the fields of one object under one key, when you want atomic per-field updates, and to save memory — a small hash is stored in a compact encoding (the listpack story is Lesson 16) that's far cheaper than the equivalent pile of top-level string keys.

The historical case against hashes was TTL: a hash has one expiry for the whole key, so for years you could not expire an individual field — that pushed people back to separate string keys when each attribute needed its own lifetime. That changed:

New in Redis 7.4 — per-field TTL HEXPIRE / HPEXPIRE / HEXPIREAT set a TTL on individual fields; HTTL / HPTTL read it and HPERSIST removes it. All are O(N) in the number of fields named, and arrived in Redis 7.4.0 — before that, field-level expiry simply did not exist. 
> HSET session:abc uid 1000 csrf "x9f2"
(integer) 2
> HEXPIRE session:abc 30 FIELDS 1 csrf   # expire just the csrf field
1) (integer) 1                          # 1 = TTL was set
> HTTL session:abc FIELDS 1 csrf
1) (integer) 30
> HTTL session:abc FIELDS 1 uid
1) (integer) -1                         # -1 = field exists, no TTL

The syntax is deliberate: FIELDS numfields field [field ...], and the optional NX/XX/GT/LT conditions mirror the key-level EXPIRE guards from Lesson 02. Returns are per-field: 1 set, 0 condition unmet, 2 field deleted (TTL in the past), -2 no such field.

So today the honest answer is: prefer a hash for an object; only fall back to separate keys when you're on a Redis older than 7.4 and genuinely need per-field expiry — or when the fields aren't really one object at all.

Check yourself

Don't peek — commit to an answer first. Retrieval is what makes this stick.

Q1. You're storing user profiles — name, email, and a login counter you bump often. Which modeling choice fits best?
Reads are usually one or two fields; the counter is incremented on every successful login by concurrent requests.
A. A hash groups the object under one key and gives HINCRBY an atomic, race-free counter for the login field. (B is the key-explosion this lesson replaces; C forces a get-parse-set race on every counter bump; D abuses a sorted set — scores are numbers for ranking, not a field map.)
Q2. A hash holds two million fields, and a client runs HGETALL on it. What happens to the rest of the server?
A. HGETALL is O(N) over the whole hash, and command execution is single-threaded (Lesson 01) — every other client waits while that one call serializes two million fields. (B: the dataset is in RAM, not paged; C: command execution is never offloaded; D: HGETALL never truncates — use HSCAN for that.)
Q3. You need individual fields of one hash to expire at different times. Which statement is correct?
A. Per-field expiry arrived with HEXPIRE & friends in Redis 7.4.0. (D was true before 7.4 — one TTL per key — and is the misconception to drop; C was the old workaround you no longer need on 7.4+; B is false — EXPIRE only ever targeted whole keys, not hash fields.)
