Caching Patterns and How They Fail

You started this course caching with GET/SET/TTL. Now build a cache that survives a traffic spike and doesn't serve dangerous stale data — and learn the three named ways caches melt under load.

Phase 3 · Patterns & Atomicity ~10 min Hands-on Builds on: TTL (L02) + the datatype toolkit
Recall first Last lesson: a Bloom filter answers "have I definitely never seen this?" in a few bits per item, with false positives but no false negatives. Hold that shape — it walks back on stage when we hit cache penetration below.

Caching is the one Redis use you already trust. The trouble is that the naive version — read the cache, on a miss read the database and write it back — is correct right up until it's under load. Then it fails in three specific, named ways. Experts know all three by name and reach for the right fix on reflex. That's today's win.

Two questions, four patterns

Every caching strategy is an answer to two questions: who fills the cache, and who writes through to the database. Four classic patterns fall out.

The four caching patterns. "App-managed" means your application code does it explicitly; "inline" means a caching layer in front of the store does it for you.
PatternRead pathWrite pathTrade-off
Cache-aside
(lazy loading)		App checks cache; on miss, app reads DB and populates cacheApp writes DB, then invalidates the cache keySimple, resilient, only caches what's read. Cold-start misses; risk of stale on races.
Read-throughApp reads cache only; cache loads from DB on miss(paired with a write policy below)Cleaner app code, but needs a caching library/layer — Redis alone isn't read-through.
Write-through(as above)App writes cache; cache writes DB synchronouslyCache and DB stay consistent; every write pays both latencies.
Write-behind
(write-back)		(as above)App writes cache; cache flushes to DB asynchronouslyFast writes, batched DB load; data-loss window if Redis dies before flush.

Cache-aside is the default, and it's what people mean when they say "we cache in Redis." Redis is a plain data store: it doesn't know your database exists, so read-through / write-through / write-behind are properties of a caching layer you put in front of the DB, not of Redis itself. Reach for them only when a library already gives them to you.Write-behind is seductive — sub-millisecond writes! — but it makes Redis the source of truth for un-flushed writes. In an in-memory store that's a durability bet. Phase 5 (persistence) is where you learn whether you can afford it.

Invalidate, don't update On a write, prefer to delete the cache key rather than overwrite it with the new value. Two concurrent writers that both set the cache can interleave and leave the older value resident — a classic stale-cache race. A DEL just forces the next reader to repopulate from the source of truth. (Single-key DEL is O(1); UNLINK frees the memory off-thread — recall the L01 single-thread cost.)

TTL is the staleness dial

A cache without invalidation is wrong; a cache with only explicit invalidation is fragile (miss one write path and you serve stale forever). So real systems use both: delete-on-write for correctness, and a TTL as a safety net that bounds how long any miss can stay stale. The TTL is a dial — shorter means fresher data but more recomputes and DB load; longer means cheaper but staler. Pick it from how stale the data is allowed to be, not from a round number.

One subtlety that becomes a failure mode below: if a batch job warms 100,000 keys in a loop with the same EX 3600, all 100,000 expire in the same second. Spread them. Compute the TTL in your app as base + random(0..spread) — Redis has no built-in jitter, so you pass a slightly different number on each SET. That one line of jitter is the entire fix for avalanche.

The three ways a cache melts

Under load, a naive cache-aside setup fails in exactly three named ways. They're often confused; the distinctions are the whole point.

1 · Stampede (thundering herd / dogpile)

One hot key expires. In the gap before anyone repopulates it, a flood of concurrent requests all miss at once and all stampede the database to recompute the same value. The cache was doing its job; a single expiry briefly removed it and the backend took the full unbuffered load. Mitigations, roughly in order of reach:

  • Per-key recompute mutex. The first miss claims a lock with SET lock NX; only the lock-holder recomputes, everyone else briefly serves stale or waits and re-reads. This is today's hands-on.
  • Probabilistic early recompute (XFetch). Before the key expires, each reader recomputes with a small, rising probability — so one lucky request refreshes it ahead of expiry and the herd never forms. Vattani et al. tune this by recompute cost and a beta knob (see the source box).
  • Request coalescing / single-flight. In-process: dedupe concurrent identical misses so only one in-flight fetch hits the backend per process. Pairs well with the mutex for cross-process coverage.

2 · Penetration

Requests ask for keys that don't exist in the database either — so the cache can never hold them, every request misses, and every miss hits the DB. Often malicious: an attacker loops over random non-existent IDs to route every request straight past your cache. Two real fixes:

  • Cache the negative. When the DB returns "not found," store a small sentinel (e.g. an empty marker) under that key with a short TTL. Subsequent lookups for that bogus ID hit Redis, not the DB. Keep the TTL short so a key that later does get created isn't masked for long.
  • Bloom filter in front. Keep a Bloom filter of IDs that genuinely exist (your L09 recall). If it says "definitely not present," skip the DB entirely; its no-false-negatives guarantee makes that safe. (Native Bloom commands — BF.ADD/BF.EXISTS — live in the RedisBloom module, which is outside core Redis.)

3 · Avalanche

A large set of keys expires simultaneously (the lock-step-TTL batch above), or the cache node itself drops out — and a wall of misses hits the DB at the same instant. Note the contrast: stampede is one hot key; avalanche is many keys at once. Fixes:

  • Jitter the TTLs so expiries scatter across time instead of firing together. This is the headline fix for the expiry-driven case.
  • For the node-loss case, the cache layer can't save you alone — that's HA (Sentinel/Cluster, Phase 5) plus a backend circuit breaker / rate limit so a cold cache can't take the database down with it.
Don't confuse the three Stampede = one popular key, momentarily missing → fix with a recompute mutex or early refresh. Penetration = keys that exist nowhere → fix with negative caching or a Bloom filter. Avalanche = many keys expiring together → fix with TTL jitter. Apply the wrong fix (jitter won't help penetration; negative caching won't help a stampede on a real key) and the incident continues while you congratulate yourself.

Hands-on — SET NX as a recompute mutex

The stampede fix you'll reach for most is a per-key lock built on one atomic command. SET key val NX EX ttl sets the key only if it doesn't exist and attaches a TTL in a single, O(1) operation. The single thread (L01) makes the "check then set" indivisible — no two clients can both see "absent" and both win.

Run this — claim, lose, rebuild, release Two clients race to rebuild a missing cache entry. Open one redis-cli, then a second in another terminal to feel the loser's path. 
> GET article:42                          # cache miss
(nil)
> SET lock:article:42 worker-1 NX EX 5    # try to claim the rebuild
OK                                       # we won → we recompute

# --- in a SECOND client, while the lock is held: ---
> SET lock:article:42 worker-2 NX EX 5    # someone already holds it
(nil)                                    # lost → serve stale or wait + re-GET

# --- back in client 1: write the fresh value, then free the lock ---
> SET article:42 "<rendered html>" EX 3677  # 3600 base + jitter
OK
> DEL lock:article:42
(integer) 1
The winner is the only one that touched the database; the loser served stale or retried a few ms later and got the fresh value cheaply. One recompute instead of a thousand.
Why SET ... NX EX and not SETNX + EXPIRE Two separate commands can be interrupted between them — a crash after SETNX but before EXPIRE leaves a lock with no TTL, i.e. a deadlock that never clears. The combined SET ... NX EX sets the value and the expiry as one atomic command. Always set the lock and its TTL together.

This is a simplified mutex, not a correct distributed lock. Releasing with a bare DEL is unsafe: if your work outran the 5-second TTL, the lock may already belong to another worker, and your DEL frees theirs. The fixes — a unique token plus a Lua compare-and-delete, and the whole Redlock debate — are Lesson 13. For taming a cache stampede on a single instance, the pattern above is enough.

Check yourself

Commit to an answer before reading the explanation — the retrieval is what makes it stick.

Q1. A single very popular cache key expires and thousands of in-flight requests all miss it in the same moment and slam the database.
The database CPU spikes for one second on every expiry of this one key, then settles until it expires again.
B. This is a stampede on one hot key: gate the recompute with a per-key SET NX mutex so a single request rebuilds while the rest serve stale or wait. (A only delays the next stampede; C spreads reads but every replica still misses and the writes still hit one DB; D makes stampedes more frequent.)
Q2. An attacker loops over random user IDs that exist in neither the cache nor the database, so every request misses the cache and queries the DB directly.
Cache hit rate collapses; the database sees a request for every bogus ID because nothing is ever cacheable.
A. This is cache penetration — the keys exist nowhere, so a real value can never populate them. Cache the negative result (a short-TTL sentinel), or front the DB with a Bloom filter of real IDs. The distractors are the right fixes for the other two failure modes: B cures avalanche, C cures a stampede on a real key.
Q3. Two workers both miss the same key at the same instant and both run SET lock token NX EX 5. Exactly one gets OK and the other gets (nil).
Interleave check: nothing outside Redis coordinates the two clients, yet only one ever wins the lock.
A. The L01 guarantee at work: the single thread runs each SET … NX to completion before the next, so the check-and-set is indivisible — one command sees "absent" and wins, the next sees "present" and gets nil. No internal slot lock (C) or external coordinator (D) is involved; B describes what the loser does after, not why it lost.
