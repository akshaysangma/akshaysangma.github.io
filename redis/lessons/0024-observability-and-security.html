Why these two topics share a lesson

Everything before this taught you what Redis does. This lesson is about the instance as a running system you are responsible for — the two questions every operator answers at 3 a.m.: "what is it doing right now?" (observability) and "who can reach it?" (security). They share a lesson because they share a mindset: a Redis you can't see into and a Redis anyone can connect to are the same failure — an instance out of your control.

The whole single-thread mental model from Lesson 1 pays off here. Observability on Redis is overwhelmingly about one thread's time: who is monopolising it, and for how long.

1 · Reading a live instance — INFO and the six numbers

INFO is the firehose: a single command that dumps server state as field:value lines, grouped into sections. Ask for just the section you need — INFO memory, INFO stats, INFO replication, INFO persistence, INFO clients — instead of paging through all of it.INFO is O(1) — it reports counters Redis already maintains, so it's safe to poll. Most monitoring agents (Datadog, Prometheus' redis_exporter) just scrape INFO on an interval.

You could memorise a hundred fields, or you could learn the six that actually move during an incident. These are the ones I'd put on a dashboard:

The six numbers worth watching — and what a bad reading means.

blocked_clientsclientsHigh → clients parked on BLPOP/WAIT/XREAD BLOCK; benign for queues, suspicious otherwise.
used_memory vs used_memory_rssmemoryRSS ≫ used → fragmentation (recall L17 mem_fragmentation_ratio); RSS < used → swapping, very bad.

instantaneous_ops_per_secstatsSudden spike or cliff → traffic change or the instance is stalled on one slow command.

Hit ratio isn't a field — you compute it: hits / (hits + misses). A healthy read cache sits well above 0.9; a number drifting down is your earliest warning that something upstream changed.

2 · Finding the slow command — SLOWLOG, LATENCY, the doctors

When ops/sec drops and everything feels frozen, the cause is almost always a single slow command holding the thread (Lesson 1, made operational). Redis keeps a built-in record of exactly these.

The slow log records commands whose execution time exceeded a threshold — slowlog-log-slower-than, in microseconds (default 10000 = 10 ms; set to 0 to log everything, -1 to disable). It excludes network and I/O time, so it isolates the part you control: time on the thread. SLOWLOG GET returns recent entries (id, timestamp, microseconds, the command + args, client addr); SLOWLOG RESET clears it.The slow log lives in memory, capped by slowlog-max-len (default 128 entries). It's a ring buffer — old entries fall off. SLOWLOG GET is O(N) over the entries returned; SLOWLOG LEN is O(1).

For latency that isn't a single command — fork pauses during BGSAVE, slow disk on AOF fsync, transparent-hugepage stalls — use the latency monitor. Enable it with CONFIG SET latency-monitor-threshold 100 (ms; 0 disables). Then LATENCY LATEST shows recent spike events by category, LATENCY HISTORY <event> the time series, and LATENCY DOCTOR reads it all and writes you a plain-English diagnosis with likely causes. Its sibling MEMORY DOCTOR does the same for memory — fragmentation, big allocations, peak-vs-current.

MONITOR is not a tracing tool MONITOR streams every command the server processes — irresistible for debugging "is my app even sending that?" But it has a real, measured throughput cost: the server must format and ship every command to the monitoring client, and a busy instance can lose 50%+ of its throughput while a MONITOR is attached. It's a debug-only peek. Run it, read a few lines, Ctrl-C. Never leave it running in production, never point it at a hot instance "just to watch," and never wire it into a script loop.

3 · Profiling the keyspace from redis-cli

redis-cli ships several built-in audits that wrap the primitives above into one command — your first move when you inherit an unfamiliar instance:

  • redis-cli --latency — samples PING round-trips continuously, printing min/max/avg ms. Quick gut-check on whether the instance (or the network to it) is healthy. Variants: --latency-history, --latency-dist.
  • redis-cli --bigkeys — SCANs the whole keyspace and reports the biggest key of each type. Safe-ish (it's SCAN-based, not KEYS), and the fastest way to find the one giant hash behind your latency. --memkeys does the same but ranks by memory (via MEMORY USAGE) rather than element count.
  • redis-cli --hotkeys — finds the most-accessed keys. Requires an LFU eviction policy (allkeys-lfu or volatile-lfu), because it reads the per-key LFU access counter (recall L18); on an LRU/noeviction instance it has nothing to read.

And CLIENT LIST enumerates every connected client — addr, age, idle time, last command, the cmd they're running. Pair it with CLIENT KILL to evict a misbehaving connection, or CLIENT NO-EVICT to protect a connection from being dropped under maxmemory-clients pressure. This is how you find the one client running MONITOR or a runaway KEYS *.

4 · Security — the part people skip until it's a headline

Here is the story that should set your defaults. For years, the single most common Redis compromise was breathtakingly simple: an instance bound to a public IP with no password. Redis spoke its plain protocol to anyone who connected — so attackers connected, used CONFIG SET to point persistence at ~/.ssh/authorized_keys or a cron path, wrote their own key in, and owned the box. Tens of thousands of instances were mass-compromised and turned into cryptominers this way. It wasn't a Redis bug. It was Redis doing exactly what it was told, by someone who shouldn't have been able to tell it anything.

That history is why modern defaults exist and why the rules below aren't optional:

The hardening checklist, roughly in order of importance.
ControlWhat it does / how
Network isolationThe real fix. Never expose Redis to the internet. Put it on a private network / security group; let only your app reach it.
protected-modeOn by default. If no bind and no password are set, Redis refuses connections from non-loopback addresses. A safety net, not a strategy.
bindRestrict which interfaces Redis listens on (e.g. bind 127.0.0.1 10.0.0.5). Don't bind 0.0.0.0 on a public host.
requirepassA password for the default user. The bare minimum auth; clients send AUTH. Use a long random secret — it's brute-forceable over a fast loopback.
ACLs (6.0+)Real user accounts with fine-grained rules. The modern answer — see below.
TLS (6.0+)Encrypt client/replica/cluster traffic. Built in since 6.0 (previously needed a proxy like stunnel). Configure certs via tls-* directives.
rename-commandLegacy hardening: rename/disable dangerous commands in config. Superseded by ACLs but still seen in the wild.

ACLs — users instead of one shared password

Since 6.0, Redis has a real access-control list. Instead of one global password, you define users, each with rules over three things: which commands they may run, which keys they may touch, and which Pub/Sub channels they may use. The built-in default user is what requirepass configures; you can lock it down and add scoped users per service.

You build a user with ACL SETUSER, composing rules: on/off (enabled?), >password (add a password), ~pattern (key access, e.g. ~cache:*), &pattern (channel access), and command grants like +@read, -@dangerous, +get, -flushall. Categories (@read, @write, @admin, @dangerous, @all) let you grant or revoke whole classes at once. ACL WHOAMI tells you who you're authenticated as; ACL LIST / ACL GETUSER show the rules; ACL CAT lists the categories. Persist them in the config or a dedicated aclfile.

The "disable the footguns" move Some commands are dangerous in the wrong hands: FLUSHALL/FLUSHDB (wipe data), KEYS (the O(N) thread-freeze from L1), CONFIG (the attack vector in the story above), DEBUG. The modern way to neuter them is per-user ACLs — ACL SETUSER app on >secret ~app:* +@all -@dangerous -flushall -keys -config. The legacy way is rename-command KEYS "" (rename to empty string = disable) in config. Prefer ACLs: they're scoped per user and don't break tooling that runs as an admin user.

Hands-on — see your own instance, then mint a scoped user

Run this — the slow log, your identity, and a least-privilege user In redis-cli, generate a slow command, read it back, then create an ACL user that can't do the dangerous things: 
> CONFIG SET slowlog-log-slower-than 0   # log every command (demo only!)
OK
> DEBUG SLEEP 0.05                       # force a 50ms command
OK
> SLOWLOG GET 1                          # newest entry first
1) 1) (integer) 7                       # entry id
   2) (integer) 1719583200             # unix time
   3) (integer) 50012                  # microseconds on the thread (~50ms)
   4) 1) "DEBUG"                        # the command + args
      2) "SLEEP"
      3) "0.05"
   5) "127.0.0.1:6379"                  # client addr
   6) ""                               # client name
> CONFIG SET slowlog-log-slower-than 10000  # restore 10ms default
OK

> ACL WHOAMI                          # who am I right now?
default
> ACL SETUSER reporter on >s3cret ~stats:* +@read -@dangerous
OK
> ACL GETUSER reporter                # inspect the rules you just set
1) "flags"
2) 1) "on"
...
"commands": "-@all +@read -@dangerous"
"keys": "~stats:*"
> AUTH reporter s3cret                # become the scoped user
OK
> GET stats:hits                      # allowed: read on stats:*
(nil)
> FLUSHALL                            # denied: not in +@read, and -@dangerous
(error) NOPERM User reporter has no permissions to run the 'flushall' command
> ACL WHOAMI                          # confirm: still the scoped user
reporter
In ten lines you measured one command's time on the thread, learned who you are, and proved a user can read its own keys but cannot wipe the database. That's the whole operational loop in miniature: see, then constrain.

Q1. Your app's Redis suddenly feels frozen — instantaneous_ops_per_sec has cratered and clients are timing out. What's the fastest first move to find the cause?
You have shell access to a healthy-looking box; CPU on the Redis process is pinned at one core's worth of work.
C. One pinned core plus stalled ops/sec is the classic single-thread symptom — a slow O(N) command holding the thread (Lesson 1). SLOWLOG GET already recorded it with timing and args, no extra load. A makes a busy instance worse — MONITOR can halve throughput. B destroys data and treats nothing. D loses your evidence and likely recurs the moment the same command runs again.
Q2. A new service needs read-only access to keys under session:* and must never be able to run CONFIG or FLUSHALL. What's the right Redis 7.x mechanism?
B. ACLs (6.0+) are exactly this: ACL SETUSER svc on >pw ~session:* +@read -@dangerous grants read on those keys and nothing else. A gives full default-user power — a shared password is all-or-nothing. C is heavy infrastructure for an authz problem ACLs solve in one line. D only gates network access when unconfigured; it grants no per-command rules once a client is authenticated.
Q3. You run redis-cli --hotkeys to find your most-accessed keys, but it returns an error about the policy. Why — and what links this to an earlier lesson?
A. --hotkeys ranks keys by the per-key LFU access counter, which only exists under allkeys-lfu/volatile-lfu (the eviction internals from L18). On an LRU or noeviction instance there's no frequency counter to read. B, C, D invent prerequisites — persistence, replica-only, and cluster have nothing to do with how hotkeys are sampled.
