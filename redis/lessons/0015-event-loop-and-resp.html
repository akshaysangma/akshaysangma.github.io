The Event Loop & the RESP Protocol

Lesson 1 told you Redis runs one command at a time. Now you see how — how one thread serves thousands of connections, what the bytes on the wire actually say, and why pipelining is free speed.

Phase 4 · Internals ~10 min Hands-on Builds on: single-threaded execution (L01)
Recall first From Lesson 14: Pub/Sub is fire-and-forget, at-most-once, no persistence. So how does one Redis process juggle a publisher, fifty subscribers, and a client blocked on BLPOP — all at once — when it executes commands in a single thread? Hold your guess; that machinery is today's lesson.

One thread, thousands of connections

The puzzle from Lesson 1: if Redis executes commands in one thread, how does it serve thousands of simultaneous clients without a thread per connection? The answer is an event loop built on I/O multiplexing. The kernel watches every client socket for you and tells Redis, in one call, which sockets have data ready to read or room to write. Redis then handles only those — never blocking on a socket that isn't ready.

That loop lives in ae.c (Salvatore's "asynchronous event" library). It's deliberately thin: aeMain() spins forever calling aeProcessEvents(), which calls aeApiPoll() — a wrapper over whatever multiplexing syscall your OS provides.Backend is picked at compile time in ae.c: ae_epoll.c on Linux, ae_kqueue.c on macOS/BSD, ae_evport.c on Solaris, falling back to ae_select.c. Same loop, different kernel API. Sockets are non-blocking, so a slow or silent client never stalls the thread — it just isn't in the "ready" set that poll returns.

The shape of the loop Poll the kernel for ready sockets → for each readable socket, read & parse a command (in networking.c) → execute it → queue the reply → for each writable socket, flush its reply. Repeat forever. Only the execute step is the single-threaded core you already know. Everything around it is event-driven I/O.

So "single-threaded" was always shorthand for "single-threaded command execution." Concurrency at the connection level is real and has been forever — it just comes from multiplexing, not from threads.

RESP: what the bytes actually say

Between client and server flows RESP — the REdis Serialization Protocol. It's deliberately simple: human-readable, prefix-typed, and every piece terminated by \r\n (CRLF). The first byte of each chunk tells you its type.

RESP2 type prefixes (the original five) + RESP3 additions (Redis 6.0)
ByteTypeExample on the wireSince
+Simple string+OK\r\nRESP2
-Error-WRONGTYPE ...\r\nRESP2
:Integer:1000\r\nRESP2
$Bulk string$5\r\nHello\r\nRESP2
*Array*2\r\n$3\r\nfoo...\r\nRESP2
_Null_\r\nRESP3
#Boolean#t\r\n / #f\r\nRESP3
,Double,3.14\r\nRESP3
%Map%1\r\n$3\r\nfoo...RESP3

RESP3 adds more still: ~ set, > push (out-of-band, e.g. Pub/Sub), ( big number, = verbatim string, | attribute. The win of RESP3 is that maps, doubles, and nulls are typed instead of being faked inside generic arrays/bulk-strings, so clients stop guessing.

Requests are arrays of bulk strings. The command and each argument is a bulk string; the whole thing is one array — the "multibulk" framing. Hand-trace SET mykey "Hello" exactly as the client sends it:

# the client → server bytes for:  SET mykey Hello
*3\r\n        # array of 3 elements (command + 2 args)
$3\r\n        # next element is a 3-byte bulk string…
SET\r\n       #   …its payload
$5\r\n        # a 5-byte bulk string…
mykey\r\n     #   …the key
$5\r\n        # a 5-byte bulk string…
Hello\r\n     #   …the value

# server → client reply (a simple string):
+OK\r\n

That's the entire conversation: 35 bytes up, 5 bytes back. A GET mykey would come back as a bulk string — $5\r\nHello\r\n — and a GET on a missing key replies $-1\r\n (the RESP2 null bulk string) or, under RESP3, the cleaner _\r\n.

Inline vs multibulk — the easy-to-miss split RESP also accepts inline commands: a bare line like PING\r\n, space-separated, no */$ framing. That's a convenience for humans typing into nc/telnet — it's parsed by processInlineBuffer() in networking.c, while real clients send the full multibulk form handled by processMultibulkBuffer(). Don't build a client on inline commands: arguments can't contain spaces or binary data safely. Multibulk is the real protocol.
Run this — see RESP on the wire redis-cli decodes RESP for you, so to watch the raw bytes, speak the protocol by hand with nc (netcat). With a Redis 7 instance on :6379: 
# An INLINE command — just type it, CRLF-terminated:
$ (printf 'PING\r\n'; sleep 1) | nc localhost 6379
+PONG            # a RESP simple string

# The same PING as a proper MULTIBULK request:
$ (printf '*1\r\n$4\r\nPING\r\n'; sleep 1) | nc localhost 6379
+PONG

# SET then GET, multibulk, in one connection:
$ (printf '*3\r\n$3\r\nSET\r\n$5\r\nmykey\r\n$5\r\nHello\r\n*2\r\n$3\r\nGET\r\n$5\r\nmykey\r\n'; sleep 1) | nc localhost 6379
+OK
$5
Hello      # bulk-string reply: length-prefixed, then payload
Then flip to RESP3 and watch a reply change shape: redis-cli -3 CONFIG GET maxmemory returns a typed map (%), where plain redis-cli CONFIG GET maxmemory returns a flat RESP2 array. Same command, richer framing.

macOS nc closes when stdin ends, so the sleep 1 keeps the socket open long enough to read the reply. redis-cli negotiates the protocol on connect by sending HELLO; -3 asks for RESP3, otherwise it stays on RESP2 for backward compatibility.

Pipelining — amortizing the round trip

Every request/reply pair normally costs one network round-trip time (RTT). Run 1,000 sequential SETs over a 1 ms link and you've spent ~1 second in latency alone — the server was idle almost the whole time, waiting on the wire, not on work. Pipelining fixes this: the client writes many requests back-to-back without waiting for each reply, then reads all the replies in order.

Because RESP is just a byte stream, the server doesn't care that ten requests arrived in one packet — readQueryFromClient() parses as many complete commands as the buffer holds, executes each, and appends each reply. The replies come back in request order. You've turned N round trips into one, and the per-command cost collapses to raw execution time.

Run this — feel the RTT collapse 
# Three commands, one connection, one round trip:
$ (printf 'PING\r\nPING\r\nPING\r\n'; sleep 1) | nc localhost 6379
+PONG
+PONG
+PONG        # sent together, replies stream back in order

# Benchmark the difference — note the ops/sec jump:
$ redis-benchmark -t set -n 100000 -q            # no pipelining
$ redis-benchmark -t set -n 100000 -P 16 -q       # pipeline depth 16
The -P 16 run reports dramatically higher throughput — same server, same commands, fewer round trips.
Pipelining is NOT a transaction This is the classic mix-up. Pipelining only batches transport — it makes no atomicity or isolation promise. Between two pipelined commands from you, another client's command can execute (each individual command is still atomic, but the batch is not a unit). If you need "these run together with nothing interleaved," that's MULTI/EXEC (Lesson 11) or a Lua script (Lesson 12) — and you can even pipeline a MULTI/EXEC block to get both. Speed and atomicity are independent knobs.Pipelining changes the network cost, not the algorithmic cost: an O(N) command is still O(N) when pipelined, and PING is O(1) either way. You're amortizing RTT, not work.

"But Redis 6 added threads!" — yes, for I/O only

Here's the misconception to kill. Redis 6.0 (2020) introduced threaded I/O (io-threads). People hear "threads" and assume commands now run in parallel across cores. They don't. The extra threads only parallelize the socket work that surrounds execution — reading bytes off sockets and parsing them into commands, and encoding/writing replies back out. Command execution stays in the one main thread, exactly as Lesson 1 promised.

The reason: at high throughput, with fast commands, Redis often spends more time in kernel read()/write() and protocol parsing than in the command logic itself. Fanning that out across a few threads (the logic lives in networking.c) lifts throughput — while the main thread still runs your commands one at a time, preserving the free atomicity the whole system is built on.

What threaded I/O does and doesn't touch Parallelized: reading from sockets, RESP parsing, reply encoding, writing to sockets. Still single-threaded: the actual command execution — INCR, ZADD, SET, all of it. Default is io-threads 1 (disabled); enable it only on I/O-bound, many-connection workloads. And it never changes a single semantic: ordering, atomicity, and "one slow command blocks everyone" all still hold.
Run this — inspect the I/O thread config 
> CONFIG GET io-threads
1) "io-threads"
2) "1"                 # default: threaded I/O off
> CONFIG GET io-threads-do-reads
1) "io-threads-do-reads"
2) "no"                # reads stay on main thread unless enabled
These are startup settings — you set them in redis.conf, not live. The point of looking: even with io-threads 4, two SETs never execute simultaneously. The threads move bytes; the main thread moves data.

Q1. A teammate sets io-threads 4 and expects two SETs on different keys to run truly in parallel across cores. What actually happens?
They're load-testing and assume more I/O threads means parallel command execution.
B. Redis 6's threaded I/O parallelizes only socket read/write and RESP parsing/encoding (networking.c). Command execution remains in the one main thread — the atomicity guarantee from Lesson 1 is untouched. (A is the headline misconception; C invents a cluster requirement; D borrows slot logic from Cluster, which governs sharding, not execution threading.)
Q2. You capture the bytes *2\r\n$3\r\nGET\r\n$3\r\nfoo\r\n heading into Redis. What is this?
A. *2 opens a 2-element array; each $3 introduces a 3-byte bulk string (GET, then foo). That's the multibulk request framing — command plus argument. (B/+ and C/: are reply types with the wrong prefix; D misreads one command as two — a single * array is exactly one command.)
Q3. You pipeline INCR a then INCR b to cut round trips. A teammate says "great, now they run atomically as one unit." Correct them.
B. Pipelining batches transport only — it amortizes RTT, nothing more. Each command is individually atomic (single thread), but between your two pipelined commands another client's command can run; the batch is not isolated. For real atomicity use MULTI/EXEC (L11) or Lua (L12). (A/D conflate batching with transactions — the headline trap; C invents per-command threads, which don't exist.)
