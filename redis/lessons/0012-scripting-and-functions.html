Lua Scripting & Functions

MULTI gives you atomicity but no logic — you can't read a value and branch on it inside the transaction. A server-side script can. Push the whole read-decide-write across the wire as one atomic unit.

Phase 3 · Patterns & Atomicity ~10 min Hands-on Builds on: MULTI / EXEC / WATCH
Recall first Last lesson: WATCH turned a check-then-set race into an optimistic-locking retry loop — read, decide on the client, hope nothing changed before EXEC. Hold that picture. Today we remove the loop entirely by moving the "decide" onto the server.

Why a script, when you already have MULTI?

A MULTI/EXEC block is a batch: a fixed list of commands queued in advance and run with no interleaving. What it cannot do is look at a value and act on it — the commands are decided before any of them run, so there's no "if the balance is ≥ 100, debit it" inside the transaction. That's why WATCH exists: you do the reading and branching on the client, then gamble that nothing changed.

A Lua script collapses that gamble. You ship code to the server; Redis runs the entire script as one command, on the single thread, with nothing else interleaving (recall Lesson 1 — one command at a time). Read, branch, write, return — all atomic, all server-side, in one round trip. No retry loop, no race window.This is the same atomicity guarantee a single INCR has, extended to arbitrary multi-step logic. The script is the indivisible unit.

The model EVAL runs your Lua on the server as if it were a single, indivisible Redis command. While it runs, no other client's commands execute — not even a fast GET. Atomicity comes for free; the bill comes due as latency for everyone if the script is slow.

EVAL: the anatomy

The signature is the part people get wrong:

EVAL script numkeys [key ...] [arg ...]

That numkeys is mandatory and load-bearing. It tells Redis how many of the following arguments are keys; the rest are plain arguments. Inside Lua you read them through two 1-indexed (Lua arrays start at 1, not 0) global tables:

  • KEYS[1], KEYS[2], … — the key names, the first numkeys args.
  • ARGV[1], ARGV[2], … — everything after them.

This split is not bureaucracy. Every key the script touches must be passed through KEYS — that is how Redis Cluster knows which hash slot the call belongs to. Hard-code a key name as a string literal inside the script body and it works on a single node but breaks (or silently mis-routes) the day you shard. Treat "all keys via KEYS" as non-negotiable discipline from day one.In Cluster, all KEYS must hash to the same slot or you get a CROSSSLOT error — use hash tags {...} to force colocation. That's Lesson 22; just bank the rule now.

The trap — a long script freezes the whole server The single thread that makes your script atomic is the same thread every other client is waiting on. A script with an accidental O(N) loop over a million-element key, or a literal infinite loop, blocks every connection. After busy-reply-threshold (default 5000 ms; the old name lua-time-limit still works) Redis starts replying -BUSY to other clients and accepts only SCRIPT KILL / SHUTDOWN NOSAVE. And SCRIPT KILL only works if the script hasn't written yet — once it has, killing it would corrupt atomicity, so your only out is SHUTDOWN NOSAVE. Keep scripts short and bounded. Always.

call vs pcall, and what comes back

Inside the script you invoke Redis through two functions:

  • redis.call(...) — runs a command; if that command errors (e.g. WRONGTYPE), it raises a Lua error that aborts the whole script and propagates to the client. This is usually what you want: fail loud, fail atomic.
  • redis.pcall(...) — the protected variant; on error it returns the error as a Lua table instead of aborting, so the script can inspect it and decide what to do.

Return values convert between Lua and Redis by fixed rules worth memorising: a Lua number becomes a Redis integer (the decimal part is truncated — return 3.9 and the client sees 3); a Lua string becomes a bulk string; a Lua table becomes an array (and stops at the first nil); Lua false becomes a nil reply, true becomes 1; and a table with an err or ok field becomes an error or status reply. Return floats as strings if you need the fraction.

EVALSHA: don't ship the source every time

Sending the full script body on every call wastes bandwidth. So Redis caches scripts by the SHA1 of their exact body. Two-step it:

  • SCRIPT LOAD "body" → compiles and caches the script, returns its SHA1. O(N) in the script length.
  • EVALSHA sha1 numkeys … → runs the cached script. If the server doesn't have it (cache was flushed, fresh restart, failover to a replica that never saw the SCRIPT LOAD), you get a NOSCRIPT error.

Real clients handle this for you: try EVALSHA, and on NOSCRIPT fall back to EVAL (which both runs and caches). You rarely write that dance by hand, but knowing it explains why a redeploy or failover can briefly surface NOSCRIPT. The script cache is not persisted and not replicated as a cache — it's rebuilt from EVAL calls, which is exactly why effects replication (next section) matters.

Hands-on — script it yourself

Run this — EVAL, KEYS/ARGV, and the SHA round-trip Type these into redis-cli and watch each rule from above fire: 
> EVAL "return 1 + 1" 0
(integer) 2
> EVAL "return redis.call('SET', KEYS[1], ARGV[1])" 1 greeting hola
OK
> GET greeting
"hola"
> EVAL "return {KEYS[1], ARGV[1], ARGV[2]}" 1 k alpha beta   # 1-indexed, table → array
1) "k"
2) "alpha"
3) "beta"
> EVAL "return 3.9" 0                 # Lua number → integer, truncated
(integer) 3
> SCRIPT LOAD "return redis.call('INCR', KEYS[1])"
"61636018f4e6b5817b89791bbed242f93fa089e3"
> EVALSHA 61636018f4e6b5817b89791bbed242f93fa089e3 1 hits
(integer) 1
> EVALSHA 61636018f4e6b5817b89791bbed242f93fa089e3 1 hits
(integer) 2
> SCRIPT EXISTS 61636018f4e6b5817b89791bbed242f93fa089e3 0000000000000000000000000000000000000000
1) (integer) 1
2) (integer) 0
The SHA1 is deterministic for an exact body — change one space and you get a different hash, and a different cache entry. Now do something a MULTI can't: read, branch, then write atomically — a debit that refuses to overdraw. 
> SET wallet:42 100
OK
> EVAL "local bal = tonumber(redis.call('GET', KEYS[1])) if bal >= tonumber(ARGV[1]) then return redis.call('DECRBY', KEYS[1], ARGV[1]) else return redis.error_reply('insufficient funds') end" 1 wallet:42 30
(integer) 70
> EVAL "local bal = tonumber(redis.call('GET', KEYS[1])) if bal >= tonumber(ARGV[1]) then return redis.call('DECRBY', KEYS[1], ARGV[1]) else return redis.error_reply('insufficient funds') end" 1 wallet:42 90
(error) insufficient funds
> GET wallet:42
"70"
No WATCH, no retry loop, no window: the read and the conditional write are one indivisible command. The second call refused and changed nothing.

Determinism & replication — the old rule, relaxed

Old Redis (before 5.0) replicated a script by shipping the script itself to replicas and to the AOF, which then re-ran it. If your script called TIME, SRANDMEMBER, or anything non-deterministic and then wrote the result, the replica would compute a different result and diverge. Hence the historical commandment: scripts must be pure functions of KEYS and ARGV.

Effects replication (a.k.a. script-effects replication) arrived as an opt-in mode in 3.2, became the default in 5.0, and — with verbatim script replication removed entirely in 7.0 — is the only mode on 7.x: Redis no longer replicates the script — it replicates the actual write commands the script produced, exactly as if you'd typed them. A SET k <random> generated inside the script propagates as that concrete SET, so replica and AOF stay byte-identical regardless of how the value was chosen. Non-determinism is now safe to replicate.

Still discipline, just for a different reason Effects replication removes the replication hazard, not the logic hazard. A script whose writes depend on wall-clock time or randomness is still hard to reason about, test, and debug — and two clients calling it can produce surprising states. Pure-function discipline (output determined by KEYS + ARGV) is no longer mandatory for safety, but it's still the mark of a script you can trust.

Redis Functions — the modern successor (7.0)

EVAL has a structural weakness: the script lives in your application. The server only knows an anonymous blob behind a SHA. There's no name, no versioning, nothing the DBA can list or audit — the logic is scattered across client codebases.

Redis Functions, added in 7.0, fix that. You load a library of named functions into the server; it persists (saved in RDB/AOF) and replicates as a first-class object, and any client calls a function by name with FCALL. The server, not the client, is the source of truth for the logic.

# a library is text starting with a shebang naming it; register each function
> FUNCTION LOAD "#!lua name=mylib
redis.register_function('debit', function(keys, args)
  local bal = tonumber(redis.call('GET', keys[1]))
  if bal >= tonumber(args[1]) then
    return redis.call('DECRBY', keys[1], args[1])
  else
    return redis.error_reply('insufficient funds')
  end
end)"
mylib
> FCALL debit 1 wallet:42 20
(integer) 50
> FUNCTION LIST
1) ... library_name "mylib" ... functions ... name "debit" ...

Two differences to internalise. First, a function takes its keys and args as parameters — function(keys, args) — not the magic globals KEYS/ARGV of EVAL. Same 1-indexed contract, cleaner shape. Second, FCALL_RO is a read-only entry point you can route to replicas, the analogue of EVAL_RO. Manage libraries with FUNCTION LIST, FUNCTION DELETE, FUNCTION DUMP/RESTORE, and FUNCTION FLUSH.Functions are the recommended path for new code in 7.x. EVAL isn't deprecated — it's perfect for one-off and ad-hoc logic — but durable, named, shared logic belongs in a library.

So: script, MULTI, or client?

Pick the lightest tool that gives the atomicity and logic you actually need.
NeedReach forWhy
Fixed set of writes, no branching on valuesMULTI/EXECAtomic batch, zero new language, no cache.
Check-then-set, simple, contention lowWATCH + retryOptimistic; no server-side code to maintain.
Read-decide-write as one atomic unitEVAL / EVALSHALogic runs server-side; no race window, one round trip.
That logic is durable, named, sharedRedis Functions (FCALL)Persisted, replicated, listable, versioned on the server.
Heavy CPU work, or logic that can tolerate racesClient-side codeDon't burn the single thread; keep the server responsive.

The throughline: scripts and functions buy you atomic multi-step logic, and you pay for it in shared single-thread time. Use them for short, bounded read-decide-write sequences. The moment a script grows a real loop or heavy computation, it stops being a clever atomic trick and becomes a latency incident waiting for the worst possible moment.

Check yourself

Commit to an answer before reading the explanation — that's the retrieval that makes it stick.

Q1. You need to atomically decrement a stock counter only if it would stay ≥ 0, otherwise reject. A single MULTI/EXEC block can't do this directly. Why not?
The decision ("is there enough stock?") depends on the current value, which you only learn at run time.
B. A transaction is a batch decided in advance — the commands are queued before execution, so none can branch on a value read by another. That's precisely the gap a Lua script fills: it reads, branches, and writes in one atomic pass. (A is false — transactions hold many writes; C is false — Redis transactions have no rollback, Lesson 11; D overstates — execution is atomic but the queue isn't a global lock you hold open.)
Q2. A script hard-codes a key name as a string literal — redis.call('GET', 'config:flags') — instead of passing it through KEYS. It works fine in your dev single node. What's the real defect?
C. Cluster decides which node/slot a script call belongs to from the declared KEYS. A key smuggled in as a literal is invisible to that routing, so the call can hit the wrong node or break under sharding — even though it passes on one node. (A is false — it loads fine; B is invented; D is false — caching keys on the SHA of the body, untouched by this.) "All keys via KEYS" is a correctness rule, not a style preference.
Q3. Your script calls redis.call('TIME') and writes the timestamp into a key. A colleague warns it'll "desync the replicas like the old days." On Redis 7.x, are they right?
The same concern would have been valid on Redis 4.x, where scripts were re-executed downstream.
A. Since Redis 5.0, scripts replicate by their effects: Redis propagates the actual SET key <that-timestamp> the script produced, not the script, so the replica stores the identical value. The non-determinism is harmless to replication. (B describes the pre-5.0 verbatim-replication behaviour; C invents a rejection; D is wrong — TIME is still non-deterministic, it's just replicated safely.) The logic caution remains, but the replication hazard is gone.
