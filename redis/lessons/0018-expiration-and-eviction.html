Expiration & Eviction Internals

Two different ways a key disappears — one you asked for, one the server forced on you. Conflate them and you'll mis-diagnose every "where did my data go?" incident. Keep them apart and you can predict exactly what Redis deletes, when, and why.

Phase 4 · Internals ~10 min Hands-on Builds on: TTL & the expires dict
Recall first Last lesson you learned each database carries two dictionaries: the main keyspace dict, and a second, smaller expires dict. What does that second dict actually store — and roughly what fraction of your keys appear in it? Hold your answer; this lesson is built on top of it.

One word, two mechanisms — don't merge them

A key can vanish for two completely unrelated reasons, and experts never blur them:

The distinction to carry Expiration is voluntary: you set a per-key TTL, and Redis honours it. Eviction is involuntary: you hit maxmemory, and Redis deletes keys you never marked for death — to make room for the write in front of it.

Expiration is per-key and deterministic — the key was always going to die at that timestamp. Eviction is global and pressure-driven — it fires only under a memory ceiling, and which key dies depends on a policy and a victim-selection algorithm. A key with no TTL can still be evicted; a key with a TTL can die early by eviction before its TTL. Same outcome (key gone), totally different cause, totally different fix. Spend the rest of the lesson keeping them in separate boxes.

Expiration: how a TTL'd key actually dies

Setting a TTL (EXPIRE key 60, or SET key v EX 60) doesn't schedule a timer that fires at second 60. Redis has no per-key timer thread — that would mean millions of timers on the one thread. Instead it records the absolute expire time (a Unix ms timestamp) in the expires dict you just recalled, and reaps the key through two cooperating mechanisms.

Lazy (passive) expiry — checked on access

Every time a command touches a key, Redis first checks the expires dict: is this key past its time? If so, it's deleted then, and the command behaves as if the key never existed (GET returns nil, etc.). This is cheap and exact at the moment of access — but it has an obvious hole: a key that's never touched again is never reaped this way, and keeps occupying memory (recall L17 — a logically-expired key still counts toward used_memory until it's actually collected).

Active (background) expiry — a sampling cycle

To plug that hole, a background job runs inside serverCron roughly 10 times a second (the hz setting, default 10). Each pass, for each DB, it does not scan every key — it samples a batch of keys that have a TTL (about 20 per database) from the expires dict, deletes the ones that are expired, and then applies a feedback rule:

The 25% rule If more than 25% of the sampled batch turned out to be expired, the cycle assumes the database is full of stale keys and immediately samples again, repeating until a batch comes back under 25% expired. The whole cycle is CPU-time-bounded so it never hogs the single thread (recall L01 — everything shares that one thread).

The 25% ceiling is the elegant bit: it makes the expired-but-uncollected population converge toward at most a quarter of keys-with-TTL, statistically, without ever doing an O(N) sweep. You trade a small, bounded amount of stale memory for never blocking the event loop.

Big-O of the TTL commands themselves: EXPIRE/PEXPIRE/EXPIREAT, TTL/PTTL, PERSIST are all O(1) — they just read or write one entry in the expires dict. The work is in the reaping, not the marking.

Replicas don't expire on their own

This one trips up people building read replicas. A replica does not independently expire keys — neither lazily nor actively. It waits for the master to decide a key is gone and to propagate an explicit DEL/UNLINK down the replication stream. Why? So a key expires at the same logical moment everywhere; otherwise clock skew between master and replica would make them disagree on which keys exist.

The replica subtlety A replica won't delete a logically-expired key until the master's DEL arrives — but it also won't serve it. A read on a replica for a key that's past its TTL returns nil (Redis masks it), even though the key is still physically in the replica's dataset. So: present in memory, invisible to reads, deleted only on the master's command. Don't assume "replica returned nil" means "replica freed the memory."

Eviction: when maxmemory forces Redis's hand

Now the involuntary side. Set a ceiling with maxmemory (e.g. maxmemory 2gb; 0 means no limit, the default). Before running a write that would push used_memory over that ceiling, Redis tries to free space by deleting existing keys, according to maxmemory-policy. There are exactly eight policies — memorise them as a 2×4 grid:

The eight maxmemory policies. "Candidate pool" = which keys are even eligible to be evicted.
PolicyCandidate poolVictim chosen
noevictionnonenothing — writes fail with an error

allkeys-lfuevery keyapprox. least-frequently-used

volatile-lfukeys with a TTLapprox. least-frequently-used

volatile-ttlkeys with a TTLthe one nearest its expiry

The split is clean: allkeys-* can sacrifice any key (the cache mindset — everything is disposable); volatile-* only touches keys you explicitly marked expirable (the mixed-workload mindset — some keys are precious and untagged, so leave them alone). volatile-ttl is the odd one: it approximates "evict whatever was going to die soonest anyway."

The trap that pages people at 3am Pick a volatile-* policy and forget to put a TTL on anything, and you've effectively configured noeviction. When you hit maxmemory there are zero eligible victims, so Redis can't free space — and every write starts failing with (error) OOM command not allowed when used memory > 'maxmemory'. The reads keep working, which is exactly what makes this so confusing to diagnose. volatile-* is only safe if a meaningful share of your keyspace actually carries a TTL.

LRU and LFU are approximated, not exact

Here's the part that separates a real understanding from a guessed one: Redis does not maintain a perfect LRU or LFU ordering. True LRU needs a linked list threaded through every key, updated on every access — too much memory and CPU on the hot path. Instead Redis samples: on each eviction it picks maxmemory-samples keys at random (default 5) from the candidate pool, and evicts the best victim among that sample, fed through a small pool of remembered good candidates. Raise maxmemory-samples toward 10 and you get closer to true LRU at more CPU; the default 5 is a deliberate accuracy/speed trade.

LRU uses a 24-bit clock stamped on each object at access time (visible via OBJECT IDLETIME). LFU is cleverer: it stores an 8-bit probabilistic frequency counter (visible via OBJECT FREQ) that doesn't simply increment. It saturates logarithmically — controlled by lfu-log-factor (default 10), so the counter rises ever more slowly as it climbs, letting one byte represent a huge access range — and it decays over time via lfu-decay-time (default 1 minute), so a key that was hammered once last week doesn't outrank a key that's busy now. That decay is what makes LFU track sustained popularity rather than one historical spike — usually the better cache policy, which is why allkeys-lfu is a strong default for a pure cache.

Then prove lazy vs active expiry directly — switch the active cycle off and watch a dead key linger until you touch it: 
> DEBUG SET-ACTIVE-EXPIRE 0    # disable the background reaper
OK
> SET ghost boo PX 100         # dies in 100ms
OK
# wait a second, then:
> DBSIZE                       # still counted! active reaper is off, nobody touched it
(integer) 1
> GET ghost                    # this access triggers LAZY expiry →
(nil)
> DBSIZE                       # now it's gone — deleted on access, not on schedule
(integer) 0
> DEBUG SET-ACTIVE-EXPIRE 1    # turn the reaper back on
OK
Watch two INFO counters to tell the mechanisms apart in production: expired_keys (voluntary — TTLs being honoured) vs evicted_keys (involuntary — memory pressure). A rising evicted_keys is your signal that maxmemory is biting; that's the applied story in L23.

Check yourself

Commit to an answer before reading the explanation — that's the retrieval that makes it stick.

Q1. Your cache hits maxmemory under volatile-lru, but none of your keys were ever given a TTL. A client issues a SET.
Reads keep succeeding fine; only writes are misbehaving, and you can't see why memory won't drop.
B. A volatile-* policy can only evict keys that carry a TTL. With zero such keys, the candidate pool is empty, so Redis frees nothing and behaves exactly like noeviction — writes fail with OOM while reads sail through. (A and C describe what would happen if keys had TTLs; D never happens — maxmemory is a hard ceiling.) Fix: give keys TTLs, or switch to an allkeys-* policy.
Q2. A key's TTL has passed on the master, but the master hasn't yet propagated its DEL. A client reads that key from a read replica.
C. Replicas never expire keys on their own — they wait for the master's explicit DEL/UNLINK. But to avoid serving stale data, a replica masks a logically-expired key from reads, returning nil while the key still physically occupies memory. (A is wrong — the replica doesn't delete; B would serve stale data; D isn't how replica reads work.) So "returned nil" does not mean "freed the memory."
Q3. You put the same TTL on a million keys, all set to expire at 12:00:00 exactly. At 12:00:01 you check used_memory.
You expected a cliff-edge memory drop the instant the clock ticked past the expiry second. You don't see one.
B. There's no timer that fires at the TTL instant. Expired keys are reclaimed lazily (on next access) and actively (the ~10Hz cycle samples ~20 TTL'd keys per DB, repeating while >25% of a batch is stale). Until a key is actually collected it still counts toward used_memory (recall L17) — so a synchronized mass-expiry drains over seconds, not in one step. (A imagines a timer that doesn't exist; C and D ignore both reapers entirely.)
