Which Data Structure Should I Reach For?

A one-page decision aid for Redis 7.x. Start with the intent, not the type. The right structure makes the operation O(1) or O(log N); the wrong one quietly turns it into an O(N) scan that blocks the single thread.

1 · By intent

Find the row that matches what you actually need. The catch column is where most production incidents come from — read it before you commit.

“I need to…” → the structure to reach for first. Commands shown are the core few, not the full surface.
The needRecommendedKey commandsWhy / the catch
Ranked leaderboard (top-N, rank lookup) Sorted Set ZADD ZRANGE REV ZRANK ZINCRBY Ordering by score is the whole point; rank and range are built in. Writes are O(log N), not free — the skiplist + hashtable pair costs ~2× a plain set in RAM.
FIFO job queue (at-most-once is OK) List LPUSH + BRPOP LMOVE Both ends are O(1) and BRPOP blocks without polling. The catch: a popped job lives only in the worker’s memory — if it crashes mid-process, the job is gone. No acks, no replay.
Durable queue with acks & replay Stream XADD XREADGROUP XACK XAUTOCLAIM Consumer groups give per-message acks, a pending list, and history you can replay. The catch: it grows forever unless you cap it (XADD MAXLEN ~) and you must claim stuck pending entries yourself.
Unique membership / tags, set algebra Set SADD SISMEMBER SINTER SUNION O(1) add and membership test; intersect/union/diff are first-class. The catch: SMEMBERS and SINTER over big sets are O(N)/O(N·M) — iterate with SSCAN.
Object with fields (user, config) Hash HSET HGET HMGET HINCRBY One key, field-level reads/writes, O(1) per field — beats N top-level keys. The catch: HGETALL is O(N); per-field TTL only arrived in 7.4 (HEXPIRE).
Atomic counter String INCR INCRBY DECR INCRBYFLOAT Single-threaded execution makes increments atomic with no locking. The catch: it’s still a string parsed as a 64-bit int — overflow past 2^63-1 errors out.
Approximate unique count at scale HyperLogLog PFADD PFCOUNT PFMERGE ~12 KB fixed per HLL regardless of cardinality, ~0.81% standard error. The catch: it counts, it can’t enumerate — you can never ask “who’s in it?”
Rate limiter (sliding window) Sorted Set · or String for fixed-window ZADD ZREMRANGEBYSCORE ZCARD Score = timestamp; drop the old scores, count what remains — a true sliding window. The catch: one member per request costs memory. A fixed window is just INCR+EXPIRE and far cheaper if you can tolerate the boundary burst.
Presence / feature flags as bits Bitmap (String) SETBIT GETBIT BITCOUNT BITOP 1 bit per user-id — millions of dense flags in a few MB, with set-wise BITOP. The catch: it allocates up to the highest offset, so sparse / huge ids waste RAM (offset 4e9 ≈ 500 MB).
Geospatial nearest (radius / box) Geo (Sorted Set) GEOADD GEOSEARCH GEODIST Geohash packed into a sorted-set score gives radius and bounding-box queries. The catch: it is a sorted set — remove members with ZREM, and very tight radii still scan candidates.
Pub/Sub fan-out Pub/Sub SUBSCRIBE PUBLISH (SSUBSCRIBE/SPUBLISH in cluster) Fire-and-forget broadcast to every connected subscriber. The catch: zero persistence — an offline or slow subscriber simply misses messages. Need delivery guarantees? Use a Stream.
Secondary index / range query Sorted Set · or a Set per value ZRANGEBYSCORE ZRANGEBYLEX SINTERSTORE Score = the numeric attribute → range scans; equal scores + ZRANGEBYLEX → prefix/lex queries. The catch: you maintain the index by hand on every write. For rich multi-field querying, reach for RediSearch instead.
Rule of thumb If the access pattern is by key → String/Hash. By order or rank → Sorted Set. By membership → Set. By position at the ends → List. By time, durably → Stream. When two fit, pick the one whose hot operation is O(1) or O(log N), and confirm the O(N) operations stay off the hot path.

Encoding note: listpack replaced ziplist in Redis 7.0 as the compact representation for small Hashes, small Lists, small Sorted Sets, and the nodes inside a quicklist; Sets gained a listpack encoding (for small non-integer sets) in 7.2. A collection stays compact until it crosses its *-max-listpack-entries / *-max-listpack-value threshold (or, for Sets, set-max-intset-entries), at which point Redis silently promotes it to the full hashtable / skiplist / quicklist form — and never demotes back.

3 · Traps

O(N) commands block the one thread Redis runs your command on a single core. SMEMBERS, HGETALL, LRANGE 0 -1, ZRANGE 0 -1, and especially KEYS are O(N) — on a million-element key they stall every other client until they finish. Use the cursor variants (SCAN, SSCAN, HSCAN, ZSCAN) and bounded ranges. KEYS in production is a near-guaranteed latency incident.
Lists are O(1) only at the ends A List is a linked list of listpacks, not an array. LINDEX, LINSERT, and LSET into the middle are O(N). If you need random access by position or by key, you reached for the wrong structure — use a Hash or a Sorted Set.
A Set is the wrong tool for “how many uniques?” Storing tens of millions of members just to call SCARD burns real RAM (tens of bytes per member in a hashtable). If you only need the count and can tolerate ~0.81% error, a HyperLogLog gives it in a fixed ~12 KB. Keep the Set only when you must enumerate or test individual membership.
Bitmaps allocate up to the highest offset SETBIT key 4000000000 1 doesn’t set one bit — it forces Redis to allocate the whole 500 MB string up to that offset. Bitmaps are only memory-efficient when ids are dense and start near zero. Sparse or hashed ids belong in a Set or a Roaring-style structure, not a bitmap.
The encoding flip is a one-way cliff Crossing hash-max-listpack-entries, zset-max-listpack-entries, set-max-intset-entries, etc. converts the key to its full encoding and it never converts back, even after you delete elements. Memory estimates made on small keys don’t hold once a key grows past the threshold — size capacity against the promoted form.
Pub/Sub drops, it doesn’t queue PUBLISH delivers only to subscribers connected at that instant. There is no buffer, no ack, no replay — a reconnecting client has a permanent gap. If a missed message is a bug, you need a Stream with a consumer group, not Pub/Sub.
