1 · Persistence — RDB vs AOF

Two mechanisms, different durability/cost trade-offs. They are independent and can run together.
 RDB (snapshot)AOF (append-only file)
WhatPoint-in-time binary dump of the whole dataset (dump.rdb).Log of every write command, replayed on load.
TriggerSAVE (blocking, avoid), BGSAVE (forks child), or save points.Continuous append per appendfsync; compacted by rewrite.
MechanismParent fork()s; child writes snapshot while parent serves. Pages shared copy-on-write — memory spikes only for pages mutated during the save.Buffer of write commands flushed to disk; periodically rewritten to the minimal command set.
Data-loss windowEverything since the last successful snapshot (minutes).everysec ≈ ≤1s; always ≈ none; no = up to OS flush.
Restart speedFast — load a compact binary.Slower — replay the log (mitigated by 7.x base file).
File sizeSmall, compact.Larger; grows until rewrite.
Best forBackups, fast restarts, replication bootstrap, tolerable loss window.Lowest data-loss durability requirement.

Save points & fsync settings

save <sec> <changes>
RDB fires BGSAVE when ≥changes keys changed in sec seconds. Default: save 3600 1 300 100 60 10000. save "" disables RDB.
appendfsync always
fsync every write — slowest, strongest (~no loss). Rarely used.
appendfsync everysec
fsync once a second — the recommended default. ≤1s loss on crash.
appendfsync no
Let the OS decide (~30s on Linux). Fastest, weakest.

AOF rewrite & the 7.x multi-part format

  • Rewrite (BGREWRITEAOF / auto via auto-aof-rewrite-percentage) forks a child and writes the smallest command sequence that recreates current state — keeps the file from growing unbounded.
  • Redis 7.0+ multi-part AOF: a base file (RDB-format by default — the hybrid), one or more incremental files, and a manifest tying them together (stored under appenddirname). Combines RDB's compact base with AOF's fine-grained durability.

Restart load order

On startup, if appendonly yes, Redis loads the AOF (more complete, smaller loss window) and ignores the RDB. Only if AOF is disabled does it load the RDB.

Not a backup Persistence protects against process/host restart, not against FLUSHALL, bad deploys, ransomware, or disk loss. A live RDB/AOF on the same box is not a backup — copy snapshots off-host on a schedule and test restores.

2 · Replication

One master, N replicas. Asynchronous by default: the master acknowledges a write to the client before it reaches replicas.

Async caveat — acknowledged writes can be lost Because propagation lags the client ack, a write the master confirmed but had not yet shipped is lost if that master fails and a replica is promoted. Replication improves availability and read scale; it is not a strong-durability guarantee. WAIT and min-replicas-* narrow the window but do not close it — failover is never fully lossless.
REPLICAOF host port
Make this node a replica of host:port. REPLICAOF NO ONE promotes it back to master. (Config: replicaof.)
read-only replicas
replica-read-only yes (default) — replicas reject writes, so app traffic can't diverge from the master.
WAIT numreplicas timeout
Blocks until numreplicas have acked all prior writes (or timeout, ms). Per-command durability barrier — still not synchronous replication.
min-replicas-to-write / min-replicas-max-lag
Master refuses writes unless at least N replicas are connected with lag ≤ M seconds. Trades availability for durability.

Resync: full vs partial

 Full resyncPartial resync
WhenFirst sync, unknown replid, or gap too large for the backlog.Brief disconnect where the replica's offset is still inside the backlog.
CostMaster BGSAVE → ships RDB → streams buffered writes. Expensive.Master replays only the missing bytes from the in-memory backlog. Cheap.
MechanismPSYNC negotiates using the master replication ID (replid) + offset. The repl-backlog-size circular buffer holds recent stream; if the replica's offset is still in it, a partial resync suffices.

Size repl-backlog-size for your worst expected disconnect × write throughput, or every blip becomes a full resync. repl-diskless-sync yes streams the RDB over the socket instead of writing it to disk first.

3 · Sentinel (high availability)

A separate fleet of redis-sentinel processes that monitor masters/replicas, detect failure, elect a leader, and perform automatic failover — then steer clients to the new master. Use Sentinel for HA on a non-sharded deployment.

SDOWN — Subjectively Down
One Sentinel hasn't heard a valid PING reply within down-after-milliseconds. Local opinion only.
ODOWN — Objectively Down
At least quorum Sentinels independently report SDOWN. This is what authorizes starting a failover.
Quorum vs majority — the subtlety Quorum (configurable) is only the count needed to declare ODOWN — to agree the master is down. It does not by itself start a failover. To actually authorize the failover, a Sentinel must be elected leader, and that election always requires a strict majority of the total Sentinel set (N/2 + 1), independent of the quorum value. So a low quorum speeds detection but a majority of all Sentinels must still be reachable to act. This is why you run an odd number ≥ 3: you can't form a majority if too many Sentinels are partitioned away.

Failover steps

  1. Quorum of Sentinels mark the master ODOWN.
  2. Sentinels elect a leader (needs majority of all Sentinels).
  3. Leader picks the best replica (priority, replication offset, runid).
  4. Leader issues REPLICAOF NO ONE to promote it.
  5. Remaining replicas are repointed at the new master; old master becomes a replica when it returns.
  6. Sentinels publish the new master address.

Client discovery

Clients must be Sentinel-aware. They never hardcode the master; they ask:

SENTINEL get-master-addr-by-name <master-name>

and subscribe to the +switch-master pub/sub event to re-resolve after a failover.

4 · Cluster (horizontal sharding)

Data is partitioned across masters, each owning a subset of 16384 hash slots. Provides scale-out + HA (each master has replicas) without a separate Sentinel tier. Recommended minimum: 3 masters (so a majority survives one loss).

Slot of a key
CRC16(key) mod 16384. Each master owns a contiguous-ish range of slots; total must be 16384 with full coverage.
Hash tags {…}
If a key contains {...}, only the substring inside the first {} is hashed — e.g. user:{42}:profile and user:{42}:cart land in the same slot. The tool for co-locating multi-key ops.
CROSSSLOT
Multi-key commands (MGET, SINTERSTORE, transactions, Lua) error if keys span different slots. Co-locate them with a shared hash tag.
Redirections — a smart client caches the slot map and follows these.
ReplyMeansClient action
MOVED slot host:portSlot now permanently lives on another node.Update the cached slot map and retry there.
ASK slot host:portSlot is mid-migration; this key already moved.Send ASKING then the command to that node — one-shot, do not update the map.

Gossip bus: nodes chatter on a second port = data port + 10000 (e.g. 6379 → 16379) carrying heartbeats, config epochs, and failure detection. Open it in the firewall or the cluster can't form.

Sentinel vs Cluster Don't run both for the same data. Sentinel = HA for a single (non-sharded) master. Cluster = sharding + built-in HA. Choose one based on whether you've outgrown one node's memory/throughput.

5 · Memory & eviction

maxmemory
Cap on dataset memory. Leave headroom below the host RAM: the fork+copy-on-write of RDB/AOF saves can transiently duplicate mutated pages, and the allocator carries fragmentation. A common rule: set maxmemory well under physical RAM (e.g. ≤ ~50–60% if you snapshot under heavy writes).
maxmemory-policy
What to do when the cap is hit — one of the 8 below.
The 8 eviction policies — by candidate set (rows) × victim choice (columns).
 LRULFURandomTTL
all keysallkeys-lruallkeys-lfuallkeys-random—
keys with TTLvolatile-lruvolatile-lfuvolatile-randomvolatile-ttl

Plus noeviction (default): reject writes with an OOM error once full — reads and deletes still work. volatile-* policies only consider keys that have a TTL set; if none qualify they behave like noeviction.

Approximated LRU / LFU
Redis does not scan every key. It samples maxmemory-samples keys (default 5) and evicts the best victim from the sample — close to true LRU/LFU at a fraction of the cost. Raise samples for accuracy, lower for speed. LFU adds lfu-log-factor / lfu-decay-time.
Expiration ≠ eviction
Expiration removes keys past their TTL — lazily (on access) plus an active background sampler. Eviction is pressure-driven removal under maxmemory, governed by the policy. A key can be evicted before it ever expires.
Key memory metrics (from INFO memory / INFO stats).
MetricWatch for
evicted_keysAny sustained rise = you're over capacity; cache is shedding data.
mem_fragmentation_ratioused_memory_rss / used_memory. ≫1 = fragmentation; <1 = swapping (bad).

6 · Observability & debugging

INFO [section]
The dashboard in one command. Useful sections: server, clients, memory, persistence, stats, replication, cpu, keyspace, commandstats, latencystats.
SLOWLOG GET / RESET
Ring buffer of commands exceeding slowlog-log-slower-than µs. First stop for "why was that slow" — it times command execution, not network.
LATENCY DOCTOR / LATENCY HISTORY / LATENCY RESET
Built-in latency monitor — human-readable diagnosis of spikes (fork, expire cycles, slow commands).
MEMORY DOCTOR / MEMORY USAGE <key> / MEMORY STATS
Per-key footprint and a plain-language memory health report.
redis-cli diagnostic modes.
FlagDoes
--bigkeysScans for the largest key per type — find the keys blowing your memory/latency budget.
--hotkeysMost-accessed keys. Requires an LFU policy (reads the access counter).
--latency / --latency-historyContinuously samples PING round-trip latency.
--memkeys / --scanMemory-by-key sampling / safe cursor iteration of the keyspace.
MONITOR — debug only MONITOR streams every command the server runs. It is a heavy diagnostic that can cut throughput dramatically — never leave it running on production. Use SLOWLOG / LATENCY first.

7 · Security hardening

First principle Redis is meant to run on a trusted network. Never expose it directly to the internet. Most "Redis hacks" are simply an open port 6379 with no auth.
protected-mode
On by default. If no bind and no password are set, Redis only accepts loopback connections — a guardrail, not real security.
bind
Pin listeners to specific internal interfaces (e.g. bind 127.0.0.1 10.0.0.5). Don't bind 0.0.0.0 on a public NIC.
requirepass / AUTH
Set a strong password. Legacy single-secret auth; superseded by ACLs but still the floor.
ACLs (6.0+)
Per-user rules over commands, command categories, and key patterns (ACL SETUSER, acl.conf). Give apps least privilege instead of one shared password.
TLS (6.0+)
Native TLS for client and replication links (tls-port, certs). Encrypt anything crossing a network boundary.
Rename / disable dangerous commands
rename-command FLUSHALL "" (disable) or rename CONFIG, KEYS, DEBUG, SHUTDOWN to an unguessable string. With ACLs, prefer denying the command per-user.

Layer defenses: network isolation (VPC/security groups) + bind + auth/ACLs + TLS. No single control is sufficient on its own.
