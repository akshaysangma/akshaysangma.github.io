Making it fast — reading the plan, partitions, and caching

Diagnose a slow Spark job in three steps: read the query plan, fix the partition count, and cache what is worth keeping.

Track: Databricks / PySpark ~14 min Hands-on: Databricks + local Windows Builds on: Lessons 1 and 4
The win today After this lesson you will be able to look at a slow Spark pipeline and say why it is slow — not guess. You will use df.explain() to read the query plan and spot the shuffle (Exchange) that is costing you, control partition count with the right tool, know when cache() pays off and when it wastes memory, and see how partitionBy() on a write can turn a full table scan into a targeted file read. These are the moves data engineers reach for every day on the job.

Reading the query plan

In Lesson 1 you saw that Spark is lazy — it builds a recipe (the query plan) and runs nothing until an action fires it. df.explain() lets you read that recipe before the action runs. It is the first diagnostic tool you reach for when a pipeline feels slow. No job fires when you call it; it only prints.

Spark keeps two plan versions. The logical plan is a high-level description of what you asked for: filter this, join on that. The physical plan is Catalyst's decision about how to actually run it — which join algorithm, how many partitions to create, which filters can be pushed down toward the data source. df.explain() with no argument shows the physical plan. df.explain("formatted") gives a cleaner, annotated breakdown that is easier to read on a long plan.¹

How to read a physical plan Physical plans print bottom to top — bottom is where execution starts (reading data from source) and top is where it finishes (your result). Two node types tell you the most about cost:
  • Scan (e.g. FileScan parquet or Scan ExistingRDD) — reading data from storage. This is where partition pruning either kicks in or doesn't.
  • Exchange (e.g. Exchange hashpartitioning(customer_id, 200)) — a shuffle: rows are redistributed across executors over the network. Every Exchange costs time and disk I/O. Count the Exchanges — each one is a network shuffle you may be able to eliminate or reduce.

The number 200 inside hashpartitioning(customer_id, 200) is the shuffle partition count — how many partitions Spark writes after the shuffle. Its default comes from spark.sql.shuffle.partitions, which defaults to 200.⚑ That made sense for large multi-node clusters but is almost always too high for small datasets, creating 200 near-empty tasks with more scheduling overhead than real work.

A note on Adaptive Query Execution (AQE): Spark 3.x introduced AQE, which monitors actual partition sizes at runtime and can automatically coalesce tiny post-shuffle partitions, re-plan join strategies, and handle some data skew without you doing anything. In Databricks runtimes, AQE is on by default.⚑ That is good news — but AQE is a fallback, not a substitute for understanding the plan. Read the plan first; let AQE handle the residual.

See it: explain() on a real pipeline

Run this — Databricks or local Windows Databricks Free Edition: paste from orders_data = [...] onward into a notebook cell — skip the SparkSession lines, spark already exists.
Locally (Windows): save as perf.py in your activated venv and run python perf.py. Requires PySpark and Java 17+ with JAVA_HOME set. 
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, broadcast, sum as _sum

# --- Local only: on Databricks, spark already exists ---
spark = SparkSession.builder.appName("perf-demo").getOrCreate()

# ── Two tables: orders (fact) and regions (small lookup) ──────────────────
orders_data = [
    (1, "eu", 120.0), (2, "us",  80.0), (3, "eu", 200.0),
    (4, "us",  50.0), (5, "eu", 300.0), (6, "ap",  90.0),
]
regions_data = [("eu", "Europe"), ("us", "Americas"), ("ap", "Asia-Pacific")]

orders  = spark.createDataFrame(orders_data, ["order_id", "region", "amount"])
regions = spark.createDataFrame(regions_data, ["region", "region_name"])

# ── Step 1: read the plan before any action fires ─────────────────────────
pipeline = (
    orders
    .join(regions, on="region", how="inner")     # wide transform: shuffle
    .groupBy("region_name")
    .agg(_sum("amount").alias("total"))           # wide transform: shuffle
)

pipeline.explain()
# == Physical Plan ==
# AdaptiveSparkPlan isFinalPlan=false
# +- HashAggregate(keys=[region_name], functions=[sum(amount)])
#    +- Exchange hashpartitioning(region_name, 200)    <-- shuffle 2 (groupBy)
#       +- HashAggregate(keys=[region_name], functions=[partial_sum(amount)])
#          +- SortMergeJoin [region], [region], Inner
#             :- Sort [region ASC NULLS FIRST], false, 0
#             :  +- Exchange hashpartitioning(region, 200)  <-- shuffle 1a (join, left)
#             :     +- Scan ExistingRDD[order_id, region, amount]
#             +- Sort [region ASC NULLS FIRST], false, 0
#                +- Exchange hashpartitioning(region, 200)  <-- shuffle 1b (join, right)
#                   +- Scan ExistingRDD[region, region_name]
Read it from the bottom up Execution starts at the two Scan lines at the bottom — those are the raw data reads. Follow the arrows upward: each side gets its rows hashed and redistributed (Exchange) so that matching region keys land on the same executor. That is the SortMergeJoin's shuffle. The result is then shuffled again for groupBy. Three Exchange nodes for six rows. On terabyte-scale data, each Exchange is a multi-minute bottleneck. This is what you are diagnosing. 
# ── Step 2: eliminate the join shuffle — regions has 3 rows, broadcast it ─
pipeline_fast = (
    orders
    .join(broadcast(regions), on="region", how="inner")  # no join shuffle
    .groupBy("region_name")
    .agg(_sum("amount").alias("total"))
)

pipeline_fast.explain()
# == Physical Plan ==
# AdaptiveSparkPlan isFinalPlan=false
# +- HashAggregate(keys=[region_name], functions=[sum(amount)])
#    +- Exchange hashpartitioning(region_name, 200)    <-- only 1 shuffle now
#       +- HashAggregate(keys=[region_name], functions=[partial_sum(amount)])
#          +- Project [region_name, amount]
#             +- BroadcastHashJoin [region], [region], Inner, BuildRight
#                :- Scan ExistingRDD[order_id, region, amount]
#                +- BroadcastExchange HashedRelationBroadcastMode(...)
#                   +- Scan ExistingRDD[region, region_name]

# SortMergeJoin is gone. BroadcastHashJoin replaces it.
# Exchange count: 3 → 1. The groupBy shuffle is unavoidable — it stays.
# BroadcastExchange is not a network shuffle: it sends the small table once.

This connects directly to Lesson 4: broadcast() ships a copy of the small table to every executor so each executor can join locally. No rows need to travel across the network for the join. The remaining Exchange (for groupBy) is unavoidable because aggregating across all regions requires gathering partial sums from every executor.

Partitions — how many is right?

A Spark DataFrame is divided into partitions — slices of rows processed in parallel, one partition per task per executor (Lesson 4). Getting the partition count wrong is the most common self-inflicted performance problem. There are two ways to get it wrong.

The two partition-count failure modes, their symptoms, and the right fix for each.
ProblemSymptom you seeFix
Too few partitions Cluster cores sit idle; a handful of tasks run for minutes while the rest of the cluster waits. repartition(n) — full shuffle, even distribution, can increase or decrease count.
Too many partitions Thousands of tiny tasks; Spark spends more time scheduling tasks than running them. coalesce(n) — merges existing partitions locally, no full shuffle, can only decrease count.

Check your current partition count with df.rdd.getNumPartitions(). A rough rule of thumb: aim for each partition to hold between 100 MB and 200 MB of data. A cluster with 8 cores processing 4 GB might want 20–40 partitions — enough for each core to get real work without the overhead of scheduling thousands of empty tasks.

repartition() vs coalesce() — the one-line version Increasing count or need even distribution? Use repartition(n) — it does a full shuffle and balances the rows evenly. Expensive but correct.
Reducing count before a write? Use coalesce(n) — it merges partitions locally on each executor, no network transfer. Cheap but cannot increase the count and may produce slightly uneven partitions. 
# Check partition count — before and after a shuffle
print("Before shuffle:", orders.rdd.getNumPartitions())
# 2  (tiny in-memory DataFrame — very few partitions)

shuffled = orders.groupBy("region").agg(_sum("amount"))
print("After shuffle:", shuffled.rdd.getNumPartitions())
# 200  (spark.sql.shuffle.partitions default — too many for 6 rows)

# Option A: set the config for this session before the operation
spark.conf.set("spark.sql.shuffle.partitions", "8")
shuffled_small = orders.groupBy("region").agg(_sum("amount"))
print("After config change:", shuffled_small.rdd.getNumPartitions())
# 8

# Option B: coalesce an already-computed DataFrame (no full shuffle)
fewer = shuffled.coalesce(8)
print("After coalesce:", fewer.rdd.getNumPartitions())
# 8

Partitioning on write: partitionBy()

When you write a DataFrame to Parquet or Delta Lake, you can tell Spark to organize the output files into subdirectories by column value using partitionBy("col"). A later query that filters on that column skips every subdirectory that does not match — Spark never reads those files at all. This is partition pruning, and it turns a full table scan into a targeted read. 

# Write orders partitioned by region — creates subdirectories eu/, us/, ap/
# On Databricks, use a DBFS path like "/tmp/orders_by_region"
orders.write \
      .partitionBy("region") \
      .mode("overwrite") \
      .parquet("/tmp/orders_by_region")

# A later query on region="eu" skips the us/ and ap/ folders entirely
eu_orders = (spark.read
                  .parquet("/tmp/orders_by_region")
                  .filter(col("region") == "eu"))

eu_orders.explain()
# FileScan parquet [order_id, amount]
#   PartitionFilters: [isnotnull(region), (region = eu)]
#   ReadSchema: struct<order_id:bigint, amount:double>
# Only the eu/ partition directory is opened. us/ and ap/ are never touched.
High-cardinality partition columns — the small-files problem Partitioning on a column with millions of distinct values (e.g. user_id, order_id) creates millions of subdirectories, each with one or a few tiny files. Object storage (S3, ADLS) is slow at listing and opening millions of small files — far slower than reading a handful of large ones. The optimization backfires completely. Good partition columns have low to moderate cardinality and appear frequently in WHERE clauses: date, region, event_type, status. If you need to filter by a high-cardinality column efficiently, that is a job for Delta Lake's Z-ordering — covered in a later lesson.

Caching — pay the plan cost once, reuse many times

Because Spark is lazy (Lesson 1), calling an action re-runs the whole plan from scratch. Two actions on the same DataFrame = two full plan executions. If that plan includes an expensive join, aggregation, or large file scan, you pay twice — or N times if you call N actions.

df.cache() materializes the DataFrame after the first action that touches it and holds it in memory (spilling to disk if memory runs short). Every subsequent action reads from that materialized result instead of re-running the plan. The expensive work is paid once; all future reads are fast. 

# Without cache: the broadcast join and scan runs TWICE (once per collect)
enriched = orders.join(broadcast(regions), on="region", how="inner")

count_result  = enriched.groupBy("region_name").count().collect()  # runs join
total_result  = enriched.agg(_sum("amount")).collect()             # runs join again

# ── With cache: compute once, read twice ──────────────────────────────────
enriched_cached = (orders
                   .join(broadcast(regions), on="region", how="inner")
                   .cache())

count_result  = enriched_cached.groupBy("region_name").count().collect()  # runs + caches
total_result  = enriched_cached.agg(_sum("amount")).collect()             # reads cache

enriched_cached.unpersist()  # release memory — do not forget this
When cache() helps vs when it hurts Cache when: a DataFrame results from an expensive computation — a join, aggregation, or large scan — and will be consumed by two or more downstream actions.

Do not cache when:
  • The DataFrame feeds only a single action — caching adds a write step for zero reuse benefit.
  • The cached data does not fit in executor memory — it spills to local disk, and spill I/O may be no faster than re-running the plan from source.
  • The DataFrame is large and computed rarely — holding it in memory crowds out other jobs sharing the cluster.
Always call unpersist() when you are finished. Spark does not automatically evict a cached DataFrame until the session ends or memory pressure forces it — a leaked cache silently crowds out other work over time.

cache() is a shorthand for persist() with the default storage level, which is MEMORY_AND_DISK — it tries memory first and spills to local executor disk if needed. If you want explicit control (e.g. memory-only so that Spark drops the cache rather than spilling), use persist(StorageLevel.MEMORY_ONLY) from pyspark.storagelevel. For most pipeline work, plain cache() is the right default.

Data skew and AQE — brief

Every Exchange in your plan is a shuffle, and every shuffle redistributes rows by key. If your data has a very popular key — say, one customer accounts for 60% of all orders — then after the shuffle, one partition holds 60% of the rows and its task runs 60% of the job. The rest of the cluster sits idle waiting. This is data skew, and the job is only as fast as its slowest (largest) partition.

The two practical moves:

  • Broadcast join (Lesson 4 callback): if one side of the join is small, broadcasting it eliminates the shuffle entirely. Skew becomes irrelevant when there is no key-based redistribution to skew.
  • AQE: Spark 3.x's Adaptive Query Execution monitors partition sizes at runtime and can automatically coalesce small post-shuffle partitions, re-plan join strategies, and split skewed partitions. In modern Databricks runtimes, AQE is on by default.⚑ It handles moderate skew invisibly. For extreme skew, advanced techniques (key salting, explicit skew hints) are the next step — and a topic for further study once you have a real skewed dataset to work with.

Three anti-patterns to stop doing immediately

Easy to write, hard to notice at small scale, expensive at production scale.
Anti-patternWhy it hurtsThe fix
collect() or toPandas() on a large table Pulls every row to the driver process. The driver has a fixed RAM budget. At millions or billions of rows it crashes or freezes. All distributed parallelism is lost. Keep data in Spark. Only collect small results: counts, final aggregates, a handful of sample rows. If you genuinely need pandas, filter aggressively to a small slice first.
Calling an action inside a loop Each loop iteration triggers a new Spark job that re-runs the whole plan. N iterations = N full jobs. The job latency multiplies with N. Build your iteration logic as Spark transformations and call a single action at the end. If you need iteration with data, collect a small summary once outside the loop and iterate over that in Python.
repartition() without a reason repartition() is a full network shuffle. Adding it "just to be safe" or "to balance things" introduces exactly the Exchange cost you are trying to eliminate elsewhere. Use repartition() only when you need to increase the partition count or guarantee even distribution. Use coalesce() to reduce. If the default count is the problem, set spark.sql.shuffle.partitions instead.

Commit to an answer before revealing — retrieval is what builds memory.

You call df.explain() and see a node labelled Exchange hashpartitioning(customer_id, 200) in the plan. What does that node tell you?
A is correct. Exchange in the physical plan is the shuffle node — Spark must redistribute rows across executors over the network so that all rows sharing the same customer_id land on the same machine. The 200 is how many output partitions the shuffle will write (from spark.sql.shuffle.partitions). B confuses Exchange with a file-scan partition count. C describes a BroadcastExchange — a different node type that sends a small table to all executors without redistributing the large one. D is wrong because Spark is lazy: calling explain() prints the plan but fires no job.
You have a DataFrame with 400 shuffle partitions and need to reduce to 8 before a write step. Which call avoids a full network shuffle?
B is correct. coalesce(n) reduces partition count by collapsing existing partitions locally on each executor — no rows cross the network. It is the right call when you are reducing count and even balance matters less than avoiding shuffle cost. repartition(n) (A) always triggers a full shuffle and produces even partitions — correct when you need to increase count or guarantee balance, but overkill and expensive here. C describes what coalesce does, incorrectly attributed to repartition. D describes what repartition does, incorrectly attributed to coalesce.
Which scenario is the strongest reason to call cache() on a DataFrame?
B is correct. Caching pays off when an expensive computation is reused by multiple actions — here the join runs once, and three downstream actions all read from the cache instead of each re-running the plan. A and D describe DataFrames consumed by a single action: caching would add a write-to-cache step with zero reuse benefit, since the plan only runs once anyway. C describes a DataFrame that does not fit in memory — it will spill to executor-local disk, which may be no faster than simply re-computing from source and avoids tying up memory the cluster needs for other work.
