Three names for every table

Unity Catalog — how Databricks organizes, secures, and tracks every table you produce. The governance layer your pipelines write into.

Track: Databricks / PySpark ~13 min Hands-on: Databricks (UC) Builds on: Lessons 9–14
Why this, now Until now your tables have been loose Delta files in paths like /tmp/.... On a real Databricks platform, every table lives inside Unity Catalog (UC) — the governance layer that controls who can see what, tracks where data came from, and gives every table a proper name. It's ~11% of the DE Associate exam and the single biggest blind spot for anyone who learned on Free Edition alone. This lesson closes that gap.

The one idea: a three-level namespace

Classic Spark/Hive used two levels: database.table. Unity Catalog adds a level on top, so every data asset has a three-part name:¹ 

catalog . schema . table

# e.g.
SELECT * FROM main.sales.orders
                # ^catalog ^schema ^table

Think of it as a filing system: the catalog is the drawer (often one per environment or team — dev, prod, sales), the schema (a.k.a. database) is the folder, and the table is the document. The metastore is the cabinet that holds all the drawers — the top-level container for a Databricks account, usually one per region.¹

The hierarchy of securable objects metastore → catalog → schema → table / view / volume / function / model.
Permissions granted higher up can flow down, and you need traversal rights at each level to reach an object (more below).²

Access control: plain SQL GRANT / REVOKE

UC uses standard ANSI SQL GRANT/REVOKE — the same idea as any database, applied to the three-level objects.¹ The catch beginners miss: to read a table, a user needs traversal privileges on its parents too. 

# A user needs USE on the catalog AND schema to even "see into" them,
# then SELECT on the table itself:
GRANT USE CATALOG ON CATALOG sales      TO `data-analysts`;
GRANT USE SCHEMA  ON SCHEMA  sales.web  TO `data-analysts`;
GRANT SELECT      ON TABLE   sales.web.orders TO `data-analysts`;
The gotcha Granting SELECT on the table alone is not enough — without USE CATALOG and USE SCHEMA on the parents, the user can't traverse to it and the query fails. Also: UC grants target account-level groups, not individual workspace users, for anything maintainable.¹

Tables, views, and volumes

What lives inside a schema. Volumes are the UC answer to "where do my raw files go?"
ObjectWhat it is
Managed tableDelta table whose data + lifecycle UC manages in metastore-governed storage. The default — prefer it.
External tableTable whose data lives in a storage location you manage; UC governs access but not the files' lifecycle.
ViewA saved query. Useful for exposing a safe, column-filtered slice without granting the base table.
VolumeGoverned storage for non-tabular files (CSV/JSON/images) — the proper replacement for ad-hoc /tmp/ or DBFS paths you used earlier.

Lineage: where did this data come from?

UC automatically captures table- and column-level lineage — which tables (and which columns) fed each table, down to the notebook/job that produced it.³ For a data engineer this is gold: when a Gold number looks wrong, lineage shows you the exact Silver/Bronze inputs to check; when you want to change a column, it shows you everything downstream that would break. (A user needs BROWSE or SELECT to view a table's lineage.)

Rewriting your pipeline the production way

Everything you built in Lessons 11–14 used file paths. With UC, you write to named tables instead — the medallion layers become catalog/schema objects: 

# Instead of: df.write.format("delta").save("/tmp/bronze_orders")
spark.sql("CREATE CATALOG IF NOT EXISTS dev")
spark.sql("CREATE SCHEMA  IF NOT EXISTS dev.taxi")

bronze.write.saveAsTable("dev.taxi.bronze_trips")      # managed Delta in UC
silver.write.mode("overwrite").saveAsTable("dev.taxi.silver_trips")
gold.write.mode("overwrite").saveAsTable("dev.taxi.gold_revenue_by_zone")

# query by three-level name
spark.table("dev.taxi.gold_revenue_by_zone").show()
Try it — Databricks (UC is on by default) In a Free Edition notebook, run the SQL/PySpark above with a tiny DataFrame, then in the left sidebar open Catalog to see dev.taxi.* appear. Click a table → Lineage tab to see the graph build as you create silver from bronze.
Free Edition honesty Free Edition runs on Unity Catalog, so the three-level namespace, managed tables, volumes, and lineage all work. But it's a single-user environment — multi-group GRANT/REVOKE, account-level groups, row/column masking, and Delta Sharing are limited or not exposed. Read those in the docs for the exam; you can't fully exercise them here.²

Check yourself

A teammate has SELECT on sales.web.orders but their query fails with a permission error. What is the most likely fix?
In Unity Catalog you must be able to traverse to an object: USE CATALOG on the catalog and USE SCHEMA on the schema, in addition to SELECT on the table. Granting the table privilege alone is the classic mistake.
In the name prod.finance.invoices, what does the middle part finance identify?
The three-level name is catalog.schema.table, so finance is the schema (also called a database) — the folder grouping tables inside the prod catalog.
A Gold metric looks wrong and you need to find which upstream tables feed it. Which Unity Catalog feature helps most directly?
UC's automatic lineage shows exactly which tables and columns feed a given table — the fastest way to trace a bad number back to its Silver/Bronze inputs, or to assess what a change would break downstream.
