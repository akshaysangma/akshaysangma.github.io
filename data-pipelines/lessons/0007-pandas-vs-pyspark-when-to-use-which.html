Pick the right tool before you write a line

pandas or PySpark? A one-question decision rule, the symmetry of operations, and the danger of bridging them wrong.

Track: Python / pandas Track: Databricks / PySpark ~12 min Hands-on: Databricks + local Windows Builds on: Lessons 1, 3 & 6
The win today Lesson 6 ended with a tension: pandas is fast and familiar, but it loads everything into RAM on one machine. PySpark is distributed, but it carries startup cost and a bigger API surface. By the end of this lesson you will have a one-question decision rule, a side-by-side demo showing the operations are nearly identical, and the vocabulary to explain why in an interview without bluffing. This lesson is more judgment than new syntax — and that is exactly what interviewers test.

The decision rule in one sentence

If the data fits comfortably in RAM on one machine, use pandas. If it is large, distributed, or already lives in a cloud lakehouse, use PySpark.

Decision flow — four questions 1. Does the data fit in RAM?
A modern laptop has 8–32 GB of RAM. As a rule of thumb, datasets under 1–2 GB work fine in pandas. Larger than that, start thinking Spark — even a single 5 GB CSV will make pandas choke on a standard machine.

2. Where does the data live?
Data already in a Delta table or cloud storage (S3, ADLS) on Databricks belongs in PySpark. Pulling it into pandas means calling .toPandas() first — which drags the whole table to one machine. More on that danger below.

3. Is a cluster already running?
Inside a Databricks notebook, spark already exists and a cluster is attached — zero extra startup cost. For a small CSV on your Windows laptop where you'd spin up a local Spark context just to read 500 rows, pandas wins instantly; Spark can take 10–30 seconds just to initialise.

4. What does your team or platform expect?
If your org runs on Databricks, PySpark is the default for anything production. pandas still appears for small utility scripts, quick EDA, or working with a small aggregated result you collected from Spark.

The rule is about fitness for purpose, not which library is "better." pandas built the data-science Python ecosystem. PySpark scales it to a cluster. They complement each other — and as you are about to see, the operations are nearly the same.

Same concept, different scale

Every operation you learned in pandas maps almost directly onto PySpark. Read, filter, add a column, group, join, write — the concepts are identical. The API is just a little more explicit so Spark can build a distributed plan.¹

Operation-by-operation mapping. Full pandas docs: pandas User Guide. Full PySpark API: PySpark API Reference.
OperationpandasPySpark
Read CSV pd.read_csv("file.csv") spark.read.csv("path", header=True, inferSchema=True)

Add / derive column df.assign(vat=df.amount * 1.08) df.withColumn("vat", col("amount") * 1.08)
Group + aggregate df.groupby("region")["amount"].sum() df.groupBy("region").agg(F.sum("amount"))

Note on PySpark's write.csv(): it writes a directory of part files, not a single CSV — one file per partition. In production pipelines on Databricks you will usually write to a Delta table (df.write.format("delta").save("path")) rather than raw CSV.

Three behavioral differences that will trip you up

1. Eager vs lazy — the fundamental divide from Lesson 1. Every pandas operation runs immediately and returns a concrete DataFrame in memory. Every PySpark transformation adds a step to a plan and returns instantly — nothing moves until an action fires. In practice this means an error in a PySpark filter may not surface until show() runs, because that is when the job actually executes.

2. No index in Spark. pandas DataFrames carry an integer index; you can reset it, set it to a column, use .loc[] and .iloc[]. Spark DataFrames have no index. Row position is not meaningful — data is split across machines. If you need a stable row number, you have to compute it explicitly with F.monotonically_increasing_id(), and even that only guarantees uniqueness, not sequential order.

3. Row order is not guaranteed. pandas preserves insertion order by default. Spark makes no ordering guarantee unless you explicitly call orderBy(), because the data is partitioned across executors and results can arrive in any sequence. This catches people out when they expect the "first" row of a Spark result to be the first row of the source file — it might not be.

The order gotcha in practice If you collect or show a PySpark result, the row order may differ between runs — that is by design, not a bug. Parallelism means no single machine controls the sequence. If order matters (reports, ranked results, incremental IDs), always add an explicit orderBy() before your final action. Never assume order from position.

toPandas() and collect() — the bridge, and the danger

Both .toPandas() and .collect() are actions (Lesson 1). They trigger the full Spark job and then pull the results to the driver node — the single machine running your Python process or Databricks notebook kernel.

  • .collect() — returns a Python list of Row objects on the driver.
  • .toPandas() — converts the Spark result into a pandas DataFrame on the driver.

When are they fine? When Spark has already reduced the data to something small — an aggregated summary, a lookup table, a result set of a few hundred rows. The standard pattern:

# ✓ Safe: Spark filters and aggregates FIRST, then you collect the small result
summary = (
    df.filter(col("region") == "eu")
      .groupBy("product")
      .agg(F.sum("amount").alias("total"))
)
# summary might be 5 rows — fine to pull to the driver
pdf = summary.toPandas()   # action; result is tiny, driver RAM is safe
print(pdf)                 # now work in pandas as normal
The danger: pulling a huge table to the driver 
# ✗ DANGEROUS: toPandas() on a raw, unfiltered 100 GB table
pdf = raw_df.toPandas()   # tries to load 100 GB into one machine's RAM
# → driver exhausts memory; notebook or job crashes
.toPandas() and .collect() do not stream or sample — they pull every row. On a table with billions of rows this will exhaust driver RAM and crash the process. The rule: filter and aggregate in Spark first, then pull the small result.

A middle path: the Pandas API on Spark

If you have existing pandas code you want to run on a cluster without rewriting every line, PySpark ships a compatibility layer called the Pandas API on Spark: 

import pyspark.pandas as ps          # available in PySpark 3.2+ / Databricks

psdf = ps.read_csv("large_file.csv") # pandas-style read call …
psdf = psdf[psdf["amount"] > 100]   # … familiar pandas syntax …
psdf.groupby("region")["amount"].sum() # … but Spark executes it all

You write pandas-style code; Spark distributes the work underneath.¹ This is useful for migrating existing notebooks or for teams making the transition. It has performance trade-offs — some operations are not as well optimised as native PySpark, and the mixed indexing model can surprise you. Prefer native PySpark (df.filter(col(...)) style) when building pipelines from scratch. Know this middle path exists — it will come up in interviews and in legacy codebases.

Hands-on: same task, side by side

Filter sales above £100 and sum by region — done in both libraries so the symmetry is visible and the difference in timing is felt.

Run this — Databricks or local Windows On Databricks Free Edition: paste each block into a separate notebook cell. In the PySpark cell, skip the from pyspark.sql import SparkSession import and the SparkSession.builder… line — spark already exists.
Locally (Windows): save as tool_choice.py inside your activated venv and run python tool_choice.py. Requires pip install pyspark pandas and Java 17+ with JAVA_HOME set. See the environment-setup reference for the full Windows walkthrough. 
## ── pandas version ─────────────────────────────────────────────────────
import pandas as pd

data = [
    ("alice", "eu",  50), ("bob",   "eu", 200),
    ("carol", "us", 150), ("dan",   "us",  80),
    ("eve",   "eu", 300), ("grace", "us", 120),
]
df_pd = pd.DataFrame(data, columns=["customer", "region", "amount"])

result_pd = (
    df_pd[df_pd["amount"] > 100]          # filter — runs immediately (eager)
    .groupby("region", as_index=False)
    .agg(total=("amount", "sum"))          # aggregate — runs immediately
)
print(result_pd)
#   region  total
# 0     eu    500
# 1     us    270
## ── PySpark version ────────────────────────────────────────────────────
from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from pyspark.sql.functions import col

# On Databricks: remove the SparkSession lines — spark already exists
spark = SparkSession.builder.appName("tool-choice").getOrCreate()

data = [
    ("alice", "eu",  50), ("bob",   "eu", 200),
    ("carol", "us", 150), ("dan",   "us",  80),
    ("eve",   "eu", 300), ("grace", "us", 120),
]
df_sp = spark.createDataFrame(data, ["customer", "region", "amount"])

result_sp = (
    df_sp.filter(col("amount") > 100)        # filter — lazy, plan only
         .groupBy("region")
         .agg(F.sum("amount").alias("total")) # aggregate — still lazy
)
result_sp.show()  # action — runs the job now; row order may vary without orderBy()
# +------+-----+
# |region|total|
# +------+-----+
# |    eu|  500|
# |    us|  270|
# +------+-----+
What to notice The task is identical — filter, then group-sum. The pandas version runs each step immediately and produces a result in memory. The PySpark version builds a plan across two lazy transformations and only executes when .show() is called. Same logic, same output, different execution model. The PySpark version would handle a billion rows on a cluster without any code change.

The numbers: alice (eu, 50) and dan (us, 80) are filtered out. Remaining eu: 200 + 300 = 500. Remaining us: 150 + 120 = 270. The total column name comes from .alias("total") in PySpark and from the named aggregation total=("amount", "sum") in pandas — two different syntaxes, same intent.

Check yourself

Commit to an answer before revealing — retrieval is what builds memory.

Your manager emails you a 250 MB sales CSV. You will filter two columns, add a derived field, and paste the summary into a slide deck. Which option gives the right tool and the right reason?
A is correct. 250 MB sits comfortably in RAM — no cluster is needed and pandas loads and processes it instantly. B is wrong on the facts: pandas handles derived columns natively via assign() (or direct assignment). C overstates Databricks: it provides a PySpark environment but you are always free to use pandas for small in-memory work — it runs inside the notebook's Python kernel just fine. D picks the right tool (pandas) but for the wrong reason: Spark startup overhead is a real consideration, but it does not make Spark "wrong for any task" — at scale, Spark is the only practical option. Only A is correct both in tool choice and reasoning.
A colleague suggests calling .toPandas() on a raw PySpark DataFrame that holds 40 billion rows. Which statement correctly describes what happens?
C is correct. .toPandas() is an action — it runs the full Spark job and then moves every resulting row to the driver machine's RAM. There is no streaming, no sampling, and no deduplication pass. On 40 billion rows this will exhaust the driver's memory and crash the process. A contradicts the definition of an action — actions are never lazy; they force execution and materialise results. B describes what df.sample(0.001) or df.limit(1000) would do if you called them before .toPandas() — not what .toPandas() itself does. D is invented: .toPandas() runs the plan once and collects the result; it does not replay or duplicate anything.
Which statement correctly describes how pandas and PySpark differ in execution?
A is correct. pandas is eager — every line executes immediately and returns a concrete object in memory. PySpark is lazy — transformations like filter, withColumn, and groupBy build a plan and return instantly without touching data; only an action (show(), count(), collect(), write, toPandas()) triggers the actual distributed job. B reverses the models exactly. C and D are both wrong: pandas has no plan-building step — each pandas call runs immediately and produces a result in memory, regardless of what follows it.
