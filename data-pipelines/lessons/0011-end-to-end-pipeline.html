Your first end-to-end pipeline

Raw CSV files → Bronze → Silver → Gold. Every concept from Lessons 1–10 snaps together in one working notebook.

Track: Databricks / PySpark ~17 min Hands-on: Databricks Free Edition (primary) + local PySpark Capstone: integrates Lessons 1–10
The big win Ten lessons in, you have every ingredient: the lazy execution model (Lesson 1), explicit-schema reads (Lesson 2), core transformations (Lesson 3), broadcast joins (Lesson 4), Delta Lake fundamentals (Lesson 9), and the medallion pattern (Lesson 10). Today you snap those together into one complete, working pipeline — raw CSV in, Gold analytics table out. By the end you will have code you could put in a portfolio and a solid mental model of how every production data pipeline is structured.

The scenario

You work at a small e-commerce company. Every morning, a CSV of new order records lands in cloud storage — think of it as the upstream system dumping whatever it recorded, warts and all. A separate, stable reference table holds customer profiles. Your job: build a pipeline that takes those raw files, cleans them, enriches them with customer data, and produces a Gold table showing total revenue and order count per customer region.

All data below is synthetic. No real names, IDs, or contact information.

The source data

Two source datasets for this pipeline. orders arrives daily and has realistic data-quality issues; customers is a small, stable reference — a natural broadcast target from Lesson 4.
DatasetKey columnsIssues to clean in Silver
orders (raw CSV) order_id, customer_id, product, qty, unit_price, order_ts, status Duplicate rows (upstream retry sent the same order twice); rows with a null customer_id (orphaned records); cancelled orders to exclude from revenue
customers (reference) customer_id, name, region Stable, small, broadcast-safe — three regions: eu, us, apac

The flow at a glance

  raw CSV (orders, daily batch)
        │
        ▼  Step 1 — INGEST  [Lesson 2: explicit schema, metadata columns]
  ┌─────────────────────────────┐
  │       BRONZE  layer         │  raw landing zone — append-only, untouched
  └─────────────────────────────┘
        │
        ▼  Step 2 — CLEAN   [Lessons 3 & 4: dropDuplicates, filter, broadcast join]
  ┌─────────────────────────────┐

Environment setup

Databricks Free Edition (primary — recommended) Open a Python notebook. spark already exists; Delta is the default format. You only need the imports. Skip every line marked "local only" below.
Local Windows (secondary) In your activated venv, install the Delta library first — it is not included with plain PySpark:
pip install delta-spark
Then use the SparkSession setup below marked "local only". Requires Java 17+ with JAVA_HOME set (see the environment-setup reference). Delta tables will be written to the local filesystem at the path you specify in BASE. 
# ── Imports (both environments) ──────────────────────────────────────────
from pyspark.sql import SparkSession
from pyspark.sql.types import (
    StructType, StructField,
    StringType, IntegerType, DoubleType, TimestampType
)
from pyspark.sql.functions import (
    col, lit, current_timestamp, broadcast, to_timestamp
)
import pyspark.sql.functions as F

# ── LOCAL ONLY: on Databricks, delete everything below until BASE ────────
from delta import configure_spark_with_delta_pip

spark = configure_spark_with_delta_pip(
    SparkSession.builder.appName("e2e-pipeline")
).getOrCreate()
# ── END local-only block ─────────────────────────────────────────────────

# ── Where to write Delta tables ──────────────────────────────────────────
# Databricks: use a path inside your workspace, e.g. /tmp/e2e_pipeline
# Local Windows: use a relative path or C:/tmp/e2e_pipeline
BASE = "/tmp/e2e_pipeline"          # change this for your environment

On Databricks, /tmp/ is driver-local storage — fast and free for learning. In production you would write to a Unity Catalog managed table or a Volume path. On local Windows, use a path like C:/tmp/e2e_pipeline (forward slashes only in PySpark strings — see Lesson 2's Windows path callout).

Step 1 — Ingest: CSV → Bronze Delta table

Bronze is a raw landing zone: you store exactly what arrived, with no business logic applied. The only additions are audit metadata — a load timestamp and the source filename — so you can always trace a row back to when and where it came from. As covered in Lesson 2, you always supply an explicit schema rather than inferSchema=True: it skips the double-scan, prevents type guessing, and catches upstream format changes at the read rather than three steps later. 

# ── Synthetic raw orders (simulates what a real CSV read would produce) ──
# In a real pipeline you would instead do:
#   raw = spark.read.csv("path/to/orders_20240115.csv",
#                        header=True, schema=orders_schema)
# Here we use createDataFrame so the lesson runs without uploading a file.

orders_schema = StructType([
    StructField("order_id",    IntegerType(), True),
    StructField("customer_id", StringType(),  True),
    StructField("product",     StringType(),  True),
    StructField("qty",         IntegerType(), True),
    StructField("unit_price",  DoubleType(),  True),
    StructField("order_ts",    StringType(),  True),  # arrives as string in CSV
    StructField("status",      StringType(),  True),
])

raw_rows = [
    (1001, "C001", "laptop",   1,  999.99, "2024-01-15 10:32:00", "completed"),
    (1002, "C002", "headset",  2,   79.99, "2024-01-15 11:05:00", "completed"),
    (1003, "C001", "mouse",    1,   29.99, "2024-01-16 09:18:00", "completed"),
    (1004, "C003", "keyboard", 1,  149.99, "2024-01-16 14:22:00", "cancelled"),
    (1005, "C002", "laptop",   1,  999.99, "2024-01-17 16:45:00", "completed"),
    (1001, "C001", "laptop",   1,  999.99, "2024-01-15 10:32:00", "completed"),  # ← duplicate
    (1006,   None, "tablet",   1,  399.99, "2024-01-17 18:00:00", "completed"),  # ← null customer_id
]

raw = spark.createDataFrame(raw_rows, schema=orders_schema)

# ── Add ingestion metadata ────────────────────────────────────────────────
# current_timestamp() → the moment this pipeline run executed (lazy — Lesson 1)
# lit("orders_20240115.csv") simulates input_file_name(); use the real function
# when reading from spark.read.csv() in a real pipeline.
bronze = (
    raw
    .withColumn("_load_ts",      current_timestamp())
    .withColumn("_source_file",  lit("orders_20240115.csv"))
)

# ── Write to Bronze Delta table (append — preserve every historical batch) 
# This is the first ACTION in the pipeline — all transformations above run NOW.
(bronze
 .write
 .format("delta")
 .mode("append")
 .save(f"{BASE}/bronze"))

print("Bronze written.")
bronze.printSchema()
# root
#  |-- order_id: integer (nullable = true)
#  |-- customer_id: string (nullable = true)
#  |-- product: string (nullable = true)
#  |-- qty: integer (nullable = true)
#  |-- unit_price: double (nullable = true)
#  |-- order_ts: string (nullable = true)
#  |-- status: string (nullable = true)
#  |-- _load_ts: timestamp (nullable = false)
#  |-- _source_file: string (nullable = false)
Why append mode for Bronze? Bronze is a historical record. Every batch that ever arrived should be queryable — if you reprocess or discover a bug you want to be able to go back and replay from the raw source. mode("append") adds new rows without touching existing ones. Silver and Gold use overwrite because they are derived views you rebuild from Bronze; only Bronze needs the full history. (Lesson 10 covers this trade-off in detail.)

Step 2 — Clean: Bronze → Silver Delta table

Silver applies business rules to produce a validated, enriched dataset. Three things happen here: (1) deduplication — identical rows that arrived twice are collapsed to one; (2) filtering — rows that cannot be used (no customer, cancelled status) are removed; (3) enrichment — a broadcast join brings in the customer reference data, adding region. The broadcast join hint (from Lesson 4) is important: the customer table is tiny, so we ship it to every executor instead of paying for a network shuffle.

Silver also casts the order_ts column from the string that arrived in the CSV into a proper TimestampType — a classic Silver responsibility covered in Lesson 3's withColumn section. 

# ── Customers reference table (small → broadcast target) ─────────────────
customers_rows = [
    ("C001", "Alex Hayes",  "eu"),
    ("C002", "Sam Nguyen",  "us"),
    ("C003", "Jordan Wu",   "eu"),
    ("C004", "Pat Reyes",   "apac"),
]
customers = spark.createDataFrame(customers_rows, ["customer_id", "name", "region"])

# ── Read Bronze ───────────────────────────────────────────────────────────
bronze_df = spark.read.format("delta").load(f"{BASE}/bronze")

# ── Clean and enrich ─────────────────────────────────────────────────────
silver = (
    bronze_df

    # 1. Deduplicate on business key (Lesson 3: dropDuplicates)
    .dropDuplicates(["order_id", "customer_id", "order_ts"])

    # 2. Filter out bad rows (Lesson 3: filter / where)
    .filter(col("customer_id").isNotNull())       # drop orphaned rows
    .filter(col("status") == "completed")         # revenue-eligible only

    # 3. Cast order_ts from string → proper timestamp (Lesson 3: withColumn)
    .withColumn("order_ts", to_timestamp(col("order_ts"), "yyyy-MM-dd HH:mm:ss"))

    # 4. Compute line-item revenue
    .withColumn("revenue", col("qty") * col("unit_price"))

    # 5. Broadcast join: customers is tiny — no shuffle (Lesson 4)
    .join(broadcast(customers), on="customer_id", how="inner")

    # 6. Keep only the columns Silver needs; drop the raw metadata
    .select(
        "order_id", "customer_id", "name", "region",
        "product", "qty", "unit_price", "revenue",
        "order_ts", "status"
    )
)

# ── Write Silver (overwrite — rebuilt fresh from Bronze each run) ─────────
(silver
 .write
 .format("delta")
 .mode("overwrite")
 .save(f"{BASE}/silver"))

print("Silver written.")
silver.show()
# +--------+-----------+----------+------+---------+---+----------+-------+-------------------+---------+
# |order_id|customer_id|      name|region|  product|qty|unit_price|revenue|           order_ts|   status|
# +--------+-----------+----------+------+---------+---+----------+-------+-------------------+---------+
# |    1001|       C001|Alex Hayes|    eu|   laptop|  1|    999.99| 999.99|2024-01-15 10:32:00|completed|
# |    1002|       C002| Sam Nguyen|    us|  headset|  2|     79.99| 159.98|2024-01-15 11:05:00|completed|
# |    1003|       C001|Alex Hayes|    eu|    mouse|  1|     29.99|  29.99|2024-01-16 09:18:00|completed|
# |    1005|       C002| Sam Nguyen|    us|   laptop|  1|    999.99| 999.99|2024-01-17 16:45:00|completed|
# +--------+-----------+----------+------+---------+---+----------+-------+-------------------+---------+
Notice what Silver removed Four rows survive from the original seven. The duplicate (order 1001 sent twice) is collapsed to one. The null-customer row (order 1006) is dropped. The cancelled order (order 1004) is filtered out. Silver's job is exactly this: a dataset that downstream consumers can trust — no garbage, no duplicates, no ambiguous keys.

Step 3 — Aggregate: Silver → Gold Delta table

Gold answers a specific business question. It is not a cleaned copy of Silver — it is a pre-computed, narrow result shaped for a single purpose: here, total revenue and order count per customer region. This is where groupBy().agg() from Lesson 3 pays off. Gold tables tend to be small and fast to query — that is the point. 

# ── Read Silver ───────────────────────────────────────────────────────────
silver_df = spark.read.format("delta").load(f"{BASE}/silver")

# ── Aggregate to Gold (Lesson 3: groupBy + agg) ───────────────────────────
gold = (
    silver_df
    .groupBy("region")
    .agg(
        F.count("order_id").alias("order_count"),
        F.round(F.sum("revenue"), 2).alias("total_revenue"),
        F.round(F.avg("revenue"), 2).alias("avg_order_revenue"),
    )
    .orderBy(col("total_revenue").desc())
)

# ── Write Gold (overwrite — replace the whole table each run) ────────────
(gold
 .write
 .format("delta")
 .mode("overwrite")
 .save(f"{BASE}/gold"))

print("Gold written.")

Step 4 — Verify: read Gold and check results

The final step is reading Gold back and confirming the numbers make sense. This is also where you validate idempotency: if you re-run the pipeline on the same input file, Silver and Gold should produce exactly the same rows — because Silver used overwrite, not append. 

# ── Read Gold and inspect ─────────────────────────────────────────────────
gold_df = spark.read.format("delta").load(f"{BASE}/gold")
gold_df.show()
# +------+-----------+-------------+-----------------+
# |region|order_count|total_revenue|avg_order_revenue|
# +------+-----------+-------------+-----------------+
# |    eu|          2|      1029.98|           514.99|
# |    us|          2|      1159.97|           579.99|
# +------+-----------+-------------+-----------------+

print("Gold row count:", gold_df.count())
# Gold row count: 2

# ── Sanity check: verify revenue ties out from Silver ─────────────────────
silver_df = spark.read.format("delta").load(f"{BASE}/silver")
print("Silver total revenue:", silver_df.agg(F.sum("revenue")).collect()[0][0])
# Silver total revenue: 2189.95

# Should equal Gold total_revenue summed across regions:
print("Gold total revenue:  ", gold_df.agg(F.sum("total_revenue")).collect()[0][0])
# Gold total revenue:   2189.95  ← matches ✓
Idempotency: overwrite vs append Re-run the pipeline on the same file. Silver and Gold produce identical results — that is idempotency. Bronze uses append, so it will grow (you will get duplicate Bronze rows representing multiple loads of the same file). In production you guard against this with a MERGE statement that only inserts rows whose order_id does not already exist in Bronze. That is a Delta-specific operation, and it will be the first topic in Lesson 12.

The lazy-execution thread connecting all four steps

You wrote four cells. Recall from Lesson 1: every transformation is a recipe step — nothing runs. The jobs only fired at the actions:

Three write actions in the pipeline. Each one triggers a full plan evaluation for that layer's recipe.
CellAction that triggered the jobWhat Catalyst optimized before running
Bronze write .write.format("delta").mode("append").save(…) Schema application, metadata columns — one narrow stage
Silver write .write.format("delta").mode("overwrite").save(…) Filter pushdown (removes cancelled before the join), BroadcastHashJoin instead of SortMergeJoin
Gold write .write.format("delta").mode("overwrite").save(…) Reads only the region and revenue columns from Silver (column pruning)

Call silver.explain() before the Silver write to see Catalyst's physical plan — you will spot the BroadcastHashJoin confirming that the customers shuffle was eliminated.

This is ELT, not ETL — and it is medallion in practice In a traditional ETL pipeline you transform data before loading it. Here you load first (Bronze is raw) and transform in-place at Silver and Gold. That is ELT, and it is the pattern that works naturally with Delta Lake: durable checkpoints at each layer mean any step can be re-run or rolled back without going back to the source. This is exactly what Lesson 10 described in the abstract — you have now built the concrete version.

Check yourself

Commit to an answer before revealing — retrieval is what builds memory.

You land raw CSV files into the lakehouse. Which sequence correctly represents how data flows through the medallion layers, from first-written to last-written?
B is correct. Bronze is always the first layer — it is the raw landing zone where data arrives untouched. Silver cleans, deduplicates, casts types, and enriches that raw data. Gold is the final aggregated or shaped output built for a specific business question. The other options swap layer responsibilities in ways that would either skip cleaning (A, C) or put business metrics before cleaned data exists (D).
The pipeline enriches orders with customer region via a broadcast join. At which medallion layer does this join belong?
C is correct. Enrichment joins belong in Silver. Bronze must stay raw — joining in Bronze contaminates the landing zone with business logic and makes it harder to reprocess if the reference data changes. Gold is too late: you want region available before aggregation so you can group by it. D is wrong: joins are a normal Silver transformation, not an outlier. Joining in Silver — after deduplication and type-casting — also means the broadcast sends only clean, correctly-typed keys to every executor.
The pipeline writes to a Delta table after each of the three layers. What is the primary benefit of these intermediate writes?
D is correct. The core benefit is durability and independence: each layer is a stable, versioned Delta table you can query directly, re-run without touching other layers, and roll back with Delta's time-travel feature (Lesson 9). A is actually a downside rather than a benefit — Catalyst optimizes within a layer's plan, not across write boundaries. B is wrong: deduplication is done explicitly with dropDuplicates() in Silver, not by the write itself. C is wrong: schema propagation is not automatic across separate Delta tables.
