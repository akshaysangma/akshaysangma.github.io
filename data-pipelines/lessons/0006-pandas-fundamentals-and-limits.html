DataFrame and Series: what they actually are

A pandas DataFrame is a 2-D table: rows × named columns. Each column is a Series — a 1-D sequence with an index. And each Series wraps a NumPy ndarray underneath.¹

In Lesson 5 you saw that NumPy arrays operate at C speed with typed, contiguous memory. That is why df["price"] * 1.08 is fast: pandas hands the multiply straight to NumPy's compiled layer — no Python for loop. The dtypes attribute shows you which NumPy dtype backs each column: 

import pandas as pd

df = pd.DataFrame({
    "product": ["Widget", "Gadget", "Widget"],
    "units":   [120, 40, 95],
    "price":   [10.0, 25.0, 10.0],
})

print(df.dtypes)
# product     object   ← Python strings; no NumPy speed here
# units        int64   ← NumPy int64 — arithmetic is fast
# price      float64   ← NumPy float64 — arithmetic is fast
# dtype: object

# Confirm the column is a genuine NumPy array underneath:
print(df["units"].to_numpy())
# [120  40  95]   ← np.ndarray, not a Python list

The object dtype stores a Python object reference per element — strings, mixed types, anything that does not fit a numeric NumPy type. Arithmetic on object columns falls back to Python-speed loops. Arithmetic on int64 / float64 stays in NumPy.

Getting data in and out

Three IO functions cover most of what you will encounter in a data engineering context:

Core pandas IO. Full reference: pandas User Guide → IO tools.
FunctionWhat it doesWhen to use it
pd.read_csv(path) Reads a CSV file; infers dtypes automatically. Quick ingestion, exploration, files from spreadsheet tools.
df.to_csv(path, index=False) Writes the DataFrame to CSV. index=False omits the row-number column. Sharing results humans can open in Excel.
pd.read_parquet(path) Reads a Parquet file. Needs pip install pyarrow. Any time data comes from or goes to a data platform (Spark, Databricks, Delta).
Why Parquet matters to you specifically Parquet is the lingua franca of data engineering. It is columnar (scanning one column is cheap), compressed (much smaller than CSV), and schema-carrying (dtypes are stored in the file, not guessed on read). Spark and Databricks read and write Parquet natively. Learning to read it with pandas now means the files your Spark pipelines produce will never be mysterious.

Selecting data: [], .loc, .iloc, boolean masks

# Single column → Series; multiple columns → DataFrame (double brackets)
prices  = df["price"]                 # Series
subset  = df[["product", "units"]]   # DataFrame — note the inner list

# .loc — label-based. Row selector is an index label (or list/slice of labels).
first_product = df.loc[0, "product"]  # "Widget" — row label 0, column name "product"
top_two       = df.loc[0:1]           # rows labelled 0 and 1 — INCLUSIVE upper bound

# .iloc — integer-position-based (0-indexed). Slice upper bound is EXCLUSIVE.
first_row     = df.iloc[0]            # row at position 0 (first row)
top_two_pos   = df.iloc[0:2]          # positions 0 and 1 (position 2 excluded)

# Boolean filter — the pattern you will use constantly
big_orders    = df[df["units"] > 50]
widget_big    = df[(df["product"] == "Widget") & (df["units"] > 50)]
.loc vs .iloc — the one fact to burn in .loc uses labels (index values, column names). .iloc uses integer positions (0, 1, 2 …). When your index is the default RangeIndex (0, 1, 2 …) they look identical — which is exactly why the difference hides until you filter, sort, or reset an index and suddenly .loc[2] returns the wrong row. Default to .loc for most work; reach for .iloc only when you genuinely need positional access.

Transforming data: new columns, cleaning, casting

# New column — direct assignment (mutates df in place)
df["revenue"] = df["units"] * df["price"]   # vectorized: NumPy does the multiply

# .assign() — returns a NEW DataFrame; original unchanged (pipeline-friendly)
df2 = df.assign(revenue=df["units"] * df["price"])

# .apply() — arbitrary Python function across rows (axis=1) or elements
df["tier"] = df["product"].apply(lambda p: "cheap" if p == "Widget" else "premium")
# ↑ Works, but .apply() is a Python for-loop in disguise. Slow on big frames.

# Same logic, vectorized: np.where is ~10–100× faster for scalar conditionals
import numpy as np
df["tier"] = np.where(df["product"] == "Widget", "cheap", "premium")

# Other transforms you will reach for often:
df["units"]  = df["units"].astype(float)        # cast to a different dtype
df = df.rename(columns={"units": "qty"})         # rename a column
df = df.dropna(subset=["price"])                 # drop rows with NaN in "price"
df = df.fillna({"tier": "unknown"})              # fill NaN values per column
.apply() is the slow path .apply() exits the NumPy fast lane and calls a Python function once per element or row. The rule: if arithmetic, np.where, .str. string accessors, or .dt. datetime accessors can express the same logic, use them. Reserve .apply() for logic that is genuinely impossible to vectorize.

Aggregating, joining, and sorting

These three operations will feel almost familiar when you arrive at PySpark — the API spellings differ slightly, but the concepts are the same. 

# groupby + named aggregation (pandas ≥ 0.25 named-agg syntax)
summary = df.groupby("product").agg(
    total_qty   =("qty",   "sum"),
    avg_price   =("price", "mean"),
    order_count =("qty",   "count"),
)

# merge — SQL-style join
costs    = pd.DataFrame({"product": ["Widget", "Gadget"], "cost": [4.0, 12.0]})
enriched = pd.merge(df, costs, on="product", how="left")   # left join

# sort_values
enriched = enriched.sort_values("revenue", ascending=False)

The limits — where pandas stops being the right tool

This is the payoff of this lesson Every constraint below is precisely what PySpark was built to remove. Read this once and the motivation for Spark is settled — permanently.

pandas has three hard architectural constraints:

  1. Single machine, in-memory. The entire DataFrame must fit in RAM at once — not just the part you are looking at, but every row and column you have loaded. There is no lazy reading, no transparent spill to disk. Call pd.read_parquet("events.parquet") on a 200 GB file with 16 GB of RAM and the process is killed.
  2. Mostly single-threaded. Most pandas operations run on one CPU core, blocked by the Python GIL. A 64-core machine next to you cannot help. (Libraries like Polars or Modin address this, but they are different tools with their own trade-offs.)
  3. No built-in distribution. There is no concept of sharding rows across machines. Everything is local, always.

Rule of thumb: pandas is comfortable up to a few GB — roughly "fits in your machine's free RAM with room to spare." For exploratory work on extracted samples, or for transforming the output of a Spark job before handing it to a model or a dashboard, it is absolutely the right tool. Beyond that, you need a distributed engine.

Choosing the right tool by data size — rough guidance, not hard cut-offs.
Data sizeTypical toolWhy
< 1 GBpandasFits in RAM easily. Rich ecosystem, fast iteration.
1 – ~10 GBpandas (careful) or PolarsPossible with enough RAM; watch headroom. Polars is faster and multi-threaded.
> 10 GB, or exceeds available RAMPySpark / DatabricksDistributed across many machines; reads cloud storage in parallel partitions.
Any size, production pipelinePySpark / DatabricksScheduling, retries, Delta Lake, governance — you need a platform, not a script.

pd.read_csv(chunksize=N) lets you read a large CSV in batches. This helps for row-independent loads (e.g. writing rows to a database in chunks). It does not help if your aggregation needs all rows at the same time — which most aggregations do. Chunking is not a substitute for distribution.

Hands-on: clean, transform, and aggregate locally

Run this in your activated venv (pip install pandas numpy if you haven't). No external file is required — io.StringIO wraps the CSV string so pd.read_csv treats it exactly as it would a real file on disk.

Run this — Windows venv Save as pandas_demo.py and run python pandas_demo.py in your activated venv. All output comes from print() — no notebook required. 
import io
import numpy as np
import pandas as pd

# ── 1. Read CSV — io.StringIO simulates a file; swap in a real path for real data ──
CSV = """region,product,units,price
North,Widget,120,10
South,Widget,85,10
North,Gadget,40,25
South,Gadget,60,25
North,Widget,95,10
South,Gadget,25,25
"""
df = pd.read_csv(io.StringIO(CSV))

print("dtypes:\n", df.dtypes)
# region     object
# product    object
# units       int64
# price       int64
# dtype: object

# ── 2. Boolean filter — only rows where more than 50 units were sold ──
busy = df[df["units"] > 50]
print("\nBusy rows (units > 50):\n", busy.to_string(index=False))
# region product  units  price
#  North  Widget    120     10
#  South  Widget     85     10
#  South  Gadget     60     25
#  North  Widget     95     10

# ── 3. Add columns — vectorized; NumPy does the arithmetic ──
df = df.assign(revenue=df["units"] * df["price"])

# ── 4. Tier label — np.where is vectorized; .apply would be a Python loop ──
df["tier"] = np.where(df["price"] >= 25, "premium", "standard")

# ── 5. groupby + named aggregation + sort ──
summary = (
    df
    .groupby("region")
    .agg(
        total_units=("units",   "sum"),
        total_rev  =("revenue", "sum"),
        orders     =("units",   "count"),
    )
    .sort_values("total_rev", ascending=False)
    .reset_index()
)
print("\nSummary by region:\n", summary.to_string(index=False))
#  region  total_units  total_rev  orders
#   North          255       3150       3
#   South          170       2975       3

# ── 6. merge (left join) — enrich with a cost lookup ──
costs    = pd.DataFrame({"product": ["Widget", "Gadget"], "cost": [4, 12]})
enriched = pd.merge(df, costs, on="product", how="left")
enriched["margin"] = enriched["revenue"] - enriched["units"] * enriched["cost"]

print("\nSample rows with margin:\n",
      enriched[["region", "product", "revenue", "margin"]].head(3).to_string(index=False))
#  region product  revenue  margin
#   North  Widget     1200     720
#   South  Widget      850     510
#   North  Gadget     1000     520
Notice the pattern The chain in step 5 — groupby → agg → sort_values → reset_index — reads like a pipeline of named steps. In PySpark (Lesson 3) you wrote groupBy → agg → orderBy. The thinking is identical; only the runtime changes. That is the entire point of the Python Foundation track.

Check yourself

Commit to an answer before revealing — that is where the memory is built.

Your DataFrame has a string index: rows are labelled "ada", "alan", "grace" in that order. "grace" sits at integer position 2. Which call returns the row by its label — not by its position?
.loc is label-based: df.loc["grace"] finds the row whose index value is the string "grace" — regardless of where it sits physically. .iloc is position-based: df.iloc[2] always returns the third physical row. In this case both happen to return the same row, but if you ever sort or filter the DataFrame before accessing it, the positions shift while the labels do not. df.iloc["grace"] raises a TypeError — .iloc requires integers. Default to .loc.
Your new pipeline must aggregate a 300 GB Parquet event log. You run pd.read_parquet("events.parquet") on a laptop with 32 GB of RAM. What happens — and what is the correct move?
C is correct. pandas loads the entire DataFrame into RAM. 300 GB on a 32 GB machine will OOM-kill the process. A is wrong: pandas does not stream Parquet lazily — it loads all rows. B is partially true for the read step, but chunksize does not help once you need a global aggregation that requires all rows together. D is false: the Arrow backend stores values more efficiently per row but does not distribute work across machines and does not remove the single-machine constraint. The right answer is to reach for PySpark, which reads from cloud storage in parallel, distributes rows across a cluster, and was designed for exactly this scale.
You need to multiply every value in the price column by 1.08. Which approach is fastest?
B is fastest by a large margin. df["price"] * 1.08 dispatches directly to NumPy's C-compiled multiply — there is no Python interpreter overhead per element. A (.apply) and C (.map with a lambda) both invoke a Python function once per element: Python object creation and interpreter overhead on every call, typically 10–100× slower than a vectorized op. D (iterrows) is the slowest possible pattern in all of pandas — never use it for numeric operations. The rule: if arithmetic or a built-in pandas/NumPy method can replace .apply, it should.
