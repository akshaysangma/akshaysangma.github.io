The core transformation toolkit

Shaping a DataFrame: select, filter, withColumn, groupBy, and the handful of operators you'll use in every real pipeline.

Track: Databricks / PySpark ~14 min Hands-on: Databricks + local Windows Builds on: Lessons 1 & 2
The win today You'll walk away able to take a raw DataFrame and produce a clean, aggregated result using the operators every data engineer reaches for first: select, filter, withColumn, when, groupBy, orderBy. These map almost one-for-one onto the pandas operations you already know — the transfer is fast. By the end you'll build a five-step pipeline chain, run it in one shot, and see exactly why five lazy steps still produce only one Spark job.

Why col() — column expressions, not column values

In pandas you reference columns by subscript: df["amount"] or df.amount. Both work in PySpark too, but the idiomatic way is col("amount"), imported from pyspark.sql.functions. The distinction matters: col("amount") creates a Column expression — a named reference Spark resolves against your schema at plan time, not actual in-memory data. Because it is not bound to a specific DataFrame object, it works cleanly inside when(), agg(), and joins where both sides share a column name.

These are the two import lines you will use in every PySpark script:

from pyspark.sql import functions as F           # F.sum, F.avg, F.count, F.max …
from pyspark.sql.functions import col, lit, when  # most-used, unpacked for convenience

col("x"), F.col("x"), and df["x"] are all valid column references and produce identical plans. col() is preferred in function arguments; df["x"] is fine in simple filters. lit(42) wraps a Python constant into a Column so it can sit alongside column expressions in the same expression tree.

Picking columns: select, selectExpr, drop

select() is the PySpark analogue of pandas' column-list subscript. It returns a new DataFrame with only the columns you list, in the order you specify. drop() is the inverse: keep everything except the named columns — useful when a schema is wide and you only want to remove one or two fields. 

# Keep two columns by name — order in the call is the output order
df.select("customer", "amount")

# col() lets you transform inline and give the result a name
df.select("customer", (col("amount") * 1.08).alias("amount_vat"))

# selectExpr: same power via SQL strings — handy for quick arithmetic
df.selectExpr("customer", "amount * 1.08 as amount_vat")

# drop — keep everything except the listed column(s)
df.drop("coupon", "internal_id")

Filtering rows: filter and where

filter() and where() are identical — two names for the same method. Use whichever reads more naturally at a given call site. Both accept a Column expression (preferred) or a SQL-string predicate. 

df.filter(col("region") == "eu")         # Column expression — idiomatic
df.where("region = 'eu'")                # SQL string — same result

# Combine predicates: use & (AND) and | (OR), each condition in its own parentheses
df.filter((col("region") == "eu") & (col("amount") > 500))
Gotcha: use & / |, not and / or Python's and / or keywords do not work on Column expressions — they raise a ValueError at runtime. Always use & for AND and | for OR, and always wrap each sub-condition in its own parentheses so Python operator precedence doesn't bite you.

Reshaping columns: withColumn, withColumnRenamed, distinct

withColumn("name", expr) adds a column to the DataFrame. If a column with that name already exists it is replaced, not duplicated — so withColumn doubles as an in-place update. withColumnRenamed("old", "new") renames a column while keeping all others intact. 

# Add a new column
df.withColumn("amount_vat", col("amount") * 1.08)

# Replace an existing column (same name in both arguments)
df.withColumn("amount", col("amount") * 1.08)

# Rename — preserves all other columns
df.withColumnRenamed("amount", "price")

# Deduplication
df.distinct()                              # unique rows across ALL columns
df.dropDuplicates(["customer", "product"]) # unique on a subset only

distinct() is shorthand for dropDuplicates() with no arguments — both produce unique rows across all columns. Use dropDuplicates(["col1", "col2"]) when you want to deduplicate on a key subset and don't care which duplicate row is kept.

Conditional logic: when(…).otherwise(…)

when(condition, value) is PySpark's equivalent of numpy.where or an Excel IF(). It produces a Column expression that evaluates to value when the condition is true, and to whatever .otherwise() says when it is not. You use it inside withColumn() or select() to derive a new column from conditional logic. 

df.withColumn(
    "tier",
    when(col("amount") >= 1000, "premium")
    .otherwise("standard")
)
Omitting .otherwise() → silent null If you leave off .otherwise(), any row where no when() branch matches produces null — not an error, just a value you may not notice for a long time. Always write an explicit .otherwise(), even if it is .otherwise(lit(None)), so the intent is clear.

Chain multiple .when() calls for multi-branch logic — they are evaluated in order and the first matching branch wins:

when(col("score") >= 90, "A")
.when(col("score") >= 75, "B")
.when(col("score") >= 60, "C")
.otherwise("F")

Grouping and aggregating: groupBy(…).agg(…)

groupBy() returns a GroupedData object — not yet a DataFrame. Calling .agg() on it collapses the groups and gives back a DataFrame, one row per group. Pass one or more aggregate functions from pyspark.sql.functions, each given a readable name with .alias(). 

import pyspark.sql.functions as F

(
    df
    .groupBy("region", "product")
    .agg(
        F.count("*").alias("orders"),        # counts every row, including nulls
        F.sum("amount").alias("total"),
        F.avg("amount").alias("avg_amount"),
        F.max("amount").alias("max_amount"),
    )
)

count("*") vs count("col"): F.count("*") counts every row in the group regardless of nulls. F.count("amount") counts only rows where amount is non-null. This difference matters the moment your data has gaps — choose deliberately.

Naming collision to know: df.groupBy("x").count() is a transformation — GroupedData's .count() returns a new DataFrame with a count column. df.count() called on a plain DataFrame is an action — it returns a Python integer and fires a job. Same word, two entirely different roles.

groupBy is still lazy — but a shuffle is coming groupBy().agg() is a transformation. Nothing moves until an action fires. But when the job does run, Spark must redistribute rows across the cluster so each worker holds all rows for its groups — that redistribution is called a shuffle, and it is the most expensive operation in Spark. Lesson 4 covers why and what to do about it.

Ordering: orderBy / sort

orderBy() and sort() are aliases for the same operation. Attach .asc() or .desc() to a Column to control direction (ascending is the default). For multi-column sorts, pass multiple arguments. 

df.orderBy(col("total").desc())                       # highest first
df.orderBy(col("region"), col("total").desc())        # region asc, then total desc

# Null handling: by default, nulls sort FIRST in ascending order
# Use explicit methods to override:
df.orderBy(col("amount").asc_nulls_last())            # push nulls to the bottom
df.orderBy(col("amount").desc_nulls_last())           # desc, nulls still at bottom
Every operator above is lazy — Lesson 1's model still holds select · filter/where · withColumn · withColumnRenamed · drop · distinct · dropDuplicates · when().otherwise() · groupBy().agg() · orderBy — every one of these is a transformation. They extend the query plan and return a new DataFrame instantly. The actual distributed work starts only when you call an action: show(), count(), collect(), write.save(), and so on. Rule of thumb from Lesson 1: if it returns a DataFrame, it is lazy.¹

Hands-on: build a mini pipeline (both environments)

Run this — Databricks or local Windows On Databricks Free Edition: paste everything from data = [...] downward into a notebook cell — skip the SparkSession line, spark already exists.
Locally (Windows): save as transforms.py inside your activated venv and run python transforms.py. Requires PySpark installed and Java 17+ with JAVA_HOME set. See the environment-setup reference if needed. 
from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from pyspark.sql.functions import col, when

# --- Local only: on Databricks, spark already exists ---
spark = SparkSession.builder.appName("core-transforms").getOrCreate()

# ── Inline dataset: EU and US sales rows ────────────────────────────────
data = [
    ("alice",  "eu", "laptop",  1200.0),
    ("bob",    "us", "phone",    800.0),
    ("carol",  "eu", "laptop",  1200.0),
    ("dan",    "us", "tablet",   350.0),
    ("eve",    "eu", "phone",    750.0),
    ("grace",  "eu", "tablet",    None),  # null amount — watch orderBy
]
df = spark.createDataFrame(data, ["customer", "region", "product", "amount"])

# ── Step 1: select — drop the customer column, keep what we need ────────
df2 = df.select("region", "product", "amount")

# ── Step 2: filter — EU orders only ────────────────────────────────────
df3 = df2.filter(col("region") == "eu")

# ── Step 3: withColumn — classify tier, then compute VAT price ──────────
df4 = (
    df3
    .withColumn("tier",
        when(col("amount") >= 1000, "premium").otherwise("standard"))
    .withColumn("amount_vat", col("amount") * 1.08)
)

# ── Step 4: groupBy + agg — totals per product and tier ─────────────────
summary = (
    df4
    .groupBy("product", "tier")
    .agg(
        F.count("*").alias("orders"),
        F.sum("amount_vat").alias("total_eur"),
        F.avg("amount_vat").alias("avg_eur"),
    )
)

# ── Step 5: orderBy — highest revenue first, nulls pushed to bottom ─────
result = summary.orderBy(col("total_eur").desc_nulls_last())

# ACTION — the entire five-step plan runs here, in one job ───────────────
result.show()
# +-------+--------+------+---------+--------+
# |product|    tier|orders|total_eur| avg_eur|
# +-------+--------+------+---------+--------+
# | laptop| premium|     2|   2592.0|  1296.0|
# |  phone|standard|     1|    810.0|   810.0|
# | tablet|standard|     1|     null|    null|
# +-------+--------+------+---------+--------+
Notice: five steps, one job Every call from df.select() through .orderBy() was lazy — the plan just grew, nothing touched data. Only .show() fired the job, and Catalyst optimized the plan before running it (for example, pushing the filter as early as possible so fewer rows flow through later steps). Delete the last two lines and Spark does zero work over this dataset.

The tablet/standard row has null in total_eur because grace's amount was null — arithmetic on null propagates null in Spark (three-valued logic). F.count("*") still returns 1 because it counts rows, not values.

Where we go next

You got a preview today: groupBy().agg() is lazy, but when the job runs it triggers a shuffle — rows moving across the network so each worker can hold a complete group. A shuffle on a large table is the single most expensive thing Spark does, and understanding it is what separates passable pipelines from fast ones. Lesson 4 shows what a shuffle is, why joins cause them, and the practical patterns (broadcast joins, repartition, partition pruning) that keep costs under control.
