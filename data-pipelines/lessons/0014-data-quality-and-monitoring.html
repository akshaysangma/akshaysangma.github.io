Green doesn't mean good

Data quality, monitoring, and trustworthy pipelines — because a pipeline that runs green but produces wrong data is worse than one that crashes.

Track: Databricks / PySpark ~12 min Hands-on: Databricks (recommended) · local PySpark Builds on: Lessons 9, 11, 12
The win for your career switch In interviews and on the job, data engineers are judged not just on whether a pipeline ran but on whether the output can be trusted. A job that completes with a green tick but writes 40% fewer rows than expected — silently — is the worst kind of failure: no alert fires, stakeholders make decisions on wrong numbers, and the problem surfaces weeks later. This lesson gives you the pattern that stops that: fail loudly. You will build a reusable validate() function that raises when data looks wrong, understand the Delta constraints that block bad writes at the table level, learn the quarantine pattern for routing bad rows without discarding them, and know exactly where to look in Databricks when a Job does fail. One lesson, one win: pipelines that fail loudly or succeed honestly.

The silent failure problem

Imagine a pipeline that ingests daily orders. Overnight, an upstream system changes the value "completed" to "COMPLETED". Your Silver filter — filter(col("status") == "completed") — drops every single incoming row because the case no longer matches. The write action succeeds: Delta appends zero rows, which is a valid write. The Databricks Job shows green. Your Gold table now says zero revenue for today, and that number flows into a BI dashboard at the business team's morning stand-up.

The fix is not a better filter. The fix is a quality gate: a check that runs before writing Silver and raises loudly when row counts, null ratios, or value ranges look wrong. A crashed pipeline is easy to find. A quiet one that writes wrong data is not.

The rule: fail loud, not silent Silently dropping bad rows — df.filter(is_valid) then writing on — feels safe. It is not. You lose visibility of how many rows were dropped, on which day, and why. Every quality check that catches a problem should either raise (stop the pipeline now) or quarantine (route the bad rows to a separate table you can inspect). Never silently discard.

Five dimensions of data quality

Every quality check you write targets at least one of these five dimensions. Naming them precisely matters in design conversations and code reviews.

The five DQ dimensions, each with the PySpark signal to check and an example from the orders pipeline built in Lesson 11.
DimensionQuestion it answersPySpark signalOrders example
Completeness Are required fields present and non-null? filter(col(c).isNull()) customer_id must never be null
Uniqueness Are primary-key rows duplicated? count() vs countDistinct("order_id") Each order_id should appear exactly once
Validity Do values fall within allowed ranges or enums? filter(~col(c).isin(...)) unit_price > 0, status in known set
Consistency Do related tables agree on shared keys? Join and count unmatched rows customer_id in orders must exist in customers table
Timeliness Did fresh data actually arrive today? max(col("order_ts")) vs current date Most recent order should be within 24 hours of pipeline run

Keep checks targeted: pick the two or three dimensions that matter most for your specific table. Checking everything is noise; checking nothing is dangerous. For the Silver orders table, completeness (customer_id), validity (unit_price > 0), and uniqueness (order_id) are the three that would hurt most if they silently failed.

The validate() pattern: fail loudly in PySpark

The most practical pattern is a small function that runs assertions over a DataFrame and raises if any check fails. You call it just before writing to the next layer. When data is clean, nothing changes in your pipeline flow. When it is not, the job fails immediately with a message that tells you exactly what broke — and nothing gets written downstream.

Environment On Databricks, paste each cell block into a separate notebook cell — spark already exists. Locally, run from your activated venv (plain PySpark, no Delta package needed for the validate() demo — the quarantine cell later uses Delta writes). 
# ── CELL 1: define validate() — one function you will reuse everywhere ────
from pyspark.sql.functions import col, count, when

def validate(df, label="df"):
    """
    Quality gate: raise AssertionError if df fails any check.
    Returns df unchanged — chain it: validate(silver_df, "silver").write...
    """

    # Check 1 — Completeness: no nulls in business-critical columns
    critical_cols = ["order_id", "customer_id", "unit_price"]
    null_row = (
        df.select([count(when(col(c).isNull(), 1)).alias(c) for c in critical_cols])
          .collect()[0]
    )
    for c in critical_cols:
        n = null_row[c]
        if n > 0:
            raise AssertionError(
                f"[{label}] NULL check FAILED — '{c}' has {n} null(s)"
            )

    # Check 2 — Validity: unit_price must be strictly positive
    bad_price = df.filter(col("unit_price") <= 0).count()
    if bad_price > 0:
        raise AssertionError(
            f"[{label}] Range check FAILED — {bad_price} row(s) with unit_price <= 0"
        )

    # Check 3 — Uniqueness: each order_id appears exactly once
    total        = df.count()
    distinct_ids = df.select("order_id").distinct().count()
    if total != distinct_ids:
        raise AssertionError(
            f"[{label}] Duplicate check FAILED — {total} rows but {distinct_ids} distinct order_ids"
        )

    print(f"[{label}] PASSED — {total} rows, all checks green.")
    return df    # passthrough: validate(silver_df, "silver").write.format("delta")...

# ── CELL 2: run on good data — expect it to pass ─────────────────────────
good_rows = [
    (1001, "C001", "laptop",  1,  999.99),
    (1002, "C002", "headset", 2,   79.99),
    (1003, "C001", "mouse",   1,   29.99),
]
good_df = spark.createDataFrame(
    good_rows, ["order_id", "customer_id", "product", "qty", "unit_price"]
)

validate(good_df, "good_df")
# [good_df] PASSED — 3 rows, all checks green.

# ── CELL 3: run on bad data — expect it to raise loudly ──────────────────
bad_rows = [
    (2001, None,   "tablet", 1,  399.99),   # null customer_id  ← fails Check 1
    (2002, "C003", "mouse",  1,   -9.99),   # negative price    ← would fail Check 2
]
bad_df = spark.createDataFrame(
    bad_rows, ["order_id", "customer_id", "product", "qty", "unit_price"]
)

try:
    validate(bad_df, "bad_df")
except AssertionError as e:
    print(f"CAUGHT: {e}")
# CAUGHT: [bad_df] NULL check FAILED — 'customer_id' has 1 null(s)
What to notice The function raises on the first failing check and stops — nothing is written downstream. The second bad row (negative price) never gets evaluated because the null check fires first. In production you might collect all failures before raising — loop over checks, append to an errors list, raise at the end. Either form is valid; raising immediately is simpler to start with and works well for most pipelines. The important thing is that the raise happens: the write is cancelled, the job shows red, and the alert fires (Lesson 12).

Delta constraints: enforcement at the table level

validate() runs inside your pipeline code. If someone writes directly to the Delta table via a notebook, SQL query, or a different pipeline, those checks do not run. Delta constraints fix this: they live on the table itself and are enforced on every write, from any source.¹

Delta supports two constraint types. Both are enforced atomically at write time — a violating write fails with an AnalysisException and the table stays exactly as it was: 

-- ── Run these as SQL in a Databricks notebook cell, or via spark.sql("...") ─

-- CHECK constraint: any boolean expression; rejects writes that evaluate to false
ALTER TABLE silver_orders
  ADD CONSTRAINT valid_price CHECK (unit_price > 0);

ALTER TABLE silver_orders
  ADD CONSTRAINT valid_status CHECK (status IN ('completed', 'pending', 'cancelled'));

-- View the constraints stored on the table
SHOW TBLPROPERTIES silver_orders;
-- key                                    | value
-- delta.constraints.valid_price          | unit_price > 0
-- delta.constraints.valid_status         | status IN ('completed', ...)

-- Drop a constraint when a business rule changes
ALTER TABLE silver_orders DROP CONSTRAINT valid_status;

-- NOT NULL constraint: enforced at the column level on every future write
-- Delta validates all existing rows first — add this to a table that is already clean
ALTER TABLE silver_orders ALTER COLUMN order_id SET NOT NULL;
Constraints reject — they don't retrofit Adding a CHECK or NOT NULL constraint to a table that already contains violating rows will fail immediately. Delta validates the whole existing table first. Fix or remove the bad rows, then add the constraint so it guards future writes. This is why quality checks in pipeline code (validate()) and table-level constraints are complementary, not alternatives: checks keep bad data from landing; constraints are a permanent last-line defence if they do.

This builds on schema enforcement from Lesson 9: Delta already rejects any write whose schema does not match the table. CHECK constraints add a second layer that rejects writes whose values break a declared rule. Together they form a two-level, table-owned defence that travels with the table — not with any particular piece of pipeline code.

Lakeflow Declarative Pipelines: quality rules as first-class code

The two approaches above — pipeline-code checks and Delta table constraints — work with any Spark notebook or Job. Databricks also offers a higher-level abstraction: Lakeflow Declarative Pipelines (formerly Delta Live Tables, renamed at the June 2025 Data + AI Summit²). You define pipeline tables declaratively, and quality rules called expectations are declared inline with the table definition. The key difference from validate(): expectations are tracked as metrics in the Pipeline UI automatically — you can see how many rows violated each rule over every run without writing any logging code.

Three expectation modes control what happens when a row violates a rule:

DLT / Lakeflow expectation modes — the same concept as fail-loud vs quarantine, but declared as metadata rather than imperative code.²
ModeSQL keywordOn violationWhen to use
Warn EXPECT Records metric; keeps the row Soft rules — you want visibility but can tolerate imperfection
Drop EXPECT … ON VIOLATION DROP ROW Removes the violating row; records the count Known-bad rows you want to track but exclude from the output
Fail EXPECT … ON VIOLATION FAIL UPDATE Fails the entire pipeline update Hard rules — a single bad row means the whole batch is suspect 
-- In a Lakeflow Declarative Pipeline notebook (SQL syntax):

CREATE OR REFRESH STREAMING TABLE silver_orders (
  CONSTRAINT valid_price   EXPECT (unit_price > 0)          ON VIOLATION DROP ROW,
  CONSTRAINT has_customer  EXPECT (customer_id IS NOT NULL)  ON VIOLATION FAIL UPDATE
)
AS SELECT * FROM STREAM(bronze_orders);

The Python API uses decorators: @dlt.expect_or_drop("valid_price", "unit_price > 0") and @dlt.expect_or_fail("has_customer", "customer_id IS NOT NULL") stacked above @dlt.table(name="silver_orders"). Light coverage here — the important things to know are (1) what the three modes do, (2) that expectations travel with the table definition rather than a function call, and (3) that they surface metrics in the Pipeline UI automatically. The underlying behaviour mirrors what you built manually with validate().

Naming note: DLT vs Lakeflow Databricks renamed "Delta Live Tables" (DLT) to "Lakeflow Declarative Pipelines" at the June 2025 Data + AI Summit. The Python module (import dlt) and the underlying SQL keywords remain unchanged, and existing DLT code runs without migration — only the product name changed. Official docs and the certification exam may still use either name. Treat them as synonyms; the feature is the same.

The quarantine pattern: route bad rows, never silently drop

Sometimes you do not want to fail the whole pipeline on bad rows — you want the valid majority to flow through while the bad rows are preserved for investigation. That is the quarantine pattern: one filter sends clean rows to Silver; the complement (~quality_ok) goes to a separate quarantine Delta table. Nothing is silently discarded. 

# ── CELL 4: quarantine pattern ────────────────────────────────────────────
from pyspark.sql.functions import col

BASE = "/tmp/e2e_pipeline"   # same as Lesson 11; change for your environment

# Simulate incoming Bronze data (in a real pipeline: spark.read.format("delta").load(...))
rows = [
    (1001, "C001", "laptop",  1,  999.99, "completed"),
    (1002, "C002", "headset", 2,   79.99, "completed"),
    (1003,   None, "tablet",  1,  399.99, "completed"),   # null customer_id
    (1004, "C003", "mouse",   1,  -19.99, "completed"),   # negative price
]
bronze_df = spark.createDataFrame(
    rows, ["order_id", "customer_id", "product", "qty", "unit_price", "status"]
).cache()   # cache: Spark scans bronze once, not once per filter branch

quality_ok = (
    col("customer_id").isNotNull() &
    (col("unit_price") > 0)
)

silver_clean  = bronze_df.filter(quality_ok)
quarantine_df = bronze_df.filter(~quality_ok)

# Silver: overwrite keeps it idempotent — safe to re-run (Lesson 11)
silver_clean.write.format("delta").mode("overwrite").save(f"{BASE}/silver")

# Quarantine: append accumulates the full history of every bad row ever seen
quarantine_df.write.format("delta").mode("append").save(f"{BASE}/quarantine")

print(f"Silver: {silver_clean.count()} rows")
print(f"Quarantine: {quarantine_df.count()} rows")
# Silver: 2 rows
# Quarantine: 2 rows
Why quarantine beats silent drop The two quarantined rows above — the null-customer row and the negative-price row — are not gone. They sit in a Delta table you can query, understand, and act on. Tracking quarantine_df.count() over time is a cheap monitoring signal: if today you quarantine 200 rows versus 2 yesterday, something upstream broke. You do not need a formal monitoring tool to spot that jump — a simple daily count assertion will catch it.

Monitoring: where to look when a job fails

With quality gates in place, a pipeline that catches bad data will fail loudly. Now you need to know where to look in Databricks to diagnose the failure fast. There is a specific path through the UI:

The four-step diagnostic path for a failed Databricks Job run — work through them in order.
StepWhere in the UIWhat to look for
1. Run history Workflows → Jobs → select your job → All Runs Which task failed, at what time, after how many retries
2. Task error message Click the failed run → click the red task box The top-level exception type and message — often enough to diagnose without logs
3. Driver logs Failed task panel → Logs tab → stderr Full Python traceback; look for AssertionError (quality gate), AnalysisException (constraint or schema), FileNotFoundException (missing source)
4. Spark UI Failed task panel → Spark UI link → SQL / DataFrame tab Only needed for performance failures: which stage timed out, which task skewed. Not needed for AssertionError or AnalysisException

Retries and alerts are configured at the Job level — how many times Databricks re-attempts a failed task before giving up, and whether to send an email or webhook on failure. Those settings were covered in Lesson 12. The critical connection here: retries are only safe if your pipeline is idempotent. If re-running the same input twice would create duplicate Gold rows, retries make the problem worse. Always use mode("overwrite") for Silver and Gold (as in Lesson 11) or a Delta MERGE for Bronze, so a retry produces exactly the same output as the first run.

The three-tool diagnostic stack Run history → confirm which task failed and whether retries exhausted. Driver stderr → read the actual exception message. Spark UI → only if the failure is a performance issue (OOM, shuffle skew, timeout), not a code or data error. Most data-quality failures are fully diagnosed at step 2 or 3 — the Spark UI is rarely needed.

Check yourself

Commit to an answer before revealing — retrieval is what builds memory.

You check whether customer_id is null before writing to Silver. Which data-quality dimension does this check target?
B — Completeness is the DQ dimension about required fields being present and non-null. Checking customer_id IS NOT NULL asks "is this field there?" — that is completeness. Validity (C) is about whether a present value falls within an acceptable range or set of values — for example, unit_price > 0. Uniqueness (A) is about duplicate rows on a key. Consistency (D) is about agreement across tables. Knowing the names precisely matters: calling it "a completeness check" in a design review signals DQ fluency; calling it "a null check" does not.
Your pipeline silently drops rows with a null customer_id rather than raising an error — the Databricks Job shows green. Why is this more dangerous than raising an AssertionError and stopping?
A is the core reason. When a pipeline drops bad rows silently, the job shows green, dashboards update, and stakeholders make decisions on incomplete data — often for days or weeks before anyone notices. A pipeline that crashes is found immediately. A pipeline that quietly under-counts is trusted until it does serious damage. B is false: filtering rows is not slower than writing them — Spark evaluates both branches in one pass. C is partly true (the Delta log does not record dropped rows by default), but that is not the danger — the danger is the consumer-trust problem in A. D is false: null values in filtered rows do not affect the output schema because those rows are excluded before writing.
You run ALTER TABLE silver_orders ADD CONSTRAINT valid_price CHECK (unit_price > 0). What happens the next time a write attempts to insert a row where unit_price = -5?
B is correct. A Delta CHECK constraint is enforced atomically: if any row in the incoming write violates the condition, the entire write fails with an AnalysisException and the table is rolled back to exactly the state it was in before the write attempt. Delta does not log and continue (A), silently drop individual rows (C), or coerce values (D). This all-or-nothing behaviour is what makes CHECK constraints reliable as a last-line defence — partial writes and silent data mutations are both impossible. The failure shows up in the Job run's driver stderr as an AnalysisException: CHECK constraint ... violated by row(s) message.
