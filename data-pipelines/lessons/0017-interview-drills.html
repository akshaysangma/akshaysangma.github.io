How to use this lesson — three habits

Done right, this is more useful than re-reading every lesson. Done wrong, it is just clicking buttons. The difference is these three habits:

  • Cover first, answer second. For every question, commit to an answer out loud — say it, don't just think it — before clicking any button. Guessing after partial reading is recognition. Committing before is retrieval. Only retrieval builds the memory that survives an interview.
  • Return in 24 hours, then 3 days, then a week. Spacing repetitions forces your brain to reconstruct the memory each time, which strengthens it far more than one long session. Your recall score and your hesitation time are the signals to track. Both should improve across sessions.
  • Treat wrong answers as the most valuable signal you get. A wrong answer identifies a real gap — one you might not have discovered until mid-interview. Go back to that lesson, re-read the key section, then return here and answer again.

Testing before you feel ready, spacing sessions across days, mixing topics across lessons — this approach is what learning researchers call desirable difficulty. It is harder than re-reading your notes and far more effective at building the recall that works under pressure.

Round 1 — interleaved recall

Twelve questions spanning all four phases of the course. Topics are deliberately scrambled — resist the urge to group them mentally. Commit to an answer before you click.

In the ELT pattern, when and where does the transform step run?
A is correct. ELT's defining characteristic is that raw data loads first — exactly as it arrived — and the transform then runs inside the target platform using its own compute (Spark, on Databricks). B describes ETL: transform before load, on external compute. C describes in-flight filtering, which is neither pattern as standardly defined. D is also ETL-adjacent. The economic shift that made ELT dominant on modern cloud platforms: cheap object storage makes landing raw data nearly free, and Spark in the lakehouse provides the transform compute you previously needed on a separate server. See Lesson 8.
Which of these calls actually triggers a distributed Spark job to run?
D is correct. collect() is an action: it needs a concrete result (a Python list of Row objects), so it forces the full plan to execute. A, B, and C all return DataFrames — they are transformations that add steps to the query plan and return instantly without touching any data. The rule from Lesson 1: if it returns a DataFrame it is lazy; if it returns a value, a list, or writes to storage it is an action. Note that B chains three transformations — even a multi-step chain is lazy until an action fires.
Why does a NumPy operation like prices * 1.08 outperform an equivalent Python for loop by 10–50×?
C is correct. A NumPy ndarray stores every element as the same declared type (dtype) in a flat, contiguous block of bytes. When you write prices * 1.08, NumPy hands the whole array to a compiled C routine — the loop happens in C, with no Python interpreter overhead per element. A Python list holds object pointers; each arithmetic step must check each element's type at runtime, which is where the slowdown comes from. A is false — NumPy has no disk cache. B is partially true for some BLAS operations but is not the primary mechanism. D is false — NumPy is a single-machine library with no Spark integration. See Lesson 5.
Explain out loud — "What is lazy evaluation in Spark?"

Say the answer without looking, then compare to the model below.

Model answer: In Spark, a transformation like filter or join does not run immediately — it only records a step onto a query plan. Spark builds the full recipe of operations first, lets the Catalyst optimizer rewrite it (pushing filters down, dropping unused columns, choosing join strategies), and then runs the whole thing at once when you call an action like count() or collect(). That is lazy evaluation. The benefit is optimization: because Spark sees the entire plan before executing, it can make changes an eager system cannot — an eager system has already run each step before seeing the next one.

The one-sentence version for an interview: "Spark only records what you want to do; nothing runs until an action asks for a concrete result, and by then Catalyst has optimized the whole plan."

A Spark job writing 10 million rows to a Delta table crashes after 6 million rows have been written. What does a reader see immediately after?
B is correct. A Delta write is atomic: either the entire transaction commits — one new JSON entry appears in the _delta_log — or nothing changes and the table stays at its last fully committed version. A crashed write produces no commit entry, so readers continue to see a consistent prior snapshot. A and D both describe partial-write visibility, which is what happens with plain Parquet — and the exact gap Delta fills with its transaction log. C is wrong: Delta does not reset to version zero; it simply shows the most recent successful commit. See Lesson 9.
Which operation causes Spark to move rows across the network between executors?
C is correct. A join is a wide transformation: rows with matching keys may sit on different executors, so Spark must shuffle — redistribute rows across the network — until each key's rows are co-located. A (withColumn), B (filter), and D (select) are narrow transformations: each output partition depends on exactly one input partition; zero data moves across the network. The shuffle is the most expensive thing Spark regularly does. When one side of a join is small, wrapping it in broadcast() sends a copy to every executor instead, eliminating the shuffle entirely. See Lesson 4.
An analyst needs a pre-built table showing weekly revenue by product category. Which medallion layer is the correct home for it?
C is correct. Gold is the serving layer: pre-aggregated, business-level tables built for a named consumer — a BI tool, a dashboard, an analyst. It is produced by reading silver and applying the final groupBy + agg. Bronze (A) holds raw, unfiltered data — not the place for curated reporting. Silver (B and D) holds cleansed, deduplicated row-level detail; it is the single source of truth for row-level work, but it is not pre-aggregated. Weekly revenue by category is a business aggregate: it belongs in gold. See Lesson 10.
Explain out loud — "What is a shuffle and why is it expensive?"

Model answer: A shuffle is when Spark must move rows across the network between executors so that all rows sharing the same key end up on the same machine. This happens in wide transformations — join, groupBy, distinct, orderBy. It is expensive for three reasons: (1) rows must be read off every executor, (2) serialized and sent over the network, and (3) written to disk on the destination executor before the next stage can start. On a large dataset, a single shuffle can take minutes and generate hundreds of gigabytes of temporary disk I/O. The main mitigation is a broadcast join: if one side of a join is small enough to fit in executor memory, wrapping it in broadcast() ships a copy to every executor, so each executor joins locally — no rows travel across the network.

What is the specific risk of calling .toPandas() on a 50 GB Spark DataFrame in a Databricks notebook?
B is correct. toPandas() is an action that collects every row from every executor and assembles them into a pandas DataFrame on the driver — a single machine with finite RAM. On 50 GB of data, this will almost certainly crash the driver or stall it in disk swap. A is wrong — schema inference happens at read time via inferSchema, not at toPandas(). C is false — the Delta log is independent of how you read the table. D is wrong — cache state is unrelated to toPandas(). The safe pattern from Lesson 7: aggregate in Spark first to produce a small result of thousands of rows, then call .toPandas() on that small output.
What does inferSchema=True actually do when reading a large CSV, and what is its cost?
A is correct. inferSchema=True causes Spark to make a second pass over the file, sampling values to determine each column's best type — IntegerType, DoubleType, StringType, etc. In development this is convenient. On a very large file in production, that second scan doubles I/O cost, which is why providing an explicit schema=StructType([...]) is the production best practice. B is the opposite of the default: without inferSchema, Spark reads all columns as StringType — not Python types. C describes schema validation, which is a different mechanism. D is unrelated to CSV reading. See Lesson 2.
Explain out loud — "What is the difference between ETL and ELT, and why did the industry shift?"

Model answer: Both patterns share the same three steps — Extract, Transform, Load — but ETL runs the transform step before data reaches the target, on a dedicated external server. Only clean, pre-validated data lands in the warehouse. ELT flips the order: raw data loads first, then the transform runs inside the target platform using its own compute (Spark, in a Databricks lakehouse). Two things changed to make ELT the modern default: cloud object storage became cheap enough that landing raw data costs almost nothing, and cloud platforms provide massively parallel compute right where the data lives. There is no longer a reason to pay for a separate transform server. ELT also gives you a full audit trail — the raw layer is never modified, so if a transform has a bug you fix and replay without going back to the source system. ETL still earns its place when the target lacks compute, or when regulations require that raw PII never be persisted.

What does a Delta MERGE INTO statement do that a plain .write.mode("append") cannot?
A is correct. MERGE INTO (also called an upsert) matches source rows to target rows on a key: WHEN MATCHED rows can be updated or deleted; WHEN NOT MATCHED source rows are inserted. All of this lands as one atomic commit in the _delta_log — either all changes succeed or none do. A plain mode("append") blindly adds every source row regardless of whether it already exists, producing duplicates. Without MERGE, an upsert in a raw data lake requires loading the whole table, deduplicating in memory, and rewriting everything. B, C, and D describe things that do not happen in a MERGE. See Lesson 9.
You open a 12 GB CSV in pandas on a laptop with 16 GB of RAM. After loading, the df.groupby("category").sum() call makes the process crash. What is the most likely cause?
D is correct. Pandas loads the entire dataset into memory — a 12 GB CSV can expand to 2–3× that in pandas' in-memory representation once object overhead and intermediate copies are counted. The groupby operation produces additional in-memory intermediates. On a 16 GB machine this easily exhausts RAM, and the OS kills the process. This is the core scalability limit of pandas covered in Lesson 6: it is single-machine and entirely in-RAM. A is false — groupby works on any column. B is false — inconsistent widths cause parsing errors, not crashes. C is false — pandas does not use disk as a backing store for groupby; it holds everything in RAM.
Explain out loud — "Why use Delta Lake instead of plain Parquet?"

Model answer: Delta Lake is Parquet plus a transaction log — the _delta_log directory — that records every write as an ordered, append-only sequence of JSON commit files. That one addition gives you four capabilities plain Parquet cannot provide: (1) ACID transactions — a write either commits fully or not at all, so a crashed job never leaves partial data visible; (2) time travel — you can read any past version of the table using TIMESTAMP AS OF or VERSION AS OF; (3) schema enforcement — Delta rejects writes whose schema does not match the table, protecting you from accidentally dropping a column; and (4) MERGE / upsert — atomic insert-or-update without rewriting the entire table. The underlying file format is still Parquet — Delta is an open standard layer on top of it, not a replacement. On Databricks, Delta is the default format for every table you create.

You read a large Delta table and call the same aggregation three times in a notebook — each call re-reads the table from storage. What is the most targeted fix?
D is correct. df.cache() (equivalent to df.persist(StorageLevel.MEMORY_AND_DISK)) marks the DataFrame to be stored in cluster memory after the first action materializes it. On the second and third aggregation calls, Spark finds the cached partitions and skips re-reading the Delta table from storage entirely. A (repartition(1)) forces all data to a single partition — a severe bottleneck on large data and unrelated to caching. B misunderstands persist(): you call it on the source DataFrame you want to keep in memory, not after each derived result. C is wrong: explain() displays the query plan for debugging; it does not control or advise Spark on which data to reuse. See Lesson 13.
In a Databricks Job, Task C (gold aggregation) is configured to depend on Task B (silver cleaning). Task B fails mid-run. What happens to Task C?
C is correct. Databricks Jobs honour the dependency graph you configure. When an upstream task fails, all tasks that depend on it are automatically skipped for that run — you will never build a gold layer on top of incomplete silver data. A is wrong — downstream tasks do not start on separate clusters to compensate for failures. B is wrong — retry logic applies to the failed task itself, not to its dependents. D is wrong — dependents do not run in parallel with retries; the dependency is enforced, not advisory. Configuring explicit task dependencies is exactly what makes a multi-stage pipeline reliable as a Databricks Job. See Lesson 12.
Explain out loud — "When would you use pandas vs PySpark?"

Model answer: The decision rule is: if the data fits comfortably in RAM on one machine, use pandas. If it is large, distributed, or already lives in a cloud lakehouse, use PySpark. In practice: datasets under roughly 1–2 GB on a standard machine are fine in pandas. Anything larger risks OOM errors, since pandas loads everything into RAM and intermediate operations can expand that footprint 2–3×. On Databricks, spark already exists and a cluster is already attached — there is no startup overhead — so the bar for using PySpark is low. One important warning: calling .toPandas() on a large Spark DataFrame pulls all the distributed data to the single driver machine. The correct pattern is to aggregate in Spark first to a small result, then call .toPandas() on that small output if you need pandas-specific tooling or plotting.

Behavioral and project questions

Technical recall is half the interview. Expect at least one question asking you to walk through something you actually built. Prepare it now, before the call — candidates who have practiced the walk-through aloud are noticeably more confident than those who have only thought it through silently.

Walk-through prompt — your portfolio pipeline

Practice saying this answer out loud, targeting under two minutes:

"Tell me about a data pipeline you designed and built. Walk me through the architecture, the key decisions you made, and what you would do differently."

Structure your answer around the pipeline you built in Lesson 15:

  • What: the dataset you chose and why it was interesting to a hypothetical stakeholder.
  • Architecture: bronze (raw, append-only, Delta table) → silver (deduplication, type-casting, null validation) → gold (business aggregate the stakeholder cares about). Name specific Delta features you used: ACID writes, time travel, MERGE if you did upserts.
  • Key decisions and why: ELT over ETL (raw data retained for replay), Delta over plain Parquet (ACID + time travel), broadcast join if you had a small dimension table on one side.
  • What you'd do differently: add explicit data quality checks comparing input vs output row counts between layers; schedule it as a Databricks Job with task dependencies; run OPTIMIZE after heavy ingestion to compact small files.

A candidate who walks through a real pipeline using vocabulary like medallion, ACID, broadcast join, and task dependency stands out from candidates who have only read about these concepts. The vocabulary signals genuine understanding.
