Why nothing happens until it does

Spark's lazy execution model — the one idea that separates "I dabbled in Spark" from "I get Spark."

Track: Databricks / PySpark ~12 min Hands-on: local PySpark Builds on: pandas you already know
Why this, first Your mission is a data-engineering role. In interviews and on the job, the single most common "do they actually understand Spark?" tell is whether they know the difference between a transformation and an action — and why a job seems to "do nothing" and then suddenly does everything. Master this and the rest of PySpark stops being magic.

The one idea

In pandas, every line runs immediately. df[df.amount > 100] filters the data right now and hands you a new DataFrame sitting in memory. This is eager evaluation.

PySpark is lazy. When you write df.filter(df.amount > 100), Spark does not touch your data. It just records "the user wants a filter" onto a plan — a recipe of steps. Your DataFrame is not a table of data; it is a description of how to compute a table of data.

The plan only runs when you call an action — something that needs a concrete result, like counting rows or showing them. Everything before that is a transformation, and transformations just grow the recipe.

The mental model Transformations = writing down recipe steps (lazy, instant, return a new DataFrame).
Actions = "now actually cook it" (eager, trigger a real distributed job, return a value or write output).

Why Spark is built this way

Laziness is not a quirk — it is the whole point. Because Spark sees the entire recipe before running anything, its optimizer (Catalyst) can rewrite it: push your filter down so less data is read, combine steps, drop columns you never use. An eager system can't optimize across steps because it has already executed each one before seeing the next. Laziness is what lets one engine run efficiently over terabytes across many machines.¹

See it with your own eyes

This is the win for today: prove to yourself that transformations are free and actions are where the work happens.

First: get an environment (Windows) You have two ways to run today's code — set up either (both, ideally) via the Environment Setup reference:
  • Databricks Free Edition (cloud, zero install) — sign up at databricks.com/learn/free-edition, open a Python notebook, and spark already exists. Fastest start. (Community Edition was retired in 2025; Free Edition replaces it.¹)
  • Local Python (Windows) — in a venv: pip install pyspark. Needs Java 17+ with JAVA_HOME set. Full Windows steps are in the setup reference.
Run this On Databricks: paste the body below into a notebook cell — skip the SparkSession lines, spark is already there.
Locally: save as lazy.py and run python lazy.py in your activated venv. 
from pyspark.sql import SparkSession
from pyspark.sql.functions import col

spark = SparkSession.builder.appName("lazy-demo").getOrCreate()

# A tiny dataset: (name, amount)
data = [("ada", 50), ("alan", 150), ("grace", 300), ("linus", 90)]
df = spark.createDataFrame(data, ["name", "amount"])

# --- Transformations: these return INSTANTLY. No data is processed. ---
big = df.filter(col("amount") > 100)      # lazy
big = big.withColumn("amount_eur", col("amount") * 0.92)  # lazy
print("Built the plan. Nothing has run yet.")

# Want to SEE the recipe Spark built? (still no job runs)
big.explain()                              # prints the physical plan

# --- Action: THIS is what triggers the actual distributed job. ---
big.show()                                 # action — runs the job now
# +-----+------+----------+
# | name|amount|amount_eur|
# +-----+------+----------+
# | alan|   150|     138.0|
# |grace|   300|     276.0|
# +-----+------+----------+

print("Row count:", big.count())          # count() is also an action
The "aha" to notice The two print/explain lines appear before any data is crunched, even though filter and withColumn came first in your code. The work only happens at show() and count(). If you delete the last three lines, Spark does zero data processing. That is laziness, live.

Transformation or action? The cheat you'll reuse forever

The split you must internalize. Full list lives in the glossary.
Transformations (lazy)Actions (eager — trigger a job)
select, filter/whereshow()
withColumn, dropcount()
groupBy(...).agg(...)collect(), take(n)
join, orderBywrite.save(...) / saveAsTable(...)
distinct, unionfirst(), toPandas()

Rule of thumb: if it returns a DataFrame, it's a transformation (lazy). If it returns a value, a list, or writes to storage, it's an action (eager).

Why this matters on the job

  • Debugging: an error in a filter often surfaces only at show() — because that's when it actually runs. Beginners get confused; you won't.
  • Performance: calling an action repeatedly re-runs the whole recipe each time. (The fix — cache() — is a later lesson, but it only makes sense once you own this model.)
  • Cost: collect() and toPandas() pull all data to one machine — fine for 4 rows, catastrophic for 4 billion. Knowing actions trigger real work tells you which calls are dangerous.

Check yourself

Commit to an answer before revealing — retrieval is what builds memory.

You run df.filter(...).withColumn(...) and the cell finishes in 2 ms over a 1 TB table. What happened?
Both are transformations — lazy. They return a new DataFrame instantly by extending the plan; no data is read or processed until an action runs. The speed is the tell.
