Build a portfolio pipeline employers will respect

The career-switch asset. A project spec, a phased build plan, a definition of done — and exactly how to talk about it in interviews.

Track: Databricks / PySpark ~15 min read Project: 4–8 hrs to build Integrates Lessons 1–14
The big win Lessons 1–14 gave you the full toolkit: lazy execution, explicit schemas, Delta Lake, the medallion architecture, an end-to-end pipeline, orchestration, performance tuning, and data-quality checks. Now comes the piece that turns skills into a job: evidence. A working pipeline you built, on public data, pushed to GitHub, that an interviewer can clone and inspect. For a career switcher with no prior DE job history, that evidence is often the difference between an interview and a rejection. This lesson is your project spec, your phased build plan, and your definition of done. Your job: execute it.

Why employers need to see a project

Completing a course teaches you data engineering. A portfolio project proves you can do data engineering — and there is a meaningful gap between the two. Employers are not dismissive of self-taught engineers; they are cautious about claims they cannot verify. A public GitHub repository containing working notebooks, a README, sample output, and a documented architecture turns an unverifiable skill claim into an inspectable artifact.

Three things a project demonstrates that no quiz or certification can replicate. First, you can navigate ambiguity: you chose a dataset, decided what "clean" means for it, and defined a Gold question worth answering — none of which was handed to you. Second, you can ship: the pipeline runs, it has output, it is not half-finished. Third, you can explain decisions: your README says not just what you built, but why. That third one is what separates a junior-DE hire from a course-taker.

The strongest career-switch portfolios show one thing done well rather than many things done partially. Scope accordingly: one dataset, one Gold business question, one scheduled Job. Depth over breadth. Recommended default: the NYC TLC Taxi Trip Records (details below) — it's public, already in Parquet, contains no personal data, and is large and well-known enough that interviewers recognise it. If nothing pulls you more strongly, use it and move on; the choice matters less than the execution.

The project brief

Project spec Build an end-to-end batch data pipeline on Databricks Free Edition using the medallion architecture. Ingest a public, real-world dataset into a Bronze Delta table; clean and validate it into a Silver Delta table with data-quality assertions; aggregate it into a Gold Delta table that answers one specific business question; orchestrate the whole thing as a scheduled multi-task Databricks Job. Document it for GitHub.

The constraints are the point. Using Databricks Free Edition means the environment is real — a cloud Lakehouse, not a local toy. Using public data means reviewers can verify your work. Using the medallion architecture means you are demonstrating exactly the pattern that appears in nearly every Databricks DE interview. And documenting your decisions in writing is itself a core DE skill — one that separates people who can build from people who can also be hired and trusted to work autonomously.

No real PII, ever Your dataset must contain no real personal data — names, email addresses, phone numbers, or financial identifiers. Public open datasets are typically safe, but read the data description before you download and confirm there is no embedded PII. If you encounter any, do not ingest it, even into a private repository. Use anonymised or synthetic stand-ins. This is not a course rule; it is a professional standard that will come up in your first DE job on day one.

Choosing your dataset

Pick something you find genuinely interesting — you will be talking about it in interviews. The recommended default is NYC TLC (first row); the other two are equally valid if they grip you more. Always download from the official publisher and read its license/terms page before ingesting — confirm the terms allow personal-portfolio use (NYC TLC is published under the standard NYC Terms of Use; CC0/CC-BY datasets are also fine).

Define your Gold question first The Gold question is the anchor of the whole project. Write it in one sentence before you write any code. It should be specific and answerable from the data, something a real analyst might ask, and explainable to a non-technical interviewer in a single breath. If you cannot state it clearly in one sentence, narrow it. A concrete question drives every downstream decision: what columns Silver must preserve, what the groupBy keys are, and what a "sane" Gold result looks like for a manual sanity check.

Your phased build plan

Work through these phases in order. Each has a sub-checklist — complete it before moving on. The goal is not speed; it is a working, tested, documented pipeline at the end. Estimated time is a guide; your first run will reveal the real unknowns.

Phase 1 — Scope and data (30–60 min)

  • Pick your dataset from the three options (or propose your own — check with the teacher first)
  • Locate the official source portal; download one month's batch to inspect locally or in a notebook
  • Read the license page and confirm the terms allow portfolio use
  • Write your Gold question in one sentence; paste it at the very top of a README draft
  • Sketch the Bronze schema: list every column the raw file contains and its likely type
  • Identify at least two data-quality issues you expect to clean in Silver (nulls, duplicates, impossible values, cancelled records)

Phase 2 — Bronze ingestion (30–60 min)

  • Create a Databricks notebook named 01_ingest_bronze
  • Upload one batch file to DBFS (/FileStore/uploads/) or read from a public HTTPS URL if the dataset supports it
  • Define an explicit StructType — no inferSchema=True
  • Add _load_ts (ingestion timestamp with current_timestamp()) and _source_file (literal filename) as metadata columns
  • Write to Bronze: .write.format("delta").mode("append").save(BASE + "/bronze")
  • Verify with printSchema() and count() — confirm the row count matches the source file

Phase 3 — Silver cleaning and DQ (1–2 hr)

  • Create a notebook named 02_clean_silver
  • Read Bronze: spark.read.format("delta").load(BASE + "/bronze")
  • Apply dropDuplicates() on the business key columns (e.g. trip ID + timestamp, order ID + customer ID)
  • Filter out rows with nulls in key columns; filter out rows with invalid status values
  • Cast string date/time columns to TimestampType; numeric strings to DoubleType or LongType
  • Add any derived columns your Gold question needs (e.g. revenue = qty * unit_price, trip_minutes = duration_sec / 60)
  • If your Gold question requires a reference table (zone names, category labels, station metadata): load it and join with broadcast()
  • Write DQ assertions before the Silver write: null count on key columns must be zero; business key must be unique; a key numeric column must be non-negative. Raise a Python exception on any failure — do not silently write a dirty Silver table
  • Write to Silver: .write.format("delta").mode("overwrite").save(BASE + "/silver")
  • Verify: compare row counts before and after cleaning; confirm the DQ assertions pass; run silver.explain() and note the physical plan

Phase 4 — Gold aggregation (30–60 min)

  • Create a notebook named 03_aggregate_gold
  • Read Silver and run groupBy().agg() to answer your Gold question exactly as you wrote it in Phase 1
  • Sanity-check: sum a key metric in Gold and compare it to the same metric summed across all Silver rows — they must match
  • Write to Gold: .write.format("delta").mode("overwrite").save(BASE + "/gold")
  • Run a final show() on Gold; confirm the result is interpretable and matches your intuition from the raw data
  • Export 10–20 rows as a CSV — this becomes the sample_output/gold_sample.csv in your GitHub repo

Phase 5 — Orchestration (30–60 min)

  • Open Databricks Workflows (Jobs) and create a new Job
  • Add three tasks — ingest_bronze, clean_silver, aggregate_gold — each pointing to its notebook
  • Set task dependencies: Silver depends on Bronze; Gold depends on Silver
  • Set a schedule (daily is most realistic; weekly is fine for a portfolio)
  • Configure an email alert on task failure — use your own address while developing
  • Trigger a manual run and verify the Job completes end-to-end without errors; check the run log for each task

Phase 6 — Documentation (30–60 min)

  • Write the README: problem statement, dataset description with license, architecture (embed or link the diagram), how-to-run instructions, and a design decisions section
  • In the design decisions section: explain why you chose this dataset, what DQ issues you found and how you handled them, and why Bronze uses append while Silver and Gold use overwrite
  • Add the sample Gold CSV to sample_output/
  • Push everything to a public GitHub repository

Phase 7 — Polish (30–60 min)

  • Remove any hardcoded paths — replace with a BASE variable, a Databricks widget, or a Job parameter
  • Test idempotency: run the full pipeline twice on the same input; confirm Silver and Gold output is identical on both runs
  • Open the Spark UI for one completed Job run; identify the most expensive stage and note it in the README under a "Performance notes" heading
  • Draft three interview bullet points about the project (see the interview section below)
  • Ask someone — a friend, or the teacher — to read your README cold and tell you what they did not understand; fix those gaps
Why these phases are in this order Each phase produces a durable checkpoint — a working Bronze, a working Silver, a running Job — that you can inspect and roll back independently. This is the medallion discipline applied to the build process itself. If you skip Phase 3's DQ checks and go straight to Gold, you will discover data issues three phases later when they are much harder to trace. Work in layers and test at each boundary.

Deliverables: what goes on GitHub

A clean repository layout signals that you think in systems, not just scripts. The structure below is a strong default — adapt it if your project demands something different, but do not omit any of the top-level pieces. 

your-portfolio-pipeline/
├── README.md                   ← problem, architecture diagram, how-to-run, decisions
├── notebooks/
│   ├── 01_ingest_bronze.py     ← exported from Databricks (.py or .ipynb)
│   ├── 02_clean_silver.py
│   └── 03_aggregate_gold.py
├── schema/
│   └── bronze_schema.py        ← StructType definition as importable Python
├── sample_output/
│   └── gold_sample.csv         ← 10–20 rows of the final Gold table
└── architecture/
    └── medallion_flow.png      ← diagram: draw.io, Mermaid, or a clear hand-drawn scan

On Databricks, export notebooks via File → Export → Source File (.py) — this gives version-controllable plain Python. Alternatively export as .ipynb if you prefer; either format is readable on GitHub. Avoid committing .dbc bundles — they are not human-readable and reviewers cannot inspect them.

The README is the first thing a reviewer reads If your README is not clear to someone who has never heard of your dataset — if they cannot understand what the pipeline does, what data it uses, and how to run it within two minutes — the rest of the repository does not matter. Write the README for a smart DE with no prior context. Ask yourself: would I hire someone whose README I had to decode?

How to talk about it in interviews

A project is only as useful as your ability to narrate it. The STAR framework — Situation, Task, Action, Result — is the standard for technical interview answers. Below is a template; fill in the brackets with your specifics and practice saying it out loud. It should feel natural, because you built this.

STAR template — fill in the brackets Situation: I was transitioning from [previous role] into data engineering. Without prior DE job history, I needed concrete evidence I could build a production-style pipeline — not just complete a course.

Task: I designed and built an end-to-end batch pipeline on Databricks using the medallion architecture, ingesting [NYC taxi / retail orders / bike-share] data and producing a reliable, daily-refreshed Gold table that answered [your specific question].

Action: I wrote an explicit-schema PySpark reader for the Bronze landing zone, applied deduplication and data-quality assertions in Silver, aggregated to Gold with groupBy().agg(), and wrapped the three notebooks as a scheduled multi-task Databricks Job with failure alerting. All of it is documented in a README on GitHub with the architecture diagram and design decisions.

Result: A fully orchestrated pipeline that runs unattended on a daily schedule, catches data-quality violations in Silver before they reach downstream consumers, and produces a clean Gold table I can demo live. I can walk through the Spark UI, explain the physical plan for the Silver stage, and talk through trade-offs — for instance, why Bronze uses append while Silver and Gold use overwrite.

Interviewers often follow up with one of three probes. Have these answers ready before you walk into an interview.

  • "What was the hardest thing to get right?" Talk about a specific problem you actually solved: the deduplication logic on a composite key, a DQ assertion that revealed a systematic upstream issue, or getting the Job task dependencies to fail correctly when Silver's DQ check throws. Vague answers ("getting the environment set up") signal you did not go deep enough.
  • "What would you do differently?" Name a genuine limitation: you used mode("overwrite") for Bronze when a MERGE upsert would prevent re-ingesting the same file; you did not partition Bronze by date so queries require a full scan; you hardcoded the base path instead of parameterizing. Self-awareness is a stronger signal than claiming perfection.
  • "How would this scale to 100× the data volume?" Partition Bronze by ingestion date so Silver reads only that day's partition; apply ZORDER on the Silver filter columns; confirm the broadcast join hint on the reference table is still appropriate (the table must still fit in executor memory at scale); use the Spark UI to identify any new shuffle-heavy stages that appear under load.

Definition of done

Before you list this project on your resume, step through every row in this table. A row is done when the stated condition is demonstrably true — not when you think it probably is. Run the check.
