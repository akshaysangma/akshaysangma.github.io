Load first, transform later

ETL vs ELT — where transformation happens, and why the lakehouse moved it.

Track: Databricks / PySpark ~11 min Conceptual + code sketch Builds on: Lessons 1 & 7
The win today "ETL or ELT — what's the difference and why does it matter?" is on the short list of questions every data-engineering interviewer asks. It looks like a vocab quiz, but the real test is whether you can explain why the industry shifted from one to the other, and where each still belongs. By the end of this lesson you will be able to answer that clearly — and you will see exactly how it connects to the Databricks work you are already doing.

The three stages, quickly

Every data pipeline, regardless of how it is built, has the same three jobs:

  • Extract — read data from a source: a database, an API, a CSV export, a message queue.
  • Transform — reshape it: filter bad rows, rename columns, cast types, join reference tables, apply business rules.
  • Load — write the result to a destination: a data warehouse, a Delta table, a downstream service.

ETL and ELT use exactly these three stages. The only difference is the order of T and L — and that one change has large consequences for where compute lives, how much storage you need, and whether you can recover from mistakes.

ETL: transform before you load

In the ETL pattern the transform step runs before any data reaches the target. A dedicated tool — Informatica, SSIS, Talend, or a custom Python script — reads from the source, cleans and reshapes the data in memory or on a staging server, and then loads only the finished, validated result into the warehouse.

This made perfect sense for the 1990s–2000s data warehouse era. Storage was expensive, so you paid for every row that landed — you wanted only clean, modelled data to arrive. The warehouse engine (Oracle, SQL Server) was tuned for querying, not for running heavy bulk transformations. Externalizing the transform kept the warehouse lean and predictable.

ELT: load raw first, transform inside the target

In the ELT pattern the order flips: Extract → Load → Transform. Raw data lands in the target first — unfiltered, un-reshaped, exactly as it arrived from the source. Then the transform runs inside the target platform, using the platform's own compute engine. In Databricks, that engine is Spark.

Why ELT is now the dominant pattern on modern cloud platforms Two things changed to make ELT not just practical but superior to the old approach:
  • Storage became cheap. Cloud object storage (S3, ADLS, GCS) costs pennies per gigabyte per month. Keeping a full copy of raw data is no longer a luxury — it is the obvious default.
  • The target got powerful compute. Databricks runs Spark across a cluster of machines. BigQuery, Snowflake, and Redshift have their own massively parallel engines. The warehouse is no longer just a query destination — it is a transformation engine. The compute you previously needed on a separate ETL server now lives right where the data is.¹
The result: it is cheaper and faster to land raw data and transform it in place than to run a separate ETL server, move only transformed copies, and discard the originals.

Side by side in PySpark

The same pipeline task — ingest a daily events file — written two ways. Read the comments: the transform logic is identical; what changes is when the write happens and whether raw data survives.

Run this on Databricks Free Edition Paste each block into a separate notebook cell. On Databricks, spark already exists — delete the two SparkSession lines before running. To make a quick test dataset, replace spark.read.csv(...) with spark.createDataFrame([("click", "2024-01-01"), (None, "2024-01-02")], ["event_type", "ts"]). Locally (Windows): save as etl_vs_elt.py in your activated venv and run python etl_vs_elt.py. 
## ── ETL pattern: Transform BEFORE loading ─────────────────────────────
from pyspark.sql import SparkSession
from pyspark.sql.functions import col

# On Databricks: remove these two lines — spark already exists
spark = SparkSession.builder.appName("etl-vs-elt").getOrCreate()

raw = spark.read.csv("source/events.csv", header=True, inferSchema=True)

# TRANSFORM first — clean and reshape before the target ever sees the data
clean = (
    raw
    .filter(col("event_type").isNotNull())           # drop nulls now
    .withColumn("ts", col("ts").cast("timestamp"))   # fix the type
)

# LOAD: only the clean result reaches the table
clean.write.format("delta").mode("overwrite").saveAsTable("events_clean")

# Raw events.csv is never persisted inside the lakehouse.
# If the filter logic had a bug, there is nothing inside the lakehouse to replay against.
## ── ELT pattern: Load raw FIRST, transform inside the lakehouse ───────
from pyspark.sql.functions import col   # carries over from above in a notebook

raw = spark.read.csv("source/events.csv", header=True, inferSchema=True)

# LOAD first — land everything exactly as it arrived; nulls, bad types, and all
raw.write.format("delta").mode("append").saveAsTable("bronze_events")
# bronze_events is now the permanent record of what arrived from the source

# TRANSFORM: build the clean layer from what is already stored in the lakehouse
silver = (
    spark.table("bronze_events")
         .filter(col("event_type").isNotNull())
         .withColumn("ts", col("ts").cast("timestamp"))
)
silver.write.format("delta").mode("overwrite").saveAsTable("silver_events")

# If the filter logic was wrong: fix the rule, re-run these lines.
# bronze_events is untouched — the original always exists to replay against.
What to notice The transform code is identical in both patterns — the filter and withColumn calls are exactly the same. What changes is when the write happens: ETL writes once, after the transform; ELT writes twice, before and after. That second write costs a little extra storage. What it buys is a permanent, untouched copy of what arrived — independent of any business logic that may contain bugs.

ETL vs ELT at a glance

Comparing the two patterns across the dimensions that matter most. Definitions will be added to the glossary. Neither column is universally correct — the right choice depends on your platform and constraints.
Aspect ETL ELT
When transform runs Before data enters the target After raw data is already in the target
Where compute lives External tool or staging server Inside the target (Spark, SQL engine)
Raw data retained? Often no — only clean rows land Yes — raw persists, transforms build on top
Typical tooling Informatica, SSIS, Talend, custom scripts Databricks / Spark, dbt, Snowflake, BigQuery
Schema approach Schema-on-write (conform before load) Schema-on-read at the raw layer; enforced later
Best fits Legacy warehouses, constrained targets, mandatory pre-cleansing Modern cloud lakehouses, Databricks, abundant storage and compute

Schema-on-write means you define and enforce the target schema before data arrives — any row that does not conform is rejected at load time. Schema-on-read means you store first and impose structure only when you query. ELT tends toward schema-on-read at the raw (bronze) layer, then enforces progressively stricter schemas as data is promoted to cleaner layers. Delta Lake, which you will meet in Lesson 9, lets you do both — landing flexible raw data and then enforcing schema as you refine it.

Neither pattern is obsolete

The industry conversation can make it sound as though ETL is dead. It is not.

Balance check — ETL still earns its place ETL remains the right choice when:
  • The target is constrained. A legacy on-premises warehouse may not have Spark or a powerful SQL engine. The only practical place to transform data is on a separate server before it lands.
  • Pre-cleansing is a hard requirement. Regulatory or contractual rules sometimes forbid landing raw PII or sensitive data anywhere — even temporarily. The transform (anonymize, tokenize, validate) must happen before any persistence.
  • Network cost or bandwidth limits the transfer. Some architectures ETL-transform at the edge — close to the source — to reduce the volume of data that must travel before being stored.
In an interview: show you know the why behind each pattern, not just which one is newer. Saying "ETL is dead" is a flag; saying "ETL is the right call when the target lacks compute or PII cannot land raw" is the answer that lands well.

Keeping raw: your safety net for reprocessing

One of the quieter benefits of ELT is what it does for your ability to recover from mistakes. Because raw data is persisted first and never overwritten, you can always replay a transform with corrected logic. The code sketch above showed this: bronze_events is untouched when silver_events is rewritten.

The property that makes this possible — re-running a pipeline and getting a correct, consistent result — is called idempotency. We will cover it properly in a later lesson. For now, anchor the habit: land raw, keep it, build clean layers on top. When a business rule changes or a bug is found, fix the transform and re-run. No re-extraction from source. No data lost. No incident.

Forward look: the medallion architecture The pattern you are building toward is called the medallion architecture — bronze (raw), silver (cleaned and conformed), gold (business-aggregated). It is the ELT pattern applied consistently across every layer of a Databricks lakehouse. You already saw its core in the code sketch above: bronze_events → silver_events is the first hop. We will build this end to end in Lesson 10. First, Lesson 9 introduces Delta Lake — the table format that makes each hop reliable and replayable.

Commit to an answer before revealing — retrieval is what builds memory.

A nightly job reads CSV exports from a source system, applies validation rules and removes nulls on a dedicated application server, then loads only the clean rows into the company data warehouse. Which pipeline pattern does this match?
A is correct. The transform (applying validation rules, removing nulls) runs on a dedicated application server — outside the warehouse — before any data is written to the target. That is the defining characteristic of ETL: Transform before Load, on external compute. B and C both correctly describe ELT — loading raw first and transforming with the target's own engine — but in this scenario the warehouse never sees a raw or unvalidated row. D mislabels ELT behaviour (warehouse engine transforms after receiving raw data) as ETL, which is the classic acronym confusion to avoid.
Why does ELT suit a Databricks lakehouse better than ETL in most modern pipelines?
B is correct. The economic shift is the key: cloud object storage is cheap enough that landing raw data costs almost nothing, and Spark running on a cluster provides the compute to transform that data inside the lakehouse rather than on a separate ETL server. Together these two changes make ELT more practical and more powerful than the traditional approach. A is false — ETL tooling can run in cloud environments perfectly well; its place has narrowed for other reasons. C reverses the truth: Databricks lakehouses frequently exploit flexible or schema-on-read at the raw (bronze) layer — you do not need to conform schema before landing. D is false — Spark reads CSV, JSON, Parquet, Delta, and many other formats directly; it is not restricted to registered tables.
A data engineer finds a bug in the silver-layer transform three weeks after it ran. The pipeline followed ELT and landed raw API events into a bronze Delta table first. What does that raw landing make possible?
C is correct. Because the raw events were persisted in the bronze Delta table and never overwritten, the engineer can fix the transform rule and re-run it against the original data — no re-extraction from the source API required. This is the core reprocessing benefit of ELT, and the practical foundation of idempotency. A is wrong: retaining raw data does not automatically detect bugs; it only makes recovery easier after a bug is noticed. D is wrong: the buggy transform already ran and wrote corrupted rows to silver — the raw layer enables recovery, not prevention. B describes going back to the upstream source, which is sometimes an option, but the point of retaining raw in the lakehouse is that you already have it — re-extraction is not necessary.
