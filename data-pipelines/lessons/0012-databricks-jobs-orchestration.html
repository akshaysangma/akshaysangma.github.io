Make it run itself

Turning the Lesson 11 pipeline into a scheduled, multi-task Databricks Job — so your data moves even while you sleep.

Track: Databricks / PySpark ~12 min Hands-on: Databricks Free Edition (UI) Builds on: Lesson 11 pipeline
The big win In Lesson 11 you built a three-step pipeline: raw CSV into Bronze, Bronze cleaned into Silver, Silver aggregated into Gold. It works — but only when you click Run. On the job, no one runs pipelines by hand. Data must arrive on schedule, failures must retry automatically, and your team must be notified when something breaks. That infrastructure is called orchestration. Today you wrap the Lesson 11 pipeline in a Databricks Job, set a daily schedule, and watch it run without you.

Why "clicking Run" is not a pipeline

Imagine your orders pipeline must load fresh data every morning before the BI dashboard opens at 8 a.m. If the person who normally clicks Run is sick, or forgets, or clicks it twice by accident, the dashboard shows stale or doubled numbers. That is a human-reliability problem, not a data problem — and data engineers are hired to remove human reliability from the data path.

A production pipeline has four properties a manual notebook run does not:

  • Unattended execution — it starts on a schedule or event, with no human trigger.
  • Ordered dependencies — Silver only starts after Bronze succeeds, never before or in parallel.
  • Automatic retries — if a task fails due to a network blip or upstream latency, it tries again before alerting anyone.
  • Notifications — the right person is paged on failure, not when they happen to check next.

Orchestration is the layer that provides those four properties. Databricks Jobs is the orchestrator already built into the platform you have.

Databricks Jobs — the platform orchestrator

Naming note The orchestrator's current official name is Lakeflow Jobs (renamed from Workflows/Jobs at the June 2025 Data + AI Summit; the docs now live at docs.databricks.com/aws/en/jobs). Older pages, the UI, and the certification exam may still say "Workflows" or "Jobs" — they are the same feature. This lesson uses "Databricks Jobs" as the stable term throughout.

A Job is a container that runs one or more tasks in a defined order, on a schedule or trigger. Think of it as the production wrapper you put around your notebook or script.

Core concepts in Databricks Jobs. You will configure each of these in the hands-on below. Full platform reference is in the Databricks docs — see the source note at the bottom of this page.
ConceptWhat it is
Job The top-level container: a name, a schedule or trigger, one or more tasks, cluster defaults, and notification settings. One Job = the whole pipeline.
Task The runnable unit inside a Job — a notebook, Python wheel, SQL statement, JAR, or dbt project. Each task has its own cluster setting and retry policy. In your pipeline, Bronze ingest, Silver clean, and Gold aggregate are each one task.
DAG Directed acyclic graph — the dependency graph formed by your tasks. Your pipeline's DAG is linear: Bronze → Silver → Gold. Real pipelines can fan out (one upstream feeds several parallel tasks) or converge (many upstreams merge before the next step).
Dependency An ordering rule between tasks: "Task B may not start until Task A succeeds." Databricks enforces this automatically — you set it in the UI by selecting a task's upstream in the Depends on dropdown.
Schedule / Trigger When to run. A schedule uses a cron expression (0 6 * * * = every day at 06:00 UTC). A trigger can also fire on file arrival or run continuously. You can always trigger an immediate run on demand.
Job cluster A cluster Databricks creates at run-start and destroys at run-end. Cheaper than leaving an all-purpose cluster alive. Recommended for production Jobs. In Free Edition, Serverless is the default — no cluster to configure or pay for.
Retry policy Per task: how many times to retry on failure and how long to wait between attempts. Typical learning setting: 1 retry with a 30-second wait. Retries only help when the task is idempotent — see the section below.
Notification An email or webhook Databricks sends on job start, success, or failure. Connect to Slack or PagerDuty via a webhook URL.
Parameter A key-value pair the Job injects into a task at runtime — for example, the date to process or the environment (prod vs dev). Notebooks read parameters with dbutils.widgets. See the optional section below.

Mapping your Lesson 11 pipeline to a three-task Job

The Lesson 11 pipeline lives in one notebook. To turn it into a proper multi-task Job, you split it into three — one notebook per medallion layer. Each notebook handles exactly one step and reads its input from the Delta table the previous task wrote. That boundary is already there: Bronze writes to BASE/bronze, Silver reads from there and writes to BASE/silver, Gold reads from there. 

  ┌──────────────────────┐
  │    bronze_ingest     │  reads raw CSV → writes Delta Bronze table
  └──────────┬───────────┘
             │  dependency: silver_clean cannot start until this task succeeds
             ▼
  ┌──────────────────────┐
  │    silver_clean      │  reads Bronze → cleans, enriches → writes Delta Silver table
  └──────────┬───────────┘
             │  dependency: gold_aggregate cannot start until this task succeeds
             ▼
  ┌──────────────────────┐
  │    gold_aggregate    │  reads Silver → aggregates → writes Delta Gold table
  └──────────────────────┘

This is a linear DAG — the simplest shape and the right starting point. Later pipelines often branch (one Bronze feeds several Silver tables) or converge (two Silvers join before Gold). The dependency mechanism is the same regardless of shape.

Split the Lesson 11 notebook Create three new Python notebooks in your Databricks workspace — for example, in a folder called orders_pipeline/:
  • 01_bronze — imports, BASE, the raw data creation, and the Bronze Delta write.
  • 02_silver — imports, BASE, the customers reference data, the full silver transformation chain, and the Silver Delta write.
  • 03_gold — imports, BASE, the gold aggregation, and the Gold Delta write. The gold_df.show() verify cell is optional; the Job's run log records the output anyway.
Each notebook must be self-contained: its own imports and its own BASE assignment. On Databricks, spark is pre-provided in every notebook, so you do not need a SparkSession.builder block.

Hands-on: create the three-task Job in the Databricks UI

Before you start Have your three notebooks (01_bronze, 02_silver, 03_gold) saved in your Databricks workspace and run at least once manually to confirm they work in isolation. A Job that fails because of a notebook bug is harder to debug than a notebook you can run cell by cell.
  1. Open the Jobs / Workflows section. In the Databricks left sidebar, click the icon labelled Workflows or Jobs (the label varies by workspace version — look for a lightning-bolt or pipeline icon). You land on the Jobs list page.
  2. Create a new Job. Click Create job (top right). A task-creation dialog opens alongside an empty DAG canvas. At the very top, give the Job a name: for example, orders-pipeline-daily.
  3. Configure Task 1 — Bronze. In the first-task dialog:
    • Task name: bronze_ingest
    • Type: Notebook
    • Source: Workspace
    • Path: browse to 01_bronze in your workspace folder
    • Cluster: accept the default — Free Edition uses Serverless, so no cluster config is needed
    Click Create task. The task appears as a node in the DAG canvas.
  4. Add Task 2 — Silver. In the DAG canvas, click + Add task (the button that appears below or beside the bronze_ingest node):
    • Task name: silver_clean
    • Type: Notebook
    • Path: browse to 02_silver
    • Depends on: bronze_ingest — select it from the dropdown. This is the dependency wire.
    Click Create task. An arrow from bronze_ingest to silver_clean appears in the canvas.
  5. Add Task 3 — Gold. Click + Add task below silver_clean:
    • Task name: gold_aggregate
    • Type: Notebook
    • Path: browse to 03_gold
    • Depends on: silver_clean
    Click Create task. Your three-node linear DAG is now visible in full.
  6. Add a daily schedule. Find the Schedules & Triggers tab or panel on the Job settings page. Click Add schedule. Set it to Every day at 06:00, or enter a custom cron expression: 0 6 * * * (minute 0, hour 6, every day of month, every month, every day of week). Pick your timezone. Click Save.
  7. (Optional) Add failure notifications. In the Notifications section, add your email address and select On failure at minimum. You want to know when something breaks even if you skip success alerts.
  8. Run it now. Click Run now (top right). This fires an immediate on-demand run outside the schedule — exactly right for testing. Watch the DAG canvas: each task shows a spinner while running, then a green checkmark on success or a red X on failure.
  9. Inspect the run history. After the run completes, click the Runs tab on the Job page. You see a log of every run: start time, duration, status (Succeeded / Failed / Skipped), and a link to each task's notebook output. Clicking into a task shows its cell-by-cell output — the same view as running the notebook manually, but now captured and timestamped permanently.
Job cluster vs all-purpose cluster — the cost trap on paid workspaces On a paid Databricks workspace, always choose a job cluster (created at run-start, destroyed at run-end) over an all-purpose cluster for production Jobs. An all-purpose cluster stays alive between runs and costs money the entire time — even at midnight when nothing is happening. In Free Edition, Serverless is the default and avoids this entirely; there is no separate cluster to configure or pay for. On a real workspace, the cluster type is a per-task setting in the task dialog.

Optional: pass parameters to your notebooks

Right now, BASE is hardcoded in each notebook. Parameters let the Job pass the path — or a date — at runtime. This is how one Job can drive both a dev and a prod pipeline without editing notebooks.

At the top of each notebook, replace the hardcoded BASE line with the two lines below. The widget reads the Job's parameter if one is supplied; the default value kicks in when you run the notebook manually. 

# Replace the hardcoded BASE line in each notebook with this:
dbutils.widgets.text("base_path", "/tmp/e2e_pipeline")  # default for manual runs
BASE = dbutils.widgets.get("base_path")

In the Job UI, open each task, expand Parameters, and add the key base_path with the environment-specific value (e.g. /mnt/data/prod/orders_pipeline). The notebook itself does not change between environments — only the parameter value.

dbutils.widgets is a Databricks-only utility. It is not available in local PySpark. When running a parameterised notebook locally, either remove the widgets block or guard it with a try / except and fall back to the hardcoded path.

Idempotency and retries — why your tasks must be safe to re-run

A retry only helps if the task is idempotent: running it twice on the same input produces the same result as running it once. A non-idempotent task that retries three times leaves you with four copies of the data or a corrupted table.

Your Lesson 11 pipeline is mostly idempotent already, because of the write modes you chose:

  • Silver uses mode("overwrite") — re-running it replaces the table with identical rows. Safe to retry.
  • Gold uses mode("overwrite") — same logic. Safe to retry.
  • Bronze uses mode("append") — re-running it adds duplicate rows. Not safe as-is.

The correct fix for Bronze — flagged in the Lesson 11 trap callout — is a MERGE statement (MERGE INTO in SQL): insert a row only when its order_id does not already exist in the Bronze table. Delta Lake supports MERGE natively; we will cover it fully in the dedicated Delta operations lesson. For now, when you are learning on Free Edition, be aware that re-running the Job will grow the Bronze table with duplicate rows for the same input file — and that is the exact problem MERGE solves in production.

Practical retry settings Set retries in the task settings dialog. A reasonable starting point: 1 retry with a 30-second wait. For a production task reading from an upstream API that occasionally times out, you might use 3 retries with exponential backoff (30 s → 60 s → 120 s). The rule is simple: only set retries greater than zero once you have confirmed the task is idempotent.

Beyond the UI — code-defined Jobs and alternatives

The UI is the right tool while you are learning. As you grow into production work you will encounter two common extensions and two common alternatives:

  • Databricks Asset Bundles (DABs) — define Jobs as YAML or JSON files, version-control them alongside your notebooks, and deploy with the Databricks CLI (databricks bundle deploy). Teams use DABs so Job configuration goes through code review and CI/CD the same way code does. The UI and DABs describe the same Job object; you can export a UI-defined Job to YAML as a starting point.
  • Databricks CLI / REST API — the same Job can be created, updated, or triggered programmatically, useful in CI/CD scripts or integration tests.
  • Apache Airflow — an open-source orchestrator many companies run alongside Databricks. Airflow can trigger Databricks Jobs via the Databricks provider, letting you mix Databricks tasks with non-Databricks steps (e.g. an FTP file drop, a dbt run, a Salesforce API call) in one DAG.
  • dbt (data build tool) — not a general orchestrator, but a SQL/Python transformation layer with built-in dependency management. dbt integrates with Databricks and often handles Silver and Gold transforms while Databricks Jobs handle Bronze ingestion and scheduling.

Start with the Jobs UI. Add Asset Bundles when you need version-controlled, repeatable deployments. Reach for Airflow when you need to orchestrate steps outside the Databricks ecosystem.

Check yourself

Commit to an answer before revealing — retrieval is what builds memory.

A Databricks Job is made up of tasks. Which best describes what a single task is?
A task is the runnable unit inside a Job — a notebook, SQL statement, Python wheel, or similar. Each task has its own cluster config and retry policy. The schedule (B), cluster (C), and notifications (D) are all Job-level or task-level settings, but they are not tasks. In your pipeline, bronze_ingest, silver_clean, and gold_aggregate are each a task.
A colleague says "I just click Run in the notebook every morning — what do I need a Job for?" Which answer best explains why orchestration matters?
The core value of orchestration is reliability without human involvement: the pipeline starts on schedule (even when you are sick or asleep), retries on transient failures, and notifies someone when intervention is needed. B is false — Jobs may add cluster startup time, not remove it. C and D describe capabilities Jobs do not provide by default.
In your three-task Job, silver_clean has bronze_ingest listed as a dependency. What does that dependency express?
A dependency is an ordering constraint: silver_clean will not start until bronze_ingest reaches a Succeeded status. Without it, Silver might start reading the Bronze Delta table while Bronze is still writing — or before it has written anything at all. A is the opposite of what a dependency does (tasks run sequentially, not in parallel, when one depends on the other). C reverses the order. D is not what a dependency controls — each task has its own independent retry policy regardless.
