Getting data in

The SparkSession and reading files into a DataFrame — the real first line of every pipeline you'll ever write.

Track: Databricks / PySpark ~13 min Hands-on: local PySpark + Databricks Builds on: Lesson 1 (lazy model) + pandas you know
Why this matters for the career switch Every data engineering pipeline starts with a read. In interviews and take-homes you'll be handed a file path and expected to produce a clean, typed DataFrame in seconds. This lesson makes that reflex automatic — you'll know the two API forms, which file format to reach for first (and why), and how to sanity-check your schema before writing a single transformation.

The SparkSession: your entry point to everything

In pandas you just import pandas as pd and go. PySpark needs a running SparkSession first — it is the object that connects your Python process to the Spark engine, manages configuration, and is the factory for reading data. Everything starts here.¹

How you get one depends on where you are:

How spark arrives — the most common source of beginner confusion.
EnvironmentWhat you doWhy
Databricks notebook Nothing — spark already exists Databricks pre-creates a session bound to the cluster/serverless compute when the notebook attaches. Creating a second one would conflict.
Local Python (venv) SparkSession.builder.appName("...").getOrCreate() No platform provides it for you; you build it yourself. getOrCreate() is safe to call multiple times — it reuses an existing session rather than starting a second one.
Don't call SparkSession.builder in Databricks In a Databricks notebook, spark is injected by the platform. Calling SparkSession.builder...getOrCreate() there is harmless (it returns the same session) but marks you as someone copying local code without understanding the environment — an easy interview trip-wire. Use spark directly in notebooks.²

Two ways to read: the short form and the flexible form

spark.read is a DataFrameReader — an object with convenience methods for common formats and a general .format(...).option(...).load(...) chain for everything else. You will see both in real codebases; knowing they are equivalent removes a lot of confusion.¹

Short form vs flexible form — same result, different readability trade-offs.
StyleExampleWhen to use
Short (convenience method) spark.read.csv(path, header=True, inferSchema=True) Fewer options needed; quick exploration.
Flexible (format chain) spark.read.format("csv").option("header","true").load(path) Many options; dynamic format; config from a variable.

The two forms are functionally identical — the short methods are just wrappers around the format chain. Pick whichever reads more clearly for the number of options you need.

Reading CSV, JSON, and Parquet

Here is the core reading vocabulary. Study the pattern, not the memorization — it is always the same shape.

# CSV — two equivalent forms
df = spark.read.csv("data/employees.csv", header=True, inferSchema=True)

df = (spark.read
      .format("csv")
      .option("header", "true")
      .option("inferSchema", "true")
      .load("data/employees.csv"))

# JSON — one record per line (newline-delimited JSON, the Spark default)
df = spark.read.json("data/employees.json")

# Parquet — no options needed; schema is embedded in the file
df = spark.read.parquet("data/employees.parquet")
Pandas contrast In pandas: df = pd.read_csv("data/employees.csv") — one line, runs immediately, loads the whole file into RAM on your machine. In PySpark the read returns a lazy DataFrame (a plan, from Lesson 1) — no data is actually read from disk until an action like show() runs. This is why PySpark can describe reading a 500 GB file in milliseconds.

Schema: printSchema, show, columns, dtypes

Once you have a DataFrame — even a lazy one — you can inspect its structure instantly, because schema metadata is available without scanning data. 

df.printSchema()
# root
#  |-- name: string (nullable = true)
#  |-- department: string (nullable = true)
#  |-- salary: integer (nullable = true)
#  |-- hire_date: string (nullable = true)

df.show(5)          # action — triggers a real job, prints first 5 rows
# +-------+----------+------+----------+
# |   name|department|salary| hire_date|
# +-------+----------+------+----------+
# |    Ada| Analytics| 95000|2021-03-15|
# |   Alan|  Platform| 88000|2020-07-01|
# |  Grace|  Platform|112000|2019-11-20|
# +-------+----------+------+----------+

print(df.columns)   # list of column name strings — no job triggered
# ['name', 'department', 'salary', 'hire_date']

print(df.dtypes)    # list of (name, type) tuples — no job triggered
# [('name', 'string'), ('department', 'string'), ('salary', 'int'), ('hire_date', 'string')]

df.columns and df.dtypes are properties on the schema object Spark has already resolved — they don't trigger a job. df.show() is an action and does.

inferSchema vs an explicit StructType

inferSchema=True is convenient for exploration but has two real costs in a production pipeline:

  • Extra pass over the data. Spark must read your file twice — once to sample types, once to read values. On a large file that is significant compute.
  • Type guessing can be wrong. A column of ZIP codes like 01234 becomes an integer (1234), silently dropping the leading zero. A date column may land as a string. You find out downstream, at the worst possible moment.

In a real pipeline you supply an explicit schema using StructType. Spark trusts it and skips the inference pass entirely.¹ 

from pyspark.sql.types import StructType, StructField, StringType, IntegerType, DateType

schema = StructType([
    StructField("name",       StringType(),  nullable=True),
    StructField("department", StringType(),  nullable=True),
    StructField("salary",     IntegerType(), nullable=True),
    StructField("hire_date",  DateType(),    nullable=True),  # explicit date, not string
])

df = spark.read.csv("data/employees.csv", header=True, schema=schema)
df.printSchema()
# root
#  |-- name: string (nullable = true)
#  |-- department: string (nullable = true)
#  |-- salary: integer (nullable = true)
#  |-- hire_date: date (nullable = true)   ← date, not string
Rule of thumb Use inferSchema=True when you are exploring a new dataset for the first time. Switch to a defined StructType before you commit the read to a real pipeline — your future self will thank you when the upstream data changes and Spark catches the mismatch at the read, not three stages later.

File formats: CSV vs JSON vs Parquet

Choosing the right format is not pedantry — it directly affects pipeline speed, storage cost, and whether your schema survives a handoff between teams.

Format comparison. For new pipelines, default to Parquet unless there is a specific reason not to.
FormatSchema stored?Columnar?Compressed?Splittable?Best for
CSV No (infer or supply) No (row) No (plain text) Yes (by line) Data exchange with non-Spark systems; human-readable debugging.
JSON No (infer or supply) No (row) No (plain text) Yes (newline-delimited) API outputs; nested/semi-structured data; ad hoc ingestion.
Parquet Yes (embedded) Yes Yes (Snappy by default) Yes (by row group) Everything inside your pipeline. The Spark default for good reason.

Why columnar matters: if you read a 100-column table but only need 3 columns, Parquet lets Spark skip the other 97 columns entirely on disk. A row format (CSV/JSON) must read every column to reach the ones you want.

Delta Lake builds directly on Parquet files and adds ACID transactions, time travel, and schema enforcement on top — you will use it from Lesson 9 onward. For now, think of Parquet as "Delta without the superpowers".³

Hands-on: read a real file in both environments

The win for this lesson: create a tiny CSV, read it into a Spark DataFrame, inspect the schema, and see your first typed column.

Step 2 — read it with PySpark (local) Save as read_demo.py in your practice folder, activate your venv, run python read_demo.py. 
from pyspark.sql import SparkSession
from pyspark.sql.types import StructType, StructField, StringType, IntegerType, DateType

spark = SparkSession.builder.appName("read-demo").getOrCreate()

# --- Part A: inferSchema (exploration mode) ---
df_infer = spark.read.csv("data/employees.csv", header=True, inferSchema=True)
print("=== inferSchema result ===")
df_infer.printSchema()
# root
#  |-- name: string (nullable = true)
#  |-- department: string (nullable = true)
#  |-- salary: integer (nullable = true)
#  |-- hire_date: string (nullable = true)   ← date landed as string!

# --- Part B: explicit schema (pipeline mode) ---
schema = StructType([
    StructField("name",       StringType(),  True),
    StructField("department", StringType(),  True),
    StructField("salary",     IntegerType(), True),
    StructField("hire_date",  DateType(),    True),
])

df = spark.read.csv("data/employees.csv", header=True, schema=schema)
print("=== explicit schema result ===")
df.printSchema()
# root
#  |-- name: string (nullable = true)
#  |-- department: string (nullable = true)
#  |-- salary: integer (nullable = true)
#  |-- hire_date: date (nullable = true)   ← correctly typed

df.show()
# +-----+---------------+------+----------+
# | name|     department|salary| hire_date|
# +-----+---------------+------+----------+
# |  Ada|      Analytics| 95000|2021-03-15|
# | Alan|       Platform| 88000|2020-07-01|
# |Grace|       Platform|112000|2019-11-20|
# |Linus|Infrastructure|104000|2018-05-09|
# +-----+---------------+------+----------+

print("Columns:", df.columns)
print("Dtypes: ", df.dtypes)

spark.stop()   # clean up when running as a script (not needed in notebooks)
Databricks version (notebook cell) In a Databricks notebook spark is pre-provided — skip the SparkSession.builder line and spark.stop(). For the file, use spark.createDataFrame to avoid needing to upload a file: 
# Databricks notebook — spark already exists, no builder call needed
from pyspark.sql.types import StructType, StructField, StringType, IntegerType, DateType

schema = StructType([
    StructField("name",       StringType(),  True),
    StructField("department", StringType(),  True),
    StructField("salary",     IntegerType(), True),
    StructField("hire_date",  DateType(),    True),
])

rows = [
    ("Ada",   "Analytics",      95000, "2021-03-15"),
    ("Alan",  "Platform",       88000, "2020-07-01"),
    ("Grace", "Platform",      112000, "2019-11-20"),
    ("Linus", "Infrastructure",104000, "2018-05-09"),
]

# createDataFrame with a schema enforces types at creation time
df = spark.createDataFrame(rows, schema)
df.printSchema()
df.show()

# Databricks also ships sample datasets at /databricks-datasets/
# Try: spark.read.csv("/databricks-datasets/airlines/", header=True, inferSchema=True).show(3)

Most Databricks workspaces mount sample data at /databricks-datasets/ (run dbutils.fs.ls("/databricks-datasets") to check yours). If it's there, run the commented line to try a real multi-file directory — Spark reads the whole folder as one DataFrame automatically.

Windows path gotcha When running locally on Windows, use forward slashes in PySpark path strings ("data/employees.csv") or raw strings with backslashes (r"data\employees.csv"). A plain "data\employees.csv" can misparse the backslash as an escape character and produce a confusing FileNotFoundException.

Check yourself

Commit to an answer before revealing.

You're building a production pipeline. Why is Parquet the better format than CSV for the intermediate steps?
Parquet's three structural advantages — columnar layout (Spark skips columns it doesn't need), built-in compression (Snappy by default), and embedded schema (no type guessing needed) — combine to make it dramatically faster and safer than CSV for pipeline intermediates. All four answers mention real facts, but only C names the reasons that actually drive the choice.
What is the main downside of using inferSchema=True in a scheduled production pipeline?
inferSchema=True triggers an extra scan pass over your data to sample types — double the I/O cost. It also guesses: a ZIP code column (01234) becomes integer 1234, silently dropping the leading zero. An explicit StructType skips the scan entirely and ensures types are exactly what you declared.
In a Databricks notebook, where does the spark variable come from?
Databricks pre-creates a SparkSession named spark and injects it into every notebook's context when compute attaches. You use it directly — no import, no builder call. This is a platform feature of Databricks; local PySpark has no such injection, so locally you must call SparkSession.builder...getOrCreate() yourself.
