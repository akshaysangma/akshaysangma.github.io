Files that remember everything

Delta Lake — turning files into reliable tables with ACID transactions, time travel, and upserts built in to every write.

Track: Databricks / PySpark ~14 min Hands-on: Databricks (recommended) · local needs delta-spark Builds on: Lesson 2 (Parquet) · Lesson 8 (ETL/ELT)
The win for your career switch Delta Lake is the default storage format on Databricks — every table you create there is already a Delta table. But "default" doesn't mean you can treat it as a black box. In data engineering interviews and on the job, you will be expected to explain why Delta is more reliable than raw Parquet, how to upsert without duplicates, and how to reproduce a dataset from six weeks ago. This lesson gives you exactly those three things.

Delta = Parquet + a transaction log

Plain Parquet is excellent: columnar, compressed, schema-embedded (Lesson 2). But it has a gap. If a write job crashes halfway through, you are left with partial files and no way to know what is valid. Multiple writers stepping on each other produce inconsistent reads. You cannot query "what did this table look like yesterday?"

Delta Lake fills that gap by wrapping your Parquet files with one extra ingredient: a transaction log. On disk, a Delta table looks like this: 

products/
  _delta_log/
    00000000000000000000.json   # commit 0 — initial write: files added, schema
    00000000000000000001.json   # commit 1 — append: new files added
    00000000000000000002.json   # commit 2 — MERGE: files added and removed
    00000000000000000010.parquet # checkpoint — compact summary every 10 commits
  part-00000-abc123.parquet     # actual data (Parquet, unchanged format)
  part-00001-def456.parquet

The Parquet files hold your data. The _delta_log directory records every change as an ordered, append-only sequence of JSON commit files. Each commit says: which files were added, which were removed, what the schema is. Everything else — ACID, time travel, safe concurrent writes — flows directly from that log.¹

The mental model Think of a Delta table as a git repository for your data. The Parquet files are your working tree. The _delta_log is the commit history. You can always check out any past commit.

What the transaction log gives you

ACID transactions

A write either commits fully — one new JSON file appears in the log — or it does not, and the table stays exactly as it was. Spark never leaves you with half-written data. Multiple writers coordinate through the log, so readers always see a consistent snapshot even while a write is in progress.¹

Schema enforcement and schema evolution

By default, Delta rejects any write whose schema does not match the table — protecting you from accidentally dropping a column or silently changing a type. When you intentionally need to add a new column, you opt in explicitly: 

df_new.write.format("delta") \
    .option("mergeSchema", "true") \   # opt in to adding the new column
    .mode("append") \
    .saveAsTable("products")

Time travel — query any past version

Because the log records every version, you can read the table as it existed at any past commit. Reproducible ML training datasets, audit trails, and "roll back to before the bad pipeline run" all become one-liners.¹ 

# SQL — read version 0 (the initial load)
SELECT * FROM products VERSION AS OF 0

# PySpark — same thing
(spark.read.format("delta")
      .option("versionAsOf", 0)
      .table("products")
      .show())

# Or by timestamp — useful for "what did this look like last Tuesday?"
(spark.read.format("delta")
      .option("timestampAsOf", "2025-01-15")
      .table("products")
      .show())

MERGE INTO — upsert in one statement

The most important Delta operation for data engineers: insert new rows, update existing ones, and optionally delete rows — all atomically. Without MERGE, an upsert in a raw data lake means loading the whole table, deduplicating in memory, and rewriting everything. Delta makes it a single SQL command.¹ 

# Step 1 — make your incoming changes available as a temp view
updates.createOrReplaceTempView("updates")

# Step 2 — MERGE: update price if product exists; insert if it doesn't
spark.sql("""
    MERGE INTO products AS t
    USING updates      AS s ON t.id = s.id
    WHEN MATCHED       THEN UPDATE SET t.price = s.price
    WHEN NOT MATCHED   THEN INSERT *
""")

The Python DeltaTable API (DeltaTable.forName(spark, "products").merge(...).whenMatchedUpdateAll().whenNotMatchedInsertAll().execute()) does the same thing without SQL strings — useful when conditions are built dynamically. Both forms are idiomatic on Databricks.

OPTIMIZE, Z-ORDER / Liquid Clustering, and VACUUM

Over time, frequent small writes leave many tiny Parquet files behind — each one is expensive to open. OPTIMIZE compacts them into fewer, larger files: 

OPTIMIZE products    # compact small files — run periodically or after heavy ingestion

Z-ORDER (the classic approach) co-locates rows with similar column values within those compacted files so range queries skip more data. Liquid Clustering is the newer alternative recommended for new tables on Databricks — you declare the clustering column once and Databricks applies it automatically over time, without a separate ZORDER pass: 

# Z-ORDER — classic, run inside OPTIMIZE
OPTIMIZE products ZORDER BY (category)

# Liquid Clustering — declare once on the table; Databricks handles the rest
ALTER TABLE products CLUSTER BY (category)

VACUUM permanently deletes Parquet files that no living version of the table references. The default retention window is 7 days — time travel is only available that far back after vacuuming.

VACUUM removes your time-travel history VACUUM products deletes old Parquet files from disk. Once vacuumed, you cannot time-travel to versions older than the retention window (default 7 days). Leave the default unless you have a specific reason — shrinking it below 7 days can break concurrent readers. VACUUM is a maintenance tool, not a recovery tool.

Writing and reading Delta tables

Core Delta write/read patterns. On Databricks, Delta is the default format — saveAsTable already writes Delta even without .format("delta"). The explicit form is still good practice.
OperationCodeNotes
Write to a path df.write.format("delta").save("/mnt/delta/products") Unmanaged table at that path. No metastore entry.
Write as a named table df.write.format("delta").saveAsTable("products") Registers in the metastore — enables SQL access and DESCRIBE HISTORY.
Append df.write.format("delta").mode("append").saveAsTable("products") Adds rows as a new commit. Fails if schema doesn't match (enforcement).
Overwrite df.write.format("delta").mode("overwrite").saveAsTable("products") Replaces all data atomically. Old version still accessible via time travel.
Read current spark.read.table("products") Reads the latest committed version.
Read past version spark.read.format("delta").option("versionAsOf", 0).table("products") Time travel — reads version 0 from the log.
Databricks: Delta is already the default On Databricks, spark.conf.get("spark.sql.sources.default") returns delta. A plain df.write.saveAsTable("products") already writes Delta — you do not need .format("delta"). You will still see it written explicitly in most production code for readability, and it is a good habit to keep.
Running Delta locally: extra setup required Databricks provides Delta out of the box. Locally, the delta-spark package must be installed and the SparkSession configured with the Delta extensions: 
# Windows PowerShell — install inside your venv (Java 17+ still required)
pip install delta-spark

# Then build a session with the Delta extension enabled
from pyspark.sql import SparkSession
from delta import configure_spark_with_delta_pip

builder = (SparkSession.builder
    .appName("delta-local")
    .config("spark.sql.extensions",
            "io.delta.sql.DeltaSparkSessionExtension")
    .config("spark.sql.catalog.spark_catalog",
            "org.apache.spark.sql.delta.catalog.DeltaCatalog"))

spark = configure_spark_with_delta_pip(builder).getOrCreate()
# The rest of the code below is identical on Databricks and locally

Hands-on: create, append, merge, and time-travel

The win: see the version counter in the transaction log move with each write, then travel back to version 0 and confirm the original data is intact.

Recommended: Databricks notebook Open a Python notebook. spark pre-exists and Delta is the default format — no imports beyond PySpark needed. Run each block as a separate cell so you can read the output before moving on. If running locally, build spark with the trap callout above first. 
########################################
# CELL 1 — create the table (version 0)
########################################
from pyspark.sql import Row

products = spark.createDataFrame([
    Row(id=1, name="Notebook",    price=4.99),
    Row(id=2, name="Pen",         price=1.49),
    Row(id=3, name="Highlighter", price=2.99),
])

products.write.format("delta").mode("overwrite").saveAsTable("products")

# Inspect the transaction log — every write creates a version entry
spark.sql("DESCRIBE HISTORY products") \
     .select("version", "timestamp", "operation") \
     .show(truncate=False)
# +-------+----------------------------+------------+
# |version|timestamp                   |operation   |
# +-------+----------------------------+------------+
# |0      |2025-06-28 ...              |CREATE TABLE|
# +-------+----------------------------+------------+

########################################
# CELL 2 — append a row (version 1)
########################################
new_row = spark.createDataFrame([Row(id=4, name="Ruler", price=0.99)])
new_row.write.format("delta").mode("append").saveAsTable("products")

spark.sql("SELECT * FROM products ORDER BY id").show()
# +---+-----------+-----+
# | id|       name|price|
# +---+-----------+-----+
# |  1|   Notebook| 4.99|
# |  2|        Pen| 1.49|
# |  3|Highlighter| 2.99|
# |  4|      Ruler| 0.99|
# +---+-----------+-----+

########################################
# CELL 3 — MERGE upsert (version 2)
# Update Pen's price; insert new Eraser
########################################
updates = spark.createDataFrame([
    Row(id=2, name="Pen",    price=1.79),   # price changed — should UPDATE
    Row(id=5, name="Eraser", price=0.79),   # new product — should INSERT
])
updates.createOrReplaceTempView("updates")

spark.sql("""
    MERGE INTO products AS t
    USING updates      AS s ON t.id = s.id
    WHEN MATCHED       THEN UPDATE SET t.price = s.price
    WHEN NOT MATCHED   THEN INSERT *
""")

spark.sql("SELECT * FROM products ORDER BY id").show()
# +---+-----------+-----+
# | id|       name|price|
# +---+-----------+-----+
# |  1|   Notebook| 4.99|
# |  2|        Pen| 1.79|  ← price updated from 1.49
# |  3|Highlighter| 2.99|
# |  4|      Ruler| 0.99|
# |  5|     Eraser| 0.79|  ← newly inserted
# +---+-----------+-----+

########################################
# CELL 4 — time travel back to version 0
########################################
df_v0 = (spark.read.format("delta")
              .option("versionAsOf", 0)
              .table("products"))
df_v0.show()
# +---+-----------+-----+
# | id|       name|price|
# +---+-----------+-----+
# |  1|   Notebook| 4.99|
# |  2|        Pen| 1.49|  ← original price, before the MERGE
# |  3|Highlighter| 2.99|
# +---+-----------+-----+
# Only 3 rows — the Ruler and Eraser don't exist yet at version 0

# Confirm all three versions are in the log
spark.sql("DESCRIBE HISTORY products") \
     .select("version", "operation") \
     .show()
# +-------+------------+
# |version|operation   |
# +-------+------------+
# |      2|MERGE       |
# |      1|WRITE       |
# |      0|CREATE TABLE|
# +-------+------------+
What to notice Each write produced exactly one new version in the log. The Parquet data files from all three versions still exist on disk — nothing was deleted. Reading version 0 works because the log tells Spark exactly which files were valid at that point. The Ruler (version 1) and Eraser (version 2) do not appear in the version-0 read because those files weren't part of the commit yet.

Check yourself

Commit to an answer before revealing — retrieval is what builds memory.

What is the key structural difference between a plain Parquet directory and a Delta table?
Delta is still Parquet underneath — the data files are the same columnar, compressed format you know from Lesson 2. What Delta adds is the _delta_log: an ordered, append-only sequence of JSON commit files. That log is the source of every Delta superpower: ACID (a write is one commit or nothing), time travel (version = commit number), schema enforcement, and safe concurrent-writer coordination. No caching, no encryption, no ORC — just a log on top of Parquet.
What does a Delta MERGE INTO statement do that a plain DataFrame mode("append") cannot?
A plain mode("append") blindly adds rows — it has no concept of "does this row already exist?" MERGE matches source rows to target rows on a key, then branches: matched rows get updated (or deleted), unmatched rows get inserted. All of this happens in one atomic commit to the transaction log — either all changes land, or none do. B, C, and D describe things that do not happen in a MERGE.
You need to reproduce a Delta table's data exactly as it was before this morning's pipeline wrote bad rows. Which feature solves this?
Time travel reads the _delta_log to find which Parquet files were valid at the requested version or timestamp, then reads only those — without touching anything else on disk. OPTIMIZE compacts files for performance; it does not restore data. mergeSchema adds new columns; it does not roll back data changes. VACUUM is the opposite of recovery — it permanently deletes old files, which is exactly what makes those versions unavailable afterward.
