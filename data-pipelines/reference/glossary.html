Glossary

The course's shared vocabulary. Terms are defined once here and used consistently in every lesson.

Spark execution model (Lessons 1, 4, 13)

DataFrameA distributed, table-like collection of rows with named, typed columns. In Spark it is a description of a computation, not data held in memory.
Lazy evaluationSpark records operations as a plan and runs nothing until an action forces a result. Contrast with pandas' eager evaluation (every line runs at once).
TransformationAn operation that returns a new DataFrame by adding a step to the plan. Lazy. E.g. select, filter, withColumn, groupBy, join, orderBy.
ActionAn operation that needs a concrete result and so triggers the job to actually run. Eager. E.g. show(), count(), collect(), take(), write.save(), toPandas().
Narrow transformationEach output partition depends on a single input partition — no data moves across the network (e.g. filter, select, withColumn). Cheap.
Wide transformationOutput partitions depend on many input partitions, requiring a shuffle (e.g. groupBy, join, distinct, orderBy). Expensive.
ShuffleThe redistribution of data across executors over the network to co-locate matching keys. The main cost in many Spark jobs; shows up as an Exchange in the plan.
Query planThe recipe Spark builds from your transformations. Inspect it with df.explain() (logical → physical plan).
CatalystSpark's query optimizer. Because evaluation is lazy, it can rewrite the whole plan (e.g. push filters down) before execution.
AQEAdaptive Query Execution — Spark re-optimizes the plan at runtime using actual data statistics (e.g. coalescing shuffle partitions, handling skew). On by default in modern Spark.
SparkSessionYour entry point to Spark, conventionally named spark. Created locally with SparkSession.builder...getOrCreate(); in Databricks notebooks it already exists.

Cluster & partitions (Lessons 4, 13)

DriverThe coordinating process that holds your program, builds the plan, and schedules work. collect()/toPandas() pull data to the driver — dangerous at scale.
ExecutorA worker process that runs tasks on partitions of the data in parallel across the cluster.
PartitionA chunk of a DataFrame processed by one task on one executor. Parallelism = number of partitions worked at once.
repartition() vs coalesce()repartition(n) reshuffles into n partitions (full shuffle, can increase or decrease). coalesce(n) only reduces partitions, avoiding a full shuffle.
Partition pruningWhen a table is written partitionBy a column, a query filtering on that column skips (prunes) irrelevant files — faster reads.
Broadcast joinSending a small table to every executor so a join needs no shuffle. df.join(broadcast(small), "key").
Data skewUneven distribution of rows across partitions (one key dominates), making some tasks far slower. A common cause of slow jobs.
cache() / persist()Store a DataFrame's computed result in memory (or disk) so reused branches don't recompute the whole plan on each action. unpersist() releases it.

Storage, formats & Delta (Lessons 2, 9, 14)

SchemaThe column names + types of a DataFrame. printSchema() shows it; a StructType defines one explicitly (preferred over inferSchema in pipelines).
inferSchemaLetting Spark guess column types by scanning the data (an extra pass; can guess wrong). Fine for exploration, risky for production.
ParquetColumnar, compressed, splittable file format that carries its own schema. The default for analytics; Delta is built on top of it.
Delta LakeAn open table format = Parquet files + a transaction log, adding ACID transactions, schema enforcement, and time travel. The lakehouse table format; default on Databricks.
Transaction log (_delta_log)The ordered record of every commit to a Delta table. Source of ACID guarantees, time travel, and concurrent read/write safety.
ACIDAtomicity, Consistency, Isolation, Durability — the transactional guarantees that stop partial/corrupt writes and make concurrent access safe.
Schema enforcement / evolutionEnforcement rejects writes whose schema doesn't match the table. Evolution lets the schema change deliberately (e.g. mergeSchema).
Time travelQuerying a previous version of a Delta table (VERSION AS OF / TIMESTAMP AS OF) — for audit, reproducibility, rollback.
MERGE (upsert)The MERGE INTO operation: insert new rows, update changed rows, optionally delete — in one atomic step. The core incremental-load operation.
OPTIMIZE / Z-ORDER / Liquid ClusteringDelta maintenance: OPTIMIZE compacts small files; Z-ORDER and Liquid Clustering co-locate related data for faster filtering. VACUUM removes old unreferenced files.
Delta constraintA table-level rule (NOT NULL, CHECK) that rejects writes violating it — data quality enforced at the table.

Pipeline design (Lessons 8, 10, 11, 12, 14)

ETLExtract → Transform → Load: transform data before loading it into the target.
ELTExtract → Load → Transform: land raw data first, then transform inside the warehouse/lakehouse. The modern lakehouse default.
Medallion architectureOrganizing lakehouse data into progressively refined layers: bronze (raw), silver (cleaned/conformed), gold (curated/aggregated for consumption).
IdempotencyA pipeline step that produces the same result whether run once or many times — so retries are safe. Often achieved via overwrite or MERGE.
OrchestrationRunning pipeline steps unattended in dependency order, on a schedule or trigger, with retries and alerts. On Databricks: Jobs (Lakeflow Jobs / Workflows).
Job / Task / DAGA Databricks Job is one or more tasks; task dependencies form a DAG (directed acyclic graph) defining run order.
Data quality dimensionsCompleteness (nulls), uniqueness (dupes/keys), validity (ranges/types), consistency, timeliness/freshness — what quality checks measure.
Quarantine patternRouting rows that fail quality checks to a separate table instead of dropping them silently — so bad data is visible, not lost.
Expectations (DLT / Lakeflow)Declarative data-quality rules on Databricks declarative pipelines (e.g. expect, expect_or_drop, expect_or_fail).

Python foundation (Lessons 5, 6, 7)

NumPyPython library for fast numerical arrays (ndarray); the vectorized layer pandas is built on.
VectorizationApplying one operation across a whole array at once (in compiled code) instead of looping element-by-element in Python. The source of NumPy/columnar speed.
BroadcastingNumPy's rule for combining arrays of different shapes by virtually stretching the smaller one (e.g. array + scalar). (Distinct from a Spark broadcast join.)
pandasPython library for in-memory, single-machine tabular data (DataFrame/Series). Eager; great up to ~a few GB, then reach for Spark.
.loc vs .ilocpandas selection: .loc by label, .iloc by integer position.
toPandas() / collect()The bridge from a distributed Spark DataFrame to local data on the driver. Safe for small results, catastrophic on large data.
Pandas API on Sparkpyspark.pandas — pandas-like syntax executed on Spark; a middle path for scaling familiar pandas code.

Platform & certification (Setup, Lesson 16)

Databricks Free EditionNo-cost Databricks workspace with serverless compute, for learning. Replaced the retired Community Edition in 2025. See Environment Setup.
PySparkThe Python API for Apache Spark.
LakehouseAn architecture combining a data lake's cheap open storage with a warehouse's reliability/performance (via Delta) — the Databricks model.
Unity Catalog (UC)Databricks' governance layer for data & AI assets — access control, lineage, discovery, auditing across workspaces. Lesson 18.
Three-level namespaceUC names every table catalog.schema.table (catalog = top-level container/drawer, schema = database/folder, table = the asset). Replaces the old two-level database.table.
MetastoreThe top-level UC container for an account/region; holds all catalogs. The root of the securable-object hierarchy (metastore → catalog → schema → table/view/volume).
GRANT / REVOKEANSI SQL access control in UC. Reading a table needs USE CATALOG + USE SCHEMA on its parents plus SELECT on the table; grants target account-level groups.
VolumeUC-governed storage for non-tabular files (CSV/JSON/images) — the governed replacement for ad-hoc DBFS//tmp paths.
Data lineageUC's automatic record of which tables/columns feed each table, down to the job/notebook. Used to trace bad numbers and assess downstream impact of a change.
